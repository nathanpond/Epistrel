# Epistrel — Technology & Architecture

**Companion to the Whitepaper · Working draft**

This document specifies the technology stack and runtime architecture for Epistrel. It assumes the design in *01 — Whitepaper*: Epistrel = **Engine Core** (deterministic, model-free data layer) + **Orchestrator** (the agent that does the work); models run externally but are configured inside Epistrel; PostgreSQL + pgvector is a single transactional store.

Target deployment is **self-hosted, dev/hobby scale** (a few concurrent stories). Choices favor operational simplicity and single-host deployment, while keeping the port/adapter seams that let a future platform-scale deployment scale out without rewriting the core.

---

## 1. Design constraints

- **Deterministic Engine Core.** The Engine Core makes no model calls; identical inputs produce identical outputs. Nondeterminism is quarantined in the Orchestrator's model calls, which are stubbable for tests.
- **Single transactional store.** World state, memory, beliefs, and the event log commit together or not at all — this rules out splitting memory into a separate vector database.
- **Model-agnostic, Epistrel-configured.** Any OpenAI-compatible model (public or local) works; Epistrel holds the per-purpose configuration and connects directly.
- **Thin consumer.** The consumer sends the respond request (story, character(s), prompt parameters, scene context, player input), registers external-data providers, and supplies model config; it receives a finished message and implements no memory logic.
- **Self-host simplicity.** `docker compose up` plus at least one model endpoint stands the system up.
- **Permissive licensing.** Apache-2.0 for Epistrel; every dependency must be license-compatible.

---

## 2. Runtime topology

Epistrel is two components in one product; the model servers and the consumer's game sit outside it.

**Three boundaries, deliberately separated:** the *consumer* holds no memory logic; the *Engine Core* holds no model; the *model processes* run outside Epistrel but are configured and called by Epistrel's Orchestrator. "Epistrel runs independently of the LLM" is literally true of the Engine Core and of Epistrel's own process (models are separate servers).

## 3. Language and service layer

- **Python 3.14.** The single supported version (ADR-148): one interpreter to test, one set of wheels to pin, and the ecosystem the stack needs (FastAPI, SQLAlchemy, psycopg, pgvector bindings, eval tooling) ships for it. Typed throughout; `mypy`/`pyright` in CI.
- **FastAPI** for the REST surface — async, OpenAPI generation, Pydantic-native.
- **Pydantic v2** for all public contracts (the respond request, the composed response with its beats, claims, verdicts, directives, model config). This is also the validation boundary for untrusted input.
- **Uvicorn** (ASGI); **Gunicorn**-managed workers as needed.
- **asyncio** throughout — the hot path is I/O-bound (DB + occasional model call).

Epistrel is also importable as an **in-process library** exposing the same contract; the REST server is a thin wrapper over it. There is no MCP server (ADR-092).

## 4. Data layer (Engine Core)

### 4.1 PostgreSQL
Primary and only datastore, version 16+ (18 supported), for transactional integrity across world state and memory.
- **Driver:** `psycopg` v3 (async). **Access:** SQLAlchemy 2.x Core for most queries; raw SQL for the hot retrieval-scoring query and vector ops. ORM kept thin — the schema is the contract.
- **Migrations:** Alembic.
- **Job queue:** Postgres `SELECT … FOR UPDATE SKIP LOCKED` + `LISTEN/NOTIFY` for Orchestrator background workers — no broker at hobby scale. `NOTIFY` is a latency hint only: workers also poll, and they own every timer (§10).

### 4.2 pgvector
Vector search for episodic/semantic/reflection memories in the **hot** retrieval tier only (FR-MEM-8): `memories.retrieval_tier ∈ {hot, retired}` is independent of timeline membership. **Budgets** are engine-profile dials (prospective, FR-PROF-5): each character's unpinned hot memories are held to `memory.hot_set.memories_per_character` (FR-MEM-8's `hot_memory_budget_per_character`, default 2,000) and the story's unpinned hot vectors to `memory.hot_set.vectors_per_story` (`hot_vector_budget_per_story`, default 50,000); a holder-less memory counts toward the story's vectors only, and a memory counts toward the vector budget once its vector is stamped. **Pinned** memories (`memories.pinned`, `POST|DELETE /stories/{id}/memories/{mid}/pin`) are exempt and never retired, but admission-limited by the deployment's `max_pinned_per_character` (default 200) and `max_pinned_per_story` (default 2,000, the story's text pins included): a pin past either is `422 pin_limit_exceeded` until something is unpinned. **The bounds** (NFR-SCALE-2 (a), as FR-MEM-8 phrases them): hot memories per character ≤ `hot_memory_budget_per_character` + `max_pinned_per_character`, and hot vectors per story ≤ `hot_vector_budget_per_story` + `max_pinned_per_story`, except during an overflow episode; neither the active record count nor total storage is claimed to be bounded (both grow linearly with story length). **Enforcement** is eventual with a bounded lag, per overflow episode (`overflow_episodes`): the commit that takes a set from within budget to over it opens an episode whose deadline is `memory.hot_set.retirement_max_lag` (default 50) committed turns later and never moves while it lasts; that commit enqueues priority consolidation and the episode's retirement job (`hot_set_retirement`, a `maintenance` operation). Retirement prefers records already **covered** by an active hot consolidation output or with decayed importance below `memory.hot_set.importance_floor` (default 0.2), then lowest decayed importance, then oldest last access; the turn commit that reaches the deadline retires the lowest-ranked uncovered records anyway (`retired_reason = uncovered`, with consolidation queued to cover them), ending the episode, and a set back within budget ends it too; a later overflow opens a new episode. The counters (`stories.hot_counts`) are kept in the transactions that change them and recounted exactly (two index-only reads of the hot set's partial indexes) after a truncation, swap or regeneration and by a daily reconcile; overflow is reported by `epistrel_hot_overflow{scope}` and `epistrel_hot_overflow_episodes_open{scope}` (FR-OBS). Commitments, thunks, and schedules are structured rows that never need hot-set protection. Retired rows stay active history and drop their vectors unless `memory.hot_set.retain_retired_vectors`; they are rehydrated on demand by the resolution pipeline via time-window and lexical lookup without returning to the hot set (M4 does not re-promote a record that is re-accessed repeatedly; FR-MEM-8 allows it to stay retired, and pinning it brings it back). Vectors exist only for active hot records: a truncation, swap or regeneration drops the vectors of the memories it makes inactive unless `memory.hot_set.retain_dormant_vectors`, and a reactivation re-embeds them with the pinned embedding-model version (FR-STORE-30). `GET /admin/stories/{id}/hot-set` shows the counters, budgets, pins, open episodes and the latest retirements. Version 0.8.x; **HNSW** index; **cosine** default. `halfvec`/binary quantization available for long-running stories. Capacity is claimed only for the range P-06 measures (NFR-SCALE-1); a hobby story stores thousands of vectors.

### 4.3 Lexical / hybrid search
Postgres `tsvector` full-text (zero extra deps), behind a retrieval interface that a BM25 backend can replace. Epistrel bundles no BM25 extension: ParadeDB `pg_search` is AGPL-3.0, so an operator may install it only as their own choice, outside the Apache-2.0 distribution (NFR-MAINT-1).

### 4.4 Event store and projections
- **`events`** — append-only source of truth: `(id, story_id, seq, operation_id, category, narrative_turn?, turn_variant?, beat?, step?, slot_k?, character_id?, principal, type, payload jsonb, valid_time, tx_time, provenance, authority)`. `seq` is global recording order only; the position columns hold the full narrative position (FR-STORE-31).
- **`operations`** — one row per unit of work: `(operation_id, story_id, kind ∈ {turn, inter_turn, genesis, consolidation, rewrite_session, backfill, import, control, maintenance}, narrative_turn?, turn_variant?, slot_k?, status, principal, base_revision, config_revision, membership, membership_tx, source_window?)`. Records follow their operation's membership; `status` tracks a staged turn's stage (FR-EXT-16). A long-running operation's progress is read through `GET /operations/{id}` as `label` and `stages [{name, status ∈ {pending, running, done, failed, skipped, partial}, at}]` (M3, #128): a `genesis` (`validated`, `snapshotted`, `materialized`, all at its one commit; `snapshotted` is skipped for a blank story); a rating change's or reactivation's `control` operation, from its `rating_check_jobs` row (`checking`, then `applied`/`reactivated` or `refused`); an offboarding's, from its `offboarding_jobs` row (one stage per entity type in processing order); and an erasure, from `operations.stage_log` (`[{stage, status, at}]`: `redacted`, `ledger_written`, `regenerated`, `rebuilt`; a catalog erasure skips the last two). The job-backed kinds are linked from their job row's `operation_id`, not from `jobs` (#117, #118).
- **Event categories:** `narrative_state`, `input`, `derived`, `amendment`, `audit`, `control` — views filter on these (FR-STORE-25).
- **Projections** — materialized current-state tables (beliefs, relationships, placement/inventory, scene state) maintained transactionally and rebuildable by folding the log (CQRS-lite); the structured ones (`relationships`, `placement`, `scene_state`, and `belief_state` over `beliefs`, #159) fold from stored state instead of the log.
- **Three coordinates, never substituted for one another** (FR-BITEMP-5): **narrative position** (turn index + variant of the introducing turn, carried on every record as `narrative_turn`; not `seq`), **valid-time** (`valid_from`/`valid_to`, story-time), and **transaction-time** (`tx_from`/`tx_to`, record-time). Superseded facts are closed in transaction-time, not deleted.
- **Canon storage (#133):** each `facts` row is one version of a fact: its proposition, valid-time in story-minutes (outer and inner bounds, an `int8range` under GiST), `tx_from`/`tx_to`, provenance, authority, visibility (`objective`, `public`, `engine`, or `characters: [...]`), and the derived-record columns (operation, source events, narrative position, membership). `commit_fact` and `supersede` run in the writing operation's commit transaction. Each one appends a `derived` `fact_committed`/`fact_superseded` event and runs the fact hooks (`proposition_changes`, projections). An overlapping version of the same functional key, or of the opposite polarity, is closed, and what lies outside the new span is kept as remainder versions. A version is closed by the rows whose `supersedes` names it, and `tx_to` records the first closure, written once. In the corrected view, a version no *active* row closes is current, so a truncation that discards the closing operation makes the old version current again without any write. `canon_at(T)` reads the current versions covering story-time T (optionally through a narrative position). `canon_as_recorded(T)` reads the versions recorded by record-time T that no row recorded by then had closed. The table is append-only by trigger: only erasure and story deletion delete rows.
- **Memory records (#135):** each `memories` row is one memory: its `kind` (`episodic`, `semantic`, `reflection`), its text, its provenance (`record_provenance`) and a trust tier derived from it, a holder (`NULL`: shared, as every render-derived memory is in M4) and a visibility of the facts' shape, an importance (0..1, `NULL` until the `importance_scoring` job scores it) with the turn it holds from, the derived-record columns (operation, source events, narrative position with the beat, membership), the propositions it wraps, a retrieval tier, an embedding (pgvector: the untyped `vector` until the first embedding pins the dimension, retypes the column to `vector(d)` and creates the HNSW cosine index, #138) with its model version, and created/last-accessed times. `write_episodic` runs in the turn's commit transaction and writes one episodic memory per observable beat (`say`, `do`, narration; never `think` or `latent`), only when the story's `episodic` module is on. Working memory is a function over events, never stored. Importance decays as `importance · 0.5^(age / memory_importance_half_life_turns)` over committed turns of the active chain, computed when read. Erasure redacts a memory's text in place and nulls its vector in the same transaction, and deletes, with markers, the memories the subject holds or voiced.
- **Belief partitions (#159):** each `beliefs` row is one belief of one holder (a modeled character): a viewpoint-free proposition with its holder, kind (`first_order`; `attributed`, `speech_act` and `nested` are #167's), a polarity copied from the proposition, a categorical confidence (`unknown`, `suspected`, `believed`, `known`) and an optional scalar, the inner proposition's valid-time in story-minutes, the narrative positions between which the holder holds it (`held_from`/`held_to`, five columns each: turn, variant, slot, beat, step), `tx_from`/`tx_to`, a provenance (#160's acquisition), the derived-record columns, and a visibility that names the holder alone (CHECK). A false belief is stored exactly like a true one: it is the holder's truth (FR-EPI-3). Canon and partitions are separate tables, holders and writers: canon never reads a belief and a partition read never reads a fact (FR-EPI-1, `tools.gates check-epistemic-separation`). The player's character has no partition (FR-EPI-12). The table is append-only by trigger (`tx_to` and `held_to` are written once; erasure and story deletion delete rows), and one open first-order belief per holder and proposition is a partial unique index. `belief_state` is the queryable projection (FR-EPI-6): one row per belief a holder holds now at `suspected` or above, with its level, scalar, polarity and the position since which it holds, kept in the belief write's transaction and after every membership flip, and folded by a rebuild, erasure and a fork. A retrieval for character A, with the `partitions` module on, composes one visibility filter into every arm and returns A's own beliefs; verification against `belief(A)` reads A's partition plus the canon A may read, the belief winning (ADR-167).
- **Belief transitions (#160):** every belief-set change is one `belief_transitions` row: the holder, the belief it produced or changed (`beliefs.provenance` is the producing transition: NOT NULL, a deferred foreign key both ways, and a constraint trigger refusing a belief without one), its kind (`observation`, `testimony`, `inference`, `discovery`, `correction`, `forgetting`, `revision`, `author`, `resolution`; FR-EPI-7), its antecedent (`antecedent_kind` `record` (a fact, event, utterance or belief), `staged_beat`, `render_step` (through an `AntecedentOracle`) or `resolution`, with `antecedent_ref`), the source character, the story-time (`valid_at`), the dual confidence and accessibility it left, a testimony's `outcome`, the beliefs it closed (`prior_belief_ids`) and the in-place state it replaced (`prior`), and the dependent step's five-column `position`. `core.epistemic.transitions.transition()` is the only writer of `beliefs` (an AST gate): the antecedent must strictly precede the step in (turn, slot, beat, step) order (else 422 `self_attestation`; a resolution is exempt), a scalar projects onto the level by fixed bands (422 `confidence_inconsistent`), a held belief changes in place, and a contradicted one is closed whole (`held_to`, `tx_to`, `state = corrected`, `corrected_by`; `lineage_id` links the chain). Forgetting halves the scalar or drops a band, lowers `accessibility` by 0.3 and marks the belief `decayed` (#143's consolidation of a character scope calls it). A derived record of its operation: a membership flip re-settles what its transitions touched (a truncated correction reopens the prior). `POST /admin/stories/{id}/beliefs` writes an `author` transition (ADR-168).
- **Perception routing (#161):** `core.epistemic.perception.route_perception(beat, scene_state, qualifiers, level)` is the one perception decision, pure over authoritative state: `core.epistemic.scene` loads the scene at a turn's start (#137's placements, with `placement.since_beat` so a move takes effect from the next beat; canon's `located_in` containment, `adjacent_to` adjacency with its `barrier` — `none`, `door_open` (the default), `door_closed`, `window`, `thin_wall`, `wall` — and `on_channel` channels, read through `KeyedLookup`; `characters.languages`). The consumer's roster is never an input (FR-TURN-10). Same location → perceive, different → not; the actor perceives its own beat, a `think` reaches its thinker only. At `co_location` every co-located character perceives the whole beat. At `full` a `say`'s envelope reaches the room and its content its audience: `whisper_to`/`aside` narrow it, `eavesdrop_by` (a plausible path through anything but a `wall`, directly or via `located_in`) and `remote_channel` (the speaker on the channel) widen it to exactly whom the render names, with `partial_text` when it limits an eavesdropper, and a `language` a perceiver lacks leaves them the envelope. A `do` is an observation for the room, and a sound-category `do` (`audible.json`) reaches adjoining places through anything but a wall as an envelope. Envelopes are rendered by fixed templates: "<Speaker> whispers something to <Target>", "<Speaker> says something to <Target> in a language you don't understand", "<Speaker> speaks into the phone", "<Speaker> says something, <manner>" when there is no addressee, and "You hear <sound> from <place>". A widening qualifier with no valid path, a whisper target not in the room, an unknown character or place is repaired (dropped: #151's rung 1, a `render_rejected` record, `turn_report.perception.qualifiers_repaired`, `epistrel_perception_repairs_total{reason}`). The beat's validated qualifiers are on its `beat_*` payload (`perception`); routing results are never stored. A structured turn routes at its commit, at the level its effective configuration has then (`perception_level` is a configuration dependency; partitions switched off mid-turn regenerate), and hands the results to `PERCEPTION_SINKS`: the memory sink writes one `memories` row per perceiver (`fidelity`, `channel`, `characters: [perceiver]`), replacing the shared writer under partitions. The core predicates `spoke_to` and `spoke` are an utterance's envelope for the observation sinks (#160, #162, #164). #55's age-conditioned policies read authoritative presence through `scene.placed_elsewhere` (a character placed away from the scene is marked not present for the check). `tools.gates check-perception-authority` keeps the scene and topology reads in these modules (ADR-169).
- **Testimony (#162):** a routed `say` is a speech act for every content witness with a partition (never the speaker): each gets, per claim, a `kind = speech_act` belief (`believes(H, said(S, X))`, its testimony transition naming the speaker and the decision as `outcome`), and what it makes of the claim is a separate transition decided by `core.epistemic.testimony.testimony()`: #140's `check()` over the witness's partition and visible canon (`contradicted` → reject, or a correction by a speaker trusted at 0.8 or more over a `suspected` belief; `supported` → a one-level revision capped at `believed`; `novel` → a `testimony` belief at `believed` from a trusted speaker (0.65 or more), else `suspected`; `uncertain` → suspend), trust derived from the `relationships` projection and the witness's own transition history (never stored), and the perceived intent (`joking` → the speech act alone; `deceptive` reads as sincere). Salient witnesses (a salience-marked beat, or a claim touching the witness's partition; never a minor) may be adjudicated by `belief_adjudication` before composition, as optional budget kind `testimony`, at most two a turn; the commit recomputes the default and takes the model's decision only at confidence 0.6 or more and never over a contradiction. An unfunded adjudication is `testimony_defaulted` (NFR-PERF-7 step 3). Witnesses neither salient nor addressed are left to #164's exposures. `turn_report.epistemic.testimony` and `epistrel_testimony_total{outcome}`/`epistrel_adjudications_total{result}` report it (ADR-170).
- **Character modeling (#163; FR-EPI-9..12, FR-CAT-7):** `core.epistemic.modeling` models a story entity as a character on two triggers only, never on mere appearance: an **interaction** found deterministically in the turn's beats (an interaction verb of `detectors/interaction.json` in a `do` or narration with a modeled character on one side and an unmodeled person on the other, the player's own input included and one-sided acknowledgment enough; a vocative in a `say`; words inside speech and a mention are appearance) or **salience** (the salience step's new `characters` list, a render's `introduces`, or the author's `POST /stories/{id}/entities/{eid}/model`). With per-character partitions on, the structured turn plans the candidates after verify/repair, asks their true ages in one optional age-repair call (unfunded or implausible: `modeling_deferred`, the entity waits) and, in the commit before routing, `maybe_model` creates each `characters` row (`definition` = the triggering beat, `true_age_source = repaired`, `weight = minor`, `modeled_at` = the triggering beat's position; an existing entity is adopted, its id becoming the character's, while a description such as "the delivery driver" mints the entity with its words as descriptors, so "the driver" later resolves to the same character), indexes it for erasure, appends `character_defined` and the derived `character_modeled {trigger, entity_id, position}`, and has `core.turns.beats.write_character_facts` write its `age` and its `located_at` in the scene (the epistemic model writes no canon); the new character joins the routed scene, so the triggering beat lands in its partition. **Weight** (`characters.weight`, Postgres enum `character_weight`; the cast, the player and an author-added character `major`, M4's render-introduced rows backfilled `minor`) is conservative and set by the author only (`POST /stories/{id}/characters/{cid}/weight`, prospective; the player is always `major`). A `minor` is sparse: the memory sink keeps its memory of a perceived beat only when it acted, was addressed or took part in the interaction (exposures and observation transitions unfiltered), its consolidation window is `max(1, window_memories // 5)`, its hot budget the character budget × the deployment's `minor_hot_budget_fraction` (0.2), its records score × 0.5 in retrieval, it is never the default render character and never takes a testimony adjudication; its `think` and partition follow every visibility rule (FR-EPI-11). `turn_report.modeling {modeled, deferred}` and `epistrel_characters_modeled_total{trigger}` report it (ADR-171).
- **Timeline membership** on every record: `membership ∈ {active, discarded}` plus `membership_tx` (the transaction-time of the last change). Truncation and un-truncation flip this; valid-time is never touched by them.
- **`amendments`** — side-channel history rewrites: `(id, story_id, tx_time, author, authority, payload, reverted_by?)` with **no** narrative position. Each amendment is decomposed into `amendment_parts` of two kinds: **proposition parts**, keyed by `(subject, predicate, qualifiers, valid-time scope)` and applied in whatever continuation is active; and **record parts**, keyed by exact `record_id` and following that record's membership. Amendments carry typed dependency edges to the facts they rely on (including other amendments' facts). Undo is a new amendment that computes its own blast radius over those edges and runs the normal resolution/preview flow; `reverted_by` links the original to its undo.

### 4.5 Key logical entities
`stories`, `characters` (the cast and every modeled character: true age, `weight` ∈ {minor, major} and the `modeled_at` position, FR-EPI-10), `events`, `facts` (objective canon, bitemporal, visibility-scoped — including snapshots of external data with `external@timestamp` provenance), `beliefs` (per-character, incl. social and false beliefs; nested beliefs as records with `attributed_holder`, an inner proposition or inner belief reference (depth ≤ configured, default 2), attributed confidence, provenance, and holder/attribution/proposition times — verified only against the holder's own records, FR-BELIEF-15; lazily resolved beliefs carry `exposure_position` — `(turn, beat, step)` or an inter-turn slot `(turn, slot_k)` — and `resolution_operation_id` — inclusion follows the resolution operation's membership and position, valid-from follows the exposure position, FR-BELIEF-12..14), `memories` (episodic/semantic/reflection, embedded, provenance+importance+visibility, each with a `source_event`), `utterances` (speech acts with three independent labels: `objective_relation`, `belief_relation`, `intent`), `divergences` (asserted-vs-believed, recorded on deceptive intent), `policies` (immutable rules/guardrails), `promissory_ledger` (pending commitments), `thunks` (introduced-undetermined references), `external_providers` (registered data authorities and their declared trust tier), `external_read` events (every provider call: provider, query, value, timestamp — the single source of truth for an external value), `model_config` (per-purpose model routing), `entities` + `entity_aliases` (canonical IDs and alias resolution), `predicates` (the registry — layer, argument types, cardinality, temporal kind, exclusions, containment, implications, symmetry, owner), `propositions` (subject, predicate, object/literal, qualifiers, polarity, valid-time bounds with exactness flags — wrapped by facts, beliefs, and utterances), `state_definitions` (State schema: name, type, scope, constraints, visibility, owner ∈ {story, external}, rules), `state_changes` (event-sourced changes: state, scope key, delta/new value, reason, source, operation_id — a State's value is the fold of its active changes in a view), `state_proposals` (engine-suggested new States awaiting approval), `external_effect_outbox` (pending effects for write-capable providers, with idempotency key and confirmation/reconciliation status). Field-level requirements are in *03*.

### 4.6 Time travel, forking, and deletion
Narrative position is the turn index (plus variant), not `seq` — `seq` interleaves turns with consolidation, audit, and control events. A message is identified by its turn operation; every derived record (memory, fact, belief, divergence, utterance) carries its `source_event`, `operation_id`, and a membership flag. **Stories are fully self-contained** — no record references another story — which is what makes forking and deletion simple.

Two views of "as of N" exist, and they are different queries:
- **Current corrected history through N** (the default for every player-facing operation): position ≤ N (turns through N excluding N's inter-turn slots, or through slot k for `N⁺k`), `membership = 'active'`, and `category IN (narrative_state, input, derived, amendment)` (derived records by source eligibility), reading the **latest** transaction-time version of each record — i.e., with all amendments in force — plus amendment-introduced facts whose valid-time starts at or before the story-time of checkpoint N (FR-STORE-20). Each world-proposition correction part stores `timing_uncertain` and an optional `position_bound` (turn and variant, or the story's start); an undecidable comparison follows the story's `ambiguous_retcon_timing` — `include_if_possible` (default) marks the part `timing_uncertain`, and `ask_author` adds a required question to the rewrite session (§4.7) whose answer becomes the part's `position_bound`.
- **As originally recorded at N** (audit/debug): `narrative_turn ≤ N`, reading each record's version as of the transaction-time when turn N was recorded; derived records included only if *created* by then; audit records available.

Operations, all on narrative position:
- **Truncate** (delete a message and everything after, within a story): set `membership = 'discarded'` (with `membership_tx`) on operations (and so their records) positioned after the boundary — turn N's inter-turn slots and everything later for `N`, slots after k and everything later for `N⁺k`. Valid-time untouched — a discarded flashback whose valid-time precedes the checkpoint still leaves the active timeline. Non-destructive and reversible; amendments survive it (FR-STORE-21), and the rewrite conflict check runs on any amendment whose rationale referenced discarded records (FR-STORE-22); after a swap it runs against the restored chain (FR-STORE-29).
- **Regenerate:** discard turn N's active variant by truncating to `(N−1)⁺k`, keeping the inter-turn slots committed before it, and generate a new variant of turn N (FR-STORE-12, FR-COMMIT-8) — reverts that message's committed facts, preserves earlier ones, re-rolls thunks.
- **Fork** (duplicate at a point): a **full, independent copy** of the *current corrected history through N* (records, applicable amendments, projections, memories, facts, beliefs, utterances, divergences, vectors) under a new `story_id` — a bounded set of `INSERT … SELECT` statements in one transaction, the same order of work as the message/memory copying existing roleplay engines do. Isolated at creation; later changes on either side never propagate. After copying, the rewrite conflict check runs on any amendment whose rationale referenced excluded records (FR-STORE-22).
- **Delete a story:** `DELETE WHERE story_id = X` (or drop its partition). No reference-counting, no cross-story garbage collection, no effect on any other story.
- **Undo a rewind:** if no turns were written since, reactivate the discarded operations. If new turns exist, the default is a **swap**: the original continuation's turn variants become active and the newer chain becomes dormant (invariant: exactly one active variant per turn index, forming a single chain). The swap is itself reversible. Alternatively the consumer promotes the dormant continuation into its own story via fork. Resolutions (lazy beliefs, resolved thunks, commitments) follow the membership of the operation that produced them, so each continuation keeps its own.

Derived memory (semantic/reflection) is included in the corrected view iff all its source records are; on truncation or swap, excluded reflections are rebuilt by **re-running consolidation at the new head**. Consolidation jobs run as their own operations with a declared **source window** (upper-bound turn + exact inputs), read only those inputs, and on commit recheck that every input is still active — if the user truncated mid-job, the output is dropped rather than committed (FR-STORE-27). **Every external-authority read is recorded as an `external_read` event**, so within-story reconstruction, regeneration, and audit are deterministic without re-calling live providers (which would return today's value, not the as-of-N value); a commit that depends on an external value references its `external_read` event rather than re-capturing it (single source of truth). Discarded in-story records persist (storage is cheap at hobby scale); optional compaction can reclaim them, irreversibly and only through an explicit, two-stage control operation (FR-STORE-32). That operation bumps `timeline_revision`, deletes the chosen discarded tails and dormant continuations, writes compaction markers, and leaves amendments, outcome records, outbox rows, erasure markers, and feedback rows in place; undo, swap, or promotion that needs compacted records then returns `compacted`. Destructive operations are whole-story deletion and right-to-be-forgotten (§11 / FR-ADMIN-2); because stories are self-contained, both are scoped deletes with no cross-story reach.

The retcon-then-fork case is handled by the corrected-history view, not by event ordering: play to 1,000, amend Bobby's childhood at transaction-time 1,001, fork at 800 — the amendment has no narrative position, it corrects records with `narrative_turn ≤ 800`, so the fork includes the corrected childhood. A plain "fold events through `seq` 800" would wrongly exclude it.

**Story bundles (FR-STORE-7, FR-ADMIN-4).** A bundle is one gzip-compressed tar archive (`.epistrel.tgz`): `manifest.json` (semver format version, engine and schema versions, source story ID and revision, rating and profile references, a SHA-256 per file), `events.jsonl` (the event log in `seq` order, with membership, amendments, the story's audit-category events within retention, and compaction and erasure markers), `records/<table>.jsonl` for the durable story tables that are not projections (derived outputs with model, version, and prompt hash; outbox rows and outcome records; settings and overrides; feedback and its rating history), `catalog/` (the story's frozen snapshots), and `media/<sha256>` with `media.jsonl`. Its JSON Schema is published with the OpenAPI document. Deployment-level records — counters, reservations and costs, the deployment's own audit logs, operational logs, and idempotency results — are never included. **Export** is a job that reads in one `REPEATABLE READ` transaction pinned to one revision, as a fork does. **Import** validates the manifest, the rating choice, and the profile impact up front; if the impact report warns and `ignore_warnings` is not set, it returns the report and imports nothing. Otherwise an import job streams and verifies the archive — total uncompressed size, entry count, and per-entry size against deployment limits while decompressing (`bundle_too_large`), then checksums and the bundle schema (`corrupt_bundle`) — refuses a newer major format with `unsupported_format_version`, migrates older ones, and inserts its rows under a fresh `story_id` with `stories.status = importing`, remapping story-scoped keys as a fork does and keeping audit events' original recording times; every story endpoint answers `409 story_importing` until the job ends. The job applies the erasure ledger, runs the FR-RATE-7 tightening check over the active history against the chosen rating, records imported inactive turns with an empty `checked_guardrails` (so reactivating them later checks them first), parks outbox rows with no terminal outcome as `imported_unsettled` (never claimed by the dispatcher; listed for reconciliation), rebuilds projections, re-embeds active records, and sets `status = ready`. A refusal deletes the partial story with a `story_id`-scoped delete and returns the validation report.

### 4.7 History rewrite (natural-language side-channel)
Rewriting established history (FR-REWRITE) is exposed as a natural-language side-channel, since the structured store is not hand-editable. The Orchestrator parses the author's directive, computes the blast radius with `verify` + `fact_neighborhood` (the retroactive repair ladder), and applies it as one atomic, reversible **amendment** within the single story — a transaction with no narrative position, so it applies to every checkpoint view whose history it corrects and survives truncation. Two orthogonal consumer-set parameters ride a shared pipeline (detection identical; mode governs disposition; preview is an early exit before commit): `resolution_mode` ∈ {`synchronous`, `best_effort`, `threshold(severity)`} and `preview` ∈ {`preview_first`, `apply_directly`}, both defaulting to the safe end. Conflict-resolution Q&A occurs on the side-channel and is recorded for audit.

### 4.8 Concurrency, retries, and idempotency (FR-CONC)
- **Timeline revision:** `stories.timeline_revision` (bigint), incremented in the same transaction as any committed change to story truth (turn, each truth-changing stage of a staged turn, truncate, untruncate, swap, amendment, directive, State API change, pinned-memory or custom-instruction edit, ingest, late settlement, genesis, erasure, compaction — FR-CONC-1). Consolidation, importance, re-embed, rebuild, and audit writes do not touch it.
- **Optimistic commit:** an operation captures `base_revision` and its read set (record IDs + versions). Model calls run with no DB locks held. The commit transaction takes `SELECT … FROM stories WHERE story_id = $1 FOR UPDATE`, compares revisions, and applies the FR-CONC-4 outcome: commit, rebase (re-run deterministic verify), regenerate within budget, or abandon on an intervening control action.
- **Query keys (FR-CONC-11..13):** every deterministic lookup used for a verdict, precondition, or blocker records `(subject, predicate, object|*, holder, time window, result_hash)` — empty results included. Commit intersects these keys with a `proposition_changes` index of everything committed since `base_revision` (additions included) or re-runs the keyed lookups. Rewrite apply re-runs the dependency search and treats any newly found dependent as staleness.
- **Per-story turn concurrency:** `stories.turn_concurrency ∈ {reject, queue}` (default `reject`) and `stories.turn_queue_max`. `reject` returns a busy error, using a durable per-story in-flight marker — an `in_flight_turn` column with a lease, never a database lock held across model calls (FR-CONC-2) — that survives a crash so a staged turn can resume. While the story is paused (`stories.status` ∈ {`paused`, `paused_for_conflicts`} — a backfill, rating check, or reactivation check), truth-changing calls return `409 story_paused` (FR-CONC-5). `queue` uses a per-story FIFO table drained by the Orchestrator; each queued turn starts only after the previous one commits or fails. Different stories never contend.
- **Idempotency:** `idempotency_keys (scope, scope_id, key, request_hash, operation_id, status, result jsonb, revision, owner_token, lease_until, created_at, expires_at)` with a unique constraint on `(scope, scope_id, key)` — `scope = story` for calls on a story, and `scope = deployment` for calls that create a story (creation, import) or touch no story (catalog, personas, media, profiles, ratings). A matching key + hash returns the stored result (or waits on the in-flight operation); a mismatched hash is rejected. The stored `result` is purged after the result window (default 24 hours); the row then remains as a tombstone `(key, request_hash, operation_id)` for the life of its scope (the story, or for `scope = deployment` the deployment), so a late retry returns a reference to the original operation (fetchable via the operations API) and is never re-executed (FR-CONC-6, NFR-REL-4). Deleting a story also removes the deployment-scoped key bound to one of its operations (its creation), so no stored result outlives the story (FR-STORE-16). The `in_flight` row is written in its own short transaction before the operation, with an `owner_token` and a lease the running call renews; the operation binds itself to the key in its commit transaction (a late original whose lease a retry took over is refused there), and a dead original's key is taken over and re-executed only when nothing committed (#61).
- **Rewrite previews:** the preview response carries `base_revision`; apply re-checks the blast radius against the current revision at final commit and re-previews if stale.
- **Background workers:** jobs persist input record versions with their source window; the commit rechecks active-and-unchanged and otherwise drops the output and re-enqueues the job.
- **Inter-turn slots (FR-STORE-31):** `events.position = (turn, variant, beat, step)` for turn content and `(turn, variant, slot_k)` for inter-turn operations (State sets, settlements), ordered after the turn's completion; checkpoint `N` excludes slots, `N⁺k` includes slots 1..k; the as-originally-recorded view at `N` uses turn N's completion transaction-time and at `N⁺k` slot k's commit transaction-time; slots belong to the variant of N and are discarded with it.
- **Fork snapshot:** the fork copy runs in a single `REPEATABLE READ` transaction pinned to one revision.
- **Configuration revisions (FR-CONC-14..16):** `config_changes (scope, scope_id, config_revision, setting, old, new, class, actor, at)`, with `stories.config_revision` and a deployment-level revision. Each setting in the Pydantic config schema carries `class ∈ {interpretive, prospective}` (untagged → interpretive). For staged turns the rebase covers only uncommitted stages: before intent it is the normal path; after intent the pending effect is revalidated at claim; after claim and before the outcome transaction commits, that transaction validates its conditional effects and reservation settlements under the current configuration, reporting failures as `settlement_conflict`; after the outcome transaction, its settled effects are durable, and only the outcome step and still-pending conditional effects are revalidated. Operations store the revisions they ran under; the commit transaction reads the current revisions and, if an interpretive setting in the operation's dependency set changed, runs the FR-CONC-4 rebase path under the new configuration. For multi-beat turns the rebase recomputes each beat's exposures, drops staged acquisitions that no longer hold, and regenerates from the first beat whose antecedents or perceived inputs changed (the beat's recorded render-input set makes this a lookup, not a guess). Prospective changes are read only at operation start. The dispatcher re-reads provider registration at claim.

### 4.9 Propositions, predicates, and entities (FR-PROP)
- **Claim detection (FR-VERIFY-13,14):** three layers feed normalization — declared structure; deterministic detectors that always run (uncovered entity/alias mentions, quantities, possession/transfer/consumption/injury/movement lexicon, time expressions, and protected-content matching against an index of names, aliases, and values hidden from the speaker's viewpoint); and the model extraction backstop (`gated` by default: it runs only on the beats a detector flagged or whose structural parse is incomplete, with a shadow sample, after the turn commits, recording what gating missed; `always` runs it on every render, as the Structured (M4) profile does). The same pipeline runs on the composed message and reactive narration. Every detected claim is matched to a declared proposition or verified as a new claim, and nothing reaches verification except through detection. Metrics report detection (`epistrel_claims_detected_total{layer,category}`) and checking (`epistrel_claims_checked_total{verdict,category}`) as separate series. Zero unchecked detected claims is a guarantee; complete detection is a measured rate (NFR-QUAL-10).
- **Normalization:** declared turn structure and the claim-detection layers produce `propositions` rows; the mention resolver maps names, pronouns, and descriptions to `entities` via `entity_aliases` and the speaker's viewpoint. Anything that fails to normalize is `uncertain`.
- **Predicate registry layers:** `core` (shipped, documented semantics), `author` (declared per scenario), `auto` (registered on first use with weakest semantics: `multi`, no exclusions, implications, or containment; direct polarity conflicts still apply). Each predicate stores its **uniqueness key** (subject plus named key qualifiers); functional checks group by that key, never by subject alone. **Closed sets** are stored as explicit propositions (`closed_set(key, predicate, members, valid_time)`) and are never inferred. Strengthening an `auto` predicate writes a proposal for author approval; it never takes effect automatically.
- **Deterministic check (inside `verify`):** fetch holder-scoped propositions with the same subject and predicate (and any declared exclusions or implication sources, and for an affirmed claim the consequents of the declared rules from its predicate, their closed sets and joins, and the subject's presence predicates), then apply FR-PROP-10 in order: polarity conflict (all predicates; an affirmed presence inside a negated one's place through containment conflicts too) → functional-object conflict on the same uniqueness key (respecting containment) → max-cardinality and closed sets (object sets, and sets over a key qualifier's values: "his only undergraduate degree is `bobby_ba`", `closed_sets.key_set`) → exclusion → implication (bounded closure depth; a negated claim against what canon implies, and an affirmed claim's own consequences checked by the rules above) → temporal overlap. A negated presence at the claim's object (or what contains it) on another predicate that no declared rule reaches is `uncertain(world_knowledge)` (ADR-160). **Support** computes coverage: the claim's valid-time minus the union of matching holder intervals; an empty remainder is `supported`, a non-empty one is `uncertain(partial_coverage)` and the remainder is re-checked as its own claim (novelty path, no model call). Valid-times are either `[start, end)` ranges with `start < end` or instants (stored with a granularity; never as empty ranges). Undecidable cases from approximate bounds, unresolved entities, and semantic questions on weak predicates return `uncertain` to the Orchestrator's entailment fallback.
- **Escalation and the dependency cluster (#142; FR-VERIFY-1,3,6,8):** `orchestrator.verify.Verifier.verify(claim, viewpoint, position)` runs the deterministic check first, and a conclusive verdict makes no model call. `partial_coverage` and `granularity_refinement` settle from their remainders. Any other `uncertain` verdict goes to the escalation gate (`orchestrator.verify.gate`), which escalates (a) `unresolved_predicate` and (b) `world_knowledge`/`weak_semantics` when the deterministic confidence is below min(`verification.entailment_gate`, the shape's threshold). Nothing escalates under (c) (#467, ADR-162). The default gate is 1.0, so every such verdict escalates, and #155 tightens per `(layer, cardinality, temporal kind, polarity)`. Unresolved entities, times and argument types never escalate, and neither does `approximate_bounds`. FR-PROP-10 already resolves an approximate-bounds residual deterministically to `uncertain`: the rules have shown that the admissible readings disagree, a verdict needs every reading, and the model knows no more about the bounds than the records do. So it takes the safe disposition at once, with no model call, and leaves no `escalations` row. Below `verification.level = entailment`, the residual takes the safe disposition with no call. The `entailment` purpose sees only the claim and the holder's records: the fetched set plus the subject's own facts, up to `entailment_max_records`. Valid-times are rendered readably (#460): as calendar dates when the story has a calendar anchor (`stories.story_epoch`), as offsets from the story's start when it has none (FR-CLOCK-3), and an approximate bound (on a record shown with another residual) as "sometime between A and B". Its answer goes through `structured_call`. A parse failure, a confidence below `entailment_min_confidence`, a model `novel`, an unreachable model or a spent budget all take `verification.safe_disposition`. The safe disposition is: `repair` (the default) or `surface` to the author in `uncertain_claims`. None of them is ever a silent `supported`. One exception is surfaced whatever the profile says (#479, ADR-163): an extraction claim of its own (not merged with a declared or detector claim, no protected content) that is `uncertain` only because a weak relation (unregistered, or auto-registered with the weakest semantics) names something no entity holds (the resolver found no mention at all), with no other argument resolved to another modeled character or the player's, is listed in `uncertain_claims` and released, not repaired. A weak relation never yields `contradicted` from cardinality, exclusion, implication or containment (FR-PROP-4), and a direct polarity conflict needs the identical proposition, which an untracked argument cannot form. Repairing such a claim therefore buys no consistency and only removes scene texture a render may introduce (FR-VERIFY-11). Detector findings, `unknown_name` and `protected_value` claims, unresolved pronouns, claims touching another modeled character or the player, and every claim in a core or author relation keep the safe disposition (such a relation's place or object argument mints under option 2, see novelty below). Every residual leaves an `EscalationRecord`; #155's table keeps those the gate escalated or a tightened shape skipped. `core.verify.neighborhood.fact_neighborhood(seed, depth=2)` returns a repair's dependency cluster as context reads through `KeyedLookup`, current, active and viewpoint-filtered, capped at `neighborhood_max_facts`. It holds the same subject and predicate, declared implications both ways, the key's closed sets, shared-subject facts in both directions, projections and linked memories.
- **The repair ladder (#151; FR-REPAIR-1..4, FR-VERIFY-12, FR-GUARD-6):** with the profile's `repair` module on, the structured pipeline hands every rendered beat with a claim that `needs_repair` (contradicted, undecided under the `repair` disposition, or a denied novel claim; not a `say` declared deceptive or joking) to `orchestrator.repair.ladder.RepairLadder`, after the follow-up render and before the commit. Its context is each contradicted claim's cited facts (a cited closed set brings its subject's facts of that predicate) and their `fact_neighborhood(depth 2)`, read as the speaker may. The rungs run in order, skipping what does not apply: (1) drop the sentences that carry the claims (`core.repair.rungs.narrow`); (2) for a functional predicate citing one fact, splice canon's value over the claim's object (a restatement, never canonized again); (3) the `regeneration` purpose rewrites the beat in place under typed constraints `{kind, text, cites}` with the contradicted facts and the neighborhood, reserved atomically with `can_afford_unreserved` + `hold` (render, extraction, one re-check per model-assisted output policy) and bounded by `repair.max_attempts` per turn, else `repair_deterministic`; (4) the stored safe fallback (`safe_fallback`; a `think`/`latent` beat is dropped). Every rung's output passes the output gate and is re-detected (#148) and re-verified (#142) before it replaces the beat at its index with `repaired_from {rung, class}`; the rejected beat's canon requests are dropped. Each rejected text is a `render_rejected` audit event and the beat's verdicts a `verify_verdict`, written at the commit; `turn_report.repairs[]` carries the rung, the FR-REPAIR-4 class (`core.repair.rungs.classify`: rung 4 or a neighborhood above `cascade_threshold` → `cascade`, rung 2 on two facts or more → `substitution`, else `cosmetic`), the neighborhood and the contradicted fact ids.
- **Novelty permission and canonization (#144; FR-VERIFY-4,11,12):** a claim that ends `novel` passes `core.verify.permission` before it is canonized or repaired. The check is model-free and reads only structured data: entity kinds, `characters.id`/`is_player`, the predicate's owner, the `author_locked` flag of the claim's (subject, predicate) facts and the subject's placement (through `KeyedLookup`), and the story setting `allow_new_arrivals`. It answers `Permitted(basis)` or `Denied(reason)`, and each denial has exactly one reason: `external_value` > `locked_canon` (including a character's definition-locked `age`, `name`, `appearance_of`, `visual_identity_of`) > `state_change` (M6) > `player_character` > `other_character_secret` > `player_authority` (player input about another character: not repaired, never canonized) > `policy` (an arrival while `allow_new_arrivals` is off) > `protected_content`. M5's reactive-narration and `co_author` exceptions are not delivered yet, so claims they would admit are judged without them. A permitted claim is written by `core.canon.canonize` through #133's `commit_fact` in the turn's commit step, with provenance `render`/`director`/`player`/`author`, its beat's visibility (`objective`, or a `latent` beat's scope) and an anchor (the neighborhood's same-subject-and-predicate fact, else the most recent same-subject fact). A place or object first named there becomes an entity then (#479). When normalization cannot resolve an argument in a `place` or `item` slot of a registered predicate (the story's index has no mention of it, or the name is an unknown proper name, and it is not an indefinite such as "something" or "a mug"), the turn mints an id for it (`core.verify.introduce`). The same name later in the turn reuses that id, through the same resolver. The claim is then checked as `novel` and passes the permission check like any other. Only its canonization creates the entity (`canonize(..., introduces=...)`), so a denied, uncertain or repaired claim creates nothing. Literal slots (quantities, durations, dates), `person`, `organization` and `any` slots, and unregistered predicates never mint, and their untracked arguments stay `uncertain(unresolved_entity)`. The extraction backstop's snake_case arguments (`the_inn`) are read with spaces. Paraphrases that share no word ("the inn" and "Crossroads Inn") still become two entities (#481). `think` claims never canonize, and `say` claims canonize only when they are about the speaker's own actions or backstory. A denied claim goes to #151's repair tagged `unpermitted` and is listed in `turn_report.verify.denied`. The arrival policy and the set of locks are members of a structured turn's configuration dependencies, and its answers are re-run at a rebase (`REBASE_CHECKS`).
- **Registry storage (#131):** story-time is an integer count of minutes from the story's epoch (`stories.story_epoch`, the calendar instant of minute 0; `story_minute_zero` is where the story starts), so valid-times compare as integers; an approximate bound is stored as its inner and outer value (exact when equal) and an instant as its minute and granularity, with the possible span in an `int8range` under the GiST index. Core predicates have fixed ids and are re-synced from the code at every start; their semantics are published in `docs/predicates.md` (generated, CI-checked). An author's predicates, closed sets and implication rules are read from #108's `starting_state.predicates`, `closed_sets` and `rules` (kept as loose lists in the scenario document, typed when the registry reads them) and registered at structured genesis; author rules are stored on the story (`stories.predicate_rules`). Auto-registration and an approved proposal are interpretive story configuration changes (a `config_changes` row, the revision bumped); `GET /stories/{id}/predicates` lists the registry and `POST /stories/{id}/predicates/{predicate_id}/approve|reject` decides a pending proposal.
- **Resolution (#139; FR-PROP-6,9, FR-RET-2):** `core.resolution` resolves text before any search or verdict, purely and deterministically, with no model call (an import contract keeps it off the Model Access Layer). **Entities:** every story character has an entity with the character's id, written beside its `characters` row in every profile (blank creation, `POST /stories/{id}/characters`, genesis); its aliases are its name (`entity_aliases.source = canonical`), the catalog character's aliases, the role's name overrides and the persona's name; `entities.gender` (from the persona, else the one gender noun of the appearance) is the pronoun source, `entities.descriptors` the appearance's words. A scenario's `world.locations[]` (`place`) and `world.entities[]` (their optional `kind`, else `other`) become entities at structured genesis (#149), places and objects first named in canon at #144's canonization. **Mentions:** names and aliases (exact and case-folded, longest whole-word match, single words of multi-word names as implicit aliases), first and second person (the speaker; the one other entity present in #137's scene), pronouns bound to the most recent compatible entity (same sentence, earlier sentences, then the last 20 beats of working memory; the speaker never a third person's antecedent), descriptions by descriptor overlap, relational descriptions through one `relationships` hop, groups (`those guys`) with no entity; two candidates with no deterministic tie-break are `uncertain` with both listed. **Time:** story-time at a position is `story_minute_zero + turn × 10` until the clock (M6); a table-driven English grammar (`time_grammar.json`) resolves "now", offsets, coarse spans (approximate bounds) and, with a calendar anchor (`story_epoch`), calendar expressions; ages anchor on the subject's `born`/`age` canon read through the keyed lookup. **Event types:** a ~40-type vocabulary (`events.json`), extended by a scenario's optional `world.event_types`. Every unresolved result carries a reason (`unresolved_entity`, `unresolved_time`, `unresolved_event_type` families) for #140's `uncertain` verdicts and #155's gate reasons.
- **Identity:** `same_as` is an ordinary holder-scoped proposition, so identity knowledge is asymmetric like any other fact; entity merges/splits are amendments.
- **Indexes:** `(story_id, subject_id, predicate_id, holder)` plus a valid-time range index (Postgres `tstzrange`-style or story-time range type with GiST) so overlap checks stay within the verify latency budget (NFR-PERF-2).

### 4.10 Catalog, scenarios, and media (FR-CAT, FR-SCN, FR-MEDIA)
Starting points for stories live in their own schema (`catalog`), outside story data. Running stories never read it; story creation copies from it.
- **Tables:** `character_catalog` (ID, owner principal, listing status, status, current published version, and the one draft) and `character_versions` (immutable once published), whose draft and version documents (jsonb, `CharacterDraft`; #115) hold the **public card** — name, public description, a primary image and a gallery (media asset IDs); the **character definition** — true age (FR-CAT-12), appearance, personality and temperament, likes and dislikes, behavioral dispositions as five closed five-step settings with free-text nuance — threat response, dominance, honesty, warmth, caution — values and motivations, interaction style (speech style, mannerisms, vocabulary, sample dialogue), and optionally background flavor, a deflection style (FR-GUARD-7) and a safe fallback line; the optional **visual identity** — preferred image model, base appearance prompt, negative prompt, seed, reference images each declaring its audience (`perceivable` or `restricted`, no default: a save without one is refused), opaque adapter parameters, and an optional restricted-details prompt (FR-CAT-4); and **metadata** — aliases, labels, content rating. A draft may hold any subset (a name alone); a publish needs the true age, the content rating, every disposition axis and the rest of the definition, an audience on every reference image, live images, and a primary image when the deployment's `require_primary_image` is on (off by default), and its report names every missing field at once. The `card` shows each image as its ID and alt text only; `full` inlines each image's and reference image's media row (alt text, caption, MIME type, dimensions, generation metadata as stored). No world-truth items: those live in the character's companion scenario; `scenario_catalog` (with `companion_of`) and `scenario_versions` (with a companion's `pinned_character_id`/`pinned_character_version`), whose draft and version documents (jsonb) hold presentation, optional visual style, world description, locations and entities (an entity with an optional `kind`, #139), the story's own event types (`world.event_types`, #139), seeded world memories with visibility, State schemas and initial values, starting clock settings, scheduled events, predicates/closed sets/rules, opening, plot hooks, objectives, director guidance, planned reveals, milestones/endings, settings defaults (among them `allow_new_arrivals`, the arrival policy FR-VERIFY-11's permission check reads, default true, copied to the story's settings at genesis; #144), guardrail policies, required providers, overridable-field list, `max_characters_at_start`, and the **roles** — inside the document, not a table of their own (#108): per role, kind, required, fill mode, public label and setup description, default or locked `character_id@version`, eligibility filters, role seeds — each with holder, audience, and disclosure — relationships, role-scoped State values, starting location, default participation role, name overrides; `personas` (owner principal, name, gender, age, short description); genesis seeds a persona by audience — gender, visible appearance, and an apparent age band as perceivable; name, exact age, and description as beliefs of the player role's acquaintances — owned by their principal and not catalog entries; `media_assets` (owner, kind, MIME, size, dimensions/duration, checksum, content rating, caption, generation metadata — seed, model, prompts, parameters, reference IDs — and blob key). JSON columns hold the open-ended text fields; anything the engine must validate (seeds, States, roles, settings) is typed and validated by Pydantic models.
- **Personas and a story's own characters (FR-CAT-6..8; #114):** `personas` lives in the default schema beside `stories`, not in `catalog`, because a persona is not a catalog entry. A persona's name is unique per owner, ignoring case (`(owner_principal, lower(name))`; a creation, a rename or an owner transfer that would repeat one is `409 persona_name_taken`). Deleting a persona is a hard delete recorded by a `persona_deleted` audit row. A player character keeps `characters.persona_id` (a plain identifier) and `characters.persona_snapshot` (`{persona_id, name, gender, age, description, snapshotted_at}`), copied at genesis, so editing or deleting the persona never changes a story. A character added to a running story (`POST /stories/{id}/characters`) is a `characters` row with a true age, no `source_catalog_id` and optional `images` (media IDs by reference, a media reference source). It is recorded by a `control` operation with no turn position that bumps the revision and records `character_defined`, as a pinned-memory edit does: a truncation keeps it and a fork copies it. Any story character may store a `deflection_style` (#115; FR-GUARD-7): how it refuses or changes the subject, checked by the input gate like the definition and rendered with its author notes, so a reply regenerated after a guardrail violation stays in character; genesis copies a catalog character's `definition.deflection_style` there. Promotion (`POST /stories/{id}/characters/{cid}/promote`) makes a new draft through the character catalog's own create, copying only definition fields (true age, the free-text definition as `definition.background_flavor`, the safe fallback line and deflection style, images by reference, and the story's rating unless another is named; a character the story was created with from the catalog is promoted from its genesis snapshot's typed definition and images instead, #119) and appending the entry's ID to the character's `promoted_to`; it writes no story event and moves no revision. Its optional `seed_memories` (at most 50 memory IDs, each once; #498) seeds those memories' text into the new character's **companion scenario** draft, never into the character: one `starting_state.seeded_memories` item each, in order, held by the locked `npc` role with audience `self` and disclosure `open`, `valid_time` omitted (before the story began, FR-SCN-8), and recorded with provenance `seed` at genesis. Each must be an active, unquarantined memory of the story that the character holds (`holder_character_id`) or can know (no holder, visibility `objective`, `public`, or `characters` naming it); anything else is `422 seed_memory_invalid` (`details {field, memory_id, reason}`: `not_in_story`, `inactive`, `quarantined` or `not_known`) and nothing is written. In the promotion's transaction the memory rows are read `FOR SHARE`, the copied texts pass the resurrection guard against the story's erasures (a `DIRECT` content write path), and the companion draft keeps its save rules and size limit, stays at draft revision 1, and is re-indexed in the catalog scope of the subject index; publishing or validating the companion runs the full validation over the seeds, input policies included.
- **Companion scenarios (FR-CAT-5,10; #116):** the catalog service creates one per character in the character's own creation transaction (a promotion's too): `companion_of = character_id`, unique, with a locked NPC role `npc` (its `character` the new character, with no version until the character's first publish) and an open player role `player`, the character's name and content rating, an empty world, no opening, and `max_characters_at_start` 2, owned and listed as the character is. This is application code, not a database trigger. The slots — each role's `id`, `kind`, `fill` and `character`, matched by `id` — are kept by the scenario save (`422 companion_slots_fixed`, before any other rule) and checked again by the validation's companion check, not by a constraint, since roles live in the document; every other field is editable. The companion's owner, listing status, archiving and deletion follow the character's in the same transaction and are refused on the companion alone (`422 companion_follows_character`); a deleted companion records its own `deleted` ownership event and `catalog_entry_deleted` audit row. Its draft takes the character's content rating whenever that changes, until a save sets the companion's own (`scenario_catalog.content_rating_explicit`). Versions are separate and linked by the pin: a companion version records the character version its locked role uses in `scenario_versions.pinned_character_id`/`pinned_character_version` (a foreign key to `character_versions`) and in the role's `character.version`; reads show it as `pinned_character_version` in `full`. Drafts carry a `draft_revision`; saves and publishes compare it (optimistic concurrency). Every companion path takes its row locks character first, then companion. A character publish runs one transaction: validate the character draft → insert the character version → copy the latest published companion content (on the character's first publish, the companion's defaults; such a copy needs no world description or opening) into a new companion version re-pinned to it → run companion validation → commit; any failure rolls back both, and a refusal names its side (`details.entity`: `character` or `companion`). An open companion draft is re-pinned, not published. `POST /catalog/characters/{id}/publish?with_companion=true` (with `companion_draft_revision`) publishes both drafts as one pair under the full rules; a companion-only publish pins the latest published character version, never a draft, and is refused before the character's first publish (`character_not_published`). A rating difference between a character and its companion is a `rating_looser` warning in the companion's report, either way, and never blocks (FR-RATE-5). `GET /catalog/characters/{id}/companion` reads the companion (its draft while it was never published). Migration 0033 gave every character created before #116 its companion.
- **Genesis (FR-SCN-9):** `POST /stories` with a scenario runs one transaction: resolve versions → validate assignments, eligibility, overrides, and the slot limit → input-policy check of personas, ad-hoc definitions, and seeds (FR-GUARD-10) → resolve the story's rating (the scenario's, or the requested one; a stricter one is checked against the genesis content, FR-RATE-7) and collect rating-mismatch warnings → merge (personality: character > scenario, with personality warnings, under every profile; facts: scenario world > scenario role > character, with same-type conflicts detected, dropped, and returned only with `structured` — a Lite story renders the scenario's facts first and reports the fact-merge check as `check_unavailable`, FR-SCN-7) → create the story, configuration, policies, and characters (with `source_catalog_id@version`) and snapshot every scenario and character field (the version's whole document in `stories.scenario_snapshot`, each catalog character's in a `character_snapshots` row; #119) → materialize by field class and the story's effective capabilities (FR-SCN-11): with `structured`, entities, aliases, seeded canon and memories (provenance `seed`), and predicates; with per-character partitions, partitions and seeded beliefs; with the States and clock modules, States, the clock, and scheduled events. A Lite story renders knowledge seeds and director guidance into the Lite prompt instead. Each class is handled as in the table below, and only deferrable fields the story cannot use are recorded in `genesis_deferred (id, story_id, operation_id, field_ref, field_class, location, capability_needed, payload, created_at, materialized_at)`, one row per item and one capability per row, the payload the item's original JSON with the story character ids genesis resolved (#122) → record the genesis operation at position 0 → record the opening narration as turn 1. Snapshots are copies, so stories stay self-contained (ADR-019).
- **Structured genesis (#149):** when the chosen profile runs `pipeline = structured` (#129's `level_at_least`), the creation plans its materialization before the transaction, from the creation's `genesis_deferred` items (`payload.value`, `payload.characters`; no re-parse) and the resolved cast (`core.genesis.structured`): the world's places and entities become entities (#139); the story rules are typed by `ScenarioRules` and laid out by `author_layer` with fixed ids; each seed's text goes through the claim detectors (#148's `detect_seed`, the holder named in the context window) and `normalize` (#140), with an open start when it names no time; role relationships map through the registry and #140's alias table; the opening placement becomes `located_at`; each character's definition prose is the character layer. #140's `merge_layers` decides conflicts (closed sets, then world, role, character); a loser writes nothing and is reported `merge_conflict {winner, loser, rule}`, and `strict` refuses (`creation_conflicts`); a `canon` seed naming an entity the cast and world lack refuses with 422 `seed_unnormalizable`. Visibility follows the audience: `public`/`perceivable` (not `secret`) is `objective` for a world seed and `public` for a role's; otherwise the characters it names, else `engine`; a planned reveal's truth is `engine`. A seed with a shared visibility gets one memory (`provenance = seed`, importance 0.8): `semantic` when it normalized, `episodic` for free text, none when all its facts lost; under `memory.episodic` off the memory is a `genesis_deferred` row under `episodic`. Each character's `name` (`public`) and true `age` (`engine`) are facts. In the genesis operation's commit step the writer records all of it (`commit_fact` with `provenance = seed`, `authority = author`, unlocked) and stamps `materialized_at` on the `structured` rows it consumed; `partitions`, `clock` and `states` rows stay `NULL`. The creation report gains `materialized[]` (each item's `outcomes`: `canon`, `memory`, `deferred`, `merge_conflict`, `entity`, `rule`) and `counts.materialized.by_outcome`, both absent from a Lite report. `deferred_items` reads the rows back for a later switch to `structured` before any turn (#150). At publish, where the deployment provides the pipeline, `seed_normalization` and `fact_consistency` read the seeds the same way against an ephemeral registry and entity set (filled roles as their characters, other roles as placeholders): a declaration genesis would refuse (a core predicate's name, an unknown reference, a rule cycle) or a canon seed with an unresolved name is `seed_unnormalizable` (the warning `seed_unresolved_cast` when an open role could carry the name), and a same-layer contradiction is the error `seed_contradiction` (a warning across layers).
- **Field classes (FR-SCN-11):** every scenario field is tagged in the schema with one of the eight requirement classes — `public_card`, `knowledge_seed`, `story_rule`, `starting_state`, `director`, `configuration`, `recommendation`, or `style` — and each class has one serializer, one genesis writer, and one prompt channel. `configuration` fields also carry a `use`: `story_setting` (settings defaults and default participation roles), `policy` (story-scoped guardrails and required external providers), or `creation_only` (creation rules, fill modes, eligibility filters, and `max_characters_at_start`, read only while the story is created). There is no separate creation-rule class. `director` fields are stored with the snapshot and read only by the director-context assembler (or the Lite prompt's author-notes block); no canon, memory, or retrieval writer accepts them. A data-producing profile increase drains the story's `genesis_deferred` rows for the capabilities it adds, writing them at position 0 in the upgrade's operation (FR-PROF-18).

  | Class | Lite story | Structured story | Deferrable |
  |---|---|---|---|
  | `public_card` | Stored in the catalog and snapshot; never in a prompt | Same | No: there is nothing to activate |
  | `knowledge_seed` | Rendered as scenario text; the structured form is deferred | Canon and memories; beliefs and opening exposures with per-character partitions, otherwise deferred; scheduled events with the clock, otherwise deferred | Yes |
  | `story_rule` | Deferred | Written to the predicate registry | Yes |
  | `starting_state` | Opening narration recorded as turn 1; roles present shown as text; trackers and the clock in their prompt-only Lite forms when enabled, otherwise deferred | Opening narration as turn 1; States and the clock with those modules, otherwise deferred | Yes, except the opening narration |
  | `director` | Consumed: the Lite prompt's author notes | Consumed: the director's context only | No |
  | `configuration` · `story_setting` | Applied; stored and listed `inactive` when its capability is missing | Same | No |
  | `configuration` · `policy` | Applied | Applied | No |
  | `configuration` · `creation_only` | Consumed during creation | Same | No |
  | `recommendation` | Consumed: compared with the profile, producing warnings | Same | No |
  | `style` | Stored; read only by image prompts | Same | No |
- **Media store:** a `BlobStore` port with two adapters — local filesystem (default, a Docker volume) and any S3-compatible endpoint; assets are immutable and content-addressed by checksum. A periodic sweep purges assets that no catalog version, catalog draft, story, or live candidate references; it skips assets in state `candidate`, which only the candidate-expiry sweep removes, and it deletes bytes only when no asset row of any state still has their checksum. Erasure purges directly. Upload passes through an optional consumer moderation hook and, when an image-check model is configured, the image policies (FR-IMG-3). **Delivery (FR-MEDIA-3):** content reads honor `Range` headers; the S3 adapter issues short-lived presigned GET URLs, and the local store an Epistrel-signed content URL that is enough on its own to read that asset (ADR-152); uploads above a size threshold use resumable multipart sessions; every video gets a poster image, uploaded or extracted from its first frame with ffmpeg, which the image installs and runs as a separate process (ADR-151). No transcoding. Image generation is §4.13.
- **Projections (FR-SCN-10):** catalog serializers have two projections. `card` (the default) emits only the public cards — scenario name, public description, media, labels, content rating; role label and setup description; character name, public description, images, labels, content rating — and, for story creation, the story ID, cast cards, conflict and warning counts, counts of deferred and inactive items by field class and capability, and the names of `check_unavailable` checks. `full` emits everything, including merge-conflict details and every creation-report entry. No query filters by owner, relation, label, or listing status unless the request asks for it, and none gates on them (FR-AUTH-8). Public descriptions are never passed to genesis.
- **Ownership, relations, and offboarding (FR-AUTH-4..8):** `owner_principal` on `stories`, `character_catalog`, `scenario_catalog`, `personas`, `media_assets`, and `engine_profiles`, set at creation (the requesting principal, or the `owner` the request names; a fork is a creation) and changed only by a transfer or offboarding. A companion follows its character: transferring the character transfers the companion in the same transaction, and a companion cannot be transferred, or given relations, on its own (`companion_follows_character`). `entity_relations` (entity type, entity ID, principal, relation name, created at, created by; unique per entity, principal and name; names are 1–64 of `A-Z a-z 0-9 _ -`, so they never collide with a path or the `name:principal` filter), with no meaning attached to names. `ownership_events` (entity type, entity ID, kind `transfer` | `relation_added` | `relation_removed` | `listing_status` | `deleted`, old and new values, acting principal, offboarding job, transaction time) records every transfer, relation change, listing-status change, and deletion. One registry in `core/ownership.py` maps each entity type to its table, URL segment, and companion rule; ownership writes are `control` operations (the story's own for a story, story-less otherwise) with no story event and no revision change, allowed whatever the entity's state, and every delete path calls `drop_entity`, which removes the entity's relations and records the deletion. Nothing reads an owner or a relation to decide anything (FR-AUTH-8): they exist for listing, attribution, and offboarding, and list filters apply only when a request names them. Principal IDs are opaque strings and are never resolved. `listing_status` on catalog entries is checked against the deployment's configured value list (`deployment_state.listing_status_values`, default `private`, `in_review`, `public`; a new entry takes the first) by the application, never by a constraint, so an operator adds a value without a migration; a value an entry still holds cannot be removed from the list (`409 listing_status_in_use`), and a companion's value follows its character's. Lookup is an index scan of owner columns and `entity_relations`. Offboarding is a worker job (`offboarding_jobs`, whose id is its `jobs` row's: principal, per-type actions, transfer target, the request, status, the snapshot of entity ids taken in the request's transaction, progress, counts, report, error, and the request's committed `control` operation; the request's `Idempotency-Key` binds that operation and stores the 202, so a retry answers the same job) that processes one entity per transaction, as `system`, with its id on every `ownership_events` row it writes — companions with their characters, media referenced by transferred entries moved with them, deletions through each type's normal delete path, and retire-not-purge for referenced media and profiles. Before each entity the job records it as the one in hand, and afterwards records its outcome and moves past it under the job's fence, so a resumed job records an entity whose action already ran (gone, or already at the new owner) without acting again; a busy story is retried at the end of the pass, and the job yields every 100 entities. The report (deleted, transferred, removed, kept and skipped entities by type, and what is still linked to the principal) is kept for `offboarding_report_retention_days` (90) after the job ends, longer than the `jobs` row. A request whose dry run has warnings returns them unless it carries `ignore_warnings`.

### 4.11 Engine profiles, the Lite pipeline, and backfill (FR-PROF, FR-LITE)
- **Profiles:** `engine_profiles` and `engine_profile_versions` (module settings as a typed, validated Pydantic model), `stories.engine_profile_id` (with `stories.engine_profile_version_pin`, the version an `upgrade_unavailable` story keeps until M7; null while it follows the latest), and `story_profile_overrides`. Each setting in the schema is tagged `behavioral` or `data-producing` (untagged fails the build) as well as `interpretive`/`prospective` (FR-CONC-15). A dependency graph over modules validates every profile and every effective configuration (FR-PROF-4), and the schema exposes only modules and levels the deployment has delivered. Perception has three levels — `none` (shared knowledge), `co_location` (every co-located character perceives every beat in full), and `full` (envelope/content split, qualifiers, and their validation) — and each requirement area applies only under the modules the capability map lists (FR-PROF-13); the router, verifier, and belief resolver read the effective levels rather than assuming them. Presets Lite, Standard, Full, and Max ship as seed rows; Lite from M3, the others from M7.
- **Follow-latest:** a story resolves its effective configuration (deployment defaults → latest profile version → story overrides) at each turn start; a new profile version is a configuration change under FR-CONC-14..16. The deployment defaults are `deployment_state.profile_defaults`, a complete settings document seeded from Lite and edited through `/admin/settings`; a story's overrides are a sparse settings document with a revision, changed by `PATCH /stories/{id}/profile-overrides` (a JSON merge patch) and kept across profile versions and a reassignment (`PUT /stories/{id}/engine-profile`); `GET /stories/{id}/effective-config` shows the three layers and the result. The turn captures the resolved configuration at its start and runs under it to the end, and the resolution is cached per process by profile version, overrides revision and deployment configuration revision. Behavioral deltas apply at the next turn; data-producing increases go through the two-stage impact flow and then a backfill (or `forward_only`, which derives nothing from earlier turns; either way, deferred genesis content is written at position 0, FR-PROF-18), and a story with history for which no upgrade mode is available is reported `upgrade_unavailable` and keeps its configuration (FR-PROF-7); decreases stop writing and leave existing rows dormant; a switch to `lite` also queues a summarization job that builds the rolling summary from the transcript (FR-LITE-6).
- **Certification (FR-PROF-15..17):** `profile_certifications (fingerprint, profile_version, model ids/versions per purpose, quality-relevant settings hash, floors passed, sample sizes, bounds, run at)`. The effective configuration's fingerprint is computed per turn; responses carry `quality_status`: `certified` when a valid certification matches the fingerprint; `uncertified` when none ever has (any change to a quality-relevant setting, model, or reported model version yields a new fingerprint); `stale` only when a matching certification was later invalidated — by a scheduled canary falling below a floor, or by drift detected in a model whose identifier and reported version did not change. A certification run executes the eval suite against the fingerprint.
- **Two-stage flow:** profile-affecting mutations compute an impact report (affected stories, capability deltas, backfill estimates from transcript length and the model matrix's per-call costs, unmet scenario recommendations, quality status and whether certification survives the change (FR-PROF-16), guarantees lost). Without `ignore_warnings` nothing changes and the answer is `{applied: false, impact}` (the call keeps no idempotency record, so the confirmation may reuse its key); with it, the change applies and the answer carries the report too. `POST /stories/{id}/impact-preview` computes the same report for one story and writes nothing. Only invalid configurations and calls without a valid service credential are hard errors. Core builds the report and the fingerprint; the Orchestrator supplies the model ids and template hashes they need.
- **Lite pipeline:** a separate Orchestrator path: input guardrails (FR-GUARD-10) → prompt assembler (rating guidance → custom instructions → knowledge seeds and character definitions from the story snapshot, the persona guidance, and the director's author notes, labeled apart → pins → rolling summary → last N messages → input) → exactly one generation call → guardrail evaluation if policies are defined (deterministic rules cost no call; each model-assisted policy adds one `guardrail check` call per text it checks, so one on both input and output adds two; a violation triggers bounded regeneration, then the safe fallback) → transcript events. No claim detection, so no reserved detection calls; summary compression runs as a background job, outside the turn's budget. A worker maintains `lite_summary_segments (story_id, covers_from, covers_to, level, text, membership)`: compress the oldest window into a segment when the verbatim window exceeds its budget; merge segments into coarser ones as the summary grows; rebuild segments touched by truncation, regeneration, or fork.
- **Backfill worker:** reads the transcript events in scene-sized chunks (scene boundaries from location/time changes or a fixed size), runs extraction per chunk in parallel, then one ordered reconciliation pass writes positions, valid-times, exposures (inferred), commitments, clock advances, and State changes with provenance `backfill`. Conflicts apply `backfill_conflict_policy`; `ask` leaves the story in `paused_for_conflicts`. Progress, checkpoints for resume, and cancel (which drops the backfill's operation and restores the previous configuration) are exposed through the story API. Stories queued by a multi-story profile edit are processed by the same worker pool, each paused only during its own run.

### 4.12 Content ratings, true ages, and guardrail scope (FR-RATE, FR-CAT-12, FR-GUARD-8..11)
- **Tables:** `content_ratings` and `content_rating_versions` (name, content-policy description, display order, prompt guidance, image guidance, own policy IDs, `inherits_from` rating IDs); `stories.content_rating_id`; a rating on catalog versions and `media_assets`. Effective guardrails are the transitive closure over `inherits_from` (cycles rejected on save, each policy once), cached per closure — keyed by the versions of every rating in it, so an edit to an inherited rating invalidates its descendants. `policies` gain `scope` ∈ {global, rating, story, character}, `applies_to` ⊆ {text_input, text_output, image_prompt, image_output} (default {text_output} for rating, story, and character policies; {text_input, text_output} for global ones), an optional `age_condition` (a minor involved or present), and a user-facing `message`; policy edits are audited with the acting principal. Deployment settings hold `minor_age_threshold` (18) and the default rating for blank stories. Seed rows: the four ratings with inheritance Everyone → Teen → Mature → Explicit, and the global minors policy `minors_no_sexual_content` (`applies_to` = text input and output from M2, all four targets once the image targets land in M8; `age_condition = minor_involved_or_present`; a model-assisted sexual-content check whose `on_uncertain` is `violation`), inserted by migration `0009` from `orchestrator/policies/seeds/policies.py`. **The minors policy ships enabled at every rating, Explicit included; it is ordinary policy data, so an administrator can edit or retire it through `/admin/policies` (recorded with the acting principal), and removing it is the deployment's decision and responsibility.** The age condition is evaluated deterministically before any model call (`orchestrator/policies/age.py`): under Lite every cast member counts as present, a character's current age is its true age (no world clock until M6), and a minor is younger than `minor_age_threshold`, read live. A story without a minor never calls the model for the policy; when one is present, the `guardrail check` purpose receives the text, the policy prompt with the threshold filled in, and every cast member as an opaque positional label with its age (`character_1`, …, in creation order) — never a name.
- **Prompt assembly:** the guidance of the story's current rating version is a fixed section of every generation template — renders, repairs, director, opening narration, composition, and the Lite prompt.
- **Input gate:** the first step of respond, ingest, directives, rewrites, and story-text edits, and a genesis step: evaluate input-applicable policies (deterministic first, then model-assisted within the turn budget) before any event is written. A violation returns `422 guardrail_violation` with policy IDs, names, and messages; age-conditioned violations say that a minor is involved or present, never who. The audit record keeps policy IDs only.
- **True ages:** `characters.age_at_creation` with `age_recorded_at` (story time, or clock offset when the clock is unanchored); current age = recorded age + full years elapsed on the world clock. The age is a canon fact with engine-only visibility, the character's own belief, and a perceivable apparent age band (FR-SCN-8). The render schema for a new character requires `age`; an omission is a structured-output defect repaired in the turn. Age-conditioned policies read authoritative co-location (FR-TURN-10) for presence and each character's current age at the beat's start time.
- **Rating changes:** `PUT /stories/{id}/content-rating` compares effective guardrail sets by live policy id. A subset (relaxing, an equal set included) applies as a configuration change (story setting `content_rating_id`, interpretive); a Lite turn in flight depends on the story's rating, so it is re-checked under the new one before it commits. Anything else starts a `rating_check_jobs` row and its job, records a committed `control` operation with a `story_paused` event, and pauses the story (`stories.status = paused`, `paused_by`) like a backfill (`409 story_paused` with `{job_id, cause, progress}` for every truth-changing call). The job waits for a turn already in flight to commit, then evaluates the target's effective policies over the active history (deterministic first, then model-assisted within `rating_check_model_calls_per_record`; results cached per record and policy version in `guardrail_check_results`). It then applies the change in one transaction (restamping every active turn) or refuses it with the violation list (positions and policy ids only, plus an `audit_log` row), and the story resumes (`story_resumed`). A history or target rating that moved meanwhile runs the check again; a last attempt that fails resumes the story on its old rating. Each turn variant records `checked_guardrails` (`{rating_id, rating_version_id, global, rating, story, character}`, each `{policy_id: version}`: the set it last passed) at commit. Untruncate, swap, and promoting a dormant continuation into a fork run the same check job over every turn they would reactivate whose recorded set lacks a policy now in effect — turns discarded before a tightening, turns older than a newly added policy, and inactive turns from an import alike — and refuse with the violation list if any fails.
- **Rating suggestion:** for each rating, deterministic policies run over the entry's text, then one `rating suggestion` call per rating receives the rating's description, guidance, and effective guardrails plus the entry's full content, with instructions to report only conflicts with those policies; the response is a row per rating `{rating, version, appropriate, concerns: [{policy or clause, entry element, explanation}]}`. No writes.

### 4.13 Images: generation, prompts, and story images (FR-IMG, FR-CAT-4, FR-MEDIA-3)
- **Port and adapter:** `ImageGenerator.submit(request, idempotency_key) → {attempt_ref, outputs?, usage?}`, where `request` = (prompt, negative_prompt, seed, size or aspect_ratio, quality, n, reference_images) and the key is sent to the provider when `idempotency_keys` is declared; `collect(attempt_ref) → {outputs: [bytes, media type], usage, cost}`; and `capabilities() → {submission: async | sync, confirms_completion, idempotency_keys, …}`. An `async` adapter's `submit` returns on the provider's acknowledgement with the request identifier and no outputs; the worker commits it (`send_state = accepted`) and only then calls `collect`. A `sync` adapter's `submit` returns the identifier and the outputs together and `collect` is unused, so its whole call is the ambiguity window. Then — only for adapters declaring `confirms_completion` — `status(attempt_ref) → {state: running | succeeded | failed | cancelled | unknown, outputs (on succeeded), usage and cost when the provider supplies them}` and `cancel(attempt_ref) → accepted | not_supported` — both required for such adapters; registration rejects an adapter that declares `confirms_completion` without them, or with `sync` submission. The `attempt_ref` is the provider's request identifier: for an `async` adapter it is persisted on the reservation row before the results are awaited; for a `sync` adapter, together with them. Only a terminal status (`succeeded`, `failed`, `cancelled`) is definitive; an `accepted` cancel is not, and `unknown` never is. The bundled **OpenRouter adapter** is `sync` — `POST /api/v1/images` returns its images in the response — so it does not declare `confirms_completion`. It calls `POST /api/v1/images` with `model`, `prompt`, `seed`, `aspect_ratio` or `size`, `quality`, `n`, and `input_references` (reference images as signed URLs or data URLs), and writes each returned `b64_json` image to private staging (see Checks). Capabilities are discovered **per endpoint**, not per model: the adapter reads `GET /api/v1/images/models/{id}/endpoints` (each endpoint's `supported_parameters`, sizes, streaming support, pricing) and caches it with a TTL. A request carrying a seed or reference images is routed only to endpoints that list them (`provider.only`, fallbacks off); if none does, it is sent without them and the job records `seed_applied` / `references_applied = false`. Parameters no chosen endpoint supports are dropped and recorded; dimensions and format are read from the returned bytes, since providers clamp sizes. A negative prompt is folded into the prompt, since the API has no field for it. Credentials and defaults live in model config. With no adapter configured, generation endpoints return `not_configured`.
- **Jobs:** `image_jobs` (kind ∈ {catalog, story}, target, viewpoint, prompt, status ∈ {queued, generating, checking, promoted (story), candidates_ready (catalog), failed, stale, target_gone, cap_reached, cancelled}, attempts, policy results, asset ID, usage and cost, idempotency key, and the **origin**: story ID, originating operation ID, target turn and variant, position, timeline revision at enqueue — or entry ID, draft revision, and image-input fingerprint), run by workers (`SKIP LOCKED`) outside turn budgets; every applicable limit — deployment, story, turn, and catalog entry — is reserved at enqueue, and a request whose reservation fails is rejected (FR-IMG-11). **Promotion** is one transaction after the checks: lock the target; revalidate — story exists and is not paused (else wait), target turn variant still active, no amendment touching the turn's beats or depicted characters' appearance since the enqueue revision, current policies pass, erasure ledger clear — then insert the `media_assets` row and the `story_images` row. Catalog results skip story revalidation: unless the entry is gone, each passing output is copied from staging to its content-addressed key and gets a `media_assets` row with `state = candidate` plus an `image_candidates` row (candidate ID, entry, job, draft revision, fingerprint, `expires_at`), and the job ends `candidates_ready`. Candidate assets are excluded from general media reads and projections and are served only by the candidate endpoints. Attaching is a draft save that names `draft_revision`, compares the fingerprint, and sets `state = attached`; a candidate sweep deletes unattached candidates (row and bytes) past `candidate_ttl`. The staging sweep only ever sees staging objects. Any revalidation failure ends the job `stale` or `target_gone` and deletes the staged bytes.
- **Prompt builder:** gathers visual identities, each depicted character's apparent age band as the audience perceives it ("a woman in her thirties" — never the true age, which only the safety path sees), only `perceivable` visual-identity elements unless the image is omniscient, the scenario's visual style, the rating's image guidance, and, for story images, the scene from the viewpoint's filtered beats (FR-RESP-12,13), the viewpoint character's own location as that character has perceived it, and the characters present as the viewpoint perceives them (identity only where known) — never hidden world state such as an unperceived occupant or a concealed feature of the place (FR-IMG-8); the `image prompt` purpose writes the final prompt. Under Lite, the scene comes from the delivered message. `POST /image-prompts` returns this without generating.
- **Viewpoint inputs (FR-IMG-8):** for a story image, the scene description, the list of depicted characters, and the reference images are all derived from the viewpoint's filtered beats and its perception of who is present. A character whose `same_as` identity the viewpoint does not hold is described from perceived appearance, and that character's visual identity, seed, and references are withheld; a known character contributes only visual-identity elements marked `perceivable` (references and add-ons must declare an audience when saved). The final prompt then runs through the deterministic protected-content matcher for the viewpoint before generation. Nothing inspects the generated pixels for unperceived content; uploaded and consumer-prompted images carry the consumer's guarantee only.
- **Safety path (FR-IMG-12):** the generation request is built by a function that receives only the audience's filtered view — it has no handle to canonical ages — while the safety context is built separately from canon: the union of declared or builder-depicted subjects, characters named in the prompt, caption, or alt text (alias resolution), and characters authoritatively present at the story position, each with its true age; unresolved figures are classified adult, minor, or indeterminate by the guardrail-check model, and indeterminate counts as minor. The safety context goes to prompt-policy evaluation and the image check, never to the adapter. It is serialized for those calls as opaque subject labels with true ages and the prompt's own visual descriptors — no story text, beliefs, or other canon, and no character name the prompt does not already contain (FR-IMG-13). With a hosted `guardrail check` or `image check` model, that payload and the image leave the deployment and are kept on the provider's terms; the published data-flow table states this per purpose, and a deployment that needs the data kept in-house points both purposes at self-hosted models.
- **Checks:** image-prompt policies (known subjects, true ages, and presence deterministically; figures that resolve to no character classified by the guardrail-check model, indeterminate counting as minor; then model-assisted text checks) → generate → bytes into a private `staging/` prefix of the `BlobStore` (no asset row, no URL, never served) → the `image check` purpose on each output for image-output policies → on a violation, delete from staging and retry within the budget. If an applicable image-output policy has no configured image-check model, the job fails closed and names the policy. Promotion copies the passed bytes to their content-addressed key; bytes become addressable only when the asset row commits. A staging sweep deletes staging objects older than `staging_ttl` (1 hour); a separate pass deletes content-addressed blobs that have had no asset row for longer than `staging_ttl`, so a promotion in progress is never touched. Every generated asset records the image-check model and, per applicable policy, the result and whether that model is certified for the policy (no blanket certification). `media_assets` carry `source` ∈ {generated, generated_from_consumer_prompt, uploaded}, `check_status` ∈ {passed, unchecked}, per-policy results, `depicted_subjects` (required on upload and consumer-prompted generation, filled from the prompt builder otherwise, and written to `subject_references`), and, for story images, `viewpoint_basis` ∈ {filtered_inputs, protected_term_match, none}. Uploads use the same staging and checks when a checker exists; otherwise they are promoted with `check_status = unchecked`.
- **Story images:** `story_images` (story ID, turn and variant, beat index or inter-turn slot, `audience_viewpoint`, `camera_pov`, asset ID, prompt, operation ID, membership). Rows follow their operation's membership like any story record, so truncation, swap, and fork treat them as they treat beats; erasure finds them through `subject_references` on depicted characters and prompt text. History reads merge active rows whose `audience_viewpoint` matches the requested viewpoint into the beat sequence at their positions. With `illustration_mode = auto`, the render's structured output may carry `illustrate` hints; after commit the Orchestrator enqueues up to `max_auto_images_per_turn` jobs and returns their IDs in the respond response.
- **Limits and cost (FR-IMG-11):** `image_limit_counters (scope ∈ {deployment, story, turn, entry}, scope_key, period, limit, reserved, used, overage, extra_outputs)` — stored materializations of the record sums defined in FR-IMG-11, where the period is the calendar day in the deployment's configured time zone (default UTC), or the turn index for per-turn counters. Default limits: deployment settings `image_limit_deployment_day = 200` and `image_limit_entry_day = 16`; story settings `image_limit_story_day = 40` and `image_limit_turn = 4`, defaulted from the deployment; `catalog_candidates_n = 4`. A limit of 0 disables its scope (`images_disabled` at enqueue); configuration validation rejects negative or missing values, and there is no unlimited setting. Before each provider call a job runs one transaction: `SELECT … FOR UPDATE` on every applicable counter in the fixed order deployment → story → turn → entry, check `used + reserved + k ≤ limit` for each, and increment `reserved` on all or none. On return it moves the returned count from `reserved` to `used` and releases the remainder; terminal states release what is left, and on lease expiry the reaper advances the job's `attempt_token` (fencing) and schedules release of that attempt's reservation at its horizon (`started_at + adapter_timeout + grace`); no new attempt starts before the horizon. After it, for an adapter declaring `confirms_completion`, the reaper calls `cancel`, then polls `status(attempt_ref)` until a terminal status — no retry, so no overlap, while it waits: on `succeeded` the job adopts the returned outputs with no retry: it settles the old attempt's row once — the row was already `released` at the horizon, so every output lands in both `used` and `overage` — then checks, revalidates, and promotes the first `n` under the current token, discarding any beyond `n` unchecked as `extra_outputs`; on `failed` or `cancelled` it settles the row and retries. A later return to the fenced worker finds the row settled, deletes its bytes, and is logged `late_duplicate`, filling in cost only if it was still `unknown`; with none by `confirm_wait_max` (30 minutes) it stops polling, falls back to the non-confirming rule, and logs the fallback — the retry may then overlap the old call, whose output, if it returns, is settled as overage (`late_after_horizon`) and never adopted; otherwise the retry may start at the horizon, and a late result is settled as overage. Outputs beyond the requested `n` are discarded unchecked and recorded as overage flagged `extra_outputs`. Reservations are rows in `image_reservations (job_id, attempt_token, counter_keys, requested, used, overage, extra_outputs, basis ∈ {actual, presumed, corrected}, state ∈ {held, settled, released}, send_state ∈ {prepared, sending, accepted, returned, ambiguous}, idempotency_key, attempt_ref, horizon_at)`; `requested` and `counter_keys` — the immutable list of (scope, scope_key, period) captured at insert — are fixed at insert. The worker commits `send_state = sending` before calling `submit`; with an `async` adapter it commits `attempt_ref` (`accepted`) when `submit` returns and only then calls `collect`, while a `sync` adapter's identifier and results commit together (`returned`). Recovery of a row left in `sending` re-sends with the same `idempotency_key` when the adapter declares `idempotency_keys`; otherwise the row becomes `ambiguous` and is settled at its horizon with `basis = presumed`, `used = requested`, and cost `unknown`, and `ambiguous_sends` is incremented for the job, story, and deployment. If the actual result later reaches the settlement path, the row is corrected once (`basis = corrected`: `used = m`, `overage = extra_outputs = max(0, m − requested)`, cost recorded), the counters in its `counter_keys` move by the difference, the outputs are deleted unpromoted, and the attempt is logged `late_after_presumed`; a further return is `late_duplicate`. A result returned before the horizon settles the row normally and it is never presumed. Counter maintenance, applied to every counter row named in the record's `counter_keys` (never recomputed from the current time or target) in the same transaction as the state change: insert as `held` → `reserved += requested`; `held → released` → `reserved −= requested`; `held → settled` with *m* outputs → `reserved −= requested`, `used += m`, `overage += m − min(m, requested)`, `extra_outputs += max(0, m − requested)`; `released → settled` with *m* outputs → `used += m`, `overage += m`, `extra_outputs += max(0, m − requested)`; presumed `held → settled` → `reserved −= requested`, `used += requested`; correction `presumed → corrected` with *m* outputs → `used += m − requested`, `overage += max(0, m − requested)`, `extra_outputs += max(0, m − requested)`. So `reserved` sums `requested` over `held` rows, and `used`, `overage`, and `extra_outputs` sum over `settled` rows. Limit checks use `used + reserved`. A nightly reconciler recomputes the sums from `image_reservations` and reports any drift. Staging promotion and attachment compare the worker's token with `image_jobs.attempt_token` (current token only). The **settlement path** accepts a fenced token for one operation only — settling its own row, idempotently, keyed by `(job_id, attempt_token)`: `held` → `settled` (returned outputs into `used`, the rest released) before the horizon, or `released` → `settled` with the outputs recorded as `overage` after it. Either way the cost is recorded, the bytes are deleted, and the attempt is logged `late_discarded` or `late_after_horizon`. An attempt that never returns is marked `released` at its horizon by the reaper, with cost `unknown` unless the adapter can look it up. An `image_costs` row per provider attempt records billed cost (zero when the provider did not bill) and rolls up per job, story, entry, and deployment.

### 4.14 Message feedback and text-quality signals (FR-FB, NFR-QUAL-14,15)
- **Feedback:** `message_feedback (story_id, message_id, turn, variant, principal, rating 1–5, tags[], text, operation_id, config_fingerprint, profile_version, models per purpose, rating_version_id, quality_status, compacted_at, redacted_at, created_at, updated_at)`, unique on (story, message, principal). `message_id` is the rated `message_rendered` event: a message the engine produced (a reply, a safe fallback, a regenerated variant, in any membership), never the consumer's own narration. The context columns are copied from that message's operation's recorded `config_revisions` when the rating is first written, never recomputed. A re-rating that changes the value appends the value it replaces to `feedback_history (story_id, message_id, turn, variant, principal, rating, tags[], text, kind replaced|retracted, rated_at, replaced_at, redacted_at)` and updates the row; the same value again writes nothing; a retraction appends the final value and deletes the row. A rating is a plain table write: no operation, no event, no idempotency key. Rows are audit category: no view, retrieval index, or prompt assembler reads them, and a test lists every module allowed to name the tables. They have their own retention setting `feedback_retention`, by default the life of the story (`story_lifetime`; or a number of days, which `retention_sweep` enforces), not the audit-record default (FR-FB-2); they are deleted with the story, a fork does not copy them, and M7's compaction marks them `compacted_at` (`core.feedback.mark_compacted`) instead of deleting them. Free text passes through the subject-indexing seam (`core.feedback.index_hook`, connected to `subject_references` by #123) for erasure. The tag set is deployment configuration (`deployment_state.feedback_tags`), seeded with the nine default tags; removing a tag a rating or its history still carries is `409 feedback_tag_in_use`. `feedback_text_max_chars` (default 2000) caps the text.
- **Reporting:** `GET /feedback/aggregates?group_by=` groups the current ratings by one dimension: profile version, fingerprint, model (the `generation` purpose's), content rating, scenario, tag, or day (UTC). The groups are computed on demand in SQL, with no materialized views, and the window (`from` inclusive, `to` exclusive) applies to when a rating was first given. Each group carries its count, distinct messages, mean, histogram and tags, and the implicit signals derived from the log. `regenerations` counts a regenerate's turn operation, which records the variant it replaced as `turn_report.regenerated_variant`; a turn written over a rewound tail is not a regeneration. `regen_after_low_rating` counts a rating of 1 or 2 followed by a regeneration within `feedback_regen_window_s` (default 300 s). `swaps_back` counts `swap` events at the message's turn back to an older variant, untruncates included, and `rewinds` counts `truncate` events whose first discarded turn is the message's. Two review lists, `GET /feedback/review/guardrail` (`should_have_been_blocked`) and `GET /feedback/review/memory` (`forgot_something` / `factual_error`), page the tagged ratings with the message, the input it answered and its context. Feedback is flag-only: the import-linter contract `feedback-is-flag-only` keeps the Orchestrator, story creation, guardrails, ratings, profiles and projections from importing the feedback modules.
- **Export:** `POST /admin/feedback/export` works only when the deployment setting `feedback_export` is on (403 `feedback_export_disabled` otherwise). It writes one JSONL file of labeled cases, one per current rating, to the blob store at `exports/<id>.jsonl`, and records a `feedback_export_log` row: who, when, the window and filters, and the case count. The row is deployment-level, so it outlives the stories. The file is served by `GET /admin/feedback/exports/{id}/content` behind the service credential, and the media sweep deletes it after 7 days. Delivered exports, meaning files that have been downloaded, are outside the erasure boundary (FR-ADMIN-8). An erasure still redacts a file that has not been downloaded yet (#124's `ERASURE_TARGETS`).
- **Quality signals:** each final message's repetition (n-gram overlap with the previous k messages and repeated openings) and length accuracy against the requested length are computed without a model at commit time and emitted as metrics (counts and ratios only). The eval harness keeps every first draft and intervention type for NFR-QUAL-14 pairwise judging, and runs the `quality judge` purpose for voice consistency and story-driver adherence; judge calibration results are stored with the certification record.

## 5. The Model Access Layer (Orchestrator)

All model calls flow through one layer the Orchestrator owns, configured inside Epistrel.

- **Per-purpose configuration held in Epistrel.** Config maps each purpose → `{base_url, model, api_key, params}`. Epistrel connects directly to the external model servers. A **runtime config API** allows changes (swap the generation model mid-story, raise temperature, repoint at a gateway) without restart. Each purpose defaults to a single configured model if not individually overridden.
- **Enumerated model purposes:**

  | Purpose | Owner | Hot path? | Notes |
  |---|---|---|---|
  | Generation | Orchestrator | Yes | Renders say/think/do/latent; honors per-request prompt params |
  | Regeneration / repair | Orchestrator | Yes | Regenerate a span under corrected constraints; usually same as generation |
  | Entailment / verify fallback | Orchestrator | Yes | The fuzzy residual of verify; calibrated judgment under budget |
  | Consolidation / reflection | Orchestrator (worker) | No | Summaries and reflections; quality-sensitive; can be larger/slower |
  | Importance scoring | Orchestrator (worker) | No | Tiny; could be a small classifier |
  | Salience detection | Orchestrator | Yes | Detect signals needing commitment; in the turn, since a salient reference blocks the turn from closing (FR-COMMIT-7) |
  | Extraction backstop | Orchestrator | Yes | Model layer of claim detection (FR-VERIFY-13); per `extraction_mode`, gated by default (only the beats a detector flagged, with shadow sampling) or on every render and on the composed message (`always`) |
  | Time estimation | Orchestrator | Yes (only on undeclared narrated skips) | Best-guess duration for narrated elapsed time (FR-CLOCK-7); defaults to the extraction-backstop model |
  | Guardrail check | Orchestrator | Yes (only for model-assisted policies) | Input and output checks for policies that declare a model check, e.g. recognizing sexual content for the minors policy (FR-GUARD-9..11) |
  | Rating suggestion | Orchestrator | No | Per-rating content-policy review of a catalog entry (FR-RATE-8); defaults to the guardrail-check model |
  | Image prompt | Orchestrator (worker) | No | Writes image prompts from perceivable visual identities, apparent age bands as the audience perceives them (never true ages, FR-IMG-12), style, rating image guidance, and the viewpoint's scene (FR-IMG-2); defaults to the generation model |
  | Image check | Orchestrator (worker) | No | Vision-capable model that checks generated and uploaded images against image-output policies (FR-IMG-3); no default — unset until configured (FR-MODEL-3) |
  | Belief adjudication | Orchestrator | Yes (salient witnesses only, optional work within the budget) | Testimony acceptance and other adjudicated belief transitions (FR-BELIEF-3); defaults to the entailment model |
  | Quality judge | Eval harness | No (never in a turn) | Pairwise prose comparisons for NFR-QUAL-14,15 |
  | Embedding | Orchestrator | Yes | Separate port; sticky dimension (see §6) |
  | Image generation | Orchestrator (worker) | No | Separate `ImageGenerator` port; bundled OpenRouter adapter (see §4.13) |

- **Purpose registry and data flow (FR-MODEL-13, FR-IMG-13).** Each purpose, the embedding port, and the image adapter are declared in one registry module: name, default model, capability floor, and a Pydantic schema of the inputs its requests may carry, each field tagged with a content category. Prompt templates render with strict undefined-field errors against that schema, and adapter payload builders are typed by it, so a prompt can carry only what its purpose declares. The model guide (`docs/models.md`) is generated from the registry in CI, and the build fails if the committed guide differs. The registry module and the guide are owned by the Model Access Layer maintainers through the code-owners file. The design-level data flow, which the generated guide replaces as the authority once the registry exists (this table is superseded by the generated `docs/models.md` from M2):

  | Purpose | Receives | Never receives |
  |---|---|---|
  | Generation | Structured: one character's definition, that character's viewpoint-filtered working memory, retrieved memories and beliefs, its time belief, the scene and earlier beats as it perceived them, the player input as perceived, rating guidance, and custom instructions. Lite: rating guidance, custom instructions, the story's knowledge seeds and character definitions, persona guidance, author notes, rolling summary, pins, recent messages, and input; on a guardrail regeneration, the messages of the output policies an earlier draft broke (FR-GUARD-6) | Other characters' private memories or thoughts; facts or true ages the viewpoint cannot know; the objective clock (FR-CLOCK-11) |
  | Director (narrator render) | Structured (#150): the rating guidance, custom instructions and scenario text; the scenario's director guidance, labelled apart from the facts (the director's context alone, FR-SCN-11); the scene and who is present; the beats so far as the narrator perceives them (`think` excluded); the retrieved context and canon; the player input. Its beats are `narration` and `latent`, and it names the characters it introduces | Any character's `think`; true ages |
  | Age repair | Structured (#150): the rating guidance, custom instructions and scene, and each character a render introduced without an age with the render's clue; answers one integer age each (FR-CAT-12) | True ages of other characters; story text beyond the scene |
  | Regeneration / repair | The generation inputs for that character, plus the repair constraints for the failed span (FR-REPAIR-1) | As for generation |
  | Entailment / verify fallback | The claim and the records it is judged against — its holder's or objective canon's | Unrelated story content |
  | Consolidation / reflection | Records of one viewpoint scope within the job's source window (FR-MEM-9) | Records from any other scope |
  | Importance scoring | One memory record | — |
  | Salience detection | The rendered beat and its scene context | — |
  | Extraction backstop | The rendered beat or the composed message | — |
  | Time estimation | The narrated skip, its activity context, and established start times | — |
  | Guardrail check | The text being checked (input or output), the policy text, and for age-conditioned policies, subject labels with true ages — for image prompts, also the prompt's visual descriptors | Other story text; beliefs; names an image prompt lacks |
  | Rating suggestion | The catalog entry's full content and each rating's description, guidance, and guardrails | Stories |
  | Image prompt | Perceivable visual identities, apparent age bands as the audience perceives them, style, rating image guidance, and the audience viewpoint's scene | True ages; restricted references; anything the audience has not perceived |
  | Image check | The image; its prompt, caption, and alt text; the policy text; subject labels with true ages and the prompt's visual descriptors | Story text; beliefs; names the prompt lacks |
  | Belief adjudication | The witness's relevant beliefs, trust and priors toward the speaker, and the perceived utterance | Other characters' private records; objective canon the witness cannot know |
  | Quality judge | Eval fixtures only (paired messages) | Live stories |
  | Embedding | The text of each record or query being embedded | — |
  | Image generation (adapter) | The built prompt, its parameters, and perceivable reference images | True ages; the safety context |

  Every row's inputs leave the deployment when that purpose is routed to a hosted provider, and are kept on that provider's terms (FR-ADMIN-8).

- **Guarantee boundary (FR-VERIFY-15, NFR-PRIV-4).** The model proposes; the engine validates structured claims, effects, and permissions. **Deterministic:** context assembly and viewpoint filtering (the primary privacy control), normalization of declared structure, contradiction rules, State effect validation and permission checks, perception routing, commitment/ledger mechanics, clock pacing and stops, timeline/concurrency operations, deterministic claim detectors. **Model-dependent, measured:** generation, model extraction of undeclared claims (NFR-QUAL-10), salience (NFR-QUAL-4), time estimation (NFR-QUAL-9), entailment fallback (NFR-QUAL-2), testimony acceptance and other belief adjudication, repair rendering, paraphrase/indirect-disclosure detection (NFR-QUAL-1, reported with an upper bound), model-assisted guardrail checks such as recognizing sexual content, and rating suggestions. Output scanning is a secondary control on top of structural context isolation.
- **Viewpoint guarantee table (FR-RESP-12,13, FR-AUTH-2, FR-VERIFY-15).** What a character-viewpoint response, history read, or beat list withholds, by the story's perception level; every result states its level as `audience_filter`. An `omniscient` result withholds nothing and is produced only when the request names it.

  | Perception (`audience_filter`) | Stories | Withheld from a character viewpoint | Everything else |
  |---|---|---|---|
  | `none` | every `lite` story (M2); `structured` with shared character knowledge | `think` and `latent` beats; audit records and true ages (omniscient reads only) | returned in full; **no audience filtering applies** |
  | `co_location` | `structured` with perception (M5) | as `none`, plus beats the character was not co-located with | perceived beats in full |
  | `full` | `structured` with perception (M5) | as `none`, plus unperceived beats | perceived content in full; envelope-only beats as their envelope |

  **Characters in `lite` (FR-LITE-5).** Several render characters are voiced in one combined generation and returned as one message (one reply beat listing them in `render_character_ids`). Their knowledge is separated **by instruction only**: each character's notes are labelled with its name, and the shared prompt says each character knows only what its notes and the scene show. Every voiced character's notes, secrets included, are in that one shared context, so nothing structural stops a reply from drawing on another character's notes. The result's `audience_filter` is `none`.
- **Per-turn budget (NFR-PERF-6,7).** A turn budget object (calls remaining, deadline, and the safety reservation S = B + C + G + O — one extraction per planned beat; one for the composed message; G, one call per model-assisted input policy plus one per model-assisted output policy for the turn's first output checkpoint, so a policy on both is two calls; and O, reserved at planning in a story with a write-capable `synchronous` provider — the outcome render, its extraction, and the second output checkpoint's policy calls — and released once every render has finished without requesting such an effect) travels with the turn; every Model Access Layer call debits it. Planning computes renders + S before the first call: if it exceeds `max_model_calls_per_turn`, extra primaries are downgraded to reactive narration (never a fixed `primary`, which is deferred) or deferred until it fits, and if one primary plus its reservation still does not fit, the turn is rejected with `budget_below_safety_minimum` before any model call. A repair starts only when its re-render and its extraction can both be reserved — plus, for a repair triggered by an output policy, the re-check by every model-assisted output policy, or the safe fallback is used; the composed-message reservation is released when deterministic assembly is used. On exhaustion the Orchestrator applies the fixed degradation order — skip polish → stop extra repairs (deterministic rungs or safe fallback) → default belief adjudication → entailment to safe disposition → remove unestimated skips → downgrade or defer extra primaries → replace any beat that can't get its reserved detection with the safe fallback — and reports `model_calls`, `elapsed_ms`, and steps taken. End-to-end latency per model tier is published in the model matrix (NFR-PERF-8).
- **Transport: the `openai` SDK → OpenAI-compatible endpoints** (Apache-2.0; ADR-150). The OpenAI chat/embeddings wire format is the de facto standard — vLLM, Ollama, llama.cpp server, LM Studio, TGI, hosted providers all speak it or shim to it — so one integration reaches the whole ecosystem. The Model Access Layer (`epistrel.orchestrator.models`) owns per-purpose routing, the turn budget owns every attempt (the SDK's own retries are off), and per-purpose call counts and cost are Epistrel's (FR-MODEL-12), so no routing library sits in between. The adapter is chosen by `EPISTREL_MODEL_ADAPTER`: `openai` (default) or `stub`, the deterministic test adapter (FR-MODEL-11); swapping it changes nothing in the Engine Core (NFR-PORT-2). **Configurable `base_url`** per purpose lets an enterprise adopter point Epistrel at their own LLM gateway (central logging, cost control, rate limiting) as long as it speaks the format, and a local server such as LM Studio is reached the same way (`http://host.docker.internal:1234/v1` from the compose container). Configuration lives in the `model_config` table: one row per configured purpose plus a `default` row, inherited per field; API keys are stored encrypted with `EPISTREL_CONFIG_KEY`. An optional **bring-your-own-completion** escape hatch allows a model that is not OpenAI-compatible, where the consumer returns a completion for a given purpose.
- **Deterministic-first, gated escalation.** Each model-using operation attempts a deterministic path first (verify is set logic in the Engine Core; it returns `uncertain` only on the fuzzy residual) and the Orchestrator invokes a model only then. The verify escalation gate is a **tunable predicate-resolution-confidence threshold** (config), launched conservatively and tightened per predicate-shape on measured **escalation yield** (flip rate × consequence), validated in shadow before promotion (FR-OBS-2/4, NFR-PERF-5). Most hot-path verify calls never reach a model, and that fraction is driven down on evidence over time. See ADR-017.
- **Output validation and graceful degradation.** Wire compatibility ≠ capability. Adapters use constrained/grammar-guided decoding where the backend supports it and parse-validate-retry otherwise; the Orchestrator **validates every structured result and never trusts it** — unparseable/low-confidence output is treated as *uncertain* (conservative default or escalation), never silently accepted. A recommended **capability floor per purpose** is documented. **Protocol vs capability:** any endpoint speaking the OpenAI-compatible format connects (protocol compatibility, NFR-PORT-1); each purpose separately publishes its capability requirements — structured output or reliable parse-validate-retry, minimum context, and passing its conformance suite at the NFR-QUAL floors — and only models that meet them are reported as capable for that purpose (NFR-PORT-3).
- **Deployment:** the model-access adapters run in-process by default (simple) or the cognition workload can be split to its own container at future scale — no Engine Core changes.

## 6. The embedding port

Separate from the chat-model purposes because embeddings have different lifecycle rules. OpenAI-compatible `/embeddings`; any local or hosted embedding model works. **Sticky dimension:** the model's dimension/semantics are baked into every stored vector, stamped with `embedding_model_version`; changing it is a **re-embed-everything migration** (a background job), not a config flip, and incompatible vector spaces are never mixed in one search.

- **As built (#138).** `epistrel.orchestrator.embeddings`: the `EmbeddingAdapter` protocol with the `openai` SDK adapter (`embeddings.create`, `encoding_format=float`, SDK retries off) and a deterministic stub (the text's SHA-256 expanded to `d` floats, L2-normalised; `d` = `EPISTREL_STUB_EMBEDDING_DIMENSION`, default 64), chosen by `EPISTREL_EMBEDDING_ADAPTER` (unset: `EPISTREL_MODEL_ADAPTER`'s). It is reached as `ModelAccessLayer.embeddings`, so every embedding is counted under `purpose=embedding`. `embedding` is a delivered **port** in the registry (schema `{text: memory_text}`, not routable by a profile) with its own `model_config` row and no fallback to `default`; its params take `timeout` only.
- **The pin** lives on `deployment_state` (`embedding_model_version`, `embedding_dimension`, `embedding_pinned_at`; `core.embeddings`). The first embedding, in the `embed` job and never in a turn, pins it in a short transaction with a `config_changes` row and retypes `memories.embedding` to `vector(d)` with the HNSW cosine index (pgvector indexes up to 2,000 dimensions). Every vector write stamps the pinned version; a vector of another dimension is 503 `embedding_dimension_mismatch` and nothing is stored. The version is `<base_url host>/<model>` (the stub's `stub:sha256:<d>`); a `base_url` change alone moves no vector space.
- **A model change** (`PUT /admin/model-config/embedding`, probed first: 422 `embedding_unreachable`) runs a `config_changes` listener in the write's transaction. It moves the pin, and when the dimension changes it nulls every vector and retypes the column. It nulls retained retired and dormant vectors, and enqueues one `reembed` job per non-archived story with vectors. Each job embeds up to `reembed_batch_size` (500) hot active memories per run, in batches of `embedding_batch_max` (64), re-checks the pin before writing and advances `stories.embedding_model_version`. `GET /admin/reembed/status` reports progress and `POST /admin/reembed/retry` retries failed stories.
- **Search** (`core.retrieval`): vectors are compared only within the pinned version; a story whose version differs is searched lexically with `degradation: ["embedding_pending"]`, and a failed query embedding gives `embedding_unavailable`. The lexical backend is the `LexicalSearch` protocol (`EPISTREL_LEXICAL_BACKEND=tsvector`, PostgreSQL full-text search over the generated, GIN-indexed `memories.search`, matching any of the query's words).
- **Retrieval pipeline** (#141, `core.retrieval.pipeline.retrieve`, on the caller's connection, no model call of its own). Each stage is timed in `timings`, excluding model calls:
  1. **Resolve.** #139's resolvers run as the pure `resolve_query`; Q-02 runs the same function. Its context reads only the relationships the text's relational descriptions need (#451): none without a relation noun, else those of its possessors.
  2. **Occasion.** When the text gives a time window or an event type, it queries the episodic memories by turn window (story-time mapped through M4's basis), `event_type` and `participants && resolved entities`, up to 5 episodes, latest first; with no time window, those best matching the text first (#458). The episodes' participants resolve the group, and their assessments are the semantic memories and reflections naming them.
  3. **Hybrid arms.** The vector arm uses HNSW, `SET LOCAL hnsw.ef_search` and `iterative_scan = relaxed_order`, over the pinned version only. The lexical arm (a hit scoring under 60% of the best hit is dropped, #458) and the exact-alias arm (the aliases of the entities the text names as phrases; the speaker's own "I"/"me" is left out, #458) run only with `memory.episodic.hybrid_search`. The arms are fused by reciprocal rank (k 60).
  4. **Rank.** `w_sim·fused + w_rec·recency + w_imp·decayed importance` (the `memory.episodic.weight_*` dials, 0.6/0.2/0.2; `recency_half_life_turns` 100). The top `k` are returned, and nothing after the query's position.
  5. **Profiles and canon.** #137's standing profiles of the resolved characters (one batched read, #451) and #133's canon about the resolved entities, read through `KeyedLookup` as retrieved rows, never keys.
  6. **Assemble.** The `retrieval_token_budget` (3,000, `len // 4`) is filled by tier: the `context_sources` hook's ledger items and pins (pins capped at 40%), the occasions, the profiles and canon, then the ranked memories.

  Retired records hit by the window or the lexical lookup are rehydrated, up to 20, re-embedded in one batched call that is not stored, and their tier is never changed. A story whose `episodic` module is off reads only its configuration. `GET /stories/{id}/retrieve` exposes the result for debugging, to `omniscient` only.

## 7. Extensibility: external-data providers (Orchestrator)

The Orchestrator is extensible so Epistrel can serve real games, not only open roleplay.

- **Registration.** The consumer registers external-data providers (tools/Skills/MCP) at configuration time (or via the config API), each declaring the predicates/domains it authoritatively answers and a trust tier.
- **Use during generation and verification, pinned per turn.** The first read of a predicate in a turn is pinned; generation, verification, and commit all use the pinned value, and verification never re-reads live. `verify` resolves *objective* claims in a provider's domain against the pinned value; a character's first-person claim is checked against that character's beliefs (FR-EXT-3).
- **Unavailability policy** per provider: `fail_turn`, `last_known` (within a freshness window), or `unknown`; default `last_known`-if-fresh, else `unknown`. The policy applied is recorded with the turn. Under `unknown`, only new objective assertions and newly acquired exact knowledge of the value are blocked; characters' existing beliefs about it (and lies about it) verify against their beliefs as usual, with the objective relation recorded as `unresolved` (FR-EXT-11).
- **Read-only by default; writes via outbox.** Implied changes to externally owned values are returned as state effects in the respond response for the consumer to apply. A write-capable provider uses a transactional outbox: the turn and an `external_effect_outbox` row commit together; a dispatcher sends the effect with an idempotency key, records confirmation, and surfaces failures through a reconciliation status. Author directives cannot override externally owned values (refused, or routed as a write).
- **Outbox lifecycle (FR-EXT-12..18):** each outbox row carries its originating `operation_id`; the dispatcher claims rows with `FOR UPDATE SKIP LOCKED` and, in the same transaction, re-checks that operation's membership — discarded → `cancelled`, never sent. The **claim commit** (`intended → claimed`) is the in-flight point: it commits before any network send, so a discard committed before it cancels the row and a discard after it lists the row for reconciliation, sent or not; claim and cancel serialize on the row lock. Row states: `intended → claimed → confirmed | failed | unknown`, `unknown → confirmed | failed`, `intended → cancelled`, and `imported_unsettled` for a row imported without a terminal outcome (never claimed; listed for reconciliation). The provider idempotency key is the row ID; providers declare `dedupes_dispatch`, and a non-deduplicating provider's claimed row with no outcome moves to `unknown` rather than being re-sent. **Turn stages (FR-EXT-16,17):** a turn with an asynchronous effect is ordinary — it commits with its `intended` row and closes, and the outcome arrives as a late settlement (FR-EXT-21); a turn with a synchronous effect commits in stages — intent (turn + row) → claim → outcome event → outcome step (a later step of the same turn) → stored response — with `operations.status` tracking the stage; a recovery sweeper and same-key retries resume from the last committed stage, a failed outcome-step render falls back to deterministic outcome narration, and nothing committed is rolled back by a later stage's failure. Ordinary turns keep the single-transaction commit; only staged turns use stages. **Terminal outcomes (FR-EXT-22):** each row has one settled terminal outcome (first terminal wins); duplicates are recorded and ignored; a conflicting later terminal outcome is listed `outcome_conflict`; a confirmation after an expired, released reservation is listed `late_success_after_expiry` with a fresh re-verification and settles only through an explicit author/consumer action (`settle_now`, re-verified at that moment, or `compensate`). **Late settlement (FR-EXT-21):** an outcome arriving after its turn closed is written as an outcome record on the outbox row (timeline-independent); if the originating operation is still active, a settlement operation is placed at the next inter-turn slot `N⁺k` after the last completed turn (valid-time = the clock immediately before the slot commits — the turn's end time plus any earlier slots' advances; deferred behind an incomplete staged turn; an in-flight ordinary turn rebases on its revision bump) that re-verifies preconditions and either commits the conditional effects or lists `settlement_conflict`; truncations, swaps, and forks that exclude the settlement operation list the effect as `confirmed_unsettled`; an outcome whose origin was discarded is listed `confirmed_discarded_origin` and applies only by explicit author/consumer action. `timeline_revision` increments at intent, outcome, and completion (not at claim or response storage); the per-story in-flight marker is held from intent to completion; history reads mark the turn `incomplete`; a fork copies the committed stages and closes the turn as "outcome not known in this story" (FR-EXT-19). **Post-effect values (FR-EXT-20):** providers declare `returns_resulting_values`; a confirmation that carries them writes a new `external_read`-style version (provenance `confirmation`) at the outcome step's position, otherwise one optional post-effect read is recorded; verification of each beat/step uses the latest version at or before its position; deltas are never applied to the pre-effect read. Forks copy outbox history with `executable = false`. Operations that discard turns with `claimed`, `unknown`, or `confirmed` effects return them with `reconciliation_required`; swaps never re-dispatch `cancelled` rows. Each provider declares `confirmation ∈ {synchronous, asynchronous}`; under `asynchronous` (and for consumer-applied effects) per-beat verification rejects prose asserting an unconfirmed outcome (FR-EXT-15), and the composition check (FR-RESP-8) keeps the composed message to verified beats.
- **Record every read; reference it on commitment.** Every provider read is recorded as an `external_read` event. When a character commits a reference to volatile external data, the Engine Core writes a fact (provenance `external@timestamp`) that references the originating `external_read` event rather than re-capturing the value — one source of truth, fixing the story's statement while the live value may drift.
- **Trust and safety.** External data gets a high-trust provenance tier within its domain, but tool results are untrusted *content* — treated as data, tiered by the provider's declared authority, never as instructions (MCP tool descriptions and results included).

### 7.1 Story States (Engine Core + Orchestrator)
Internal tracked values, so most games need no external store.
- **Schema** in `state_definitions`, declared by the author/consumer: type (number/boolean/enum/short text), scope (story or per character), constraints (min/max, non-negative, allowed values), visibility (player-visible or hidden), owner (`story` or `external`), and optional simple rules (story-time-based change, derived values) — no scripting language. The engine may insert a row into `state_proposals`; it never creates a definition itself.
- **Changes** are rows in `state_changes`, each tied to an operation and carrying a reason and source (turn, author directive, consumer API, rule). The current value in any view is the fold of active changes in that view, so truncation, regeneration, fork, swap, and amendments apply automatically. A materialized `state_values` projection caches the active-head value.
- **Turn flow:** the render's state-effects channel declares changes; the Engine Core validates them against constraints inside the commit transaction. A violation means no change and an in-character repair (the action was an attempt). Committed effects on player-visible States, with old and new values, return in the respond response; effects on hidden States are returned only to requests that name `omniscient` (FR-RESP-7,12).
- **Effect rules (FR-STATE-10..13):** `state_definitions` also store allowed sources, allowed justifying event types per direction, per-effect and per-turn caps, and transfer/conservation settings. Validation order: source permitted → justifying event present and verified → action preconditions verified as propositions (counterparty agreement, availability, location, ownership) → transfer balance → bounds. The extraction backstop diff-checks narrated consequential changes against declared effects in both directions.
- **API:** read/set States with idempotency keys and revision checks; API and "from now on" directive sets are positioned at the next inter-turn slot `N⁺k` (FR-STORE-31).
- **Contingent effects (FR-STATE-14):** `state_changes.contingency ∈ {unconditional, reservation, conditional}` with `prerequisite_effect_ids`. Reservations are rows with `status = held` that count against availability but not ownership; the outcome stage converts or releases them and commits conditional rows whose prerequisites are all `confirmed`. Rows waiting on `unknown`/timed-out effects stay `pending`; a per-State `reservation_expiry` job releases expired holds and lists them for reconciliation.

### 7.2 World clock (Engine Core + Orchestrator)
Built in and on by default (FR-CLOCK); the source of story-time.
- **Storage:** a built-in `world_clock` row in `state_definitions` (type clock: offset in minutes plus anchor, minute resolution, calendar, time-of-day bands, `mode ∈ {paced, manual, external}`, pacing table, `max_unprompted_skip` (scenario default, story override; default 24 h), `stop_at_due_events`, tolerances). Advances are ordinary `state_changes` rows with `source ∈ {pacing, declared_skip, estimate, player, author, consumer, external}`, the `(turn, beat, step)` they belong to, and estimate metadata. The value is always an exact offset in minutes from the story's start plus an anchor (complete, partial, or absent) — never a picked datetime (FR-CLOCK-3).
- **Timing within a turn (FR-CLOCK-17):** beats and declared steps carry `start_time`; beats carry `end_time`. Sequential beats start at the previous beat's end; simultaneous beats all start at the turn start and the turn ends at the latest beat end. Skips and explicit later times attach to step boundaries and shift later steps; the pacing increment is applied at the beat's end only when the beat has no in-beat advance. Claims, exposures, and acquisitions use their step's start; durative propositions span step start → next step start.
- **Anchors (FR-CLOCK-3,18):** the clock stores an exact offset plus an anchor of per-component constraints (value | range | unknown) recorded at its anchoring position; absolute times at other positions are computed by shifting the anchor by offset differences (ranges widen across midnight). Clock checks evaluate over the admissible range and return `uncertain` unless decided for every value; due tests yield `due` / `possibly_due` / `not_due`.
- **Turn flow (FR-CLOCK-17):** before a beat renders, its start time is fixed (sequential: the previous beat's end; simultaneous: the turn start). After the render, claim detection finds any undeclared narrated skip and the estimator resolves it, so every advance is attached to a step boundary before verification. Steps are then verified **in order, each at its own start time** — the beat start plus every advance attached to an earlier boundary. Each advance is validated before the steps after it are verified: initiator (player input or author directive that states or invites the skip, consumer API, or the model on its own) → for model-initiated skips only, established activity and `max_unprompted_skip` → due-event / possibly-due check (a range query over `scheduled` rows between the step's current and target time for present characters and the scene). A stop cuts the beat at that boundary and regenerates it under the cutoff before anything is committed (FR-CLOCK-16). Claims, exposures, and belief acquisitions in a step are verified and stamped at the step's start; durative propositions span to the next step's start. After the last step, the beat's end is its start plus its in-beat advances, or plus the pacing increment (over `say`+`do` word count) if it had none; the pacing increment goes through the **same** due-event / possibly-due check as any skip, and a stop inside it clamps the beat's end at the event time (no regeneration — pacing carries no narrated content); in a simultaneous turn, the check runs after reconciliation across all beats (including scheduled events created by any beat in the turn): the earliest stop is the turn's cutoff, pacing-only overruns are clamped, and beats with narrated steps, exposures, acquisitions, or effects past the cutoff are regenerated under it before commit. `possibly_due` is evaluated over the anchor range `[lo, hi)`: it starts when `hi` passes the event time and becomes `due` when `lo` reaches it. The turn's end — the last beat's end in sequential mode, the latest beat end in simultaneous mode — is the clock value committed for the turn.
- **Verification:** clock checks are deterministic propositions — current time, time-of-day band, elapsed since a referenced point, and scheduled-event status — evaluated inside `verify` against the clock value at the claim's position, with the configured tolerances.
- **Working memory (FR-MEM-11):** each character render's recent-scene block is rebuilt from history through the exposure records (content / envelope / nothing); consumer-supplied recent messages feed only orchestration-level coreference and are never placed in a character prompt.
- **Context assembly:** director passes and verification see the objective clock and all canon `scheduled` events. A character's render context gets only that character's **time belief** (derived from the story's `time_awareness ∈ {exact, approximate, none}` plus any override beliefs — a stopped watch, being told a wrong time, a span unconscious), the elapsed time they perceived, and the scheduled events they hold, with time remaining as they believe it.
- **Speaker-aware checks:** narration and director claims about time check against the clock; character `say`/`think`/`do` time claims run through the normal objective/belief/intent classification against the character's time belief, so sincere errors and lies are classified rather than blindly contradicted.
- **Scheduled events:** `scheduled_events (story_id, proposition_id, planned_time, status ∈ {pending, possibly_due, due, surfaced, completed, missed, cancelled}, owner, refinement_pause_anchor_rev, stopped_clock_at, grace)`; status transitions are events positioned at the causing turn. Only `pending` canon events stop an advance factually, once each; a `possibly_due` event pauses an advance at most once per anchor revision to prompt time establishment, never counts as the factual stop, and resolves to `pending`, `due`, or overdue/`missed` when the anchor is refined or the latest admissible due time passes; schedule statements are classified as create / change (owner only) / report, and reports never write the event; belief-only schedules live in the holder's partition and never stop the clock. When a stop shortens an advance, the beat is regenerated under the cutoff before anything is committed.
- **External mode:** the clock is an externally owned value: read and pinned per turn, and computed advances are returned to the consumer as proposed state effects instead of committed.

## 8. Multi-character composition (Orchestrator)

When a request names multiple characters, the Orchestrator renders each **against their own viewpoint** (no cross-contamination of private `think`), **verifies each against their own beliefs and the relevant external authorities**, and **reconciles** their `latent`/commitment effects against one shared timeline before composing a single returned message. Concurrent commitments that imply different truths about the same moment (the contradictory-concurrent-commitment case) are resolved here, under the authority hierarchy and the commitment rules.

- **Settings:** per story `interaction_mode ∈ {sequential, simultaneous}` (default `sequential`), `sequence_order ∈ {request, director}` (default `request`), `simultaneous_tiebreak ∈ {request_order, state:<name>, director}` (default `request_order`), `reactive_interjections` (default off); per character a `participation_role ∈ {primary, reactive, silent}` with `role_mode ∈ {default, fixed}` (default `default`; a fixed role is never changed by escalation or budget planning, only by a request that names the character or overrides its role); all overridable per request.
- **Sequential flow:** render primary character 1 → verify → stage beat 1 → render character 2 with beat 1's perceived output in context → verify → stage → … A failed beat is repaired or regenerated alone. Staged beats are not visible to anything outside the turn until the turn commit (for a staged turn with external effects, until the commit of the stage they belong to, FR-EXT-19), but a **verified** staged beat is a valid antecedent for later beats in the same turn (FR-EPI-14): Jenni can believe and act on what Bobby said one beat earlier. A regenerated beat replaces its staged version, and later beats render only against the verified version. If the turn is abandoned, beliefs formed from staged beats are discarded with it. Records carry a `(turn, beat, step)` position; exposure records store all three, and lazy resolution reconstructs to that exact point (FR-STORE-31, FR-BELIEF-5,6). Within a single render, a belief change is declared as ordered steps (observe → believe → act) verified in order (FR-TURN-12).
- **Simultaneous flow:** render all primaries against the same base (in parallel) → deterministic conflict detection over declared `do` targets and state effects on shared objects/States → tie-break → repair losing actions as in-character attempts → verify → commit.
- **Reactive narration:** recorded as the reactor's `do` with `narrated_by = <render>`; never writes the reactor's `think`/`latent`/beliefs; passes perception and could-have-known checks for the reactor; non-verbal unless interjections are enabled. Novelty checks (FR-VERIFY-11) treat a `narrated_by` reaction as permitted narration of another character, not as an unpermitted action by them. A reaction needing speech, a decision, a hidden fact, or a State change escalates the character to a primary render within the turn budget. If the character's role is fixed, or the budget cannot fit another primary render plus its safety reservation, the reaction is trimmed to reactive bounds instead (verification repairs any render that narrates speech, a decision, a hidden fact, or a State change for them), undetermined values stay open, and the response lists the character in `escalation_deferred` with `reason ∈ {fixed_role, budget}`.
- **Output viewpoint (FR-RESP-12):** every response, history read, and idempotent replay is produced for `output_viewpoint` (`character:<id>` — default the request's actor character, then the story's character default — or `omniscient`, only when named explicitly). Private reads (partitions, beliefs, divergences, hidden States, audit records, the as-originally-recorded view) are omniscient reads, and a stored result is returned only for the viewpoint it was produced for. For a character viewpoint, `think`/`latent` are never emitted at any perception level. With perception `none` (Lite, or shared character knowledge), every other beat is returned whole. At `co_location` or `full`, the audience filter (FR-RESP-13) reuses the perception routing that writes exposure records: per beat, `content` if the viewpoint character's exposure covers content, `envelope` if only the envelope (at `full` only), omitted if neither. Composition (FR-RESP-8) runs on the filtered beats, so the narrative and beat list cannot disagree.
- **Output:** one turn operation with beats ordered by `beat_index`; the response returns the ordered beats (character, channel, content) plus the composed narrative.
- **Composition check (FR-RESP-8):** the polish pass may only order and join verified beats and add connective prose. Its output passes through the full claim-detection pipeline (not only structural tracing) and is checked: every claim traces to a verified beat, attribution matches, and — for a character output viewpoint — no turn-local `think` content appears (matched against every character's private records for the turn). For an explicitly requested `omniscient` viewpoint the thought check is replaced by an attribution check: `think` content may appear only labeled and attributed to its thinker. On failure the response is a deterministic assembly of the verified beats. Stored results (idempotent replays, caches) are returned only for the viewpoint they were produced for, and history reads are computed for the requested viewpoint (FR-RESP-12); there is no per-caller role check (FR-AUTH-1). The structured pipeline (#152, `orchestrator.compose`) composes once the beats are verified and repaired, before an ordinary turn's single commit, so a failed composition leaves the beats exactly as they would otherwise be; it stores one composed message per turn, for the turn's viewpoint, and a history read for any other viewpoint gets the deterministic assembly of the beats that viewpoint receives.

## 9. API surfaces

The same core logic is exposed two ways:
1. **REST (primary).** FastAPI + OpenAPI. `respond` (request → finished message, with detected claims checked under the story's engine profile), `ingest` (record events without generating — a recorded turn takes the next turn index, an outcome or State change the next inter-turn slot; client event IDs deduplicate), plus lower-level operations (`ingest_turn`, `commit_fact`, `record_utterance`, `retrieve`, `verify`, `fact_neighborhood`, `mutate`, `apply_directive`), admin (story/character lifecycle; story export and import — `POST /admin/stories/{id}/export`, `GET /admin/stories/exports/{job_id}` and `…/bundle`, `POST /admin/stories/import`, `GET /admin/stories/imports/{job_id}` (§4.6); delete, rebuild, rewind/branch), author beliefs (`POST /admin/stories/{id}/beliefs`, #160), story inspection (`GET /stories/{id}/inspect/beliefs?character=`, `…/divergences`, `…/ledger`, `…/external-facts` — omniscient reads only, FR-ADMIN-5), external-provider registration, **model-config** endpoints (runtime read/update of per-purpose config), and per-story settings including `turn_concurrency`. Every mutating endpoint accepts an `Idempotency-Key` header and an optional expected revision, returns the new timeline revision, and signals busy/conflict outcomes with distinct status codes (e.g., `409` conflict, `429`/`423` busy).
2. **Embeddable library (in-process).** Direct calls for the transactional hot path; the REST server wraps this.

**Trust boundary (FR-AUTH-1, FR-AUTH-2, FR-AUTH-4).** The REST surface states this in its OpenAPI description, and the README repeats it word for word:

Epistrel runs behind the consumer and must never be exposed to end users. It authenticates only the calling service, which sends one of the deployment's service credentials as `Authorization: Bearer <credential>`, and it holds no user roles, grants, or permissions: which end user may call which operation, act as which character, or request which output viewpoint is the consumer's decision, made before it calls. Its privacy guarantee is relative to the request: output is produced for the output viewpoint the request names, and Epistrel does not verify that the consumer was entitled to request that viewpoint, so Epistrel by itself does not stop a player from reaching another character's secrets. Every mutating call carries an opaque requesting principal in `X-Epistrel-Principal`, which Epistrel records for attribution and never interprets; use opaque IDs rather than names or email addresses, so recorded attribution identifies no one without your own records. Ownership and relations are labels the consumer defines; the engine never grants or withholds an action because of them. Ownership exists for listing, attribution and offboarding only.

Every route requires a service credential except `GET /health`, `GET /metrics`, `GET /openapi.json`, `GET /docs`, and `GET /redoc` (project invariant 4, ADR-149), and `GET /media/{id}/content` when the request carries a valid, unexpired signed URL from `GET /media/{id}/url` (ADR-152; an expired one is `403 url_expired`, a forged one `403 signature_invalid`); a call without a valid credential is answered `401 unauthenticated` before any work. Every `POST`/`PUT`/`PATCH`/`DELETE` carries `X-Epistrel-Principal` (1–256 characters, opaque; `system` is reserved for background work) or is answered `400 principal_required` before any work. Errors use one envelope, `{"error": {"code", "message", "details"}}`; a `422 validation_error` names the first failing input in `details.field` (`body.<path>`, `query.<name>`, `path.<name>` or `headers.<name>`; `body` when the document as a whole is malformed) and lists every failure in `details.errors`. Request bodies are validated in strict JSON mode against the published types (no coercion of `"5"` to `5`), unknown fields are refused, and text may not contain NUL. The OpenAPI 3.1 document the server serves at `/openapi.json` is committed as `docs/openapi.json` (`python -m epistrel.tools.openapi --write`; CI runs `--check`), and every route's `operationId` is the name of the `Engine` method it serves, so the in-process library and REST share one contract (FR-API-1,3,4; #73). The library refuses NUL alike: in every mutation's input, in every read's arguments, and in the ids the erasure and catalog gates look up (`string_nul` at the argument; #278). A model's answer is not refused for one: the Model Access Layer removes NUL from every completion, and from a structured answer's decoded strings, before anything stores it (#275).

There is **no MCP server** (FR-API-2, ADR-092): a consumer that wants MCP access for its users builds one over REST with its own authorization. Epistrel still calls MCP tools as an external-data **client**. **Operator endpoints** — model and provider config, global policies, erasure, retention, story export and import, the low-level mutation calls, and principal offboarding — live under `/admin` so a deployment can restrict them at its proxy (FR-AUTH-1).

**Catalog and story-creation endpoints (FR-API-6):** `/catalog/characters` and `/catalog/scenarios` (create draft, list/search, get by version, update draft, publish — a character's with a new version of its companion, or `?with_companion=true` with the companion's draft as one pair — archive, delete, versions; scenarios also `validate`; and `GET /catalog/characters/{id}/companion`), `/media` (upload, metadata, content, delete), `/personas` (create, list by owner, get, update, delete), `GET /operations/{id}` (status and stages, FR-EXT-16), `POST /stories` (from a scenario with slot and player assignments and overrides, or blank), `POST /stories/{id}/characters` (an ad-hoc character added to a running story, FR-CAT-7), and `POST /stories/{id}/characters/{cid}/promote` (a new draft catalog entry, optionally with selected memories seeded into its companion scenario, FR-CAT-8). `GET /personas` lists every owner's personas newest first, narrowed by `owner` and `relation` only when asked, in keyset pages; `PATCH /personas/{id}` is a merge patch, last write wins. **Profiles (FR-PROF):** `/engine-profiles` (create, list, get by version, update → new version, copy, validate, delete) and, per story, `PUT /stories/{id}/engine-profile`, `PATCH /stories/{id}/profile-overrides`, `GET /stories/{id}/effective-config`, `POST /stories/{id}/impact-preview`, `POST|GET|DELETE /stories/{id}/backfill`, and `POST /stories/{id}/backfill/conflicts/{cid}`; profile-affecting mutations accept `ignore_warnings` and, for upgrades, `upgrade_mode`. Catalog reads take `?projection=card|full` (default `card`, FR-SCN-10). `GET /catalog/characters` and `GET /catalog/scenarios` list cards (each the single read's card plus `owner_principal` and `updated_at`), newest first: the published entries, or with `status` the drafts or archived ones; a scenario list shows companions only with `include_companions=true`. They search with `q` (`websearch_to_tsquery` over a generated `tsvector` of each entry's latest published public card, `simple` configuration; best match first, each card with its `rank`) and filter by `label` (all must hold), `content_rating`, `listing_status`, `owner`, and `relation`, each only when the request names it. Pages are keyset pages on `(updated_at, id)` (rank first for `q`), `limit` 1–200, with an opaque `next_cursor` bound to the filters (`422 cursor_invalid` otherwise). `PUT /catalog/{type}/{id}/listing-status` sets the listing status (FR-CAT-11) to one of the deployment's `listing_status_values`. A publish validates the draft (FR-SCN-5), and `POST /catalog/scenarios/{id}/validate` runs the same validation as a dry run that writes nothing (`{draft_revision?}`, or `?version=n`; `200 {valid, report}`). Publish, validate and story creation answer one report, `{errors, warnings, unavailable}`, each entry `{code, location {entry, version, role, field, seed_id}, text, outcome, source, rule}`; an error refuses the publish (`422 publish_invalid` with `details.report`), and a scenario version keeps the report its publish produced. The checks are an ordered list of modules, each declaring the capability it needs; one the deployment lacks is listed in `unavailable`. Input policies (deterministic always; model-assisted within the deployment's `validation_model_calls`) run before the publish locks the entry, so no lock is held across a model call. **Ratings (FR-RATE):** `/admin/content-ratings` (create, list, get with effective guardrails and their sources, update → new version, retire); `PUT /stories/{id}/content-rating` (relaxing applies at once; tightening starts a check job) and `GET /stories/{id}/content-rating/checks/{job_id}`; `POST /catalog/{type}/{id}/rating-suggestion`. **Images (FR-IMG):** `POST /catalog/{type}/{id}/images/generate` (candidates), `GET /catalog/{type}/{id}/images/candidates` (by job), `GET /catalog/{type}/{id}/images/candidates/{cid}/content` or `/url` (preview), `POST /catalog/{type}/{id}/images/candidates/{cid}/attach`, `POST /image-prompts` (build only), `POST /stories/{id}/images` (generate at a position and viewpoint, or upload), `DELETE /stories/{id}/images/{image_id}`, `GET /image-jobs/{job_id}`. **Media delivery (FR-MEDIA-3):** `GET /media/{id}/content` honors `Range`; `GET /media/{id}/url` returns a signed URL on S3; `POST /media/uploads` opens a resumable upload. **Feedback (FR-FB):** `PUT|GET|DELETE /stories/{id}/messages/{message_id}/feedback` (`message_id` is the message's `message_rendered` event id; rate `{rating, tags?, text?}`: `201` for the principal's first rating, `200` when it replaces or repeats one; read the requesting principal's own rating with its history, which needs `X-Epistrel-Principal`; retract: `204`, also when there is none; the writes take no `Idempotency-Key`), `GET /feedback/aggregates`, `GET /feedback/review/{guardrail|memory}`, and `POST /admin/feedback/export`. Input that fails an input policy returns `422 guardrail_violation` with the policy IDs, names, and messages. **Ownership (FR-AUTH-5..7):** `PUT /{type}/{id}/owner`, `POST|GET /{type}/{id}/relations`, and `DELETE /{type}/{id}/relations/{relation}/{principal}` for stories, catalog entries, personas, media, and engine profiles (list reads filter by `owner` and `relation=name:principal`, or `name:` for any principal); `GET /principals/{id}` (owned and related entities by type, each `{count, items, next_cursor}`, one `limit` and a cursor per page, `cursor[<type>]` or `cursor[related.<type>]`; an unknown principal answers empty pages); `POST /admin/offboarding` (`{principal, actions, transfer_to?, dry_run?, ignore_warnings?}`: a dry run, or a plan with warnings and no `ignore_warnings`, answers `200 {applied: false, counts, warnings}`; otherwise `202 {job_id, counts, warnings}` with `Location`; 422 `principal_reserved`, `transfer_target_required` or `transfer_target_invalid`, 409 `offboarding_in_progress`) and `GET /admin/offboarding/{job_id}` (status, progress, the entity in hand, the request, and once it ends the report). ## 10. Background processing (Orchestrator workers)

Off-hot-path jobs run in the same image in worker mode: **consolidation/reflection**, **importance scoring**, the shadow sample of gated extraction (FR-VERIFY-13), **re-embed** on embedding-model change, and **projection rebuild** on demand. No external broker or scheduler is required.

**Wake-up and recovery (NFR-REL-5).** Jobs and timers are rows; `LISTEN/NOTIFY` only shortens latency. Each worker claims due rows with `FOR UPDATE SKIP LOCKED` when notified **and** every `worker_poll_interval` (default 5 s), so a missed notification costs at most one interval. Every claim sets `lease_until`, renewed by heartbeat; when a lease lapses, the reaper fences the job (advancing its attempt token, §4.13) before another worker reclaims it. On start-up each worker runs a **recovery pass**: reclaim jobs with expired leases, recover `image_reservations` rows left in `sending` (FR-IMG-11), and run every overdue timer.

**Timers.** One-shot due times live in `timers (kind, target, due_at, lease_until, attempts)` — attempt horizons, `confirm_wait_max`, lease expiries, outbox claim expiries, and State reservation expiries (FR-STATE-14). Sweeps live in `recurring_tasks (name, interval, next_run_at, last_run_at, last_status)`: the staging sweep (every 10 min), candidate expiry (hourly), the media sweep (daily), idempotency-result purge (hourly), outbox recovery (every minute), retention and automatic compaction runs (daily), the image counter reconciler (daily at 03:00 deployment time), the accounting-retention purge of closed counter periods, reservation records, and cost rows past `accounting_retention` (90 days; daily), and certification canaries when a deployment schedules them (FR-PROF-17). A worker claims a due row with `SKIP LOCKED` and advances `next_run_at` in the same transaction that records completion, so with several workers each run happens once; every task is idempotent, so a run repeated after a crash changes nothing. Work that came due while no worker ran is done at the next start-up — late, never skipped — and a recurring task that missed several runs runs once. No external scheduler (cron, APScheduler, arq) is used.

**Process modes and health.** The image runs in `all` mode by default — the API plus `worker_concurrency` (default 2) worker loops in one container — so `docker compose up` (NFR-OPS-1) owns every lifecycle job; larger deployments run `api` and `worker` modes separately. `GET /health` reports worker heartbeats and the oldest overdue job and timer, and returns `degraded` when no worker has sent a heartbeat within `worker_heartbeat_timeout` (60 s) or any timer is more than `timer_lag_alert` (5 min) overdue, so an `api`-only deployment with no workers is visibly degraded.

**Consolidation scope and replay (FR-MEM-9, FR-MEM-10).** A consolidation job's inputs must share one viewpoint scope; its outputs take the intersection of input scopes and keep their inputs' epistemic type (speech acts stay attributed claims, beliefs stay the holder's; objective statements only from objective canon). Objective reflections read only public records. Each output stores `model`, `model_version`, and `prompt_hash`; reconstruction and fork copies reuse stored outputs, and a rerun is a new operation, triggered only by changed inputs or an explicit request.

**Consolidation as built (#143).** A job consolidates one window (whole turns) of one scope at one level. Its output is committed by a `consolidation` operation positioned at the window's last turn, whose `source_window` holds the window, the scope, the level, the replay key (a digest of the inputs' content and positions, the same in a fork) and every input's version; that operation is also the coverage record, so its outputs follow the turn's membership on truncation, swap and fork. Automatic windows start after the last consolidated turn and fire on `memory.consolidation.window_memories` (50) uncovered memories or `cadence_turns` (20) turns, whichever comes first; a membership change consolidates whatever it left uncovered, and every fifth window is folded into level-2 reflections. The engine recomputes each statement's modality and speaker from the records it cites, so a quoted claim can never become an objective fact. It drops a statement worded as a guess its records do not make, such as "suggests that", "may have", "seems" or "appears to" (English only in M4; #462). Such a guess has no input's epistemic type, and the operation's result counts it as `speculative`. A reactivated original window wins over an overlapping rerun, which is superseded. Outputs are `memories` rows (`level`, `modality`, `inputs_hash`, `model`, `model_version`, `prompt_hash`, and `covered_by` on their inputs), redacted by erasure like every memory.

**Mutation primitives and implication as built (#145; FR-GUARD-4,5).** `core.mutation` provides `quarantine`, `sanitize` and author canonization. Each is a position-less `control` operation that bumps the revision, served under `/admin/stories/{id}` (`…/memories/{mid}/quarantine`, `…/sanitize`, `…/facts`, `…/facts/{fid}/supersede`, `…/facts/{fid}/lock`) and as `Engine` methods.

- **Quarantine** sets `memories.quarantined_at`, `quarantine_reason` and `quarantined_by`. A quarantined memory is no candidate of any retrieval stage or consolidation window. It still counts toward working memory, history and the hot-set budgets, and it keeps its vector. History keeps the beat it came from, and an omniscient history read marks that item `quarantined: true`; a character viewpoint never sees the flag (#497).
- **Sanitize** rewrites the memory's text under `epistrel.sanitize`. It records a `sanitized` narrative-state event and a `sanitize_original` audit event, which keeps the old text. The new text passes the resurrection guard and is re-indexed and re-embedded.
- **An author fact** is #133's `commit_fact` with `provenance = authority = author`. #140's check runs first: a conflicting functional fact is superseded and an `uncertain` verdict is a warning. The fact also writes an author memory. Canon is append-only, so a lock or unlock is a supersede of the same proposition with `author_locked` flipped, which moves #144's `author_locks` dependency.
- **Implication (FR-GUARD-5).** A draft carries the records its retrieved context held. On every rejected render, the output gate's `implicate` hook (`orchestrator.policies.implication`) does three things. It records them on the `guardrail_output_rejected` event (`implicated_record_ids`, payload version 2, left out when empty). It raises `memories.implication_count` in a `system` control operation (no revision bump). It quarantines a memory once the count reaches the profile dial `repair.implication_threshold` (default 2; author pins included, reported as `pin_quarantined`). Facts are only reported. The regeneration retrieves again, and the response reports `degradation: ["quarantined_context"]`. Lite drafts carry no records, so a Lite turn never implicates.

## 11. Configuration, secrets, observability, security

- **Config:** environment + typed settings (Pydantic Settings). Model routing and external-provider registrations are config-driven and runtime-updatable via the config API.
- **Secrets:** model API keys live in Epistrel config (env/secret files), never in story data. For self-hosted OSS the adopter supplies keys to their own deployment.
- **Observability:** structured JSON logs, Prometheus metrics, OpenTelemetry traces. First-class **eval hooks** emit raw render, verdicts, repair rung, model-call counts, and latencies for the test/eval harness (*04*).
  - **Logs** are one JSON object per line on stdout (`epistrel.observability.logging`): every `Engine` call, job, queued turn and REST request writes one summary line with `operation_id`, `story_id`, `principal`, `kind`, `duration_ms` and `outcome` (`ok`, `rejected` for a 4xx, `error`), plus the current `trace_id`/`span_id`. A `ContentFilter` drops every field named `text`, `say`, `do`, `message`, `prompt`, `definition`, `pinned`, `instructions`, `summary` or ending in `_text`, at any depth, and cuts any other unvetted string to 64 characters; exceptions are logged as their type and error code (frames without locals for unexpected ones), never their message. uvicorn's access log is off; `sqlalchemy.engine`, `httpx`, `httpcore` and `openai` are capped at WARNING.
  - **Metrics** are served at `GET /metrics` (Prometheus text, unauthenticated per invariant 4, served by `worker` processes too): request latency per route name, method and status; operation counts per kind and outcome; the model-call and guardrail counters; and job, timer and worker gauges computed at scrape. Label values are enums, ULIDs, route names, HTTP statuses or sanitised model names, never content.
  - **Traces** are exported over OTLP/HTTP only when `EPISTREL_OTLP_ENDPOINT` is set (off by default; `OTEL_EXPORTER_OTLP_*` honoured): a server span per request (an incoming `traceparent` is continued), a span per `Engine` call and job, and child spans per model call and commit, carrying the same identifiers. A span processor drops content attributes, exception events and status descriptions before export.
  - **Content debug logging** (`EPISTREL_CONTENT_DEBUG_LOGGING=1`) is the only way story content reaches a log: it is refused unless `EPISTREL_DEBUG` is on (start-up exits 78), logs a WARNING at start-up, marks every line `content_logging: true`, shows as `content_logging: true` on `GET /health`, and switches itself off after 24 hours. **Retention: logs written with it on are operator-only and kept at most 7 days**, and they are subject to erasure like any other copy of story content (NFR-SEC-4). The invariant-3 guard (`tests/conformance/test_c_08.py`, C-08) scans the telemetry of the scenario suite and every operation for planted and harvested content (#74).
- **Security:** provenance/trust tiers on every memory and external result; immutable policy store (no mutation path from in-world content); viewpoint isolation enforced at retrieval; strict input validation at the Pydantic boundary; external-provider tool content (MCP tools included) untrusted. Operational logs, metrics, and traces carry identifiers and counts only — no story prose, thoughts, or memories — unless operator-only content debug logging is enabled with bounded retention (NFR-SEC-4).
- **Trust boundary (FR-AUTH):** Epistrel authenticates only the calling service — one or more equivalent service credentials checked by REST middleware; none for the in-process library — and holds no user roles, grants, groups, or permissions. The consumer decides who may call what, act as which character, see which catalog entries, and request which viewpoint. Each mutating call carries an opaque `principal`, recorded on the operation and its events and never consulted by any decision. What stays enforced is engine semantics: the output-viewpoint rules (fail closed; `omniscient` only when named; private reads are omniscient reads; stored results bound to their viewpoint), which render characters a scene may trigger, and `player_authority`. Operator endpoints sit under `/admin`. The documentation states that Epistrel runs behind the consumer, never exposed to end users, and phrases privacy per viewpoint rather than per user.
- **Erasure (FR-ADMIN-6..9):** a `subject_references (scope, story_id?, subject_kind, subject_id, record_table, record_id, field?, ref_kind)` index is written alongside every record and derived text — `scope = story`, or `scope = catalog` for catalog versions and drafts, scenario seeds, personas, and media assets not anchored in a story (FR-ADMIN-6); story images are indexed with `scope = story`. A subject is a story character, a catalog character (linking every story character sourced from it) or a persona (linking the player characters made from it); prose is scanned for its names and aliases as whole words, case-insensitively. Every writer indexes its record in its own transaction through `core.erasure.index`, whose registry `SUBJECT_WRITERS` lists the indexed tables (a test checks it against the schema), and `python -m epistrel.tools.reindex_subjects` recomputes the index from the records and reports the differences (#123). An erasure request names its subject and scope (FR-ADMIN-2); a catalog-scope erasure redacts or deletes the subject's catalog fields, seeds, and images, and the media sweep then purges the bytes. Erasure is one of the exceptions to event immutability (with opt-in compaction, §4.6, FR-STORE-32, and audit-record expiry): it deletes structured rows, redacts or regenerates referencing prose, rebuilds projections, purges stored idempotency results, redacts outbox rows (a claimed or `unknown` row's reconciliation listing is kept as its row ID, provider, and status, FR-EXT-21), and appends to an `erasure_ledger` (identifiers and scope only). The ledger lives outside the backed-up story data (its own table/volume, replicated with the deployment config) and is also copied into every backup; a restored story stays unserved until the ledger is reapplied. Replay, projection rebuilds, forks, and determinism are defined over the post-erasure log; backup verification and audit tooling treat erasure markers (identifiers and scope only) as expected gaps. Erasure runs as a control action: it bumps `timeline_revision`, so in-flight turns, rewrites, consolidation jobs, and outbox dispatches fail their revision check and abandon; every write path additionally checks the ledger and refuses content referencing an erased subject, so a late worker result cannot resurrect it. Delivered exports and provider-held data are documented as out of scope.
  In M3 (#124) the request is `POST /admin/erasure {subject: {kind, id}, scope: {story: <id>} | {catalog: true}, dry_run?}` (a story `character` scoped to the catalog is `invalid_erasure_scope`); `dry_run` reports the counts and writes nothing. A story-scope erasure is one `control` operation (it runs on archived and paused stories too) that deletes the subject's character rows, snapshots and own deferred items, each leaving a position-less `erasure_marker` event, redacts every matched span to `[erased]` in place (`events.redacted_at`, under `SET LOCAL epistrel.erasure = on`, which the events and catalog-version triggers honour), purges stored results, refolds the projections and re-indexes the story. It then regenerates the redacted rolling-summary segments through the `SummaryCompressor` port; the new text replaces the redacted text in the segment's own event, so coverage and the fold are unchanged, and without a model the redaction stands. A `maintenance` rebuild follows, and a residue scan reports what still names the subject. A catalog-scope erasure never touches stories: it lists those that reference the subject. Media depicting only the subject that another record still references follow `erasure_shared_media` (`purge` or `retire`). The ledger's authority is a file outside the database (#125: `EPISTREL_ERASURE_LEDGER_DIR/ledger.jsonl`, one hash-chained line per erasure, appended and fsynced before the erasure commits); the `erasure_ledger` table (identifiers, counts, and the scanned terms' keyed hashes) is its copy inside every backup, and the reconciler restores either side from the other (§12, ADR-153). The boundary of what an erasure reaches is `GET /admin/erasure/boundary` and [OPERATIONS.md](OPERATIONS.md).
  The resurrection guard (#127, `core.erasure.guard`) is the ledger check of every write path. `Operation._write` runs it on every event an operation commits (turns, ingest batches, job results), after the revision decision and the commit steps: it hashes each text's word spans with the ledger's key and refuses a match, or a structured reference to a deleted character, with 409 `erased_subject_referenced`, and the operation ends `abandoned`. Engine, worker and model text is always checked; text a consumer wrote (`player` or `consumer` provenance) only when its operation's base revision predates the erasure. A revalidating turn regenerates within `regenerate_retry_budget` first. The erasure itself fails queued turns with `timeline_changed`, clears the turn slot's lease, and moves the `membership_tx` of the operations whose events it redacted, so an in-flight summary job drops its output at commit and is requeued. A fork copies the story's ledger rows (`copied_from`) and is retried when an erasure of the source commits after its snapshot. The catalog and media writers refuse a new structured reference to a catalog-scope erased subject. `CONTENT_WRITE_PATHS` lists every write path and how it is covered.
- **Retention (FR-STORE-30):** discarded and dormant continuations kept until story deletion (compaction opt-in); audit records kept 90 days by default (feedback by its own setting, FR-FB-2), their expiry the third exception to immutability (FR-STORE-1); vectors only for active **hot** records (FR-MEM-8), re-embedded on reactivation or rehydration (not byte-identical to the originals; the profile dial `memory.hot_set.retain_dormant_vectors` keeps them for exact reproducibility, §4.2).

## 12. Deployment

- **Reference host (NFR-PERF-4):** the concurrency gate runs on 4 vCPU, 16 GB RAM, and NVMe SSD with Postgres and the workers co-located. Its workload is open-loop — 10 stories submitting on a fixed schedule with `turn_concurrency = queue` for 30 minutes against a stub model at a fixed 2 s per call — in three variants added as capabilities arrive: Lite (20,000-event transcripts, 50 pins, a turn every 15 s), structured (10,000 memories, single-character turns every 60 s), and multi-character (two-character turns with per-character renders every 60 s). Each gates on the engine-only p95 budgets that apply to it and, per story rather than in aggregate, on completing every turn submitted at least 2 minutes before the end, at most one turn waiting after the first 5 minutes, a queue wait no longer than one schedule interval, and queue-front-to-first-model-call p95 ≤ 1 s. Model time is excluded; other hosts are reported, not gated.
- **Running the reference workload (P-04):** `uv sync --group perf`, then `uv run python -m perf.lite_smoke --minutes 30 --host-class <class>` runs the Lite variant in one command: it starts its own compose project (`epistrel-perf`, `perf/lite_smoke/compose.perf.yml`: the stub adapter with `EPISTREL_STUB_LATENCY_S=2`, ports 8100 and 5442), seeds the ten stories through the library (or restores the cached `pg_dump` of that seed from `build/perf/cache/`), drives `respond` open-loop with Locust, samples database connections, CPU, memory and per-story queue depth every 5 s, reconciles every turn against `history`, and writes `perf/results/<date>-<time>-lite.md` with a JSON sidecar: per-story and aggregate figures and PASS/FAIL per criterion. The host class is stated by the operator: `reference` (the host above; the gate is enforced and a FAIL exits 1), `mac` (a developer machine) or `ci` (a CI runner), both reported, not gated. A run shorter than 30 minutes is a demo and writes to `build/perf/` instead. Full runs are committed; `test_p_04` fails once the newest is older than 30 days. **The structured variant (M4, #153):** `uv run python -m perf.lite_smoke --scenario structured --minutes 30 --host-class <class>` seeds ten structured stories of 10,000 memories and 20,000 events with the scale fixture's builder (cached as `build/perf/cache/structured-<key>.dump`), layers `perf/lite_smoke/compose.structured.yml` over the stack (the stub embedding at 768 dimensions, and `EPISTREL_STUB_RENDER_CLAIMS` so 10% of the stub's renders contradict planted canon and 10% make a novel claim), plays one single-character turn per story every 60 s, and adds NFR-PERF-1's retrieval and NFR-PERF-2's verify p95 budgets to the gate, read from the `retrieve` and `verify` stages of `epistrel_turn_stage_seconds`; it writes `perf/results/<date>-<time>-structured.md`, which `test_p_04__structured` requires to be newer than 30 days. `perf.yml`'s weekly `weekly-structured` job runs it on the GitHub-hosted runner (host class `ci`, reported, not gated) and the weekly docs pull request commits its report. P-03 (turn-commit latency on a 20,000-event story) runs nightly in `perf.yml`.
- **Dev/hobby:** a single `docker-compose.yml` brings up Epistrel (Engine Core + Orchestrator + workers, in the image's default `all` mode, §10), and Postgres (with pgvector). The local model server is not part of the compose file: it runs on the host (e.g. LM Studio) and the Engine reaches it via `host.docker.internal`. Minimum external requirement: one OpenAI-compatible endpoint.
- **Image channels:** `ghcr.io/nathanpond/epistrel:edge` (and `sha-<7>`) is rebuilt from every merge to `main` after the PR gate and is unstable, for Console integration and testing; `X.Y.Z`/`X.Y`/`X`/`latest` are published from `vX.Y.Z` tags, `latest` moving only to the highest stable version (see RELEASING.md).
- **Media:** a `media` volume for the default filesystem blob store, or an S3-compatible endpoint in config (FR-MEDIA-1).
- **Backup/restore (deployment):** `pg_dump` (`epistrel backup dump`) plus the media volume or bucket; the event log itself is a replayable backup (projections rebuild from events). The erasure ledger is kept outside these backups, on its own `erasure-ledger` volume (`EPISTREL_ERASURE_LEDGER_DIR/ledger.jsonl`, append-only and hash-chained), and copied into each of them as the `erasure_ledger` table. At start-up, before traffic, Epistrel compares the two: an erasure a restored database lacks becomes pending and its story `blocked_by_erasure` (503 `erasure_pending` on every read and write) until the reconciler has reapplied it; a pending catalog-scope erasure blocks no story, but every catalog entry, persona, media asset, deployment-scoped stored result and global or rating policy it reaches is refused the same way, and left out of lists (as a configuration change naming the subject is left out of the configuration history; a story's settings list such a policy with a `null` name, and a turn or write that breaks it is 503 `erasure_pending` rather than 422 naming it), until then (ADR-157, ADR-159, ADR-161), at start-up and then every 5 minutes (`erasure_reconcile_retry`). `epistrel backup verify` treats erasure markers as expected gaps (FR-ADMIN-7, ADR-153). The procedure and the erasure boundary are in [OPERATIONS.md](OPERATIONS.md). **Per-story** backup and portability use story bundles (§4.6, FR-STORE-7): restoring a story imports its bundle as a new story.
- **Upgrades:** Alembic migrations + post-migration projection rebuild when schemas change.
- **Scale-out path (not required now):** split cognition/model-access workers to their own container and autoscale; move workers to dedicated nodes; add `halfvec`/quantization (or an operator-installed BM25 backend); add read replicas — none touch Engine Core code.

|---|---|---|---|
| Language | Python 3.14 | Single supported version (ADR-148); ecosystem | — |

| Lexical | tsvector | Hybrid retrieval, zero-dep default; replaceable behind the retrieval interface | Elasticsearch (heavy); ParadeDB pg_search (AGPL, not bundled) |
| DB access | SQLAlchemy Core + psycopg3 | Thin, explicit, async | Full ORM (opaque) |
| Migrations | Alembic | Standard | — |

| Model transport | `openai` SDK → OpenAI-compatible endpoints (ADR-150) | Reaches all models; gateway-friendly; small dependency footprint; per-purpose routing is the Model Access Layer's | LiteLLM (58 packages vs 14; its routing, retries and cost tracking duplicate the Model Access Layer and the turn budget); per-provider SDKs (less portable) |

| Image generation | `ImageGenerator` port; OpenRouter image-API adapter | Many image models behind one interface; optional | Per-provider adapters only |
| Interfaces | REST + in-process library; MCP only as a client of external-data providers | The consumer fronts Epistrel; no end-user surface | An MCP server (ADR-092) |
| Observability | OTel + Prometheus + JSON logs | Standard; eval hooks | — |
