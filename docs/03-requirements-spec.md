# Epistrel — Requirements Specification

**Full-scope specification · Working draft**

This document specifies the complete intended capability of Epistrel (full vision, not a phased MVP). It is built and released in **milestones** (§22): the specification stays whole, and each milestone gates the requirements it delivers. Requirements use stable IDs (`FR-AREA-n`, `NFR-AREA-n`) so the test plan (*04*) can reference them. Priority: **M** (must), **S** (should), **C** (could). *Shall* = mandatory.

**Product boundary.** Epistrel = **Engine Core** (deterministic data layer) + **Orchestrator** (the agent). Requirements below are Epistrel's. The model *processes* and the consumer's game/front-end are out of scope except where Epistrel must provide an interface to them. So are end-user identity and authorization: the consumer decides who may do what, and Epistrel records who the consumer says is acting (FR-AUTH).

---

## 0. Glossary

- **Epistrel** — the memory engine (the product): Engine Core + Orchestrator.
- **Engine Core** — the deterministic, model-free data layer: event store, projections, epistemic model, retrieval/resolution mechanics, deterministic verification, commitment lifecycle, policy store, mutation primitives.
- **Orchestrator** — the agent: the turn loop, all model calls (via the Model Access Layer), verification escalation, grading, regeneration/repair, guardrail enforcement, extensibility, and background consolidation.
- **Model Access Layer** — the Orchestrator's per-purpose model configuration and adapters; Epistrel holds the config and connects directly to external, OpenAI-compatible model servers.
- **Consumer** — the game/front-end; sends the respond request, registers external-data providers, supplies model config, receives the finished message. Holds no memory logic. Authenticates and authorizes its own users; Epistrel trusts it (FR-AUTH).
- **Principal** — an opaque identifier, from the consumer's identity system, for the person or service a call is made on behalf of. Epistrel records principals for attribution and ownership and never authorizes against them (FR-AUTH).
- **Author** — whoever the consumer lets issue author operations (directives, rewrites, story configuration). Epistrel attaches authority to those operations, never to a user role (FR-AUTH-3).
- **Story** — a top-level isolated instance (its own characters, canon, memory); identified by StoryID.
- **Character** (≡ actor) — an entity with an epistemic viewpoint; identified by CharacterID. The human player may be modeled as a character where relevant.
- **Fact** — an objective, bitemporal, visibility-scoped truth in story canon (may be a snapshot of external data).
- **Belief** — a per-character proposition, possibly false, possibly about another character (social/nested).
- **Memory** — a retrievable record: episodic, semantic, or reflection.
- **Utterance / speech act** — the record that a character *said* something, stored distinctly from whether it is true.
- **Divergence** — a tracked gap between what was asserted and what the speaker believes (an open deception), recorded whenever communicative intent is deceptive (FR-TURN-7).
- **Speech-act dimensions** — three independent labels on every utterance: **objective relation** (true / false / unresolved), **speaker belief relation** (consistent / inconsistent / unknown), and **communicative intent** (sincere / deceptive / joking / unspecified) (FR-TURN-6).
- **Thunk** — an introduced-but-undetermined reference whose value the engine has not decided. A thunk is **global** (undetermined for everyone, including the narrator), resolves at most once in a continuation, and need never resolve (FR-COMMIT-10, FR-STORE-29).
- **Determined / undetermined** — a property of *world state*, global: has the truth been fixed yet? A determined proposition has exactly one truth value at a given valid-time; for a functional predicate, one object per uniqueness key per time (FR-EPI-8).
- **Known / unknown (to character X)** — a property of a *viewpoint*, per-character: is the fact in X's partition? Many answers, one per character. *Unknown ≠ undetermined:* a determined fact can be unknown to a character (absence), but it is never "undetermined for" that character (that would imply a second, independently resolvable value).
- **External-data provider** — a consumer-registered tool/Skill/MCP that authoritatively answers predicates the game owns outside Epistrel.
- **Viewpoint** — the epistemic scope used to filter retrieval and verification to one character's knowledge.
- **Proposition** — a viewpoint-free claim: subject entity, predicate, object or value, qualifiers, polarity, and valid-time interval. Canon facts, beliefs, and utterances all wrap propositions (FR-PROP-1).
- **Predicate** — a registered relation with declared semantics: argument types, cardinality (functional or multi-valued), temporal kind, exclusions, containment, implications, symmetry, and owner (FR-PROP-3).
- **Entity** — a person, place, item, institution, or other referent with a canonical ID and aliases (FR-PROP-6).
- **Modeled character** — a character with an engine-held viewpoint and memory. Created by direct interaction or explicit salience (not by mere appearance). The human player is a modeled character for others' purposes but has no engine-held interiority (see FR-EPI-12).
- **Narrative position** — the **turn index** (plus variant) of the narrative turn that introduced a record: where on the message timeline it entered. Only narrative turns advance it. The coordinate for checkpoints, truncation, regeneration, fork, and timeline membership. Within a turn it is refined by **beat index** and, within a beat, **step index**; between turns, inter-turn operations occupy **slots** `N⁺k` (FR-STORE-31). A full position is therefore either `(turn, beat, step)` or `N⁺k`, and there are two kinds of checkpoint boundary: `N` (immediately after turn N's reply, the default) and `N⁺k` (after inter-turn slot k). Distinct from `seq`, which is global recording order. (See FR-BITEMP-5, FR-STORE-24.)
- **`seq`** — the global recording order of events within a story; used for ordering and replay only, never for narrative meaning.
- **Operation** — a unit of work that produces events, identified by an operation ID: a narrative turn, an inter-turn operation (a State set, a late settlement, an ingested outcome), genesis, a consolidation job, a rewrite session, a backfill, an import, a control action (truncate, untruncate, fork, swap, config change), or maintenance (re-embed, projection rebuild).
- **Ordinary turn / staged turn** — an ordinary turn commits all its writes atomically. A staged turn (one with a `synchronous` write-capable external effect; a turn whose effects are all asynchronous is ordinary) is a durable workflow of atomic stages — intent, claim, outcome, completion, response — that resumes from its last committed stage (FR-STORE-5, FR-EXT-16..20).
- **World clock** — the built-in, story-owned State holding the current story date and time; the source of story-time, advanced by a deterministic pacing rule and validated time skips (FR-CLOCK).
- **Catalog character** — a reusable, versioned definition of who someone is (true age, appearance, personality, dispositions, likes and dislikes, interaction style, and optional images and visual identity), stored outside stories and never a player's own character; world truths about a character belong to scenarios (FR-CAT).
- **Persona** — the lightweight description a player plays as (name, gender, age, brief personality); not a catalog character (FR-CAT-6).
- **Scenario** — a reusable, versioned starting point for a story: world, character roles, starting state, clock, and story drivers (FR-SCN). Every catalog character has a **companion scenario** with one locked slot for it.
- **Role (slot)** — a character position in a scenario (`npc` or `player`; `open`, `default`, or `locked`), filled at story creation by a catalog character, an ad-hoc character, or (for players) a persona.
- **Genesis** — the atomic operation at narrative position 0 that creates a story from a scenario by snapshotting the chosen catalog versions (FR-SCN-9).
- **Engine profile** — a named, versioned set of capability modules and dials that determines how hard the engine works for a story, from **Lite** (today's roleplay-engine equivalent) to **Max** (FR-PROF, FR-LITE).
- **Content rating** — a deployment-defined record (seeded: Everyone, Teen, Mature, Explicit) carrying a content-policy description, prompt guidance, and guardrails, optionally inherited from other ratings. A story's rating decides how it is steered and what it may contain; it is not access control (FR-RATE).
- **Visual identity** — a character's stored image-generation settings (model, base appearance prompt, negative prompt, seed, reference images) that keep new images of them consistent (FR-CAT-4).
- **Story image** — an image anchored at a narrative position in a story that follows the story's timeline. Its **audience viewpoint** is who may receive it (and, for a generated image, whose perception it is built from); its **camera POV** is only how it is framed (FR-IMG-5).
- **True age** — the objective age every character has from the moment it is created, held by the engine and not disclosed by default; age-conditioned guardrails use it (FR-CAT-12, FR-GUARD-11).
- **Paused story** — a story whose truth-changing operations are refused with `story_paused` while a backfill, a rating check, or a reactivation check runs; reads continue (FR-CONC-5).
- **Backfill** — re-deriving structured data from a story's stored transcript after a profile change adds capability; it never regenerates messages (FR-PROF-9).
- **Event category** — narrative state, input, derived, amendment, audit, or control; decides which views read an event (FR-STORE-25).
- **Turn variant / continuation** — alternatives at the same turn index (from regeneration or an undone rewind). Exactly one variant per position is active, and the active variants form a single chain; inactive chains are *dormant continuations*.
- **Valid-time (story-time)** — when a fact is true in the world. The coordinate for retcons, flashbacks, and "what was true when." Never used for timeline membership.
- **Transaction-time** — when the engine recorded, changed, or discarded a record. The coordinate for audit, undo, and the as-originally-recorded view.
- **Timeline membership** — whether a record is an **active** or **discarded** member of the story's timeline, following the membership of the operation that produced it and stamped with the transaction-time of the change. Truncation discards; un-truncation or a swap reactivates.
- **State** — a typed, single-value tracked variable (gold, health, a flag) scoped to the story or a character, with constraints and visibility. Every tracked value has an **owner**: `story` (held by Epistrel) or `external` (owned by a provider). (See FR-STATE.)
- **State effect** — a declared change to a tracked value produced by a turn, a directive, the consumer API, or a rule.
- **Amendment** — a side-channel history rewrite (FR-REWRITE). Recorded at a transaction-time but occupying **no narrative position**: it revises existing records and may introduce facts with their own valid-time. Distinct from a directed regeneration, which is an ordinary narrative event.

## 1. The respond contract (FR-RESP)

- **FR-RESP-1 (M).** Epistrel shall expose a top-level operation that accepts `{StoryID, requesting principal, actor character (whose input this is, if any), player input, render characters (the CharacterIDs to respond), output viewpoint, prompt parameters, scene context}` and returns a single finished, polished message whose detected claims have been checked to the extent the story's engine profile enables (FR-VERIFY-15, FR-PROF-12) — under `lite`, no structured claim checking is performed. Documentation and API descriptions shall not call the message "verified" beyond that. The requesting principal, actor character, render characters, and output viewpoint are distinct fields with distinct meanings (FR-AUTH-3); the requesting principal is recorded for attribution only (FR-AUTH-4), and Epistrel does not check which characters or viewpoints a principal may use (FR-AUTH-1).
- **FR-RESP-2 (M).** The consumer shall not be required to perform retrieval, verification, grading, regeneration, or any memory logic; all such work shall occur inside Epistrel.
- **FR-RESP-3 (M).** Prompt parameters (at least length, temperature, top_p) shall be honored for the generation purpose for that request.
- **FR-RESP-4 (M).** Scene context (characters present, recent messages) shall be accepted as input and used by orchestration for continuity and coreference without being treated as authoritative canon. Consumer-supplied recent messages shall **never be placed in a character's generation context**; a character's view of the recent scene comes only from the story's own recorded history — viewpoint-filtered working memory with per-character partitions (FR-MEM-11), the shared recent scene without them, and the recorded recent messages under `lite` (FR-LITE-1).
- **FR-RESP-5 (M).** When multiple CharacterIDs are supplied, the response shall compose their individual responses/reactions into one returned message (see FR-MULTI).
- **FR-RESP-6 (M).** The respond request shall accept an optional **idempotency key** and an optional **expected timeline revision**; a request whose expected revision differs from the story's current one is rejected without side effects as a conflict that returns the current revision. The response shall return the story's new timeline revision (FR-CONC).
- **FR-RESP-7 (M).** The response shall return the turn's **state effects**: committed changes to story-owned States (with old/new values, for player-visible States) and requested changes to externally owned values for the consumer to apply (FR-EXT-9), each with its reason.
- **FR-RESP-8 (M).** The final polish/composition step shall be **constrained and verified**. Composition may order and join verified beats and add connective stage prose; it shall not add propositions, change speaker or actor attribution, or — for a **character output viewpoint** — include any character's `think` content (non-disclosure, FR-TURN-3). For an explicitly requested **omniscient** viewpoint (FR-RESP-12), attributed and labeled `think` content from verified beats is permitted; the remaining checks (traceability, attribution) apply unchanged. The composed text shall pass a final check — every proposition traces to a verified beat or is non-propositional connective text, attribution matches the beats, and, for a character viewpoint, no private content from the turn appears. If the check fails, the response shall fall back to a **deterministic assembly** of the verified beats. The check runs against the beats **as filtered for the output viewpoint** (FR-RESP-12,13 — with perception `none`, every beat less `think` and `latent`): every proposition in the composed text shall trace to a beat at the fidelity the viewpoint perceived it, so an envelope-only beat can contribute only its envelope. A composition failure never rolls back committed turn stages or external effects (FR-EXT-17).
- **FR-RESP-9 (M).** The respond request shall carry an explicit **player input** field (speech and/or action). Player input enters history as the first beat of the turn — the actor character's `say`/`do` (FR-AUTH-3) — under the request's idempotency key. Recent messages in scene context remain non-authoritative (FR-RESP-4) and never enter history.
- **FR-RESP-10 (M).** Epistrel shall provide an **ingest** operation that records events into authoritative history without generating a response (e.g., a player-only turn, or consumer-authored narration). Each ingested event shall carry a **client event ID** unique within the story; re-ingesting the same ID shall be deduplicated (returning the original result), and the same ID with a different payload shall be rejected. An ingest that records a turn — a player-only turn, or consumer-authored narration — is a narrative turn: it takes the next turn index, is a turn request under `turn_concurrency` (FR-CONC-5), and increments the timeline revision (FR-CONC-1). An ingested outcome or State change is an inter-turn operation at the next inter-turn slot (FR-STORE-31, FR-EXT-21).
- **FR-RESP-11 (M).** Player authority over other characters shall be configurable per story via `player_authority` ∈ {`own_character`, `co_author`}. Default: `own_character`. Under `own_character`, player input that describes another character's actions, speech, or thoughts ("Jenni hands me the key") is treated as a **request** the world resolves, not as fact. Under `co_author`, the player may narrate other characters' observable actions, which are still checked against those characters' viewpoints where per-character partitions are enabled (FR-EPI-4, FR-TURN-9) and may never write their `think`. Under `lite`, `player_authority` reaches the model only as an instruction in the prompt.
- **FR-RESP-12 (M).** Every respond request, history read, and returned beat list shall be produced for an explicit **output viewpoint** ∈ {`character:<id>`, `omniscient`}. Default: the request's actor character; otherwise the story's `default_output_viewpoint`, which may only be a character; if neither resolves, the request is rejected (fail closed). For a character viewpoint, no character's `think` or `latent` content is returned, under every profile; where perception is enabled, the **audience filter** of FR-RESP-13 also applies. With perception `none` — every `lite` story, and `structured` stories with shared character knowledge — every other beat is returned in full, and the guarantee table states that no audience filtering applies (FR-VERIFY-15). Both rules apply to the composed narrative and to the returned beats. **Omniscient** output (all beats at full content, `think` included and labeled) is returned only when a request names `omniscient` explicitly; it is never a default. **Private reads are omniscient reads:** a character's partition, beliefs, and divergences, hidden States, audit records, and the as-originally-recorded view are returned only to a request that names `omniscient`, and a character-viewpoint read of States returns only player-visible States. **Stored results keep their viewpoint:** an idempotent replay or cached response is returned only for the viewpoint it was produced for — a replay under the same idempotency key naming a different viewpoint is rejected as a key conflict (FR-CONC-6) — and a history read is always computed for the viewpoint it requests. Epistrel does not decide which callers may request which viewpoint; the consumer does (FR-AUTH-1,2).
- **FR-RESP-13 (M).** **Audience filter.** With perception at `co_location` or `full` (FR-PROF-2), every response, history read, and returned beat list for a character viewpoint shall be filtered beat by beat using the same perception routing as memory (FR-TURN-2,9,10): a beat whose content the viewpoint character perceived is returned in full; at `full`, a beat whose envelope only was perceived is returned as its envelope ("Jenni whispers something to Marcus"); a beat the character did not perceive at all is omitted. At `co_location`, a beat is returned in full or omitted, since no envelope is routed apart from its content. The filter applies to both the composed narrative and the returned beats, and is computed from authoritative positions — the player character needs no belief partition (FR-EPI-12).

## 2. Storage & event sourcing (FR-STORE) — Engine Core

- **FR-STORE-1 (M).** Epistrel shall record every state-changing occurrence as an immutable, ordered event scoped to a story, with a monotonic sequence number. **There are three exceptions to immutability: erasure** (FR-ADMIN-2), which deletes or redacts events and derived records about the erased subject and leaves an erasure marker (identifiers and scope only) in their place; **opt-in compaction** (FR-STORE-32), which deletes discarded and dormant records a story has explicitly given up and leaves compaction markers; **and retention expiry** of audit-category records, including feedback, at the end of their retention (FR-STORE-30, FR-FB-2) — these are never story content (FR-STORE-25), so no view of story truth changes. The rules below apply to erasure and compaction. After an erasure, "the event log is the truth" holds for the **post-erasure** log: replay, reconstruction, projection rebuilds, forks, and determinism (NFR-DETERM-1) are defined over that log, and history involving the erased subject cannot be reconstructed as it was.
- **FR-STORE-2 (M).** Each event shall carry a typed payload, provenance, authority level, story-time (valid-time), and record-time (transaction-time).
- **FR-STORE-3 (M).** Epistrel shall maintain materialized projections of current state (beliefs, relationships, placement/inventory, scene state) updated transactionally with their causing events.
- **FR-STORE-4 (M).** Any projection shall be reconstructable by folding the event log, producing a result identical to the incrementally maintained projection.
- **FR-STORE-5 (M).** All writes comprising an **ordinary turn** shall commit atomically or roll back together. The single exception is a **staged turn** — a turn with at least one `synchronous` external effect (FR-EXT-15) — which is a durable workflow of **atomic stages** (FR-EXT-16): each stage commits or rolls back as a unit, and a committed stage is never rolled back by a later stage's failure.
- **FR-STORE-6 (M).** Epistrel shall support point-in-time reconstruction of story state as of any checkpoint — the current corrected history through a narrative position (FR-STORE-11) — (rewind) and branching a story from a prior point (mechanism detailed in *Time travel* below).
- **FR-STORE-7 (M).** **Story export and import.** Epistrel shall export a complete story as a versioned **story bundle** and import a bundle as a **new story**; restoring a story means importing its bundle.
  - **Export** is an operator operation (FR-AUTH-1) and an omniscient read. It snapshots one timeline revision, as a fork does (FR-STORE-6, FR-CONC-10), and writes a single archive containing: a **manifest** — bundle format version, the exporting Epistrel and schema versions, source story ID, exported revision, export time, the story's content rating and engine profile with their versions, and a checksum per file; the story's complete **event log** in recording order — operations, timeline membership, amendments, the story's **audit-category events** still within retention (rejected renders, verification verdicts, repair attempts, rewrite questions and answers, and guardrail records, which hold policy IDs only), compaction and erasure markers (identifiers and scope only), and outbox rows with their outcome records; stored **derived outputs** with their model, version, and prompt hash (FR-MEM-10); the **catalog snapshots** taken at genesis and at every later addition (FR-SCN-9); the story's settings and profile overrides; message feedback with its rating history; and the story's **media** with their metadata (source, check status, depicted subjects). Projections, indexes, and vectors are not exported — they are rebuilt and re-embedded on import (NFR-REL-2). Deployment-level records — limit counters, image reservations and costs, the deployment's own audit logs (such as edits to global and rating policies, and the record of feedback exports), operational logs, idempotency results, provider registrations — are never exported, and neither are in-flight jobs or image candidates. A delivered bundle is outside the erasure boundary (FR-ADMIN-8).
  - **Import** always creates a new story with a new story ID, owned by the principal the request names (FR-AUTH-5). It never overwrites or merges into an existing story, so there are no ID conflicts, and the source story is untouched; the same `Idempotency-Key` returns the same imported story. The bundle is untrusted input. It is parsed against limits on its total uncompressed size, its number of entries, and the size of each entry — deployment settings with documented defaults — and a bundle over any of them is refused with `bundle_too_large`, naming the limit. A checksum mismatch, a malformed file (an unreadable archive, a missing or invalid manifest, or a record that fails the bundle schema), or an entry outside the archive refuses the import with `corrupt_bundle`. A refusal at any stage leaves nothing of the story behind. A bundle whose major format version is newer than the deployment supports is refused with `unsupported_format_version`; older versions are migrated. If the engine-profile impact report warns, the import returns it and imports nothing unless the request sets `ignore_warnings` (FR-PROF-7). The imported story is not served (`story_importing`) until all of the following have completed, and if any of them refuses, nothing remains of it:
    - this deployment's **erasure ledger** is applied, so content referencing a subject erased here is erased before anyone can read it (FR-ADMIN-7,9);
    - the request names a **content rating** in this deployment — by default the one with the bundle's rating name; one must be named if none matches — and the whole active history is checked against its effective guardrails, including global policies such as the minors policy, exactly as a tightening checks a story (FR-RATE-7). Any violation refuses the import, with each violation listed. Only active history is checked at import: imported discarded and dormant turns are recorded as having passed no guardrail set of this deployment, so an untruncate, swap, or promotion that would later reactivate them checks them first and is refused if they fail (FR-RATE-7);
    - the story is attached to the **engine profile** the request names, or the deployment default, under the rules for assigning a profile to a story with history, including `upgrade_mode` when capabilities are added (FR-PROF-7,8);
    - **outbox rows** without a terminal outcome are imported in a state that is never dispatched and are listed for reconciliation (FR-EXT-22), so an importing deployment never repeats an external effect the source may already have performed;
    - projections are rebuilt and active records re-embedded with this deployment's embedding model.
  - Catalog snapshots stay inside the imported story; no catalog entry is created or changed. Attribution principal IDs are kept as recorded (FR-AUTH-4). Media are stored by checksum and deduplicated against existing assets. Apart from the story ID, the owner, this deployment's erasures, the chosen rating and profile, and the rebuilt projections and vectors, the imported story's corrected history at every checkpoint, its as-originally-recorded view with its audit records, beliefs, States, ledger, turn variants, and message feedback are identical to the source's. Imported audit events keep the times they were first recorded, so this deployment's audit retention (FR-STORE-30) counts from those times and may remove them later. Results use the shared validation report (FR-SCN-5).

### 2.1 Time travel, forking, and deletion — Engine Core

In-story operations (truncate, regenerate) share one primitive — *the current corrected history through checkpoint N*. Story-level operations (fork, delete) treat a story as a **fully self-contained dataset**. All of these operate on **narrative position**, never on valid-time (FR-BITEMP-5).

- **FR-STORE-8 (M).** Narrative position shall be the **turn index** (plus variant) of the narrative turn that introduced a record, not a `seq` range. `seq` is global recording order and interleaves narrative turns with background, audit, and control events, so a message is identified by its turn operation, not by a contiguous `seq` range. No separate message→memory association shall be required beyond each record's source-event and operation references.
- **FR-STORE-31 (M).** Within a turn, narrative position shall be refined to **(turn, beat, step)**: beat index orders the beats of a multi-character turn (FR-MULTI-11) and step index orders the declared causal steps within one render (FR-TURN-12). Regeneration operates on whole turns; checkpoints, truncation, and fork operate at **turn boundaries** — `N` by default, or an inter-turn slot boundary `N⁺k` (below) — never inside a turn; antecedent checks (FR-EPI-14) and exposure frames (FR-BELIEF-5,6) use the full (turn, beat, step) order. Operations that change story truth **between** turns — API and directive State sets (FR-STATE-9), late settlements (FR-EXT-21), and similar inter-turn operations — are positioned at an **inter-turn slot** `(N⁺k)`: after the completion of the active variant of turn N and before turn N+1, ordered by commit (k = 1, 2, …) and belonging to that variant (regenerating or truncating turn N discards them with it). A checkpoint may name either boundary: **`N`** is the state immediately after turn N's reply (excluding its inter-turn slots) and is the default for truncation, fork, and "state as of N"; **`N⁺k`** includes inter-turn slots 1..k. An inter-turn slot is never placed inside an incomplete staged turn (FR-EXT-19): an inter-turn operation that commits while a staged turn is incomplete waits for that turn's completion and is positioned after it.
- **FR-STORE-32 (M).** **Compaction is an explicit, irreversible control operation.** A story that opts into compaction (FR-STORE-19, FR-STORE-30) shall compact only through a **compaction operation**: a control action (FR-CONC) that permanently deletes chosen **discarded** records (truncated tails) and **dormant continuations**, never active records, amendments and their history, or anything an amendment's undo depends on, and leaves compaction markers (identifiers and ranges only) in their place. It is **two-stage**. First, an impact report lists every tail and continuation to be deleted and every operation that will stop being possible — undoing the affected truncations, swapping back to the affected continuations, and promoting them to their own stories (FR-STORE-28) — and suggests promoting any continuation worth keeping beforehand. Nothing is deleted until the request is repeated with `ignore_warnings`. The operation bumps the timeline revision, so in-flight operations that read the deleted records revalidate (FR-CONC-4). Afterwards, an undo, swap, or promotion that needs compacted records is refused with `compacted`; history, replay, and determinism are defined over the post-compaction log, as after erasure (FR-STORE-1, NFR-DETERM-1); and the audit and as-originally-recorded views show the markers. Compaction never deletes outcome records, outbox rows, or reconciliation listings (FR-EXT-21), erasure markers or the erasure ledger (FR-ADMIN-7), or feedback rows, which remain, marked `compacted` (FR-FB-2). Audit records keep their own retention, and story images of compacted turns lose their references and are purged by the media sweep (FR-MEDIA-2). A story may instead set a **compaction policy** (default off), such as compacting dormant continuations older than a set age, which runs the same operation automatically. Opting into the policy is the confirmation, and each run is recorded and reported with its impact report.
- **FR-STORE-9 (M).** Every memory, fact, belief, divergence, and utterance shall carry the `source_event` and `operation_id` that produced it, its narrative position where applicable, and a **timeline-membership** status (active/discarded) stamped with the transaction-time of its last change.
- **FR-STORE-10 (M).** Truncating a story to checkpoint N (e.g., deleting a message and everything after it) shall mark every record whose narrative position is > N as **discarded**, stamped with the transaction-time of the truncation, non-destructively and reversibly; it shall **not** hard-delete them and shall **not** alter their valid-time. Membership, not valid-time, represents abandonment — a discarded message may describe something whose valid-time precedes the checkpoint (e.g., a flashback), and it must still be removed from the active timeline.
- **FR-STORE-11 (M).** "Story state as of N" shall mean the **current corrected history through N**: records with narrative position ≤ N, timeline membership active, with all amendments in force (FR-STORE-20). This view underlies rewind, regeneration, fork, and lazy belief resolution (FR-BELIEF-6).
- **FR-STORE-12 (M).** Regenerating the latest message, turn N, shall discard turn N's active variant — truncating to the boundary just before it, `(N−1)⁺k` with every inter-turn slot committed before turn N kept (FR-STORE-31) — and generate a new variant of turn N, satisfying the commit/regeneration boundary (FR-COMMIT-8).
- **FR-STORE-13 (M).** A derived memory (semantic/reflection) shall be included in the view through N iff all of its source records are active members with narrative position ≤ N; excluded derived memories shall not be deleted, and consolidation shall re-run at the new head to regenerate derived memory for the truncated timeline (cf. FR-MEM-4 source-event references, load-bearing for this cascade).
- **FR-STORE-14 (M).** A story shall be a fully self-contained dataset: no memory, event, fact, belief, vector, or other record shall reference another story.
- **FR-STORE-15 (M).** Fork/duplicate shall produce a **full, independent copy** of the source story's **current corrected history through N** (FR-STORE-11) — active records with narrative position ≤ N, all applicable amendments in force, plus derived projections, memories, facts, beliefs, utterances, divergences, and vectors — under a new `story_id`. The copy shall be isolated at creation; subsequent changes on either side shall never propagate to the other. *(Consequence: an amendment recorded before forking is present in the fork even if it was recorded after narrative position N — e.g., play to 1,000, amend Bobby's childhood at 1,001, fork at 800 → the fork has the corrected childhood. An amendment recorded after forking affects only the side it was applied to.)*
- **FR-STORE-16 (M).** Deleting a story shall remove all of its data and shall have no effect on any other story (a `story_id`-scoped delete; no reference-counting or cross-story garbage collection). Media bytes are the one deployment-level exception: they are content-addressed assets (FR-MEDIA-2), so deleting a story removes its references, and the media sweep purges bytes nothing else references.
- **FR-STORE-17 (M).** Every external-data read shall be recorded as an event, so that within-story reconstruction, regeneration, and audit are deterministic without re-calling live providers; reconstruction shall replay recorded reads, never issue live provider calls (cf. FR-EXT).
- **FR-STORE-18 (M).** Truncation and amendments (FR-REWRITE) shall be reversible: truncation by reactivating discarded records (FR-STORE-28 when new turns exist), amendments by a checked undo operation (FR-REWRITE-10) — not a blind revert, since later amendments and turns may depend on them. Neither destroys the underlying records. The one exception is compaction (FR-STORE-32): once the consumer confirms it, the truncations and continuations it removes can no longer be restored.
- **FR-STORE-19 (M).** Optional compaction of discarded and dormant in-story records shall be supported for storage reclamation, exactly as specified in FR-STORE-32.
- **FR-STORE-30 (M).** Retention defaults: discarded and dormant continuations shall be **kept until the story is deleted** (undo and swap depend on them), unless the story opts into compaction, which removes them irreversibly (FR-STORE-32); **audit records** (rejected renders, verify verdicts, repair attempts, rewrite Q&A) shall be retained **90 days by default**, configurable per deployment and per story; embedding vectors shall be kept only for active **hot** records (FR-MEM-8) and re-embedded on reactivation or rehydration with the story's pinned embedding-model version. Re-embedded vectors are **not** guaranteed byte-identical to the originals (model serving can vary), so the determinism guarantee (NFR-DETERM-1) covers Engine Core state other than live-re-embedded vectors; a per-story `retain_dormant_vectors` option keeps dormant vectors for exact reproducibility at a storage cost.
- **FR-STORE-20 (M).** An amendment's eligibility for the view through a checkpoint (`N` or `N⁺k`) shall be evaluated **per correction part** (FR-REWRITE-12), not for the amendment as a whole: (a) a **record correction** is included when the record it corrects is in the view; (b) a **world-proposition correction** is included when its proposition's valid-time begins at or before the checkpoint's story-time. That comparison is made in **clock offsets** whenever both times can be expressed against the story clock ("before the story began", "since the diner scene", "an hour before turn 40") — then it is exact regardless of how the clock is anchored. When one side is an absolute calendar time and the anchor is partial or absent ("in 2012" against a clock that knows only "Saturday afternoon"), the comparison uses the anchor's admissible range: **certainly before** → included; **certainly after** → excluded; **undecidable** → governed by the story's `ambiguous_retcon_timing` ∈ {`include_if_possible` (default), `ask_author`}. Under `include_if_possible`, the correction is included at every checkpoint it might precede and is marked `timing_uncertain` in previews and the audit view. Under `ask_author`, each undecidable correction becomes a required question during the rewrite — whatever the `resolution_mode` — asking the author to place it relative to the story ("before turn 812" / "after turn 812" / "before the story began"); the answer is stored with the correction as an explicit position bound — a turn with the variant active when the author answered, or the story's start — and used for all later eligibility checks (the one position bound FR-BITEMP-5 allows). Parts of an amendment that apply only to records after the checkpoint are out of scope for that view.
- **FR-STORE-21 (M).** Amendments shall **survive truncation**. Because an amendment occupies no narrative position, truncating to N discards narrative records after N but leaves the amendment in force for surviving records; its effects on discarded records simply fall away (and return if the truncation is undone). Undoing an amendment is a separate, checked operation (FR-REWRITE-10).
- **FR-STORE-22 (M).** When a fork or truncation retains an amendment whose rationale depended on records now excluded (narrative position > N), the engine shall run the existing rewrite conflict check (FR-REWRITE-2/3) on the resulting state and surface any unsupported amendment rather than silently keeping or dropping it.
- **FR-STORE-23 (M).** Epistrel shall also support an **as-originally-recorded** view at a checkpoint — records with narrative position at or before the checkpoint as they stood at the checkpoint's **commit boundary**, before any later amendments, discards, or derived records. For checkpoint `N` the boundary is the transaction-time at which turn N's completion committed; for `N⁺k` it is the transaction-time at which inter-turn slot k committed, so the view includes slots 1..k and excludes later slots, and excludes amendments and derived records committed after that boundary. This is an audit/debug view; it is not the default for any player-facing operation.

### 2.2 Event model: operations, categories, continuations — Engine Core

- **FR-STORE-24 (M).** Every event shall carry `seq` (global recording order), an `operation_id`, an operation kind (turn / inter-turn / genesis / consolidation / rewrite session / backfill / import / control / maintenance), and a category (FR-STORE-25). Only narrative turn operations advance the turn index; background, audit, and control operations have no narrative position of their own. Inter-turn operations that change story truth (State sets, late settlements, ingested outcomes) do not advance the turn index but occupy an inter-turn slot `N⁺k` (FR-STORE-31).
- **FR-STORE-25 (M).** Event categories shall govern view inclusion: **narrative state** (say/do/think/latent, commits, in-turn beliefs) and **input** (external reads, attributed to the triggering turn) are read by story views; **derived** records are read by source eligibility (FR-STORE-26); **amendments** are read by FR-STORE-20 scope; **audit** records (rejected renders, verify verdicts, repair attempts, rewrite Q&A) are never read by story views, only by the audit view; **control** records (truncate, untruncate, fork, swap, config changes) change membership or settings and are not themselves story content. Audit and input records follow the membership of their operation.
- **FR-STORE-26 (M).** Derived records shall be judged by **provenance in the corrected-history view** and by **creation in the as-originally-recorded view**: a reflection computed after checkpoint N from sources at or before N is included in the corrected history through N (it is a cache over pre-N history), but excluded from the as-originally-recorded view at N (it did not exist then).
- **FR-STORE-27 (M).** Consolidation and other derivation jobs shall declare a **source window** — an upper-bound turn and the exact input records — and shall read only those inputs. On commit, the job shall recheck that every input is still active **and still the same version** (an amendment can change an input without discarding it); if any input has been discarded or changed in the meantime (e.g., the user truncated or rewrote history while the job ran), the output shall be dropped, not committed, and the job rescheduled to recompute against the current timeline. Each derived record shall store its job's operation ID, source window, and input versions.
- **FR-STORE-28 (M).** Each turn shall carry a **variant ID** alongside its turn index. Exactly one variant per position shall be active, and the active variants shall form a single chain; inactive chains are dormant continuations. Undoing a rewind shall: (a) when no new turns have been written since, reactivate the discarded turns; (b) when new turns exist, default to a **swap** — the original continuation becomes active and the newer one becomes dormant, with nothing lost and the swap itself reversible. The consumer may instead **promote a dormant continuation into its own story** via a normal full-copy fork (FR-STORE-15). Undo shall never silently reject or destructively overwrite a continuation. A continuation removed by an explicit compaction (FR-STORE-32) can no longer be swapped back or promoted, and such a request is refused with `compacted`.
- **FR-STORE-29 (M).** Resolutions shall follow the membership of the operation that produced them. A lazily resolved belief, a resolved global thunk, or a commitment is established *within its continuation*: on a swap, the restored chain's own resolutions return, and anything resolved only in the now-dormant chain reverts to unresolved and resolves again if needed. World-proposition corrections from amendments survive a swap, while record corrections follow their records' membership (FR-REWRITE-12); the conflict check (FR-STORE-22) runs against the restored chain, and consolidation reruns for the active chain.

### 2.3 Concurrency, retries, and idempotency (FR-CONC) — Engine Core + Orchestrator

Atomic commits guarantee a turn lands all-or-nothing; they do not stop two requests from generating against the same stale state. Generation takes seconds and several model calls, so concurrency control is **optimistic**: record what was read, and check at commit that it hasn't moved.

- **FR-CONC-1 (M).** Each story shall maintain a monotonic **timeline revision**, incremented by every committed change to story truth: a turn commit (including any lazy belief resolutions made in it, FR-BELIEF-12; a staged turn increments once per truth-changing stage, FR-EXT-19), truncate, untruncate, swap, amendment, directive, a State change made through the API, an edit to pinned memories or custom instructions (FR-LITE-3), an ingest (FR-RESP-10), a late settlement (FR-EXT-21), genesis, an erasure (FR-ADMIN-9), or a compaction (FR-STORE-32). Derived, maintenance, and audit work (consolidation, importance scoring, re-embedding, projection rebuilds, rejected renders) shall **not** increment it, so background work never invalidates in-flight turns.
- **FR-CONC-2 (M).** Every mutating operation shall record the **base revision** it read from, and every commit shall state the revision it expects. Database locks shall never be held across model calls; the commit section locks the story row only for the duration of the commit itself.
- **FR-CONC-3 (M).** Each turn shall record its **read set**: the records, facts, beliefs, State values, and external reads it retrieved or verified against.
- **FR-CONC-4 (M).** At commit, inside the commit transaction, the engine shall revalidate: (a) revision unchanged → commit; (b) revision changed but no record in the read set was touched → **rebase** (re-run the deterministic verify against current state; commit if it passes); (c) the read set was touched → do not commit; **regenerate** against current state within a configurable retry budget, then return a conflict to the consumer; (d) a control action that changes the timeline — truncate, untruncate, swap, undo, or an erasure (FR-ADMIN-9) — landed since the base revision → **abandon** the turn and return a conflict, because the timeline changed and the old result is no longer wanted. Configuration changes are handled by FR-CONC-16, and compaction by (b) and (c), since it deletes only inactive records (FR-STORE-32). Under `lite`, a turn's read set is its assembled prompt's inputs — the verbatim window, summary segments, pinned memories, custom instructions, and any States or clock shown — a rebase re-runs only the policy checks, and a change to any of those inputs regenerates.
- **FR-CONC-5 (M).** **Same-story turn concurrency shall be configurable per story** via `turn_concurrency` ∈ {`reject`, `queue`}, set at story creation and changeable through the configuration API. Default: `reject`.
  - `reject` — while a narrative turn is in flight for the story, a second turn request is refused with a "story busy" response and nothing is generated. Suited to roleplay, where a linear one-at-a-time conversation is the norm and an overlapping request is almost always a mistake.
  - `queue` — turn requests are queued first-in-first-out per story; each queued turn generates against the state after the previous one commits, so queued turns never conflict with each other. A configurable maximum depth applies; overflow is refused as busy. Suited to games, where several scenes with different characters may be active at once and requests legitimately overlap.
  - In both modes, different stories (including forks) run fully in parallel, and non-turn operations (rewrites, background jobs, admin actions) may run concurrently and commit through the revision check (FR-CONC-4).
  - **Paused stories.** While a story is paused — for a backfill (FR-PROF-8), a rating tightening check, or a reactivation check (FR-RATE-7) — every operation that would change its story truth (respond, ingest, rewrites, directives, control actions, and State API changes) is refused with `story_paused`, with the progress of whatever paused it, and records nothing; reads are served. A pause begins only after any in-flight ordinary turn has committed; a staged turn already past intent keeps its slot and finishes its remaining stages after the pause. Provider and consumer outcomes that arrive during a pause are recorded on arrival and settled at the next inter-turn slot once the pause ends (FR-EXT-21).
- **FR-CONC-6 (M).** Every mutating request (respond, rewrite apply, truncate, untruncate, swap, fork) shall accept an **idempotency key**. The engine shall store key → operation ID and full result for a configurable **result window** (default 24 hours), and a lightweight **tombstone** (key, request hash, operation ID) for the life of the story. Within the result window, a retry with the same key returns the original result without regenerating or recommitting; after it, a retry with the same key and payload returns a reference to the original operation (its turn and outcome, readable through the history API) and is never re-executed; the same key with a different payload is an error; a duplicate arriving while the original is still in flight waits for the original's result rather than starting a second generation. (Essential because generation is nondeterministic: an unkeyed retry would produce a *different* message and could append it twice.)
- **FR-CONC-7 (M).** A rewrite **preview** shall carry its base revision, and apply shall require it. Revalidation happens at the final commit — after any synchronous Q&A, which may take minutes — not at approval: if the story moved but nothing in the plan's blast radius changed, apply; if anything in the blast radius changed, the plan is **stale** — recompute and re-preview, carrying over the author's earlier answers where they still apply.
- **FR-CONC-8 (M).** Background workers shall record the version of every input they read and commit only if every input is still active and unchanged (FR-STORE-27); otherwise the result is dropped and the job rescheduled to recompute against the current timeline. This applies to consolidation, re-embedding, and projection rebuilds.
- **FR-CONC-9 (M).** A rebased turn keeps its recorded external reads (it is the same turn); a regenerated turn is new work and reads external providers live again.
- **FR-CONC-10 (M).** A fork shall read a consistent snapshot of the source story pinned to a single timeline revision (repeatable-read transaction), so a turn committing on the source mid-fork cannot produce a partly-old, partly-new copy.
- **FR-CONC-11 (M).** **Read sets record queries, not just rows.** Every deterministic lookup a turn relies on for a verdict, a precondition, or a blocker shall be recorded as a **query key** — subject, predicate, object or wildcard, holder, and time window — together with its result, **including an empty result** ("no matching fact existed"). Semantic retrieval used only as generation context is not keyed, but any fact a verdict or precondition depends on must come from a keyed lookup.
- **FR-CONC-12 (M).** At commit, any change committed since the base revision whose proposition matches a recorded query key — **including newly added facts** — counts as touching the read set (FR-CONC-4). The engine shall check keys against a change index or re-run the keyed lookups. Example: a turn finds no lock and narrates opening the door; an amendment adds a lock while generation runs; the lock matches the turn's empty "locks on this door" key, so the turn regenerates.
- **FR-CONC-13 (M).** Rewrite revalidation (FR-CONC-7) shall re-run the dependency search for the changed facts at final commit. Any dependent added since the preview — for example a new belief derived from a changed fact in a turn played meanwhile — makes the plan stale, even if no record in the original blast radius changed.
- **FR-CONC-14 (M).** **Configuration is versioned and captured.** Every configuration change — story-scoped (predicate registry, closed-set declarations, State schema, constraints, and permissions, perception settings, `player_authority`, novelty permissions, story policies, output-viewpoint defaults, interaction settings) and deployment-scoped (provider registration, ownership, write capability, and confirmation mode; global policies; model routing) — shall be recorded as a versioned change with its own **configuration revision**, separate from the timeline revision. Every operation (turn, rewrite preview and apply, background job, dispatch claim) shall record the configuration revisions it ran under, and replay shall use the recorded configuration.
- **FR-CONC-15 (M).** Every setting shall be classified in the configuration schema as **interpretive** or **prospective**. *Interpretive* settings change how already-generated work is verified, permitted (State and novelty permissions), routed, or committed: predicate semantics and closed sets, State schema/constraints/permissions/transfers, perception rules, `player_authority`, novelty permissions, guardrail and story policies, the story's content rating and the rating definitions it uses, visibility rules, and provider ownership, write capability, and confirmation mode. *Prospective* settings affect only work started after the change: model routing and parameters, prompt templates, retry budgets, escalation thresholds, `turn_concurrency`, `interaction_mode`, retention and compaction *policies* (changing a policy deletes nothing by itself; deletion happens only in a compaction operation, which is a control action, FR-STORE-32), and observability. An unclassified setting is treated as interpretive.
- **FR-CONC-16 (M).** At commit, if an interpretive setting the operation depends on changed since its captured configuration revision, the engine shall **rebase** under the new configuration — re-run deterministic verification, State and novelty permission checks, perception routing, State validation, and policy checks, each where the story's profile enables it — and commit (recording the new configuration revision) only if they pass; otherwise regenerate within the retry budget, then return a conflict. Prospective changes never invalidate in-flight work; the operation completes under its captured configuration. **Staged turns (FR-EXT-16):** configuration rebasing applies only to work not yet committed, and committed stages are never regenerated, rolled back, or cancelled by it. Before intent commits, the turn rebases as above. After intent but before the claim, the committed attempt beats stand, and the pending effect is revalidated at claim under the new configuration — if the provider is no longer write-capable or the effect is no longer permitted, it is cancelled: in a staged turn, the completion stage narrates the attempt as not carried out; for an asynchronous effect, whose turn has already closed, the cancellation is recorded as the effect's outcome and listed for reconciliation (FR-EXT-14). After the claim and **before the outcome transaction commits**, the outcome transaction validates its conditional effects and reservation settlements under the configuration current at that commit: an effect the new configuration no longer permits (an inventory schema change, a revoked acquisition permission) is not committed and is reported as `settlement_conflict`, while the external outcome is preserved as received. **After the outcome transaction has committed**, its settled effects are durable committed story truth like any other: a later configuration change does not revoke them, and changing them requires a separate explicit operation (an author directive, a State API call, or a rewrite). Only genuinely pending work — the outcome step and its exposures, and conditional effects still waiting on other prerequisites — is revalidated, and the outcome step narrates truthfully under the new configuration. **Dependency cascade:** when the rebase changes perception routing or acquisition rules, the engine shall recompute each beat's exposures under the new configuration, **remove** any staged belief acquisition no longer supported, and treat every later beat whose antecedents (FR-EPI-14) or render input (the perceived output of earlier beats, FR-MULTI-5) included removed content as invalid: it is regenerated against the corrected staged state, together with every beat after it that depended on it, while beats before the first affected beat are kept. A rebase that only re-verifies, without this cascade, is not sufficient. The same rule applies to rewrite apply (an interpretive change makes the preview stale), to background workers (drop and recompute), and to the dispatch claim (a provider no longer write-capable, or whose ownership changed, causes the `intended` effect to be cancelled as above).

> **Destructive vs non-destructive deletion.** *Within* a story, truncation and amendments are non-destructive and reversible (membership and transaction history are preserved). *Whole-story* deletion (FR-STORE-16) and right-to-be-forgotten (FR-ADMIN-2) are destructive and intentional: each removes data for good. Because stories are self-contained (FR-STORE-14), both are simple scoped deletes with no cross-story effects.

## 3. Bitemporal canon (FR-BITEMP) — Engine Core

- **FR-BITEMP-1 (M).** Every fact shall carry valid-time (`valid_from`/`valid_to`) and transaction-time (`tx_from`/`tx_to`).
- **FR-BITEMP-2 (M).** Superseding a fact shall invalidate the prior version, not delete it.
- **FR-BITEMP-3 (M).** Epistrel shall answer "what was true at story-time T" and "what did the record say at record-time T" independently.
- **FR-BITEMP-4 (M).** A retroactive change shall be representable as true across the relevant story-time span while recording the record-time, author, and authority of the change.
- **FR-BITEMP-5 (M).** Epistrel shall keep three distinct coordinates, each with one job, and shall not substitute one for another: **narrative position** (turn index plus variant of the introducing turn — checkpoints, truncation, regeneration, fork, timeline membership; not `seq`, which is recording order), **valid-time** (story-time — when a fact is true in the world; retcons, flashbacks), and **transaction-time** (when the engine recorded, changed, or discarded a record — audit, undo, as-originally-recorded). In particular, valid-time shall never be used to represent timeline membership or abandonment, and narrative position shall never be used to bound which corrections apply (FR-STORE-20), except the explicit position bound an author gives under `ask_author`, which FR-STORE-20 stores with the correction.

## 4. Memory tiers (FR-MEM) — Engine Core

- **FR-MEM-1 (M).** Episodic memories (discrete, timestamped, embedded) derived from observable events.
- **FR-MEM-2 (M).** Semantic memories (distilled standing facts) derived from episodic memory.
- **FR-MEM-3 (M).** Reflections (higher-level abstractions) produced by consolidation.
- **FR-MEM-4 (M).** Every memory shall carry provenance (author/GM canon, including scenario seeds with provenance `seed`, FR-SCN-8; system-consolidated; in-world assertion; **external authority**; thunk **resolution**, FR-COMMIT-14; or **backfill**, FR-PROF-9), trust/authority tier, visibility scope, importance, source event reference(s), created/last-accessed times, and embedding-model version.
- **FR-MEM-5 (M).** Working memory shall be derivable from events without separate persistence.
- **FR-MEM-11 (M).** **Working memory is viewpoint-filtered.** Before any character render, that character's working memory (the recent scene and turns) shall be rebuilt from authoritative history through the same perception routing as memory writes and output (FR-TURN-2,9,10, FR-RESP-12): beats whose content the character perceived appear in full, envelope-only beats as their envelope, unperceived beats not at all, and no other character's `think` or `latent`. Director and orchestration contexts may see more; a character's generation context never does. Not writing scene context as canon (FR-RESP-4) prevents canon corruption; this requirement prevents unseen content from **influencing** behavior.
- **FR-MEM-6 (M).** Consolidation shall compress episodic detail into semantic facts and reflections such that retrievable context stays bounded regardless of story age. Consolidation runs as its own operation with a declared source window (FR-STORE-27).
- **FR-MEM-7 (M).** Importance shall be assignable (via the Model Access Layer) and shall decay.
- **FR-MEM-8 (M).** **Retrieval eligibility is separate from timeline membership.** Every memory record shall carry a **retrieval tier** ∈ {`hot`, `retired`} independent of whether it is active on the timeline. **Budgets:** each character's **unpinned** hot memories are held to `hot_memory_budget_per_character` (default 2,000) and the story's unpinned hot vectors to `hot_vector_budget_per_story` (default 50,000). **Pinned** memories (author-pinned, never retired) are outside those budgets but **admission-limited** by `max_pinned_per_character` (default 200) and story-wide by `max_pinned_per_story` (default 2,000): pinning beyond either limit is rejected with an error until something is unpinned. The aggregate bounds are therefore explicit for every permitted story: hot memories per character ≤ `hot_memory_budget_per_character` + `max_pinned_per_character`, and hot vectors per story ≤ `hot_vector_budget_per_story` + `max_pinned_per_story`. Open commitments, ledger items, thunks, scheduled events, canon, beliefs, and States are **structured records**, not memory records: they are never retired, need no hot-set protection, and reach generation contexts through their own channels (ledger, schedules, keyed lookups), so the memory records that mention them may retire like any other. **Enforcement is eventual with a bounded lag, per overflow episode:** an **overflow episode** for a hot set begins at the first commit that takes it from within budget to over budget, and ends when it is back within budget; its deadline is `retirement_max_lag` committed turns after the episode began and **does not reset** while the episode lasts, however many further commits add to it; once the set is back within budget, a later overflow starts a new episode with its own deadline. The commit that opens an episode enqueues priority consolidation and retirement; retirement prefers records already **covered** by a consolidation output (FR-MEM-6) or below the importance floor, in order of lowest decayed importance and oldest last access; if the episode reaches its deadline (`retirement_max_lag`, default 50 committed turns) still over budget, the engine retires the lowest-ranked uncovered records anyway, ending the episode (marked `retired_uncovered`, with consolidation queued to cover them later). Until then the overflow is reported as a metric (FR-OBS); per-turn retrieved context stays bounded regardless (FR-MEM-6). A retired record stays active history: it is still verified against through keyed structured lookups (FR-CONC-11), still appears in history and audit views, and can be **rehydrated** on demand by the resolution pipeline (time-window and lexical lookup, FR-RET-2) — retrieved, re-embedded if needed, and returned for that query without re-entering the hot set unless re-accessed repeatedly. Retired records drop their vectors unless `retain_retired_vectors` is on.
- **FR-MEM-9 (M).** Consolidation shall **preserve epistemic scope**. All inputs to one consolidation shall share a viewpoint scope; a derived record's visibility shall be the **intersection** of its inputs' scopes, never the union. Objective reflections shall be derived only from public/objective records. Combining private memories of different characters into one reflection is forbidden unless the output is scoped to characters who legitimately hold every input. Consolidation shall also **preserve epistemic type**: a derived record keeps the modality of its inputs — a speech act stays an attributed claim ("Bobby said P"), a belief stays the holder's belief, an observation stays an observation — and may state P as objective fact only if P is objective canon among its inputs. A source's being public widens visibility, never modality: public testimony yields "Bobby said P," not P.
- **FR-MEM-10 (M).** Consolidation results shall be stored with the model, model version, and prompt hash that produced them. **Replay** (reconstruction, fork copies, view queries) shall use the stored result. **Rerunning** the model is a new consolidation operation with new provenance, performed only when its sources changed (FR-STORE-27) or on explicit request.

## 5. Epistemic model (FR-EPI) — Engine Core

- **FR-EPI-1 (M).** Objective canon shall be represented separately from any character's beliefs.
- **FR-EPI-2 (M).** Per character: self-world beliefs, social-world beliefs (about other characters), and, when nested beliefs are enabled (FR-PROF-2), nested beliefs (about others' beliefs) to at least second order. Nested beliefs are represented per FR-BELIEF-15.
- **FR-EPI-3 (M).** False beliefs shall be represented as first-class truth for the holding character.
- **FR-EPI-4 (M).** Could-have-known shall be **mechanically enforced** via the character's dated acquisition records (FR-BELIEF): a character may reference/know a fact at story-time T only if replaying their acquisition records up to T yields a belief in it. No legitimate acquisition path by T → they cannot know it at T.
- **FR-EPI-5 (M).** Every fact and memory shall carry a visibility scope identifying which characters may access it.
- **FR-EPI-6 (M).** Belief state per character shall be a queryable projection.
- **FR-EPI-7 (M).** Belief provenance shall be **mandatory**: every belief records *which acquisition operation produced it* (FR-BELIEF), from whom/what, when (story-time), and with what confidence; a belief with no legitimate acquisition path is invalid. The permitted acquisition operations double as the permitted causes: **observation**, **testimony** (incl. the misinformation case), **inference**, **discovery**, **correction**, **forgetting/decay**, and **revision**, plus **author direction** (canon-by-fiat, top authority) and **resolution** — the knowledge a thunk binding obliges its bound character to have held (FR-COMMIT-14). Gap-fill of a genuine unknown is legitimate only within could-have-known limits (FR-EPI-4).
- **FR-EPI-13 (M).** The legal transitions of a character's belief set are exactly the causes in FR-EPI-7, each requiring an **independently verified antecedent that is available before the dependent step** (FR-EPI-14). The engine shall validate every proposed belief-state change against this rule — the same verification oracle pointed at belief deltas — and reject or flag any unlicensed transition. What is forbidden is **self-attestation** — a step establishing its own cause — not a cause and effect falling within the same turn.
- **FR-EPI-14 (M).** An antecedent qualifies when it is independently verified and precedes the dependent step in causal order: (a) a record committed in an earlier turn (a prior event, a standing trait, or an author act); (b) a **verified staged beat earlier in the same turn** in `sequential` mode, even though it is not yet committed to the database (FR-MULTI-11); (c) a **verified earlier step within the same render** (FR-TURN-12); or (d) for the knowledge obligations of a thunk resolution, the verified resolution itself, which applies from the thunk's original valid-time once the reconciliation check passes (FR-COMMIT-14). Example: Bobby says "The bridge collapsed" (beat 1, verified); Jenni hears him, believes him by testimony, and says "Then we'll take the ferry" (beat 2) — both in one atomic turn, and legitimate. Apart from (d), a belief whose only support is the same step that asserts it, or a later step or beat, does not qualify.
- **FR-EPI-8 (M).** A determined proposition shall have exactly one **truth value at a given valid-time**; for a **functional** predicate this means one object per uniqueness key per time (FR-PROP-3). Multi-valued relationships (a person attending several institutions, knowing many people) are unaffected — each proposition in the set has its own single truth value. Characters shall differ only in partition presence (known/unknown), never in the truth of a determined proposition. A character's divergent view of a determined fact shall be represented as a separate owned **belief** record (FR-EPI-3), never as a second value of the fact. The engine shall not represent a per-character value for a determined fact, and shall reject or flag any attempt to assign one via a viewpoint.
- **FR-EPI-9 (M).** Character modeling shall be triggered by **direct interaction** (dialogue, a physical exchange, mutual acknowledgment such as waving) **or explicit salience** (the model or an author directive marks an entity as a character to model). Mere appearance shall not trigger modeling. A meaningful character not yet interacted with may be modeled via salience.
- **FR-EPI-10 (M).** Modeling shall be liberal; narrative weight shall be conservative. A modeled character's existence shall imply no narrative significance; minor characters shall default to low weight and remain so unless the story develops them. Minor-character modeling shall be **lazy and sparse** — the partition accrues only from actual interactions and is consolidated aggressively — so that modeling every interaction does not become a scaling burden.
- **FR-EPI-11 (M).** A modeled minor character shall be a full character with first-class private `think`/memory, viewpoint-scoped and subject to the same non-leakage rules as any character (NFR-PRIV-1). "Minor" limits weight and sparsity, never privacy.
- **FR-EPI-12 (M).** The human player shall exist as a modeled character for other characters' purposes (others hold memory of, and beliefs about, the player), but the engine shall **not** store player interiority: the player has no engine-held private `think` or partition. The player's `say`/`do` shall be recorded as other characters witness them; viewpoint-scoped retrieval and verification shall not run for the player-character; and the human shall be authoritative over their own character's utterances.

### 5.1 Belief formation & revision (FR-BELIEF) — Engine Core + Orchestrator

Belief *storage* (FR-EPI) and belief *legitimacy* (FR-VERIFY-10) are not enough; the transition from a public event to a specific character's belief must be explicit and typed.

- **FR-BELIEF-1 (M).** A public event is not a belief update. An assertion heard or an action observed records **exposure** / a speech-act (FR-TURN-5), not belief. Belief is a separate, per-character transition that the event *affords*; hearing establishes exposure, not acceptance.
- **FR-BELIEF-2 (M).** Belief acquisition shall be modeled as dated, typed operations, each with an antecedent requirement, confidence, and could-have-known interaction: **observation** (direct perception; highest reliability; could-have-known auto-satisfied), **testimony** (someone asserted it; see FR-BELIEF-3), **inference** (derived from premises already in the character's partition), **discovery** (learning a previously-unknown fact from evidence; often resolves a thunk, FR-COMMIT-10), **correction** (replacing a prior belief on new evidence; preserves history), **forgetting/decay** (a belief losing confidence/accessibility over time without contradiction), and **revision** (the general belief-set update, of which correction and forgetting are special cases).
- **FR-BELIEF-3 (M).** Testimony shall not auto-update witnesses' beliefs. An assertion heard is recorded as a speech act; each witness's **acceptance / rejection / suspension** is a separate typed testimony transition, gated by the witness's trust, priors, and consistency with what they already know. It may yield a first-order belief, a disbelief, a suspended judgment, or a belief about the **speech act** ("believes X was *claimed*" without believing X — `believes(H, said(S, X))`). A belief about a speech act is not a belief about the speaker's belief; whether the speaker *believes* X is a separate nested belief (FR-BELIEF-15) that the witness may infer, e.g. by judging the speaker sincere. Acceptance is model-adjudicated where salient and defaulted/deferred where not. Model adjudication uses the `belief adjudication` purpose (FR-MODEL-2) as optional work within the turn budget (NFR-PERF-6); when the budget cannot fit it, the acceptance is defaulted and the response lists that degradation.
- **FR-BELIEF-4 (M).** Confidence shall be **dual**: a categorical level (unknown / suspected / believed / known) is always present; an optional scalar may be populated (needed for game scenarios, not required for fiction). When the scalar is present it is the source of truth and the categorical level is its projection; the two shall never be independently set to contradictory values.
- **FR-BELIEF-15 (M).** **Nested beliefs.** A nested belief shall be a belief record whose content is another belief: `believes(H, believes(B, P))` — holder H attributes to B a belief in proposition P — nesting to a configurable depth (default and minimum 2 when nested beliefs are enabled, FR-PROF-2). The record carries: the **holder** H (whose partition it lives in); the **attributed holder** B; the inner proposition P with its own polarity and valid-time; the **attributed confidence** (how sure H thinks B is), optional; H's own confidence in the attribution (FR-BELIEF-4); **provenance** — the typed acquisition that produced it (H observed B witness something, testimony "Bobby thinks you're angry", inference from B's behavior or exposures H knows of, correction, forgetting), each with an antecedent per FR-EPI-13; and three times — when H holds the attribution (the belief record's own validity), when H thinks B holds P, and P's valid-time. **Verification:** H's claims about B's beliefs ("Bobby thinks the knocker was Marcus") are checked against **H's** nested beliefs for their belief relation (FR-TURN-6) — never against B's actual partition, which would leak B's private state (NFR-PRIV-1). The **objective relation** of an attribution (does B actually believe P?) is computed by the Engine Core against B's partition for labeling and divergence records only, and is never placed in H's context. A nested belief is independent of both B's actual belief and objective truth: all three may differ.
- **FR-BELIEF-5 (M).** For non-salient witnesses the engine shall record an **exposure record** — the proposition exposed, the source, and the **exposure position** — a full narrative position (FR-STORE-31): either a **turn position** (turn index, **beat index**, step index within the beat) or an **inter-turn slot** `N⁺k` (for exposures created by inter-turn operations such as a late settlement witnessed in-world, FR-EXT-21) — as its evidentiary frame — rather than resolving belief; belief is resolved lazily when first needed.
- **FR-BELIEF-6 (M).** Lazy resolution shall resolve **as-of the exposure frame, not as-of now**: it uses the current corrected history through the exposure's full position — turn, beat, and step, or inter-turn slot `N⁺k` (FR-STORE-11, FR-STORE-31) — for the believer's partition and canon, so a later beat or step **in the same turn** cannot influence it any more than a later turn can, decides the testimony transition in that frame, and then folds forward any later dated transitions in narrative order. Narrative evidence introduced *after* the exposure position shall never influence the resolution of that exposure; amendments that correct the history *before* it do apply, because a retcon is defined to have always been true. (Deferral saves computation, not information — the same principle as the commitment checkpoint and recorded external reads.)
- **FR-BELIEF-7 (M).** When an exposure is finally resolved, the resulting belief transition shall be **logged as a dated event and become an established, durable belief** (with exposure-dated provenance); it shall not be recomputed ad hoc thereafter; its anchors and inclusion rules are defined in FR-BELIEF-12..14. Like other derived state it is invalidated/cascaded by retcon (FR-DIRECT/FR-REWRITE) via its provenance.
- **FR-BELIEF-8 (M).** Later legitimate evidence that reaches the character's partition shall produce a **new dated transition** (e.g., an observation at T₂ yielding a correction), distinct from resolving the earlier exposure. Canon-only knowledge not in the character's partition shall never leak into an earlier-frame resolution. The resolver reconstructs a belief's whole dated history from exposure forward; no frame ever sees evidence from its future.
- **FR-BELIEF-9 (M).** Belief formation shall be **lazy and proportionate to salience**: non-salient witnesses get exposure records / cheap defaults; only salient believers get adjudicated transitions, bounding per-event fan-out (cf. ADR-023 sparsity).
- **FR-BELIEF-10 (M).** Correction and revision shall preserve prior-belief history bitemporally (so a character can coherently have been wrong and then corrected, and so retcon cascades correctly); forgetting/decay shall be a confidence/accessibility operation feeding consolidation (FR-MEM-6).
- **FR-BELIEF-11 (M).** A witnessed observable envelope (FR-TURN-2) is a full-fidelity **observation** and may seed a low-confidence **inference** about undisclosed content (e.g., "Jenni and Marcus are hiding something"), but it creates **no acquisition path to the content itself**. A character may therefore legitimately notice, ask about, or react to a whisper, yet shall never come to *know* its words without a genuine later acquisition (someone tells them, they read it, etc.); a claim to know withheld content with no acquisition path is caught by could-have-known / FR-VERIFY-10.
- **FR-BELIEF-12 (M).** Lazy resolution shall occur only inside a narrative turn operation that needs the belief. A resolution is a change to story truth (it changes what a character believes): it is categorized as narrative state, committed atomically with that turn, and covered by that turn's timeline-revision increment (FR-CONC-1). Read-only inspection shall never persist a resolution.
- **FR-BELIEF-13 (M).** Every resolved belief shall carry two anchors: the **exposure position** ((turn, beat, step) or inter-turn slot `N⁺k`) — the evidentiary frame and the point from which the belief holds — and the **resolution operation** (turn and variant) — where the engine chose the interpretation.
- **FR-BELIEF-14 (M).** The resolution operation governs inclusion; the exposure position governs valid-from. A corrected view through checkpoint N includes the resolution iff its resolution operation is active and at or before N; within such a view the belief holds from its exposure position (viewed through turn 900, a belief from exposure at turn 10 resolved at turn 850 shows Bobby believing it since turn 10). Truncating to before the resolution operation, or swapping away from its continuation, discards the resolution and the exposure reverts to unresolved; a fork at N copies it only if its resolution operation is at or before N. (This differs from derived memory, FR-STORE-26, deliberately: a reflection is a cache over its sources, while a resolution is a choice that changes how a character behaves and so belongs to the continuation that made it.)

## 6. Structured turn contract (FR-TURN) — Engine Core

- **FR-TURN-1 (M).** Epistrel shall represent a rendered turn as structured channels — `say`, `think`, `do`, `latent` — and shall reject/flag turns that omit required structure.
- **FR-TURN-2 (M).** Routing is by **perception, not presence** (FR-TURN-9), and an utterance has two separately-routed parts. Its **observable envelope** — that speech occurred, the speaker, the apparent target, the visible manner (leaning in, contact, direction, glances), the interlocutor's visible reaction, and the surrounding observable context — routes as a full-fidelity observation to all characters **authoritatively co-located**. Its **content** (the words) routes by audience: all co-located by default, **narrowed** by an explicit whisper/aside to named targets, or **widened** by an explicit eavesdrop or remote channel to exactly whom the render names. `do` routes as an observation to all co-located. A whisper therefore writes the envelope to the whole room and the content only to its target; a non-decodable language writes the envelope and withholds the content on the same footing. The envelope/content split and the qualifiers apply with `full` perception routing; at `co_location` (FR-PROF-2), every co-located character perceives the whole beat, so a whisper is heard by the whole room.
- **FR-TURN-3 (M).** `think` shall route only to the thinking character's private partition, shall never be retrievable into another character's viewpoint, and shall never be **disclosed** in player-facing output — neither verbatim, nor paraphrased, nor as narration asserting an inner state that is recorded only in `think` ("he secretly thought she looked sad"). This does not forbid **legitimate inference**: a character's own observable `say`/`do` (a sympathetic look, a hesitation, a clipped answer) may reveal their state to anyone who perceives it, and perceivers — the player included — may draw inferences from it; such behavior is itself a verified `do`/`say` of that character. A rendered message exposes only observable channels (`say`/`do`); a character's inner thoughts remain private memory that may legitimately *surface later* only through that character's own future `say`/`do` (see FR-VERIFY-9).
- **FR-TURN-4 (M).** `latent` shall route to objective canon with an explicit visibility scope.
- **FR-TURN-5 (M).** Utterances shall be stored as speech acts and shall not be promoted to objective truth by virtue of being said.
- **FR-TURN-6 (M).** Each utterance shall carry three **independent** labels rather than a single truth label:
  - **objective relation** ∈ {`true`, `false`, `unresolved`} — the asserted proposition checked against canon (or its owner, FR-VERIFY-7);
  - **speaker belief relation** ∈ {`consistent`, `inconsistent`, `unknown`} — the asserted proposition checked against the speaker's own beliefs at the utterance's position;
  - **communicative intent** ∈ {`sincere`, `deceptive`, `joking`, `unspecified`} — declared in the render's `think` and checked, not trusted (FR-VERIFY-10).

  The dimensions combine freely. A **sincere error** is sincere, belief-consistent, and objectively false. A **lie** is deceptive and belief-inconsistent, whatever the objective relation — including an **attempted lie that happens to be true** (deceptive, belief-inconsistent, objectively true), and a lie about something the speaker falsely believes (Bobby wrongly believes X, says not-X to deceive, and not-X is in fact true). A joke is labeled as such and is not presented to hearers as a sincere assertion.
- **FR-TURN-7 (M).** An utterance with **deceptive** intent shall create a divergence record (asserted vs. what the speaker believes) that persists and is queryable. Hearers' testimony transitions (FR-BELIEF-3) consider the utterance's *perceived* intent: a joke is not accepted as sincere testimony by default, and a deception the hearer does not detect is accepted on the hearer's normal trust rules.
- **FR-TURN-8 (M).** A character's engine-held belief state (including any established false beliefs) shall be supplied in that character's generation context, and a render that introduces a *new* belief shall name its cause (FR-EPI-7). A belief appearing in a render with neither a pre-existing engine-held record nor a cited/discoverable antecedent is a contract violation, caught at verification (FR-VERIFY-10). `think` reasons over supplied belief state; it does not redefine it.
- **FR-TURN-9 (M).** Perception resolution shall be **deterministic**: presence establishes only a *candidate* audience; actual perception follows a fixed rule — same authoritative location → perceive, different location → do not — with the only deviations being **explicit** render qualifiers (whisper/aside narrows below the room; eavesdrop/remote widens beyond or outside it). Perception shall **not** be model-adjudicated — the engine does not infer distraction, inattention, or acuity; a character deviates from the co-location default only when the render explicitly establishes it. The content that enters a perceiver's partition is whatever the render established (full by default; partial only if the render explicitly limits it, e.g., an eavesdropper catching a few words), feeding FR-BELIEF exposure at that fidelity. Remote communication is simply an audience the channel defines, orthogonal to physical location.
- **FR-TURN-10 (M).** Perception and the resulting memory writes shall derive from **authoritative** state (canonical character locations, barriers, explicit channels), never from the consumer-supplied scene roster (FR-RESP-4). The roster may supply candidates and context but shall **never grant** perception: a character authoritatively co-located perceives even if omitted from the roster, and a character on the roster who is not authoritatively co-located does not. No private knowledge shall be granted on the basis of non-authoritative input (NFR-PRIV-3).
- **FR-TURN-11 (M).** The turn contract shall include a structured **state-effects** channel alongside `say`/`think`/`do`/`latent`, through which a render declares changes to tracked values (State, delta or new value, reason), including **time advances** of the world clock (FR-CLOCK-7). Effects on story-owned States are validated and committed with the turn (FR-STATE-5, FR-STATE-6); effects on externally owned values are returned to the consumer or dispatched per the provider's write policy (FR-EXT-9, FR-EXT-10).
- **FR-TURN-12 (M).** When a render's own beliefs change within it, the render shall declare an explicit **causal order of steps** — e.g., *observe* (Jenni sees the bridge is down) → *believe* (it collapsed) → *act* (she heads for the ferry). Steps are verified in declared order; a belief step may cite an earlier step only after that step has been verified, and an observation step is valid only if its object is independently verifiable (committed canon, a verified earlier beat, or a permitted fact introduced and verified earlier in the same render, FR-VERIFY-11). A belief step that cites no verified earlier step, or cites a later one, is self-attestation and is treated per FR-VERIFY-10.
- **FR-TURN-13 (M).** **Widening qualifiers must be physically possible.** An explicit eavesdrop or remote-channel qualifier shall be validated against authoritative canon before it grants perception: an eavesdropper must have a plausible perception path from their canonical location (an adjoining room, a door, a thin wall, an open window — per the location topology and barriers), and a remote channel requires an established channel event (a call in progress, a radio link). A qualifier with no valid path is repaired, not honored. Narrowing qualifiers (whispers, asides) need no validation, since they can only remove perceivers.

## 7. Commitment lifecycle (FR-COMMIT) — Engine Core

- **FR-COMMIT-1 (M).** Fact state shall be modeled as introduced → pending → committed → revised.
- **FR-COMMIT-2 (M).** A fact shall commit at the moment any character's `think` or `do` depends on its value, and not be required before that.
- **FR-COMMIT-3 (M).** Salience — content placed to be noticed — shall trigger commitment, distinct from inconsequential background texture, which requires none.
- **FR-COMMIT-4 (M).** On commitment of a salient-but-hidden fact, Epistrel shall record both an observation in the noticing character's partition and the underlying truth in canon scoped away until revealed.
- **FR-COMMIT-5 (M).** Epistrel shall distinguish *hidden* (decided, visibility-scoped, sticky) from *undetermined* (a thunk, re-resolvable).
- **FR-COMMIT-6 (M).** A committed fact is **determined globally** and has exactly one truth value at a given valid-time (for a functional predicate, one object per uniqueness key per time — FR-EPI-8); characters differ only in whether it is in their partition (*known* vs *unknown*), never in its truth. An event may therefore be *determined and known to some characters while unknown to others* (determined-but-asymmetric — e.g., the knocker is Bobby, known to Bobby, unknown to Jenni), **or** genuinely *undetermined for everyone* (a global thunk) until first resolution. These are different states: "unknown to Jenni" is an absence in her partition; it is **never** "undetermined for Jenni," which would wrongly imply she carries an independently resolvable value for a fact the world has already fixed. (A character's divergent view of a determined fact is a separate owned **belief** record, not a second value — see FR-EPI-8.)
- **FR-COMMIT-7 (M).** A promissory ledger shall track **salient** references awaiting commitment and shall prevent a turn from closing while a salient reference is unresolved. Unforced *background* thunks carry no closure obligation and may remain unresolved indefinitely (including forever).
- **FR-COMMIT-13 (M).** **Ledger obligations are per proposition.** A promissory entry attaches to the specific proposition that was made salient, not to everything about the event. Committing "a knock occurred" satisfies the ledger for a salient knock while the knocker's identity and motive remain open global thunks — unless the narration made *those* salient too (Jenni recognizes the knock, the prose dwells on who it might be), in which case each of them carries its own entry, or a modeled character knocked on a decided intent (committed on the knocker's side, FR-COMMIT-6). Salience of an event does not make its unspecified attributes salient.
- **FR-COMMIT-14 (M).** **Resolution reconciliation.** Before any thunk resolution commits — immediate, deferred, model-driven, or author-directed — the engine shall derive the **retroactive obligations** it creates at the thunk's original valid-time: propositions that become necessarily true then (Bobby was at Jenni's door at t, so not elsewhere at t) and knowledge the bound entity necessarily held from then on (Bobby knows he knocked and why). It shall run the dependency search (FR-REWRITE-2, FR-DIRECT-8) and epistemic checks (could-have-known, belief consistency, FR-EPI-4, FR-VERIFY-10) of those obligations against recorded history: the bound character's positions, and their later sincere `say`/`do`/`think` that would be inconsistent with that knowledge (Bobby later sincerely asking Jenni who was at her door). No conflict → the resolution and its obligations commit together (obligations written to the bound character's partition with provenance `resolution`, anchored at the original valid-time); conflict → handled per FR-COMMIT-11 (model-driven: rejected) or FR-COMMIT-12 (author-directed: amendment with blast radius).
- **FR-COMMIT-8 (M).** Regenerating message M shall revert **everything M committed** (those values become open again and may re-roll) and re-resolve any thunks M left open, while **preserving everything committed by messages before M**. A fact's stickiness is always relative to a checkpoint: sticky to messages *after* its commit, open at the message that committed it. (Commit boundary = regeneration boundary.)

  > **Worked example (the coin).** A fact commits in the message where a dependency first forces it; regenerating *that* message re-rolls it, regenerating any *later* message preserves it. *Same-message:* "She catches the coin, sees heads, and smiles" — the result (heads) and the reaction (smiles) both commit in this one message, because the reaction depends on the result. Regenerating this message reverts both: the coin may re-roll to tails and the reaction regenerates to match (she grimaces), as one coherent unit. *Forward stickiness:* if the result was committed in an earlier message and a later message reacts to it, regenerating the later message must **not** re-roll the result (it belongs to an earlier checkpoint) and the regenerated reaction must stay consistent with it. *Undetermined:* if the coin was caught with no dependency yet (value unstated, no reaction), it is a thunk — regenerating that message may yield a different result, and it only becomes sticky once some later message's `think`/`do` forces its commit.
- **FR-COMMIT-9 (S).** Committed facts shall support a resolution level, fixing a consequential value while deferring incidental detail until first dependence.
- **FR-COMMIT-10 (M).** A genuinely undetermined fact is a global thunk; **any** character's `think`/`do` that first needs its value shall resolve it, once, globally. Resolution shall be optional — an unforced thunk need never resolve.
- **FR-COMMIT-11 (M).** A late (deferred) thunk resolution shall inherit the weight implied by its deferral: because a salient fact would have been committed at introduction (FR-COMMIT-3), a thunk left open is evidence of low stakes, and its resolution shall be biased toward insignificance and toward entities with **no retroactive epistemic obligations** (not an existing modeled character who would plausibly have known). This bias is enforced by generation steering, not a hard check. Resolving a deferred thunk into an existing modeled character shall be a **soft flag whose severity scales with the story-time gap** since introduction (via the could-have-known check, FR-EPI-4) **when the reconciliation check of FR-COMMIT-14 finds no conflict**; a binding that the check finds in conflict with recorded history shall be rejected for model-driven resolution, and generation steered to another binding.
- **FR-COMMIT-12 (M).** An author/user directive (e.g., on a regeneration: "the knocker is George, her ex") shall override the insignificance presumption of FR-COMMIT-11 (author authority, FR-DIRECT-1). Author authority chooses the outcome but does **not** bypass the reconciliation check (FR-COMMIT-14): an undetermined fact does not guarantee a consequence-free resolution. If the check finds no conflict, the resolution needs no history rewrite beyond the normal regeneration reconciliation of the message being regenerated; if it finds conflicts, the resolution proceeds as an amendment with that blast radius under the `resolution_mode` and `preview` of the request that carries the directive (FR-REWRITE-3..6).

## 8. Retrieval & resolution (FR-RET) — Engine Core

- **FR-RET-1 (M).** Viewpoint-scoped retrieval: a retrieval for character A returns only A's partition plus objective facts known to A; other characters' private thoughts shall never be returned.
- **FR-RET-2 (M).** A resolution pipeline shall, before vector search, resolve relative time to story-time ranges, resolve event types, and resolve references using recent context.
- **FR-RET-3 (M).** Occasions shall be located by structured time-and-type query over the episode layer, with participants resolved from the located episode.
- **FR-RET-4 (M).** Hybrid retrieval shall combine vector similarity and lexical/exact-match search.
- **FR-RET-5 (M).** Ranking shall combine semantic similarity, recency decay, and importance.
- **FR-RET-6 (M).** Entity/relationship-scoped retrieval shall return standing character profiles once entities are resolved.
- **FR-RET-7 (S).** A context-assembly helper shall fill a token budget by priority tier.

### 8.1 Propositions, predicates, and entities (FR-PROP) — Engine Core

The schema deterministic verification operates on. Without it, "contradicted" cannot be distinguished from "compatible": someone can attend two universities, hold two degrees, or hold one degree jointly awarded by two institutions — exclusivity exists only where a predicate declares it over a specific key.

- **FR-PROP-1 (M).** A **proposition** shall consist of: a **subject** (entity ID); a **predicate** (registered predicate ID); an **object** (entity ID, typed literal, or none); predicate-specific **qualifiers** (e.g., degree level, quantity, role); a **polarity** (affirmed or negated); and a **valid-time**, which is either an **interval** `[start, end)` in story-time with `start < end` (each bound exact or approximate, e.g. "summer 2012", "childhood", or open-ended) or an **instant** `t` for punctual events (a literal `[t, t)` is empty and shall never be used). An instant carries a **granularity** (a day, an hour, a minute) and is covered by an interval iff its whole granule lies in `[start, end)`; an instant stated only approximately ("sometime in 2012") is an interval with approximate bounds. Three temporal relations are kept distinct: **exact equality** (same instant at the same granularity); **coarse compatibility** (the finer instant falls within the coarser instant's granule — "May 10" is compatible with both "May 10 09:00" and "May 10 17:00", which are not equal to each other); and **event identity**, which is never established by time alone — two event propositions denote the same event only through a shared event ID or the predicate's uniqueness key (e.g., a person's birth). Compatibility establishes that two times *could* agree, not that they do.
- **FR-PROP-2 (M).** Propositions shall be viewpoint-free. Holder (canon, a character's belief, an utterance), provenance, visibility, and confidence belong to the record that wraps the proposition, so a canon fact, a false belief, and a lie can share one proposition shape with different holders.
- **FR-PROP-3 (M).** Every predicate shall be registered with: argument types (subject and object); **cardinality** over a declared **uniqueness key** — `functional` (one object per key at a time) or `multi` (a set per key, with optional maximum). The key is the subject plus the qualifiers the predicate names as key qualifiers (e.g., `degree_awarded` is keyed by (person, degree ID), so a person may hold any number of degrees and each degree's awarding-institution set is single-valued; `residence` is keyed by person alone). Qualifiers not in the key never participate in uniqueness. Objects may be **sets** where the domain allows it (a jointly awarded degree has the institution set {A, B}); **temporal kind** — `permanent` (never changes), `fluent` (holds over an interval, may change), or `event` (punctual); declared **exclusions** with other predicates (e.g., `alive` / `dead`); **containment** for hierarchical objects (places, organizations); declared **implications**; **symmetry/inverse**; and **owner** (`story` or `external`, as for States — FR-STATE-2). Story States are functional predicates.
- **FR-PROP-4 (M).** Predicate semantics shall come from three layers: (a) a **core vocabulary** shipped with the engine (FR-PROP-5); (b) **author-declared** predicates per scenario, with full semantics; (c) **auto-registration**: a predicate used in a render but not declared is registered automatically with the **weakest semantics** — `multi` with no maximum, no exclusions, no implications, no containment. Weak semantics forbid **inferred** exclusivity: a weak predicate never yields `contradicted` from cardinality, exclusion, implication, or containment. It still yields `contradicted` for a **direct polarity conflict** — the identical normalized proposition (same subject, predicate, object, and qualifiers) affirmed and negated over overlapping time ("Bobby apprenticed with this blacksmith" vs "Bobby did not apprentice with this blacksmith") — because that conflict is logical, not semantic. Stronger semantics (functional, exclusions, implications) shall come only from the core vocabulary or the author; the engine may **propose** strengthening an auto-registered predicate for author approval but shall never apply it on its own. Any other contradiction question involving a weak predicate (a semantic conflict the registry cannot see) goes to the model residual.
- **FR-PROP-5 (M).** The core vocabulary shall cover at least: identity (`same_as`), location and presence, possession, life and death, kinship and relationships, membership and roles, education and employment, basic attributes, and **schedules** (`scheduled(subject, event, planned time)` with the event's participants and place, for appointments and deadlines, FR-CLOCK-9). Education keeps **distinct predicates** for distinct facts: `enrolled_at` (person, institution; `multi`, fluent), `attended_program` (`multi`; camps, courses), `member_of` with a role qualifier (teams and clubs; `multi`, fluent), and `degree_awarded` (keyed by person + degree ID; object = awarding-institution set; qualifiers level and field; event). The core vocabulary ships **no implications** between these (team membership does not imply enrollment; enrollment does not imply a degree; a degree does not name its only institution); an author may declare such rules per scenario where they hold (e.g., "varsity membership implies enrollment at that institution"). Each core predicate ships with documented semantics.
- **FR-PROP-6 (M).** Every entity shall have a **canonical ID** and registered **aliases**. A mention resolver shall map names, pronouns, and descriptions to entity IDs using the speaker's viewpoint and recent context. An ambiguous or unresolved mention shall yield `uncertain` and shall never be guessed into a contradiction.
- **FR-PROP-7 (M).** **Identity is itself a proposition** (`same_as(e1, e2)`) with a holder and visibility, so the engine can know that "the stranger" is Bobby while Jenni does not. Entity merges and splits discovered later shall be recorded as amendments with the normal cascade (FR-DIRECT-8).
- **FR-PROP-8 (M).** The world is **open**: the absence of a proposition is not its negation, so a claim with no matching record is `novel`, not `contradicted`. An author (or canon) may assert a **closed set** — an explicit statement that a listed set is exhaustive for a key and interval ("Bobby's only undergraduate degree is `bobby_ba`"; "Bobby was enrolled only at OSU in 2010–2014"); a claim adding a member to a closed set over overlapping time is `contradicted`. Closed sets are never inferred. Explicit negations ("Bobby has never been to Florida") shall be stored as negated propositions and participate fully in contradiction checking.
- **FR-PROP-9 (M).** Relative temporal expressions ("now", "last week", "when he was seven") shall be resolved against the story-time of the claim's narrative position (FR-STORE-31) and the subject's established timeline. Fluents may change over time: two values of a functional fluent in non-overlapping intervals are not in conflict.
- **FR-PROP-10 (M).** Deterministic contradiction rules, applied after entity resolution to propositions with the same subject and predicate, checked against the claim's holder (canon for narration, the character's beliefs for first-person claims, FR-VERIFY-2):
  - same proposition, same polarity, and the claim's valid-time is **fully covered** by the union of the holder's matching valid-times → **supported**. Overlap is not enough: canon "Bobby lived in Ohio 2010–2014" does not support "Bobby lived in Ohio 2000–2020";
  - same proposition, same polarity, **partial coverage** → **uncertain** with reason `partial_coverage`, reporting the covered and uncovered sub-intervals. This is resolved deterministically, not by the model: the covered part is supported and the uncovered remainder is evaluated as its own claim (normally `novel`, then the permission check, FR-VERIFY-11); if the remainder is not permitted, repair narrows the claim to what canon supports;
  - same proposition, opposite polarity, overlapping time → **contradicted** (any overlap suffices for a conflict) — for every predicate, weak ones included;
  - functional predicate, same uniqueness key, different objects, overlapping time, objects not related by containment → **contradicted**;
  - a new member of an author- or canon-declared closed set over overlapping time → **contradicted** (FR-PROP-8);
  - multi-valued predicate, a new object → **novel** (then the permission check, FR-VERIFY-11), or **contradicted** if it exceeds a declared maximum;
  - a declared exclusion holds over overlapping time → **contradicted**;
  - the claim negates a proposition that canon implies through a declared implication → **contradicted**;
  - time intervals do not overlap → **no contradiction** from that pair;
  - instants: a claimed instant is **supported** only by a matching record at the **same or finer** granularity within the claim's granule (canon "May 10 09:00" supports "May 10"); a record at a **coarser** granularity leaves the claim **uncertain** with reason `granularity_refinement` — the added precision is evaluated as a novel detail (permission check), as with partial coverage; two instants on the **same unique event** (shared event ID or uniqueness key) contradict only when they are not even coarsely compatible, or are both stated at a common granularity and differ there ("09:00" vs "17:00"); instants on events without a shared identity never contradict and are never merged into one event;
  - approximate bounds: **support** requires coverage under every admissible reading (the claim's outer bounds within the canon's inner bounds); **contradiction** requires overlap under every admissible reading; otherwise **uncertain**;
  - a semantic conflict involving a weak predicate (beyond direct polarity), an unregistered predicate, an unresolved entity, or a value that does not normalize → **uncertain** → model residual (FR-VERIFY-3).
- **FR-PROP-11 (M).** Implications shall be applied with a bounded closure (declared rules only, a configurable maximum depth, no general-purpose inference), so deterministic verification stays predictable and fast.
- **FR-PROP-12 (M).** Claims shall be normalized into propositions by the claim-detection step (FR-VERIFY-13: declared turn structure, deterministic detectors, and model extraction). A claim that cannot be normalized into a registered predicate with resolved entities yields `uncertain`, never a guessed verdict.

## 9. Verification oracle (FR-VERIFY) — Engine Core (deterministic) + Orchestrator (escalation)

- **FR-VERIFY-1 (M).** `verify(claim, viewpoint)` shall return a three-way verdict — supported, contradicted, novel — with evidence; the Engine Core may additionally return `uncertain`.
- **FR-VERIFY-2 (M).** Verification shall be viewpoint-aware: a first-person character claim is checked against that character's belief set; a narrator/objective claim against canon.
- **FR-VERIFY-3 (M).** Verification shall be deterministic-first in the Engine Core, applying the contradiction rules of FR-PROP-10 to normalized propositions (FR-PROP-1..12); the Orchestrator shall invoke the entailment model only on the `uncertain`/fuzzy residual. The escalation gate shall be a **tunable predicate-resolution-confidence threshold** (config, not hardcoded) that returns `uncertain` on (a) an unresolved predicate, (b) a world-knowledge-dependent conflict, or (c) a partial or ambiguous match that FR-PROP-10 does not resolve deterministically (`partial_coverage` and `granularity_refinement` are resolved there, never escalated); it shall launch conservatively (biased toward escalation) and be tightenable per predicate-shape (cf. NFR-PERF-5, FR-OBS-2). Without entailment escalation (FR-PROF-2), a residual `uncertain` takes the safe disposition of FR-VERIFY-8.
- **FR-VERIFY-4 (M).** On a `novel` verdict, Epistrel shall support canonization (write-back) with appropriate provenance and visibility, optionally anchored to a related fact.
- **FR-VERIFY-5 (M).** Verification shall compute the three speech-act dimensions independently (FR-TURN-6) — objective relation against canon, belief relation against the speaker's beliefs, and intent from the checked `think` — and derive the classification from them: sincere error, lie (including an attempted lie that happens to be true), joke, or hallucination (no legitimate basis).
- **FR-VERIFY-6 (M).** `fact_neighborhood(entity|fact)` shall return the dependency cluster needed for coherent repair/regeneration.
- **FR-VERIFY-7 (M).** Objective and narrator claims about a tracked value shall verify against its owner — a story State's current value (FR-STATE) or an external provider's pinned per-turn value (FR-EXT-2) — not against free-text canon. A character's first-person claim about such a value shall verify against that character's beliefs, not the owner's value (FR-EXT-3, FR-STATE-8).
- **FR-VERIFY-8 (M).** A model fallback's verdict shall be validated, never trusted: an `uncertain` or low-confidence/unparseable entailment result shall resolve to the safe disposition (treat as needs-repair, or surface to the author), never a silent `supported` (cf. FR-MODEL-6).
- **FR-VERIFY-9 (M).** A character's recall of a past private observation shall be treated as **grounded** iff backed by a recorded partition entry of appropriate date, and such grounded resurfacing is encouraged (it is the long-horizon payoff of modeling interiority — e.g., a delivery driver later recalling that the player's character seemed sad at their first meeting, matching the recorded state). A "memory" with no backing partition record shall be treated as a novel/hallucinated claim and verified accordingly (confabulation caught). The discriminator is provenance: surfacing a recorded memory vs. inventing an unrecorded one.
- **FR-VERIFY-10 (M).** Declared `think` shall be **checked, not trusted**: it shall not, by itself, legitimize a claim that contradicts canon. A belief is never accepted on its own assertion: its cause must be an independently verified antecedent that precedes it (FR-EPI-14), not a justification the same step supplies for itself. When a first-person claim contradicts canon, the engine shall resolve the trichotomy as follows:
  - **Established false belief** — if the character's engine-held belief set already contains the (false) belief, with provenance, the claim is consistent with that belief → accept, no change.
  - **New false belief** — accepted only via a **permitted belief transition backed by an independently verified antecedent available before the dependent step** — a committed record, a verified earlier beat in the same turn, or a verified earlier step in the same render (see FR-EPI-7/13/14). Resolution is **citation-with-engine-fallback**: the render should cite the antecedent in `think`; the engine confirms the citation, or if none is cited searches history for a licensing cause. If a legitimate antecedent exists, the new belief is written with that provenance; if none exists, the claim is a **hallucination → repair** (a justification the model minted for its own error).
  - **Lie** — accepted only if the character holds a legitimately formed **underlying belief** that the utterance is inconsistent with; that belief need **not** be objectively true (a character can lie about something they are wrong about). The lie is recorded as deceptive intent with a belief-inconsistent relation, and a divergence is recorded. A declared lie with no underlying belief to deviate from is treated as a hallucination.
  - **Sincere error** — a sincere, belief-consistent, objectively false claim is accepted when the belief itself is legitimately established (an established or newly licensed false belief, above).
- **FR-VERIFY-11 (M).** A `novel` verdict shall not by itself authorize canonization; novelty requires **permission** based on who asserts the claim and who owns its subject:
  - A **character's render** may introduce its own actions and thoughts, minor backstory about itself within its constraints, incidental scene texture, and resolutions of global thunks (FR-COMMIT-10). It may **not** introduce another modeled character's secrets, backstory, actions, or thoughts; the player character's actions, speech, or thoughts; changes to States except through validated state effects (FR-STATE-5); externally owned values; or anything the author has locked.
  - A **director/world pass** may introduce new arrivals and world facts per the scenario's policy, but not locked canon or externally owned values.
  - **Player input** — input whose actor is a player's own character — may introduce that character's actions, speech, and backstory; its authority over other characters follows `player_authority` (FR-RESP-11). Input whose actor is a character the platform plays (FR-AUTH-3) has that character's render permissions above and is checked like its render.
  - The **author** may introduce anything except externally owned values (FR-EXT-8).
  - **Exceptions:** attributed **reactive narration** (FR-MULTI-9) may describe another character's brief observable reactions, within that rule's limits — observable only, non-verbal unless interjections are enabled, never thoughts, and passing the reactor's perception and could-have-known checks; and under `player_authority = co_author` (FR-RESP-11), player input may narrate other characters' observable actions under the same checks. A render that binds a global thunk to an existing modeled character introduces that character's past action under FR-COMMIT-11 and FR-COMMIT-14, not under this rule.
- **FR-VERIFY-12 (M).** A novel claim that lacks permission shall be **repaired, not canonized**, through the normal repair ladder (FR-REPAIR).
- **FR-VERIFY-13 (M).** **Claim detection is distinct from claim checking.** Verification checks every **detected** claim; it cannot check a claim that was never detected, and structurally valid output (well-formed `say`/`think`/`do`/`latent`) does not establish that every factual claim inside its prose was declared. Every render shall therefore pass through the claim-detection layers its verification level enables (FR-PROF-2) — (a) and (b) at every level, (c) only at levels with claim extraction: (a) the **declared structure** (channels, declared propositions, declared state effects); (b) **deterministic detectors**, always on — entity and alias mentions not covered by a declared proposition, quantities and amounts, possession, transfer, consumption, injury, and movement language, time expressions, and **protected-content matching** (names, aliases, and values of facts not visible to the speaker's viewpoint: other characters' private records, hidden States, undetermined thunk values); and (c) the **model extraction backstop**, which, per the story's effective `extraction_mode` (an engine-profile dial, FR-PROF-2), runs on **every** render (`always`, default) or only when (b) flags a risk or the structural parse is incomplete (`gated`, with a shadow sample in which extraction still runs and the claims gating would have missed are recorded, FR-OBS-4). Every detected claim is either matched to a declared proposition or verified as a new claim. The documentation and metrics shall report checking and detection separately: zero unchecked detected claims is a guarantee; complete detection is a measured rate (NFR-QUAL-10).
- **FR-VERIFY-14 (M).** The same claim detection shall run on the **final composed message** (FR-RESP-8) and on reactive narration (FR-MULTI-9), so claims introduced by composition or narrated for another character are detected by the same layers, not only by structural tracing.
- **FR-VERIFY-15 (M).** **Guarantee boundary.** The documentation shall state the boundary as *the model proposes; the engine validates structured claims, effects, and permissions*, and shall list which steps are **deterministic** (context assembly and viewpoint filtering, proposition normalization of declared structure, contradiction rules on normalized propositions, State effect validation and permission checks, perception routing, commitment and ledger mechanics, clock pacing and stops, timeline and concurrency operations, deterministic claim detectors) and which are **model-dependent and measured** (generation, model extraction of undeclared claims, salience, time estimation, entailment fallback, testimony acceptance and other belief adjudication, repair rendering, paraphrase/indirect-disclosure detection), each model-dependent step with its eval metric (NFR-QUAL) or, where none is defined, marked unmeasured, and shall be published **per preset** (FR-PROF-12), including what does not hold under Lite (structural knowledge separation, audience filtering, verification, commitment) and, for any profile whose perception is `none`, that no audience filtering applies. A natural-language output shall not be described as "verified" beyond the claims detected in it.

## 10. Repair support (FR-REPAIR) — Orchestrator (Engine Core primitives)

- **FR-REPAIR-2 (M).** Corrected/regenerated spans shall be re-verified before acceptance.
- **FR-REPAIR-3 (M).** Both the rejected render and the accepted correction shall be recorded as events (audit + eval data).
- **FR-REPAIR-4 (S).** A repair-classification signal (cosmetic / substitution / cascade) shall be derivable from neighborhood size.

## 11. Guardrails & policy (FR-GUARD) — Engine Core store + Orchestrator enforcement

- **FR-GUARD-1 (M).** An immutable policy store shall be maintained, separate from mutable memory, with no mutation path reachable by in-world content.
- **FR-GUARD-2 (M).** Policies shall be evaluable against every outbound message independent of memory state.
- **FR-GUARD-3 (M).** No memory or external content shall override, disable, or alter a policy (policy never yields to memory).
- **FR-GUARD-4 (M).** Mutation primitives shall be provided: `quarantine`, `sanitize`, `canonize`.
- **FR-GUARD-5 (M).** Guardrail-violation feedback shall mark implicated content so the Orchestrator loop converges (e.g., auto-quarantine on repeated implication).
- **FR-GUARD-6 (M).** A bounded-retry contract shall exist; after a configured budget a safe fallback path (e.g., a stored per-character in-character deflection) shall be used.
- **FR-GUARD-7 (S).** Per-character deflection styles/voice shall be storable so enforcement renders in character.
- **FR-GUARD-8 (M).** Policies shall be scopable — **global**, **per content rating** (FR-RATE-2), **per story**, and **per character** — and layered: global policies cannot be overridden by any lower scope, and the story rating's policies cannot be overridden by story or character policies; lower scopes may add policies, never relax them. If guardrail policies are defined, no engine profile setting bypasses them (FR-PROF-14). Each policy declares what it applies to — text **output**, text **input** (FR-GUARD-10), **image prompts**, and **image outputs** (FR-IMG-3), in any combination — and carries a **message** suitable to show a user. Creating, editing, or removing a policy is recorded with the acting principal; seeded policies are ordinary policies a deployment may edit or remove.
- **FR-GUARD-9 (M).** Guardrail evaluation shall be **deterministic by default** (rules, patterns, word and entity lists). A policy may declare a **model-assisted** check, which uses the `guardrail check` model purpose (FR-MODEL-2) and counts against the turn budget. Which policies are deterministic and which are model-assisted shall be visible in the policy store, so the model-call cost of guardrails is predictable under every profile.
- **FR-GUARD-10 (M).** **Input guardrails.** Text the consumer sends into a story shall be checked against every policy that applies to input — by default every **global** policy — before anything is recorded: respond input, ingested events, directives and rewrite instructions, pinned memories and custom instructions, and, at story creation, persona descriptions, ad-hoc character definitions, the chosen catalog characters' definitions, and genesis seeds. Rating, story, and character policies apply to output by default, where they steer in character (a teen character texting "can't talk about that, my mom reads my texts lol"); any policy may be set to apply to input as well. A violation rejects the request without side effects and returns an error naming each violated policy — its ID, name, and message — so the user can rewrite the text. The rejected text is not stored in the story, and the audit record holds only the policy IDs (NFR-SEC-4). For an age-conditioned policy (FR-GUARD-11), the error reveals that a minor is involved or present — never which character, or their age. Input checks run under every engine profile; deterministic policies cost no model call, and model-assisted ones count against the turn budget (FR-GUARD-9). Catalog publishing runs the same checks and reports violations as warnings (FR-SCN-5), since catalog content enters no story until genesis.
- **FR-GUARD-11 (M).** **Age-aware policies and the seeded minors policy.** A policy may be conditioned on the true ages (FR-CAT-12) of the characters **involved in** the content or **present** for it — authoritatively co-located (FR-TURN-10) — using each character's age at the content's story time. A **minor** is a character younger than the deployment's `minor_age_threshold` (default 18, so 17 and under). Epistrel shall ship a seeded **global** policy that applies to text input and output and to image prompts and outputs (FR-IMG-3) at every rating, Explicit included: **no sexual content involving a minor, or in the presence of a minor.** The ages and presence of characters the engine knows are evaluated deterministically; recognizing sexual content, and judging the age of a figure who resolves to no character (FR-IMG-12), is model-assisted (FR-GUARD-9). Deployments may add further minor-conditioned policies. The seeded policy is data, not code: a deployment administrator can edit or remove it through the policy API like any policy, the change is recorded with the acting principal, and the documentation states that the policy ships enabled and that removing it is the deployment's decision and responsibility. Under `lite`, the policy uses the cast's true ages and its model-assisted check of the text (FR-CAT-12).

## 12. Directives & reconciliation (FR-DIRECT) — Orchestrator + Engine Core

- **FR-DIRECT-1 (M).** Author/GM directives shall carry the highest authority tier; factual directives shall apply over existing canon.
- **FR-DIRECT-2 (M).** Directives shall be classified ephemeral (transient generation guidance, not persisted as canon) or durable (a fact change); ephemeral steers shall not persist as durable facts.
- **FR-DIRECT-3 (M).** On a durable factual change, Epistrel shall walk the dependency neighborhood and identify incidental mentions (auto-fixable), cascaded justifications (needing regeneration), and irreducible conflicts.
- **FR-DIRECT-4 (M).** Irreducible conflicts shall be surfaced to the author with options (rewrite / drop / keep) rather than silently overwritten: before commit under `synchronous` (and, under `threshold`, at or above its severity), or in the conflict report under `best_effort`, which lists each resolution it chose (FR-REWRITE-3).
- **FR-DIRECT-5 (M).** A durable retcon shall be recorded bitemporally and shall be reversible.
- **FR-DIRECT-6 (M).** The authority hierarchy (author/GM > narrative canon > in-world assertion; external authority within its own domain) shall govern all conflict resolution.
- **FR-DIRECT-7 (M).** Dependencies shall be recorded as **typed edges**: `causes` (the fact was a reason for an event or decision), `presupposes` (narration assumes the fact is true), `derives` (a belief or inference drawn from premises), `mentions` (a passing reference in narration), and `asserts` (a speech act claiming the fact, independent of its truth). Belief records additionally carry their acquisition type (FR-BELIEF-2).
- **FR-DIRECT-8 (M).** Retcon cascades (FR-DIRECT-3, FR-REWRITE-2) shall follow edge type: `causes` → re-evaluate and regenerate if no longer justified; `presupposes` → fix; `derives` → cascade; `mentions` → incidental fix; `asserts` → **the utterance stays as historical record**; its **objective relation** is re-evaluated, its **speaker belief relation** is re-evaluated only if the rewrite also changes the speaker's belief, and its **communicative intent is never changed by a retcon** (only an explicit author directive about intent can change it). Example: Bobby believes he attended OSU and, to deceive, says UCLA; a retcon makes UCLA objectively correct. The utterance's objective relation becomes `true`, but unless the rewrite also changes Bobby's belief it stays belief-inconsistent and deceptive — an attempted lie that happened to be true — and the author is notified, since the scene's point may change. Beliefs acquired by **testimony** stay (the character believed what they were told); beliefs acquired by **observation** of the changed fact cascade.

### 12.1 Natural-language history rewrite (FR-REWRITE) — Orchestrator + Engine Core

A first-class capability for rewriting established history/memory, since the structured store cannot be edited by hand.

- **FR-REWRITE-1 (M).** Epistrel shall provide a natural-language **history side-channel**, distinct from the roleplay turn flow, through which an author states desired changes to established history or memory in natural language; the author shall never need to edit the datastore directly.
- **FR-REWRITE-2 (M).** The engine shall parse the directive into structured changes and compute the blast radius via `verify` + `fact_neighborhood` (the retroactive repair ladder of FR-DIRECT-3): auto-fix incidental mentions, regenerate cascaded justifications, and identify irreducible conflicts.
- **FR-REWRITE-3 (M).** Conflict disposition shall be governed by a consumer-set `resolution_mode` ∈ {`synchronous` (pause and ask per conflict on the side-channel; nothing commits until all are resolved), `best_effort` (auto-resolve each conflict by the least change — rewrite the conflicting record to fit, or drop it where it cannot be rewritten; dependent amendments that would be contradicted are cascade-undone, FR-REWRITE-10 — then commit and return a conflict report listing every resolution), `threshold(severity)` (auto-resolve as `best_effort` does below `severity`, and pause on conflicts at or above it)}. Severity is `high` for a conflict whose resolution would change something the player has seen — a delivered message, a player-visible State, or a fact exposed to the player character — and `low` otherwise. Default: `synchronous`.
- **FR-REWRITE-4 (M).** The operation shall support a consumer-set `preview` ∈ {`preview_first` (return the computed plan/blast-radius for approval before the commit phase), `apply_directly`}. Default: `preview_first`. `preview` shall be orthogonal to `resolution_mode`. A preview shall return the **base timeline revision** it was computed against, and applying it shall require that revision (FR-CONC-7).
- **FR-REWRITE-5 (M).** Blast-radius detection shall be identical across all modes; `resolution_mode` shall govern only the disposition of unresolved conflicts, and `preview` shall be an early exit before the commit phase over the already-computed plan.
- **FR-REWRITE-6 (M).** Every rewrite shall be a single **atomic, reversible** bitemporal transaction within one story, in all modes (including `best_effort` auto-resolutions); a rewrite shall never leave a story half-applied, and it shall be undoable as a whole through a checked undo operation (FR-REWRITE-10).
- **FR-REWRITE-7 (M).** A rewrite shall affect only the story it is applied to (no cross-story effect; cf. FR-STORE-14).
- **FR-REWRITE-9 (M).** A side-channel rewrite shall be recorded as an **amendment**: a transaction stamped with transaction-time, author, and authority, occupying no narrative position, that revises existing records and may introduce facts with their own valid-time. Its scope in any checkpoint view follows FR-STORE-20; it survives truncation (FR-STORE-21) and is undone only by reverting the amendment itself. (A regeneration with author direction — FR-COMMIT-12 — is not an amendment; it is an ordinary narrative event at a position.)
- **FR-REWRITE-10 (M).** **Undo is a new, checked amendment, not a revert.** Undoing amendment A shall compute its own blast radius against the story as it is now — including later amendments, turns, derived memory, and resolved beliefs that depend on A's changes — and run through the same `resolution_mode` and `preview` machinery as any rewrite (FR-REWRITE-3,4), with the same base-revision and new-dependent checks (FR-CONC-7, FR-CONC-13). For each dependent the options are: **cascade-undo** (for a dependent amendment), **repair** (for narrative or derived records, per edge type, FR-DIRECT-8), or **keep** (only if it remains consistent without A). Example: amendment A establishes UCLA and amendment B adds a UCLA graduation event; undoing A surfaces B as a dependent — undo B too, rewrite B, or cancel — and B can never be silently left contradicting restored canon. In `best_effort` mode, dependent amendments that would become contradicted are cascade-undone and listed in the report. A is never deleted; it is marked reverted by the undo, and redo is itself another checked operation.
- **FR-REWRITE-11 (M).** Amendments shall record typed dependency edges (FR-DIRECT-7) to the facts they rely on, including facts established by earlier amendments, so amendment-to-amendment dependencies are visible to undo and to retcon cascades.
- **FR-REWRITE-12 (M).** **Corrections attach by kind.** An amendment shall be decomposed into: (a) **world-proposition corrections** — changes to objective canon such as Bobby's undergraduate institution — attached to the proposition key (subject, predicate, qualifiers, valid-time scope), which apply in whichever continuation is active, survive truncation and swaps, and are re-checked against the newly active chain after any swap (FR-STORE-22,29); and (b) **record corrections** — changes to a specific narrative record such as what a line in message 900 said — attached to that **exact record ID**, which follow the record's membership: when its turn variant goes dormant the correction goes dormant with it, and returns if the variant is reactivated. The engine shall **not** automatically port a record correction to an "equivalent" event in another variant; it may suggest the port, which takes effect only on author approval.
- **FR-REWRITE-8 (M).** Conflict-resolution questions and the author's answers shall be conducted on the history side-channel and recorded for audit.

## 13. Model Access Layer (FR-MODEL) — Orchestrator

- **FR-MODEL-1 (M).** Epistrel shall hold per-purpose model configuration `{base_url, model, api_key, params}` and shall connect directly to external, OpenAI-compatible model servers.
- **FR-MODEL-2 (M).** Epistrel shall support a defined, enumerable set of model purposes: generation, regeneration/repair, entailment/verify-fallback, consolidation/reflection, importance scoring, salience detection, extraction backstop, time estimation (FR-CLOCK-7; defaults to the extraction-backstop model), guardrail check (only for policies that declare a model-assisted check; FR-GUARD-9), rating suggestion (FR-RATE-8; defaults to the guardrail-check model), image prompt (FR-IMG-2; defaults to the generation model), image check (a vision-capable model for policies on image outputs, FR-IMG-3), quality judge (used only by the eval harness, never in a turn; NFR-QUAL-14,15), belief adjudication (testimony acceptance and other adjudicated belief transitions, FR-BELIEF-3; defaults to the entailment model); image generation itself goes through its own port (FR-IMG-1) (embedding is a separate port, FR-EMBED).
- **FR-MODEL-3 (M).** Each purpose shall be independently configurable and shall default to a single configured model when not overridden — except `image check`, which needs a vision-capable model and so has no default: until one is configured, the image-output checks it serves cannot run (FR-IMG-3).
- **FR-MODEL-4 (M).** A runtime configuration API shall allow reading and updating per-purpose config without restart.
- **FR-MODEL-5 (M).** Model-using operations shall attempt a deterministic path first and invoke a model only on the residual.
- **FR-MODEL-6 (M).** Every structured model result shall be validated; unparseable/low-confidence results shall be treated as uncertain (conservative default or escalation), never silently accepted.
- **FR-MODEL-7 (M).** Structured-output enforcement shall be supported (constrained/grammar-guided decoding where available; parse-validate-retry otherwise).
- **FR-MODEL-8 (M).** `base_url` shall be configurable so Epistrel can target an enterprise LLM gateway that speaks the OpenAI-compatible format.
- **FR-MODEL-9 (S).** A bring-your-own-completion escape hatch shall allow a non-OpenAI-compatible model for a purpose, where the consumer returns the completion.
- **FR-MODEL-10 (M).** A recommended capability floor per purpose shall be documented.
- **FR-MODEL-11 (M).** A deterministic stub model adapter shall be provided for testing.
- **FR-MODEL-12 (M).** Per-purpose model-call counts and (where available) cost shall be observable for budgeting.
- **FR-MODEL-13 (M).** **Purpose registry and model guide.** Every model purpose, the embedding port, and the image adapter shall be declared in one **purpose registry** in code: its name, default model, capability requirements (FR-MODEL-10, NFR-PORT-3), and a typed schema of every input its requests may carry, each input tagged with its content category (for example story text visible to one viewpoint, a character's private memories, true ages, policy text, or images). Prompt templates and adapter payloads shall be built only from declared inputs: a template that references an undeclared field fails the build, and a payload builder that adds one fails its contract test. The published **model guide** — the capability floor of each purpose (FR-MODEL-10) and the **data-flow table** of what each purpose and adapter receives, with the hosted-provider retention notes (FR-IMG-13) — shall be generated from the registry, shall be a deliverable of every release, and shall be owned by the Model Access Layer's maintainers, named in the repository's code-owners file. CI fails when the published guide differs from what the registry generates. Purposes join the registry, and their rows the guide, as the capabilities that use them are delivered (§22).

## 15. External-data providers / extensibility (FR-EXT) — Orchestrator

- **FR-EXT-1 (M).** The consumer shall be able to register external-data providers (tools/Skills/MCP), each declaring the predicates/domains it authoritatively answers and a trust tier.
- **FR-EXT-2 (M).** The Orchestrator shall read a provider live when its domain is relevant, and shall record every such read as an `external_read` event capturing provider, query, returned value, and timestamp (cf. FR-STORE-17). Reads are **pinned per turn**: the first read of a given predicate in a turn fixes its value, and generation, verification, and commit all use that pinned value — verification never re-reads live. A rebased turn keeps its pinned reads; a regenerated turn reads again (FR-CONC-9). The original pinned read is immutable; a confirmed external effect inside the turn creates a **post-effect version** of the affected value (FR-EXT-20), and each beat or step verifies against the latest version at or before its position in the turn.
- **FR-EXT-3 (M).** An external provider determines **objective truth** for its domain; it does not determine what any character knows. Objective and narrator claims in a provider's domain verify against the turn's pinned value (FR-VERIFY-7). A character's first-person claim verifies against **that character's beliefs** and goes through the lie / false-belief / hallucination classification (FR-VERIFY-10); a character knows an external value only through a real acquisition path (FR-BELIEF).
- **FR-EXT-4 (M).** When a character commits a reference to volatile external data, Epistrel shall record a fact with provenance `external@timestamp` that **references the originating `external_read` event** rather than independently re-capturing the value; the `external_read` event is the single source of truth for that reading, fixing the in-world statement independent of later drift.
- **FR-EXT-5 (M).** External results shall be treated as untrusted content (injection surface), tiered by the provider's declared authority, never as instructions.
- **FR-EXT-6 (S).** Provider registration shall be updatable at runtime via the config API.
- **FR-EXT-7 (M).** Each provider shall declare an **unavailability policy** ∈ {`fail_turn`, `last_known` (use the most recent recorded value if within a configured freshness window), `unknown` (the objective value is unresolved for this turn)}. Default: `last_known` within the freshness window, otherwise `unknown`. The policy applied is recorded with the turn.
- **FR-EXT-11 (M).** When a value is `unknown` under FR-EXT-7, the restriction shall apply only to **new objective assertions** (narration stating the current value) and to **newly acquired exact knowledge** (a character learning the exact value this turn — e.g., checking a balance the provider can't report); both are blocked, and verification takes the safe disposition for them. **Existing beliefs keep their normal semantics:** a character who previously counted 500 gold may still say "I think I have 500" — verified against their beliefs (FR-EXT-3), sincere and belief-consistent, with an `unresolved` objective relation (FR-TURN-6). **Deliberate lies** likewise keep their normal verification semantics, since a lie is checked against the speaker's beliefs, not the provider's value.
- **FR-EXT-12 (M).** **Pending external effects follow their turn's membership.** An outbox row belongs to the operation that created it. The dispatcher shall re-check that operation's membership when it claims a row for dispatch, inside the same transaction; if the operation has been discarded (truncation, regeneration, swap away), the effect is **cancelled and never dispatched**. The **in-flight point** is the commit of that claim (status `claimed`), which happens before any network send: a discard that commits before the claim cancels the effect; once the claim has committed, the effect is treated as **potentially in flight** whether or not the send actually happened, and a later discard returns it with `reconciliation_required` (FR-EXT-14). Claim and cancel serialize on the outbox row lock, so there is no window in which an effect is both cancellable and sendable. Epistrel never promises cancellation after the claim commit.
- **FR-EXT-13 (M).** **Forks never copy executable effects.** A fork copies outbox history only as non-executable records; the fork's response lists any effects that were pending in the source at the fork point, so the consumer can decide whether to request them again in the fork.
- **FR-EXT-14 (M).** **Confirmed external actions are irreversible by internal operations.** Rewind, regeneration, swap, fork, and erasure cannot undo an effect the provider has confirmed. Any operation that discards a turn with confirmed, claimed (potentially in flight, FR-EXT-12), or `unknown` effects shall return those effects in its response with `reconciliation_required`, and the reconciliation status shall list them until resolved. Epistrel shall not compensate automatically; the author or consumer may issue a compensating effect through the normal channels. A swap that reactivates a continuation shall not automatically re-dispatch its cancelled effects; they are listed for reconciliation instead. Unclaimed (`intended`) effects referencing an erased subject are cancelled before erasure; claimed ones are listed for reconciliation.
- **FR-EXT-15 (M).** **Prose may not outrun confirmation.** Each provider declares `confirmation` ∈ {`synchronous`, `asynchronous`}. Under `synchronous`, the turn follows the staged lifecycle of FR-EXT-16: the action is committed as an attempt, the effect is dispatched and its result awaited (up to a configurable wait budget), and only then is an **outcome step** generated and final composition run; narration may state the external outcome only once confirmed, a failure is narrated in character as a failed attempt, and a wait that exceeds its budget completes the turn with the effect described as pending (asynchronous semantics). Under `asynchronous`, and for every effect on a read-only provider (applied by the consumer), narration shall describe the in-world action only as an attempt or intention and shall not assert the external outcome ("the purchase succeeded"); the response marks the effect pending. A later confirmation or failure — reported by the dispatcher or by the consumer through ingest — is recorded as an event and surfaced in the next turn, where a failure is reconciled in the narrative.
- **FR-EXT-16 (M).** **Durable effect lifecycle.** Every write-capable effect shall pass through separately committed stages, each recorded with the turn's operation ID: (1) **intent** — the verified turn (beats with the action as an attempt, checked by output policies before this commit, since they are readable from then on, NFR-PERF-6), its unconditional State effects and reservations (FR-STATE-14), and the outbox row (`intended`) commit together; the timeline revision advances and the turn is story truth from here; (2) **claim** — the dispatcher's claim commit (`claimed`), the in-flight point (FR-EXT-12); (3) **send and outcome** — the provider's result is committed as an outcome event (`confirmed`, `failed`, or `unknown` for an ambiguous result or timeout), together with any post-effect value version (FR-EXT-20) and the conditional effects and reservation settlements it decides (FR-STATE-14); (4) **completion** — for `synchronous` providers, the outcome step (narrating success or the failed attempt) is generated, verified, and committed as a later step of the same turn; (5) **response** — final composition (FR-RESP-8) runs on committed beats and the finished response is stored under the idempotency key. For a `synchronous` effect these are the stages of a **staged turn** (FR-STORE-5), which holds the story's turn slot through completion. For an `asynchronous` effect the turn is ordinary: stages 1 and 5 commit together and the turn closes; the claim and send follow, the outcome is recorded on the outbox row, and its conditional effects settle as a late settlement (FR-EXT-21); stage 4 does not occur. The operation carries an explicit status (`intent_committed`, `awaiting_outcome`, `outcome_recorded`, `completed`, or `abandoned` when a discard ends it early, FR-EXT-17) visible through the operations endpoint (FR-API-6).
- **FR-EXT-17 (M).** **Failure and resume.** Committed stages are never rolled back by a later failure; in particular, an external action is never treated as undone because composition, the outcome step, or response storage failed. The engine shall resume from the last committed stage: crash before intent → nothing committed, a retry generates anew; after intent, before claim → the dispatcher (or a retry with the same idempotency key) proceeds to claim, and a discard in this window cancels; after claim, before a recorded outcome → the dispatcher re-sends under the same provider idempotency key (FR-EXT-18) or queries the provider's status; after outcome, before completion → the outcome step is generated (within the retry budget, then a **deterministic outcome narration** from the outcome event); after completion, before the response is stored → the response is recomposed deterministically from committed beats. A retry with the same idempotency key at any point attaches to the existing operation and returns its finished response once stage 5 completes; it never starts a second turn or a second dispatch. A control action that discards the turn after the claim abandons stages 4–5 and lists the effect for reconciliation.
- **FR-EXT-18 (M).** Each write-capable provider shall declare whether it **deduplicates dispatch by idempotency key**. The provider idempotency key is the outbox row ID, stable across re-sends. If the provider deduplicates, a re-send after a crash or ambiguous result is safe. If it does not, a claimed row with no recorded outcome shall move to `unknown` and be listed for reconciliation; it shall **never be re-sent automatically**.
- **FR-EXT-19 (M).** **Staged-turn visibility and revisions.** Each stage that commits story truth increments the timeline revision exactly once: **intent** (+1), **outcome** (+1, together with any conditional State effects it settles, FR-STATE-14), and **completion** (+1, the outcome step). The claim and the stored response do not change story truth and do not increment it. The story's in-flight turn slot (FR-CONC-5) is held from intent until completion, so no other turn interleaves; the staged turn's own stage commits are not conflicts with itself. While incomplete: history reads return the turn marked `incomplete` with its committed beats (the action as an attempt), filtered for the output viewpoint, and no finished response; a **fork** that includes the incomplete turn copies its committed stages and closes the turn in the fork with a deterministic "outcome not known in this story" completion, holding the effect only as a non-executable record (FR-EXT-13) and listing it in the fork response; a truncation or swap that discards it abandons the remaining stages (FR-EXT-17).
- **FR-EXT-20 (M).** **Post-effect values.** Each write-capable provider shall declare whether its confirmation returns **authoritative resulting values** (e.g., the balance after the purchase). If it does, the confirmation records a new pinned version of each affected value (provenance `confirmation`), and the outcome step verifies against it ("you have 250 left" is supported). If it does not, success establishes only that the effect happened (the delta), not the exact resulting value: the engine may perform one recorded **post-effect read** before the outcome step and pin it as the new version; if neither is available, the exact resulting value is `unknown` for narration (FR-EXT-11) — the outcome may say "you paid 50" but not "you have 250 left." The engine shall never compute a resulting external value by applying the delta to the pre-effect read.
- **FR-EXT-21 (M).** **Late settlement.** An outcome that arrives after its requesting turn has closed — from an asynchronous provider, from the consumer through ingest, or after a synchronous wait exceeded its budget — shall be handled with separate coordinates: (a) the **requesting operation**, kept as a link only; (b) the **outcome record**, a real-world fact in the input/audit category attached to the outbox row, which no rewind, fork, swap, or regeneration removes — the only exceptions are **destructive deletion**: erasure (FR-ADMIN-2) removes or redacts outcome records and outbox rows that reference the erased subject, together with their reconciliation listings — except that the listing of a claimed or `unknown` effect (FR-EXT-14) is kept, redacted to its row ID, provider, and status, until it is reconciled — leaving only identifiers and scope in the erasure ledger (FR-ADMIN-7); and whole-story deletion removes them with the story; (c) the **settlement position**, the narrative position at which its in-story consequences are introduced — the next **inter-turn slot** after the last completed turn when it arrives (FR-STORE-31), as a settlement operation. If an ordinary turn is generating when it arrives, the settlement commits at the slot before that turn, the settlement's commit advances the timeline revision, and the in-flight turn rebases or regenerates under FR-CONC-4 if its read set is touched; if a staged turn is incomplete, the settlement waits for it to complete and is positioned after it; (d) the **effective valid-time**, the story-time at the settlement position — the **clock value immediately before the settlement slot commits**, i.e. the last completed turn's end time plus every advance made by earlier inter-turn slots after it (a `14⁺1` State API advance from 11:00 to 12:00 puts a `14⁺2` settlement at 12:00); settlements themselves do not advance the clock — never backdated (an author may backdate only through an amendment, FR-REWRITE); and (e) **knowledge arrival**, the exposures at the settlement position for whoever perceives it (the player through the next response; other characters by perception). **Automatic settlement requires an active origin:** it is allowed only while the requesting operation is an active member of the current timeline. If the request was discarded (rewind, regeneration, swap away) before the outcome arrived, the outcome is recorded and the effect is listed as `confirmed_discarded_origin` for reconciliation; no consequence is applied to the current continuation unless the author or consumer explicitly chooses **settle now** (re-verified at that moment, applied at the next inter-turn slot) or **compensate**. For an active origin, at settlement the engine shall **re-verify** the conditional effects' preconditions against the current state (FR-STATE-11): if they hold, the effects commit at the settlement position and are surfaced in the next response; if not — the sword was declared sold out in an intervening turn — nothing is committed in the story and the effect is listed as `settlement_conflict` in the reconciliation status together with its confirmed external outcome. Reservations held since intent settle as specified in FR-STATE-14. Views and checkpoints through any position before the settlement never include it; a truncation, swap, or fork that excludes the settlement position drops the in-story settlement but not the outcome record, and the confirmed effect is listed as `confirmed_unsettled` for reconciliation (in the fork's response, for a fork).
- **FR-EXT-22 (M).** **Terminal outcomes and expired holds.** Each outbox row shall have exactly one **settled terminal outcome**. (a) **Duplicates:** a repeated confirmation or failure with the same outcome for the same row is recorded as a duplicate and changes nothing. (b) **Conflicting terminal outcomes** (confirmed after failed, or failed after confirmed): the first terminal outcome recorded remains the settled one; the later conflicting outcome is recorded and listed as `outcome_conflict` for reconciliation and never reverses committed settlements or releases automatically (`unknown` is not terminal and may be followed by either). (c) **Late success after reservation expiry:** a confirmation arriving after its reservation expired and was released shall **not** convert the reservation. The engine re-verifies the resource against current state — availability, ownership, and the action's preconditions (the sword may since have been sold to someone else) — and lists the effect as `late_success_after_expiry` with that result. Settlement then requires an explicit reconciliation action by the author or consumer: **settle now** (applies the transfer at the next inter-turn slot as a late settlement under FR-EXT-21, permitted only if re-verification passes at that moment) or **compensate** (a compensating external effect, e.g. a refund, issued through the normal channels). Nothing in the story changes until one is chosen.
- **FR-EXT-8 (M).** Author directives and amendments shall **not** override the objective value of an externally owned predicate within Epistrel, because the provider is the authority for its domain and an override would desynchronize the two systems. Such a directive shall be refused with an explanation, or routed as a write request if the provider is write-capable (FR-EXT-10).
- **FR-EXT-9 (M).** Providers shall be **read-only by default**. When a turn implies a change to an externally owned value (e.g., "I spend 50 gold" against a game-owned balance), Epistrel shall return the change as a structured **state effect** in the respond response (FR-RESP-7) for the consumer to apply; Epistrel shall not assume it was applied.
- **FR-EXT-10 (M).** A provider may opt in as **write-capable**. Epistrel shall not claim atomicity across systems: the turn and a pending-effect record shall commit together in Epistrel's transaction (transactional outbox); Epistrel then dispatches the effect under the durable lifecycle of FR-EXT-16..18 with an idempotency key, records the provider's confirmation, and exposes any unconfirmed or failed effect through a **reconciliation status** queryable by the consumer, rather than treating it as applied.

### 15.1 Story States (FR-STATE) — Engine Core + Orchestrator

Simple tracked values — gold, health, reputation, a quest flag — stored in Epistrel itself, so most games need no external data store and nothing to keep in sync.

- **FR-STATE-1 (M).** Epistrel shall support **States**: typed, single-value variables belonging to a story. Each State shall declare a **type** (number, boolean, enum, short text), a **scope** (the whole story, or per character — e.g., the player's gold is separate from Jenni's), **constraints** (minimum/maximum, non-negative, allowed values), and a **visibility** (player-visible, e.g., gold; or hidden, e.g., an NPC's trust score).
- **FR-STATE-2 (M).** Every tracked value shall declare an **owner**: `story` (an internal State, held and changed by Epistrel) or `external` (owned by a registered provider, FR-EXT). Both share the same typed declaration and verification semantics; the per-turn read, unavailability, and write policies of FR-EXT apply only to externally owned values.
- **FR-STATE-3 (M).** The State schema shall be declared by the scenario author or consumer. The engine may **propose** a new tracked value (e.g., "track arrows?") for approval, but shall never create one on its own.
- **FR-STATE-4 (M).** Every State change shall be an **event** (State, delta or new value, reason, source ∈ {narrative turn, author directive, consumer API, rule}), and a State's value in any view shall be the fold of its active changes in that view. Rewind, regenerate, fork, swap, and amendments therefore apply to States exactly as they apply to all other story truth (FR-STORE-11, FR-STORE-28): rewinding to message 800 restores the balance as of 800, and each fork has its own.
- **FR-STATE-5 (M).** Narrative changes shall be **declared, not inferred after the fact**: the render emits structured state effects (FR-TURN-11) — e.g., "I spent 500 gold on a sword" → gold −500 with a reason — which the engine validates against the State's constraints and commits in the same transaction as the turn (or, in a turn with external effects, at the stage FR-STATE-14 assigns). Vague narration ("I spent most of my gold") must resolve to a concrete effect before commit, or the turn is repaired.
- **FR-STATE-6 (M).** Player actions are **attempts** that the world resolves. If a declared effect would violate a constraint (buying a 500-gold sword with 300 gold), no State changes and the turn is repaired **in character** (e.g., the shopkeeper says the player is short). The player's statement does not force the change.
- **FR-STATE-7 (S).** "Updated by rules" shall be limited to constraints plus a small set of deterministic triggers (e.g., a value that changes with elapsed story-time, or a derived value recomputed from other States). Epistrel shall not provide a general scripting language.
- **FR-STATE-8 (M).** A State's value is **objective truth, not character knowledge** (same rule as FR-EXT-3). The player sees player-visible States through the consumer's interface; an NPC knows a State's value only through a real acquisition path, and a character's first-person claim about it verifies against their beliefs.
- **FR-STATE-9 (M).** The consumer shall be able to read and set States through the API, subject to idempotency keys and revision checks (FR-CONC). A State set through the API, or by an author directive "from now on," shall be recorded as an operation positioned at the next inter-turn slot after the last completed turn (FR-STORE-31), and follows that position's membership on truncation or swap. Author directives may change story-owned States; they may not change externally owned values (FR-EXT-8).
- **FR-STATE-10 (M).** **Effects require authorization, not just valid bounds.** Each State shall declare which sources may change it (specific characters' renders, the director/world pass, the author, the consumer API, rules) and which event types may justify each direction of change (e.g., gold increases only from a sale, reward, theft, or loot event), with per-effect and per-turn magnitude caps. An effect outside those rules is unpermitted novelty and is repaired (FR-VERIFY-12). A world gain such as "found treasure" is a world fact requiring director/world permission (FR-VERIFY-11) and remains subject to the caps; an amount above a cap is repaired down to the cap, and only the author can grant more, later, through a directive or the State API.
- **FR-STATE-11 (M).** **Action preconditions are distinct from State bounds.** A State's bounds say what values are possible; an action's preconditions say whether the action happened. Preconditions — a counterparty's consent, an item's availability, presence at the right place, ownership — are verified as propositions in their own right. Having enough gold does not establish that the merchant agreed to sell: a purchase requires the merchant's agreement (a beat or decision by the merchant or the world) and the item's availability, in addition to the buyer's funds.
- **FR-STATE-12 (M).** Value moving between parties shall be declared as a **transfer**. When both sides are tracked, a transfer shall balance (configurable per State, e.g., gold conserved between buyer and merchant).
- **FR-STATE-13 (M).** **Completeness is checked in both directions.** The extraction backstop shall compare consequential narrated changes — payments, possession changes, injuries, consumption, movement — against declared effects for State-owned and tracked predicates. A narrated change with no corresponding effect is repaired (add a validated effect or remove the claim); a declared effect on a player-visible State with no narration is flagged and repaired unless the State or effect is marked silent.
- **FR-STATE-14 (M).** **Effects contingent on external actions.** Every State effect in a turn that also requests external effects shall be classified as: **unconditional** (commits at intent); a **reservation** (commits at intent as a hold — the value or item is unavailable for other use but not yet transferred — then converts to the final change on its prerequisite's confirmation or is released on failure); or **conditional** on named external effect(s) (commits only when every prerequisite is confirmed, at the outcome stage). Default for a transfer with one external and one internal side (FR-STATE-12): the internal **incoming** side is conditional (a sword bought with an external payment is granted only on payment confirmation) and the internal **outgoing** side is a reservation (a sword sold for an external payout is held, then handed over on confirmation, or released). On **failure**, conditional effects never commit and reservations are released. On **timeout or `unknown`**, conditional effects stay pending and reservations stay held until the outcome resolves or reconciliation settles it, subject to a per-State `reservation_expiry` (default: none) after which the hold is released and listed for reconciliation. **An expired reservation never converts automatically** (FR-EXT-22). On **partial success** across several external effects, each conditional effect commits or not according to its own prerequisites; succeeded external actions are not compensated automatically (FR-EXT-14), and the outcome step narrates each result. Narration may not assert a conditional effect (possession of the sword) before it commits (FR-EXT-15). The same rules apply when the confirmation arrives asynchronously or from the consumer through ingest; such **late settlements** follow FR-EXT-21 and are never positioned at the requesting turn.

### 15.2 World clock (FR-CLOCK) — Engine Core + Orchestrator

A first-class, built-in tracked value. Models rush: a character mentions a meeting at five, six hours away, and three messages later is leaving for it. The world clock makes story-time an explicit, paced, verifiable quantity, and it is the source of story-time (valid-time) for everything the story records.

- **FR-CLOCK-1 (M).** Every story shall have a **world clock**, created with the story and enabled by default: a built-in, story-owned State (`world_clock`) holding the current story date and time at **minute** resolution. It cannot be deleted; it can only change mode (FR-CLOCK-5) or be switched off by the story's engine profile (FR-PROF-2), which stops it advancing and removes it from prompts and checks until it is switched on again. It shares the State machinery (FR-STATE-4): every advance is an event, its value in any view is the fold of active advances, and rewind, regeneration, swap, fork, and amendments apply to it like any other State.
- **FR-CLOCK-2 (M).** The clock shall be the **source of story-time**: the story-time of every beat and step (FR-STORE-31) is the clock value at that position, and events, exposures, beliefs, and facts take their valid-time from it unless they explicitly state another (a flashback, a recollection, a fact about the past). Relative temporal expressions resolve against it (FR-PROP-9).
- **FR-CLOCK-17 (M).** **Start and end times within a turn.** Each beat has a **start time** and an **end time**, and each step within it (FR-TURN-12; a render may declare steps for timing as well as for belief changes) has a start time. In `sequential` mode a beat starts at the previous beat's end (the first beat at the turn's start); in `simultaneous` mode every beat starts at the turn's start. A beat's steps run in declared order, each starting where the previous one left off. A **time advance** is attached to a step boundary — a declared skip ("twenty minutes later she arrives"), or an explicit narrated time later than the current one ("at 15:10 she starts driving" when the clock reads 15:05) — and moves the start of that step and every later step in the beat; a narrated time earlier than the current one is a contradiction unless marked as a flashback. A beat's end time is its start plus its in-beat advances, or, if it has none, its start plus its pacing increment (FR-CLOCK-6), which is applied at the end of the beat. **Every advance is checked**, including the pacing increment: an end-of-beat pacing increment that would cross a `pending` canon scheduled event, or reach a `possibly_due` point (FR-CLOCK-18), is subject to the same stop rules as a skip (FR-CLOCK-9). Because a pacing increment carries no narrated time, a stop inside it **clamps** the beat's end at the event time without regenerating the beat; later beats of a sequential turn start at the clamped time with the event surfaced to them, and in a simultaneous turn the turn's end is clamped and the event is surfaced to the next turn. Each claim, event, exposure, and belief acquisition takes the start time of the step it belongs to; a durative proposition narrated by a step ("she is driving") holds from that step's start to the next step's start. In `simultaneous` mode each beat's advances move only that beat's own steps, and the turn ends at the **latest** beat end. **Simultaneous cutoff:** because simultaneous beats don't see one another, the due-event check for a simultaneous turn runs **after reconciliation** (FR-MULTI-8) over all beats together, and counts scheduled events created by any beat of the same turn (Jenni's beat establishes her own plan, "I'm leaving at 15:10," while Bobby's beat narrates "they wait fifty minutes"; a world event such as a gate closing would instead need a world/director beat, FR-CLOCK-19). The turn's **cutoff** is the earliest stop any beat's advance would hit. A beat whose only overrun is its pacing increment is clamped at the cutoff; a beat with **narrated** steps, acquisitions, exposures, or State effects after the cutoff is repaired under FR-CLOCK-16 (regenerated to end at or before the cutoff). After repair, no committed step, exposure, acquisition, or effect lies after the cutoff, every beat end is at or before the committed turn end, and the committed turn end equals the cutoff (or the latest beat end, if no stop applies). The turn's end time is the clock value committed for the turn. Example: at 15:05, "At 15:10 she starts driving; twenty minutes later she arrives" → step 1 (start driving) at 15:10, `driving` over [15:10, 15:30), step 2 (arrives) at 15:30, beat end 15:30.
- **FR-CLOCK-3 (M).** The clock's **start** shall be set by the author at story creation (date and time) or left **unanchored**. Internally the clock is always an exact **offset** in minutes from the story's start, advanced by pacing and skips; its **absolute** date and time is an **anchor** that may be complete, partial, or absent. An anchor constrains each component — year, month, day, weekday, time-of-day band, hour, minute — to a known value, an admissible **range**, or unknown ("Saturday morning" fixes the weekday and confines the time to [05:00, 12:00) at the anchoring position; the date stays unknown). Time-of-day bands default to night 00:00–05:00, morning 05:00–12:00, afternoon 12:00–17:00, evening 17:00–21:00, and night 21:00–24:00; an author may declare others (FR-CLOCK-4). Anchors are commitments (FR-COMMIT) positioned where they are established and apply backward and forward by offset: the absolute time at any earlier or later position is the anchor's range shifted by the offset difference, so a range that crosses midnight widens the day and weekday accordingly. Later statements **refine** the anchor ("it's 9:15" narrows the minute); a statement incompatible with the current range is contradicted (FR-CLOCK-10). The engine shall **never pick** a date or minute the story has not established: clock checks that are not decided under every admissible value return `uncertain`, and the clock is reported with its known components and ranges.
- **FR-CLOCK-4 (S).** The clock shall use the Gregorian calendar by default; an author may declare a **custom calendar** (named days and months, day length, year length) and **time-of-day bands** (default: night 00:00–05:00, morning 05:00–12:00, afternoon 12:00–17:00, evening 17:00–21:00, night 21:00–24:00).
- **FR-CLOCK-5 (M).** The clock **mode** shall be configurable per story: `paced` (default — advanced by the pacing rule and validated skips, FR-CLOCK-6..9); `manual` (advanced only by explicit player, author, or consumer skips; no pacing); `external` (owned by a registered provider, e.g. a game engine's clock — read and pinned per turn like any external value, FR-EXT-2; pacing and skips are returned to the consumer as proposed state effects, FR-EXT-9).
- **FR-CLOCK-6 (M).** **Pacing rule.** In `paced` mode, each beat advances the clock deterministically by the **spoken and acted length** of that beat — the words in its `say` and `do` channels, player input included; `think`, `latent`, and state-effect declarations do not count: **fewer than 5 words → 0 minutes; 5–50 words → 1 minute; more than 50 words → 2 minutes.** The thresholds and minutes shall be a per-story table (an author may add bands or change the values). In `sequential` mode beat advances add up; in `simultaneous` mode the turn advances by the **largest** single beat, because the beats happen in the same moment (FR-MULTI-5). Reactive narration contributes through the word count of the render that contains it, not separately. The pacing rule runs in the Engine Core with no model call.
- **FR-CLOCK-7 (M).** **Narrated time skips.** When a beat narrates elapsed time beyond its spoken length ("They watch the rest of the movie in silence"; "the drive takes twenty minutes"; "we talk until the diner closes"), the render shall declare a **time advance** through the state-effects channel (FR-TURN-11) — a duration or target time, with a reason. A declared advance **replaces** that beat's pacing increment. If narration implies elapsed time but declares none, the extraction backstop shall flag it (completeness, FR-STATE-13) and the Orchestrator's **time estimation** purpose (FR-MODEL-2) shall propose a best-guess duration from established context (the movie started at 19:10 and runs about two hours → roughly 90 minutes remain), recorded with its reason. Estimates and declarations are validated by FR-CLOCK-8 and FR-CLOCK-9 before commit.
- **FR-CLOCK-8 (M).** **Skip authority (anti-rushing).** Skips fall into two classes. A **player- or author-initiated** skip is one the player's input or an author directive states or invites — an explicit amount ("skip to the next day") or an activity that implies elapsed time ("I fall asleep on the couch", "I drive to Columbus"). The render carries it through and supplies the plausible duration (declared, or estimated per FR-CLOCK-7) — e.g. narrating the night and what the player wakes up to — and it is **not** limited by the unprompted-skip cap; the consumer may likewise advance the clock through the State API. A **model-initiated** skip — one a character or director render starts on its own — shall be accepted only when it (a) narrates an activity already established in the scene (finishing the movie, the drive already under way), and (b) does not exceed `max_unprompted_skip`. `max_unprompted_skip` shall be **configurable per scenario and overridable per story** (default **24 hours**; `0` disables model-initiated skips entirely). Otherwise the skip is removed and the beat repaired to stay in the present; a longer skip needs the author, who may advance the clock further through a directive or the State API. Every skip, of either class, remains subject to the due-event stop (FR-CLOCK-9). The clock never moves backward along the active timeline; earlier story-time is reached only by explicit flashback narration (which does not move the clock), truncation, or a history rewrite.
- **FR-CLOCK-9 (M).** **Scheduled events.** Time-anchored plans — appointments, deadlines, departures ("my meeting is at five", "the last train leaves at 23:40") — shall be recorded as propositions with a planned time (core predicate `scheduled`, FR-PROP-5). **Source of truth:** schedule statements are handled by two distinct operations (FR-CLOCK-19) — **creating or changing an owned intention**, which writes canon, and **reporting an existing event's schedule**, which is an ordinary claim checked against canon and never writes it. Plans set by the author, narration, the world, or a State are canon as usual; anything else a character believes about a schedule — someone else's plans, or a wrong time for a real event — is a **belief only**. Belief-only appointments shape that character's behavior and context (they may leave at five for a meeting that is really at six — a legitimate false belief) but **never stop the world clock**. **Lifecycle:** each canon scheduled event moves through `pending` → `due` (the clock reaches its planned time) → `surfaced` (presented to the next render) → `completed` | `missed` | `cancelled`, with `rescheduled` returning it to `pending` at a new time; a surfaced event that is neither completed nor cancelled by the time the clock passes its planned time plus `grace` (default 30 minutes) becomes `missed`, recorded as an event that involved characters learn of through normal perception. Transitions are events positioned at the turn that causes them and follow its membership. **Stopping:** with `stop_at_due_events` on (default), an advance that would carry the clock past a `pending` canon event involving a present character or the scene stops at the event's planned time (FR-CLOCK-16); each event stops the clock **at most once** — once surfaced it never blocks advancement again unless rescheduled. With the setting off, the event is surfaced as overdue.
- **FR-CLOCK-10 (M).** **Verification against the clock follows the speech model.** Claims about the current time, the time of day, elapsed time, and the status of scheduled events shall be normalized into propositions and checked by **who makes them** (FR-VERIFY-2, FR-TURN-6): **objective narration** (narrator, director, composition) is checked against the clock; **character speech, thought, and action** are checked for their **belief relation** against that character's time belief (FR-CLOCK-15) and classified by **intent** like any speech act. A sincere statement consistent with the character's time belief is accepted even when objectively wrong (a character with a broken watch says "it's three"); a sincere claim with no supporting time belief is a hallucination and is repaired; a deliberate wrong time or a pretext ("I have to run to my meeting" as an excuse to leave a bad date) is a lie, accepted and recorded as a divergence (FR-VERIFY-10); a joke is accepted as a joke. The anti-rush check is the belief case: a character **acting** on a scheduled event before it is due *by their own time belief* ("I have to head to my meeting" at what they know is 11:20 for what they believe is a 17:00 meeting), or treating time as having passed that they did not perceive pass ("we've been talking for hours" after twenty minutes), is belief-inconsistent with no deceptive intent and is repaired. Approximate speech is tolerated: a stated exact time within `time_statement_tolerance` (default ±15 minutes) of the believed time, and a stated elapsed time within `elapsed_tolerance` (default: a factor of 2) of the perceived elapsed time, are consistent. A character may still leave early for an established or permitted reason (FR-VERIFY-11).
- **FR-CLOCK-11 (M).** **Steering before checking, without leaking the clock.** The objective clock, every canon scheduled event, and the scene's elapsed time shall be available to orchestration, director passes, and verification. A **character's** generation context shall contain only time information that character can know: their time belief (FR-CLOCK-15), the elapsed time they perceived in the scene, and the scheduled events they hold (their own plans and any they were told), with time remaining as they believe it ("your meeting: 17:00, about 5½ hours from now"). A character's context never receives the objective clock when it differs from the character's time belief.
- **FR-CLOCK-12 (M).** Every clock advance shall be recorded as a State change with its **source** (`pacing`, `declared_skip`, `estimate`, `player`, `author`, `consumer`, `external`), the beat or step it belongs to, and — for estimates — the estimate and its reason. Replay and reconstruction use the recorded advances and never re-estimate; regenerating a turn recomputes its advances with the new content.
- **FR-CLOCK-13 (M).** The respond response shall return the clock **before and after** the turn, and the State API shall read the clock and, advance or set it forward (which callers may do so is the consumer's decision, FR-AUTH-1); setting it backward is rejected (use truncation or a rewrite). Out-of-character messages, rewrite side-channel conversations, previews, and rejected renders never advance the clock.
- **FR-CLOCK-14 (S).** A story has **one** world clock. In `queue` stories with several concurrently active scenes (FR-CONC-5), every committed turn advances the shared clock in commit order; independent per-scene local clocks are out of scope for this version.
- **FR-CLOCK-15 (M).** **Characters' time sense.** Each story shall set `time_awareness` ∈ {`exact` (default — the modern case: phones and clocks), `approximate` (the time-of-day band and the hour within ±1 hour — period and fantasy settings), `none` (no time sense beyond what the character perceives, e.g. held in a windowless cell)}. A character's **time belief** is derived from that default unless an explicit belief overrides it, formed through the normal acquisition operations (FR-EPI-7): an observation (a stopped or wrong watch, the sun going down), testimony (being told the wrong time), or a gap in perception (unconscious, asleep, or otherwise not perceiving while the clock advanced — the character perceives no elapsed time for that span and must infer or be told). Perceived elapsed time accrues only while the character is present and conscious. Under `none` and `approximate`, a hedged guess ("must be around noon") is accepted as a low-confidence belief, never promoted to fact.
- **FR-CLOCK-16 (M).** **An interrupted skip interrupts its consequences.** When a due-event stop shortens an advance, everything the beat placed after the cutoff is invalid: the beat shall be repaired by regeneration under the constraint that time stops at the event (FR-REPAIR), so its narration ends at or leads into the interruption ("…you're woken at six by a knock — the delivery"). Narration, completed actions, State effects, exposures, and belief acquisitions that the original version placed after the cutoff are never committed — the stop is applied before commit, and only the repaired version's effects and exposures are recorded. A skip requested by the player's input ("we talk until six") is resolved like any player attempt: the input is recorded as stated, and the world's response narrates the interruption at the cutoff. A stopped advance is recorded with source and the event that stopped it.
- **FR-CLOCK-18 (M).** **Scheduled events on a partially anchored clock.** Whether a scheduled event is due depends on the anchor. An event is `due` only when it is due under every admissible reading. With the current time known only as an admissible range `[lo, hi)`, an event at time E is **`possibly_due`** while `lo < E < hi` (some readings have reached it, others have not) and `due` once `lo ≥ E`. It therefore enters **`possibly_due`** — a status distinct from `due` — at the first offset at which the range's **upper** end passes E (immediately, if the anchor is established with E already inside the range), and becomes certainly due at the first offset at which the range's **lower** end reaches E. `possibly_due` is a **pause for anchor refinement, not an interruption**: (a) with `stop_at_due_events` on, an advance stops at that moment, but nothing narrates the event as due; instead the next render is steered to **establish the current time** (a character checks a phone, a clock tower strikes), refining the anchor; (b) the pause does **not** count as the event's one permitted stop (FR-CLOCK-9), and it happens at most **once per anchor state** — if the next turns don't refine the anchor, later advances proceed and the event stays `possibly_due`; a new refinement that still leaves it ambiguous may pause again. **Resolution:** when refinement shows the event is **still in the future**, it returns to `pending` (and may later stop the clock once, factually, when it is actually due); when it shows the event is **due now**, it becomes `due` → `surfaced` (its one factual stop); when it shows the event is **already past**, it is surfaced as **overdue**, and becomes `missed` if past its grace period. If the clock advances, without any refinement, to the offset at which the range's lower end reaches E, the event is certainly due: with `stop_at_due_events` on, the advance stops there as the event's one factual stop and the event is surfaced as `due`; later, it becomes `missed` once the lower end passes E plus its grace period. The engine never narrates or treats a `possibly_due` event as due.
- **FR-CLOCK-19 (M).** **Creating a plan vs reporting a schedule.** A character's sincere schedule statement shall be classified, using entity resolution on the event mentioned (FR-PROP-6), as one of: (a) **create intention** — the statement introduces a plan that resolves to no existing canon event and that the character owns (their own errand, their own departure): it is committed as a canon `scheduled` event **owned** by that character; (b) **change intention** — the event's **owner** explicitly changes it ("I moved my meeting to six", "let's push dinner to eight", or a declared `plan_change` in the turn structure): the canon event is rescheduled; only the owner, the author, or the world may change an event — an event created by someone else, or set by the author, is not changed by a participant's statement; (c) **report schedule** — any other statement about an existing event's time ("my meeting is at five" when canon already has the meeting): an ordinary claim, checked for its objective relation against canon and its belief relation against the speaker's beliefs (FR-TURN-6, FR-CLOCK-10), which **never creates or reschedules** canon. A bare statement of a time for an existing event is always a report, even from its owner; only explicit change language or a declared change is a change. A sincere report that differs from canon is a sincere error if the speaker holds that belief through a legitimate antecedent (she was told five), and a hallucination to repair if not. Ownership defaults to the creator of the event (the character who created it, or the author/world for events they set) and may be declared shared.

## 16. Multi-character composition (FR-MULTI) — Orchestrator

- **FR-MULTI-1 (M).** For multiple responding characters, each shall be rendered against their own viewpoint, with no cross-contamination of another character's private `think`.
- **FR-MULTI-2 (M).** Each character's render shall be verified against their own beliefs and the relevant external authorities.
- **FR-MULTI-3 (M).** Concurrent `latent`/commitment effects shall be reconciled against one shared timeline before composition; contradictory concurrent commitments shall be resolved under the commitment rules and authority hierarchy.
- **FR-MULTI-4 (M).** The individual responses shall be composed into one returned message (FR-RESP-5), returned both as a composed narrative and as an **ordered list of beats** with attribution (character, channel, content, beat index), **both after output-viewpoint filtering** (FR-RESP-12,13); envelope-only beats carry their envelope in place of content.
- **FR-MULTI-5 (M).** A multi-character turn shall run in an **interaction mode** ∈ {`sequential`, `simultaneous`}, set per story and overridable per request. Default: `sequential`.
  - `sequential` — an ordered sequence of observable micro-events. Characters act in order, and each primary character renders seeing the observable output (envelope and perceived content, FR-TURN-2) of the beats before it. A later character can respond to an earlier one, and physical conflicts resolve by causality: a later render sees the outcome of earlier actions (if Bobby has already pocketed the key, Jenni's attempt to lock it away fails).
  - `simultaneous` — reactions to the same moment. All primary characters render against the same starting state and none sees another's reaction from this turn. Conflicts are resolved by adjudication (FR-MULTI-8).
- **FR-MULTI-6 (M).** Order in `sequential` mode shall default to the order of CharacterIDs in the request, with a per-story or per-request option to let a director pass choose the order (who would naturally act first).
- **FR-MULTI-7 (M).** Each character shall have a **participation role** for the turn ∈ {`primary`, `reactive`, `silent`}. Roles default per story, may be set per character (e.g., a main NPC always `primary`; background characters only ever `reactive`), and may be overridden per request. Characters named in the request are `primary`; other present characters default to `reactive`-eligible. A per-character role is either a **default**, which the engine may change for a turn (escalation, FR-MULTI-10; budget planning, NFR-PERF-7), or **fixed** — a bound the engine never crosses on its own: escalation never raises a fixed `reactive` or `silent` character, and budget planning never lowers a fixed `primary` character to reactive narration (it defers it instead). Only the request changes a fixed role, for that request: by naming the character as a responder or by overriding its role.
  - `primary` — a full render (`say`/`think`/`do`/`latent`/state effects) against the character's own viewpoint, verified against their own beliefs.
  - `reactive` — no render of their own; brief visible reactions are narrated within a primary character's render or a narrator line.
  - `silent` — present but not reacting this turn.
- **FR-MULTI-8 (M).** In `simultaneous` mode, conflicting actions or state effects on the same object or State shall be **detected deterministically** and resolved by a per-story tie-break ∈ {request order, a designated State such as initiative, director judgment via the model}. Default: request order. The losing action is an **attempt** and is repaired in character (cf. FR-STATE-6).
- **FR-MULTI-9 (M).** Reactive narration shall be **attributed and observable only**: it is recorded as the reacting character's `do` (flagged as narrated by another render) and shall never write that character's `think`, `latent`, or beliefs. It shall respect the reactor's viewpoint — the reactor must have perceived the trigger (FR-TURN-9) and the reaction must not imply knowledge they lack (FR-EPI-4). By default reactive narration is **non-verbal only**; a per-story option may allow **brief interjections**, which are still checked against the reactor's viewpoint. The reactor's beliefs from what they witnessed form through ordinary exposure records (FR-BELIEF-5), so being reactive costs them no memory.
- **FR-MULTI-10 (M).** A reactive character whose reaction would require real speech (beyond an allowed brief interjection), a decision, a hidden-fact commitment, or a State change shall be **escalated to a primary render** within the turn's budget, rather than having it narrated secondhand. **When escalation is unavailable** — the character's role is fixed (FR-MULTI-7), or the budget cannot fit another primary render plus its safety reservation (NFR-PERF-6) — the reaction is limited to what reactive narration allows (non-verbal, or an allowed interjection; nothing for a fixed `silent` character), and nothing more happens for that character this turn: no further speech, no decision, no hidden-fact commitment, and no State change, and no other render may narrate one on their behalf (verification repairs a render that does, FR-MULTI-9). Undetermined values stay open. The response lists the character in `escalation_deferred` with the reason (`fixed_role` or `budget`), so the consumer can bring them in on a later turn; it is not an error.
- **FR-MULTI-11 (M).** In `sequential` mode each beat shall be **verified before the next character renders**, so later characters build only on verified events; a beat that fails verification is repaired or regenerated on its own without invalidating earlier beats. **Verified staged beats are available as antecedents to later beats in the same turn** (FR-EPI-14) before database commit; a beat that is regenerated replaces its staged version, and later beats are rendered only against the verified version. In `simultaneous` mode no character's same-turn output is available to another, so no cross-character same-turn antecedents exist. If the turn is abandoned or fails to commit, every belief formed from its staged beats is discarded with it. All beats of an ordinary turn commit together as **one turn** (one operation, FR-STORE-24) with a beat index for their order; in a staged turn the beats of each stage commit together, and the outcome step's beats commit at the completion stage under the same operation; regenerating the message regenerates all of its beats.

## 17. APIs (FR-API)

- **FR-API-1 (M).** A REST API with an OpenAPI schema covering the respond contract, lower-level operations, admin, external-provider registration, and model-config endpoints. Operator endpoints are served under `/admin` (FR-AUTH-1).
- **FR-API-2 (M).** **No MCP server.** Epistrel exposes REST and the in-process library only. A consumer that wants to give its users, or their own models, MCP access — for example, to create characters or browse public entries — builds its own MCP server over the REST API, with its own authorization (for example, OAuth). Epistrel remains an MCP **client** of external-data providers (FR-EXT-1).
- **FR-API-3 (M).** An in-process library exposing the same contract.
- **FR-API-4 (M).** All external inputs shall be validated against typed schemas at the boundary.
- **FR-API-5 (M).** External-provider tool descriptions (including MCP tools) and tool-sourced content shall be treated as untrusted (injection surface).
- **FR-API-6 (M).** **Catalog and story-creation endpoints:** characters — create draft, list and search (text, labels, content rating, listing status, owner, relation), get (latest or a version; `card` or `full` projection, FR-SCN-10), update draft (with draft revision), publish (alone, or together with the companion draft, FR-CAT-10), archive, delete, list versions, set listing status (FR-CAT-11), promote from a story (FR-CAT-8); scenarios — the same set plus **validate** (dry run, FR-SCN-5) and get-companion for a character; media — upload, get metadata, get content, delete; personas — create, list (by owner), get, update, delete (FR-CAT-6); stories — **create from scenario** (FR-SCN-6), create blank, and the existing story lifecycle; engine profiles — create, list, get (latest or a version), update (new version), copy, validate, delete (FR-PROF); per story — assign profile, set overrides, get effective configuration, impact preview, backfill start/progress/cancel, and conflict resolution (FR-PROF-7..10); **ownership** — for every owned type, transfer the owner and add or remove relations (FR-AUTH-5,6); **principals** — lookup, and under `/admin` offboarding: dry run, start, progress, and report (FR-AUTH-7); **content ratings** — under `/admin` create, list, get (with effective guardrails and their sources), update (new version), and retire (FR-RATE-1,2); per story — change the rating, with progress and result for a tightening check (FR-RATE-6,7); per catalog entry — rating suggestion (FR-RATE-8); **images** — generate candidate images for a catalog entry and attach a candidate to its draft (FR-IMG-7), build an image prompt without generating (FR-IMG-2), request or upload a story image at a position, audience viewpoint, and optional camera POV (uploads and consumer prompts declare depicted subjects, FR-IMG-9), delete a story image, read and cancel image jobs (FR-IMG-3..6), and list and preview a catalog job's candidates (FR-IMG-7); **operations** — read an operation's status and stages by ID (FR-EXT-16); **media delivery** — byte-range reads, signed URLs, and resumable uploads (FR-MEDIA-3); **message feedback** — rate, re-rate, retract, read aggregates and review lists, and, under `/admin`, export (FR-FB). Profile-affecting mutations and offboarding accept `ignore_warnings` (FR-PROF-7). All are idempotent where they mutate (FR-CONC-6) and available over REST and the in-process library. Each endpoint ships with the capability it serves (§22).

### 17.1 Trust boundary, attribution, and ownership (FR-AUTH)

Epistrel is a backend component. The consumer authenticates **and authorizes** its own users and decides who may call which operation, act as which character, see which catalog entries, and request which viewpoint. Epistrel authenticates only the calling service, records who the consumer says is acting and who owns what, and guarantees what a given viewpoint receives. It holds no user roles, grants, groups, or permissions.

- **FR-AUTH-1 (M).** **Service authentication only.** Every REST call shall carry a service credential; a call without a valid credential is rejected without side effects. A deployment may hold several credentials (for rotation); all are equivalent. The in-process library needs none. Epistrel shall hold no user roles, grants, groups, or permissions and shall perform no per-user authorization: which end user may call which operation, act as which character, see which catalog entries, or request which output viewpoint is decided by the consumer before it calls. **Operator endpoints** — model and provider configuration, global policies, content-rating definitions, and deployment settings, erasure, retention, story export and import (FR-STORE-7), the low-level mutation calls (`commit_fact`, `mutate`, `record_utterance`, and similar), principal offboarding (FR-AUTH-7), and feedback export (FR-FB-4) — are served under a separate `/admin` path prefix so a deployment can restrict them at its network edge; Epistrel itself treats them like any other call.
- **FR-AUTH-2 (M).** **Trust boundary.** Epistrel shall be deployed behind the consumer and never exposed directly to end users, and its documentation shall say so. Its privacy guarantees are stated relative to the request and the story's profile: where perception is enabled, output produced for a viewpoint contains only what that viewpoint perceived (FR-RESP-12,13, NFR-PRIV-1,4); with perception `none`, only `think` and `latent` content is withheld. Epistrel does not verify that the consumer was entitled to request that viewpoint. Documentation and product claims shall state the guarantee in that form and shall not claim that Epistrel by itself prevents a player from reaching another character's secrets.
- **FR-AUTH-3 (M).** **Authority comes from the operation, not the caller.** What a call means is fixed by which operation it is and by the story's rules, never by who sent it: a directive is author canon because it arrives through the directive operation (FR-DIRECT); history rewrites, story configuration, and the low-level mutation calls are what they are whoever sends them; respond and ingest input is the in-world speech or action of the named **actor character**. For every respond or ingest call: (a) the **actor character** may be any character of the story — who may act as whom is the consumer's decision — and is the only character whose speech or action the input supplies; input for a player's own character is that player's authoritative speech or action (FR-EPI-12), while input for a character the platform plays is supplied on its behalf and checked against its viewpoint like its own render (FR-VERIFY-11); (b) the **render characters** must be characters the story lets the actor's scene trigger (default: modeled NPCs co-located with the actor's character, or named by the scene), and triggering a render grants no right to supply those characters' speech, actions, thoughts, or decisions — except narration permitted under `player_authority = co_author`, still verified against their viewpoints (FR-RESP-11) — while their private state is used only inside the Orchestrator; (c) the **output viewpoint** follows FR-RESP-12. A request whose actor is not a character of the story, or that names a render character the story does not permit, is rejected without side effects.
- **FR-AUTH-4 (M).** **Attribution.** Every mutating call shall carry a **requesting principal** — an opaque identifier from the consumer's identity system that Epistrel stores but never validates, resolves, or interprets — and Epistrel shall record it on the operation and its events (background workers record `system`). It serves audit and attributes input in multi-player stories; it is never an input to generation, verification, or any story-truth decision, so the same request under a different principal produces the same story. It keys only what is per principal by definition: a principal's rating of a message (FR-FB-1) and the default owner of what it creates (FR-AUTH-5). Documentation shall recommend opaque principal IDs rather than names or email addresses, so recorded attribution identifies no one without the consumer's own records.
- **FR-AUTH-5 (M).** **Ownership.** Every story, catalog character, scenario, persona, media asset, and engine profile shall have exactly one **owner** principal, set at creation (default: the requesting principal; a creation request may name another) and changed only by an explicit **transfer** or by offboarding (FR-AUTH-7). Every change is recorded with the acting principal and time. A companion scenario always has its character's owner and is transferred with it. Presets shipped with Epistrel are owned by `system`. Ownership confers no permission inside Epistrel; it exists for listing, attribution, and offboarding.
- **FR-AUTH-6 (M).** **Relations.** Each of those entities may carry any number of **relations** — (principal, relation name) pairs with consumer-defined names such as `editor`, `co_author`, or `player` — added and removed through the API with the acting principal recorded, and usable as list filters. Epistrel never interprets a relation name. Story creation records each player slot's principal as a `player` relation on the story (FR-SCN-6), so principal lookup finds shared stories.
- **FR-AUTH-7 (M).** **Principal lookup and offboarding** — for example, when the consumer deletes a user account.
  - **Lookup.** Epistrel shall list every entity linked to a principal, by type — stories, catalog characters (with their companions), scenarios, personas, media assets, engine profiles — separated into **owned** and **related** (with relation names), with counts and pagination.
  - **Per-type actions.** One offboarding operation applies an action to the principal's owned entities, chosen separately for each type: `delete`, `transfer` (to a named principal), or `keep` for stories, characters, scenarios, personas, media assets, and engine profiles; and `remove` or `keep` for relations naming the principal on entities it does not own. A type not named is kept. Example: delete every story and persona, and transfer characters, scenarios, and media to a curator principal.
  - **Type rules.** A character's companion scenario follows the character's action, never the scenarios action. Media referenced by a catalog entry that is transferred are transferred with it, to the same new owner, whatever the media action. Deletion uses each type's normal deletion: whole-story deletion (FR-STORE-16), which removes the story for every participant; catalog deletion, which never alters existing stories (FR-CAT-9); persona deletion, which leaves stories created with the persona unchanged (FR-CAT-6); and media and engine-profile deletion, which retire an item that something still references (FR-MEDIA-2, FR-PROF-1).
  - **Warnings, never blocks.** A dry run returns per-type counts and warnings: stories to be deleted that have other principals related to them (another player in a shared story); engine profiles to be deleted that other owners' stories use; media to be deleted that other owners' entries reference. Execution follows the two-stage flow of FR-PROF-7: a request whose dry run has warnings returns them and changes nothing unless it carries `ignore_warnings`.
  - **Execution.** Offboarding runs as a background job under an idempotency key. Each entity's change is atomic; the job is resumable and safe to repeat; entities created for the principal after the job starts are not included. Progress is readable, and the final report lists every entity deleted, transferred, or kept, and anything still owned by or related to the principal.
  - **Not erasure.** Offboarding leaves the principal ID recorded as attribution on events in stories it did not own (FR-AUTH-4). Removing a person's content from other principals' stories is erasure of their persona as a subject (FR-ADMIN-2), requested separately.
- **FR-AUTH-8 (M).** **Nothing gates on ownership, relations, labels, or listing status.** Any catalog entry can be read in either projection (FR-SCN-10), and any published, unarchived entry can be used to create a story, whoever owns it and whatever its listing status (FR-CAT-11). Filtering by owner, relation, label, or listing status happens only when a request asks for it. Restricting access is the consumer's job.

## 18. Administration & lifecycle (FR-ADMIN)

- **FR-ADMIN-1 (M).** Story lifecycle (create, archive, delete), including the characters defined inside a story. Catalog entries and stories created from scenarios have their own lifecycle requirements (FR-CAT-3,9, FR-SCN-1,6).
- **FR-ADMIN-2 (M).** Right-to-be-forgotten: complete, verifiable erasure of a subject's data within the **supported erasure boundary** (FR-ADMIN-6..8) across events, projections, memories, beliefs, States, audit records, stored idempotency results, outbox rows, and vectors, within each affected story. It is destructive (distinct from non-destructive in-story truncation via timeline membership, §2.1) and forfeits reconstruction of in-story timelines involving the erased subject. An erasure request names its subject and its scope: one story (including its story images), or the catalog and media (catalog characters, scenarios, personas, and media assets, FR-ADMIN-6). Because stories are self-contained (FR-STORE-14), a story-scoped erasure never reaches across stories; a subject present in several stories or forks must be erased in each.
- **FR-ADMIN-3 (M).** Projection rebuild on demand.
- **FR-ADMIN-4 (M).** Snapshot/restore and rewind/branch (per FR-STORE-6). A story **snapshot** is a story bundle, and **restoring** one imports it as a new story (FR-STORE-7). Deployment-level backup and restore is a documented operator procedure rather than an API operation: a database dump plus the media store, with the erasure ledger kept outside the backup and reapplied before any restored story is served (FR-ADMIN-7).
- **FR-ADMIN-5 (S).** A story-inspection/debug interface (a character's belief set, divergences, the promissory ledger, snapshotted external facts), served only as omniscient reads (FR-RESP-12); which callers may use it is the consumer's decision (FR-AUTH-1).
- **FR-ADMIN-6 (M).** **Subject-reference indexing** shall be maintained at write time — including catalog entries and media assets (FR-CAT, FR-SCN, FR-MEDIA), so erasure reaches a subject's catalog characters, scenario seeds, and images as well as stories — every record and every derived text (reflections, summaries, rendered messages, rejected renders) shall index the entities it references, and every image indexes its depicted subjects and the subjects named in its prompt, caption, or alt text (FR-IMG-9) — so erasure can locate subject references in prose as well as in structured records. Derived text referencing an erased subject shall be **redacted or regenerated** without the subject; rebuildable state (projections, caches) shall be rebuilt.
- **FR-ADMIN-7 (M).** Erasures shall be recorded in an **erasure ledger** (subject identifiers and scope, without the erased content). The ledger shall be stored **outside** the backups it governs (and also copied into every backup), so restoring a backup that predates an erasure still finds it; a restored story shall not be served until the ledger has been reapplied. **Recovery and audit:** backup verification, point-in-time recovery, and audit tooling shall treat erasure markers as expected gaps, not corruption; the as-originally-recorded and audit views show the marker (identifiers and scope, never content) where erased records were; and operators are told, in backup and recovery documentation, that restore + ledger reapplication reproduces the post-erasure state, not the pre-erasure one.
- **FR-ADMIN-9 (M).** **No resurrection by in-flight work.** Erasure shall act as a control action on the story: it bumps the timeline revision, so every in-flight turn, rewrite, consolidation job, and outbox dispatch whose base revision predates it fails revalidation and is abandoned (FR-CONC-4). In addition, every write path — turns, workers, dispatch, ingest, imports — shall check the erasure ledger before committing and refuse content referencing an erased subject, so a generation context built before the erasure can never write that content back.
- **FR-ADMIN-8 (M).** The documentation and API shall state the erasure boundary explicitly. **Out of scope:** exports already delivered to the consumer; data retained by external model, image, or data providers — including what a hosted `guardrail check` or `image check` provider keeps of the prompts, images, and true ages it was sent (FR-IMG-13); and subjects who appear in an image only visually, with no declared or named reference — Epistrel does not recognize people in pixels (FR-IMG-9). Epistrel's own operational logs shall not contain story content by default (NFR-SEC-4).

### 18.1 Character catalog (FR-CAT) — Engine Core store + API

A library of reusable **starting points** for characters, outside any story. The catalog never participates in a running story: a story is created from **snapshots** of catalog entries (FR-SCN-9), so stories stay self-contained and nothing in the core engine or Orchestrator depends on the catalog at runtime.

- **FR-CAT-1 (M).** Epistrel shall store reusable characters in a **character catalog** (`character_catalog` and its version table), separate from story data. Catalog entries are created and managed through dedicated endpoints (FR-API-6) and are never read by a running story.
- **FR-CAT-2 (M).** A catalog character defines **who someone is**, not what is true in any particular world. It shall carry:
  - **Public card** — what the `card` projection returns for search, browsing, and story setup (FR-SCN-10): **name**, a **public description** (free text, never seeded into a story), and **images** (FR-CAT-4).
  - **Private character definition** — seeded into every story the character joins, and returned otherwise only in the `full` projection (FR-SCN-10): **true age** (FR-CAT-12); **appearance**; **personality and temperament**; **likes and dislikes**; **behavioral dispositions** — how they respond to being threatened or challenged, dominant or submissive, honest or deceitful, warm or cold, cautious or reckless, and similar axes, each as a setting plus free-text nuance; **values and motivations** in general terms; **interaction style** (speech style, mannerisms, vocabulary, sample dialogue); and optional free-text **background flavor**.
  - **Metadata** — aliases; **labels** that describe the character (`bubbly`, `chatty`, `quiet`, `nervous`, `dominant`, `submissive`, and the like) and the **content rating** (required to publish, FR-RATE-3), both used for search and filtering, returned with the public card, and never seeded; the owner and relations (FR-AUTH-5,6); the **listing status** (FR-CAT-11); and the version **status** ∈ {`draft`, `published`, `archived`}.
  A character carries no world truths of its own. Truths about a character's world — an affair known only to her, a sister, a past career — belong to a **scenario**, normally the character's companion scenario (FR-CAT-5). If an author nevertheless writes world facts into a character's fields, they are seeded at the **lowest precedence** and any scenario fact overrides them (FR-SCN-7).
- **FR-CAT-3 (M).** **Versioning.** Drafts are editable; **publishing** creates an immutable, numbered version. Stories record the exact `catalog_id@version` they were created from. Editing a published character means publishing a new version; existing stories are never changed by it (FR-SCN-9). Every catalog entry has at most one **draft**, protected by optimistic concurrency: each save and each publish carries the draft revision it was based on, and a stale revision is rejected with a conflict rather than overwriting another editor's changes.
- **FR-CAT-4 (M).** **Images and visual identity.** A character **may** have a **primary image** and a gallery; images are optional, so text-only and accessibility-focused deployments need none. A deployment setting `require_primary_image` (default off) makes a primary image required to publish, for visual products. Every image stores its **generation metadata** — adapter, model, prompt, negative prompt, seed, parameters, and reference-image IDs — whether Epistrel generated it (FR-IMG) or the consumer uploaded it. A character may also carry a **visual identity**, versioned with the character: the preferred image model, a **base appearance prompt** (drafted from the character's appearance, editable), a negative prompt, a **seed**, **reference images**, and adapter-specific parameters kept opaque (a character-specific model add-on, for example). Every reference image and add-on declares an **audience** — `perceivable` (only what anyone who meets the character can see) or `restricted` (hidden details, a true form, the real face behind a disguise) — with no default: one saved without an audience is rejected. The base appearance prompt is always `perceivable`; restricted details go in a separate, optional restricted-details prompt. Epistrel's generation uses it (FR-IMG-2), and consumers that generate images themselves read it. It keeps new images as consistent as the image model allows: a seed reproduces one picture for the same prompt and model, while consistency across poses and outfits comes mainly from reference images.
- **FR-CAT-5 (M).** **Companion scenario.** Creating a catalog character shall automatically create its **companion scenario**: a scenario with exactly one NPC slot, **locked** to that character, plus one player slot — the "just talk to this character" starting point. The companion scenario is where the character's **default world** lives: their backstory facts, relationships, secrets, and starting situation (Linda's affair, known only to her, would be seeded here). That world belongs to the companion scenario only; when the character is used in any other scenario, **the companion scenario is not brought in** — only the character definition is. The companion scenario's slots cannot be changed or added to; its other fields are editable like any scenario's. Its versioning follows FR-CAT-10; archiving or deleting the character archives or deletes its companion scenario in the same transaction.
- **FR-CAT-6 (M).** **Player personas are not catalog characters.** A catalog character is never a player's own character — a consumer may still send input for one as a respond actor, and that input is checked like the character's own render (FR-AUTH-3). A player plays a **persona**: a **name**, **gender**, **age** (the persona's true age, FR-CAT-12), and a **short description** (personality, and optionally appearance) that the player asserts they will play as. Personas may be saved per principal for reuse or created ad hoc at story creation; they are owned by their principal (FR-AUTH-5) and are not catalog entries. A story holds a snapshot of the persona it was created with, so editing or deleting a saved persona never changes a story. The scenario fixes which role the player fills. At genesis the persona is seeded like any other knowledge, by audience (FR-SCN-8):
  - **Perceivable** to anyone who meets the player: gender, visible appearance from the description, and an **apparent age band** ("a man in his twenties") — never the exact age. Characters may draw ordinary inferences from what they perceive (a twenty-something walking the halls of a retirement home is probably visiting someone, not moving in).
  - **Known to acquaintances** — the characters the player role's relationships make family, friends, coworkers, or acquaintances: the name, the exact age, and the personality description, seeded as those characters' **beliefs** about the player (a sibling knows Sam has a short fuse and may handle him gently). Because they are beliefs, the player's actual behavior in the story can revise them through the normal belief operations.
  - Strangers learn the name and personality only through play — by being told, or by observing and inferring.
  The player keeps no engine-held interiority (FR-EPI-12); the persona's description is also given to the orchestration as guidance for narrating the player character consistently. The description is **player-provided and never objective canon**: it creates no canon facts — only the perceptions and acquaintances' beliefs above and narration guidance — so what the player actually does in the story revises those beliefs instead of contradicting canon. The persona's name and true age are the only exceptions: the name is the player character's canonical name, and the true age is engine-held canon for age-conditioned guardrails (FR-CAT-12).
- **FR-CAT-7 (M).** **Ad-hoc characters** created inside a story (by narration, the director, or the author) are story-scoped and are **not** added to the catalog. Each has a true age from creation (FR-CAT-12).
- **FR-CAT-8 (S).** **Promote to catalog.** An author may promote a story character to a new **draft** catalog entry. Only character-definition fields (true age as of the promotion's story time, appearance, personality and dispositions, likes and dislikes, interaction style, images) are copied; story facts and memories are never copied into the character, but the author may choose to seed selected ones into the new character's companion scenario.
- **FR-CAT-9 (M).** Archiving or deleting a catalog entry, or changing its owner or listing status, never alters existing stories; they keep their snapshot and a provenance reference (identifiers only). Archived entries cannot be used to create new stories.
- **FR-CAT-10 (M).** **Companion versioning.** A character and its companion scenario keep **separate version sequences**, linked by a pin: every companion version records the character version its locked slot uses, and every story created from it snapshots that pair (FR-SCN-9).
  - **Companion edited alone.** Publishing a companion draft creates a new companion version pinned to the character's **latest published** version — never to a character draft. The character's version does not change.
  - **Character published alone.** Publishing a character draft creates the new character version **and**, in the same transaction, a new companion version that copies the latest published companion content (on the character's first publish, when none exists yet, the companion's defaults: its two slots and an empty world) and re-pins the locked slot to the new character version. An unpublished companion draft is not published by this; it stays a draft, with its pin moved to the new character version.
  - **Both edited.** They may be published separately (the rules above, in either order), or **publish together**: one operation that publishes the character draft and the companion draft as a single pair, with the companion pinned to the new character version.
  - **Atomicity.** Each of these publishes is one transaction. The companion version is validated (FR-SCN-5) as part of publishing the character; if that validation or any write fails — for example, a companion seed refers to an alias the new character version no longer has, so it no longer resolves to an entity (FR-PROP-12) — nothing is published: no character version exists without a matching companion version, and the error names the companion problem, which can be fixed in the companion draft before publishing both together.
  - **Concurrency.** Each publish names the draft revisions it is based on (FR-CAT-3); if either draft changed since, the publish is rejected and nothing is written. Two editors publishing the same character concurrently produce exactly one new version; the other request is rejected as stale (or returns the first result under the same idempotency key, FR-CONC-6).
- **FR-CAT-11 (M).** **Listing status.** Every catalog character and scenario shall carry a **listing status**: a consumer-defined publishing-workflow value, separate from labels (which describe the entry) and from the version status (`draft`, `published`, `archived`). The allowed values are configured per deployment — default `private`, `in_review`, `public` — and new entries start at the first value; a value outside the set is rejected. Each change is recorded with the acting principal and time, and list and search can filter on it. A companion scenario always has its character's listing status and changes with it. Epistrel never interprets the value: it restricts no read, no story creation, and no transition between values (FR-AUTH-8). What `public` means is the consumer's decision.
- **FR-CAT-12 (M).** **Every character has a true age.** Every character — a catalog character, an ad-hoc character, the player's persona, and any character introduced during play — shall have a **true age**: an objective canon fact the engine holds from the moment the character is created. Catalog characters and ad-hoc definitions declare it (required to publish or create); a persona's age is its true age (FR-CAT-6); a character introduced by narration or the director is given one **lazily** when it is created — a single concrete age, plausible for what the story has established, taking the most specific clue available (the old man who stopped to help with a flat: 64; a student on a college campus: anywhere from 18 to 23, but 18 at freshman orientation; a mother with three young children: somewhere from 27 to 35). The render that introduces the character declares its age; an omission is repaired like any missing structured field (FR-REPAIR), within the turn budget. The age is recorded with the story time of creation, and the character's current age adds the full years since elapsed on the world clock. It is **not disclosed**: the character knows its own age; other characters perceive an apparent age band, as for personas (FR-CAT-6), until they learn more; and it is otherwise held by the engine (returned only in omniscient reads, FR-RESP-12). Age belongs to the character, not the role: a scenario never changes it, and a role may restrict it only through an eligibility age range (FR-SCN-3). Later claims about a character's age are verified against it like any claim (FR-TURN-6). Under `lite`, which tracks no entities, characters improvised in narration have no engine-held age; the cast's ages still apply (FR-GUARD-11).

### 18.2 Scenarios and story creation (FR-SCN) — Engine Core store + API

A **scenario** is a reusable starting point for a story: the world, the cast slots, the starting state, and what drives the plot.

- **FR-SCN-1 (M).** Epistrel shall store scenarios in a **scenario catalog** (`scenario_catalog` and its version table) with the same draft/publish/archive lifecycle, versioning, owner and relations (FR-AUTH-5,6), labels, listing status (FR-CAT-11), and content rating as catalog characters (FR-CAT-2,3).
- **FR-SCN-2 (M).** A scenario shall carry:
  - **Public card** — what the `card` projection returns (FR-SCN-10): the **name**, the **public description** (free text, never seeded), and **media** — cover image, gallery images, and videos with captions (FR-MEDIA-1). **Labels** that describe the scenario (`family`, `RPG`, `dark theme`, `happy ending`, and the like) and the content rating are search and filtering metadata, returned with the card and never seeded. **Every other field of the scenario is private**: it is returned only in the `full` projection and is used according to its **class** (FR-SCN-11). Only knowledge seeds become story facts; director guidance, settings, recommendations, and style are never seeded as facts.
  - **World:** the **world description** (setting and lore, seeded as canon), named **locations**, and named **entities** (organizations, items, places) with aliases.
  - **Cast:** the **character roles** (FR-SCN-3), relationships between roles, and `max_characters_at_start` (FR-SCN-4).
  - **Starting state:** **seeded world memories** (canon facts with visibility — public knowledge, known to specific roles, or secret; FR-SCN-8); **State trackers** with initial values, including role-scoped States (FR-STATE); the **starting clock** — start date and time, or an unanchored or partial anchor, calendar, `time_awareness`, pacing table, `max_unprompted_skip`, and `stop_at_due_events` (FR-CLOCK); pre-scheduled events with owners (FR-CLOCK-9); author-declared predicates, closed sets, and story rules (FR-PROP); and the **opening** — opening narration, starting location, and which roles are present.
  - **Story drivers:** **plot hooks** and **objectives** (goals the story offers the player); **director guidance** — hidden author notes on tone, pacing, and where the story should and shouldn't go; **planned reveals** — hidden truths seeded as secret canon (`latent`) with the roles allowed to learn them; and optional **milestones** and **endings** (S).
  - **Story settings defaults** (what the story is, not how hard the engine works): `interaction_mode`, `turn_concurrency`, `player_authority`, default output viewpoint, `ambiguous_retcon_timing`, `backfill_conflict_policy`, retention options, story-scoped guardrail policies (which can never override global ones, FR-GUARD), the **external providers** the scenario requires the game to register (FR-EXT), and its **recommended engine profile and capabilities** (e.g., a mystery recommends per-character partitions) — unmet recommendations produce warnings, never blocks (FR-PROF-7). Engine dials such as `extraction_mode` and per-turn budgets belong to the engine profile, not the scenario (FR-PROF-2).
  - **Visual style** (optional): an art-style prompt and negative prompt applied to every image generated for the scenario and for stories created from it (FR-IMG-2).
  - **Creation rules:** the list of fields a story creator may **override** at creation (e.g., start time, a role's default character, settings within bounds).
- **FR-SCN-3 (M).** **Character roles (slots).** Each role has an ID, a **public label and setup description** ("Mother — her children are home for the weekend"), shown to the player at story setup so they can choose who fills it, `kind` ∈ {`npc`, `player`}, `required` (true/false), and a **fill mode** ∈ {`open` — the creator picks a catalog character or defines an ad-hoc one; `default` — pre-filled with a catalog `character@version` the creator may replace; `locked` — fixed to a catalog character, not replaceable}. A role may also carry (all private, each used according to its class, FR-SCN-11): **eligibility filters** on structured catalog fields (labels, the content ratings the role accepts, an age range, FR-CAT-12); **role seeded memories** — the role's world and story facts and secrets ("you have three children"; "you know the house is being sold"; "you had an affair, known only to you"); **relationships** to other roles (mother_of, sibling_of), seeded as canon and as beliefs of the roles that know them; role-scoped State initial values; a starting location; a default participation role (primary/reactive/silent, FR-MULTI-7); and optional **name overrides** (for example a shared family surname, added to the character's canonical name and aliases in that story). A scenario may have zero predefined characters (all roles `open`), any number pre-filled (`default`), and any number selectable. Role fields follow the classes of FR-SCN-11: the public label and setup description are public card; seeded memories, relationships, name overrides, and the starting location are knowledge seeds; role-scoped State initial values are starting state; fill mode, eligibility filters, and the default participation role are story configuration. A role defines **situation, not personality**: it shall not assume the personality of whoever fills an `open` or `default` role. The scenario may say the Mother had an affair she keeps secret; it may not make her deceitful — how she handles the secret comes from the character who plays her. Personality-like statements in role text are treated as guidance that always yields to the character (FR-SCN-7). The **player role** is always fixed by the scenario; the player does not choose which role they play.
- **FR-SCN-4 (M).** **Starting-cast limit.** The number of character slots at story start, **including player slots**, shall not exceed `max_characters_at_start`. The deployment default is **16**; each scenario may set its own value, and a story-creation request may override it for that story. An operator may optionally set a deployment-wide ceiling (default: none) that neither may exceed. Characters introduced later in the story are not limited by this setting.
- **FR-SCN-5 (M).** **Validation.** A scenario shall be validated on publish and on demand (dry-run endpoint), running every check the deployment's capabilities support. **Always:** slot count within the limit; locked and default characters exist, are published, and pass role eligibility filters; rating mismatches (FR-RATE-5) and content that fails an input policy (FR-GUARD-10) are reported as warnings; media types and sizes are allowed; required providers are declared; every knowledge seed declares its holder, audience, and disclosure (FR-SCN-8). **Where the deployment provides the structured pipeline:** every seed normalizes to registered predicates with resolved entities (FR-PROP-12), and seeds are mutually consistent under the contradiction rules (FR-PROP-10), or the conflicts are reported. **Where it provides States:** State schemas and initial values are valid. A check the deployment cannot run is listed in the report as `check_unavailable`, never silently passed. Story creation re-runs validation for the capabilities the new story uses, so a check skipped at publish runs before any story relies on what it checks, and its errors reject the creation. Publishing fails on errors and reports warnings. Validation, publish, and story creation return one **validation report** shape: errors and warnings, each with a stable code (for example `personality_in_role`, `fact_conflict_dropped`, `belief_conflict`, `rating_looser`, `input_policy`), its location (entry, version, role, field, seed ID), the exact text affected, what happened to it — `ignored` (kept only as guidance that yields to the character), `dropped`, `kept`, `deferred` (kept in the snapshot until the story has the capability it needs, FR-SCN-11), or `inactive` (a stored setting for a capability the story lacks) — the source that prevailed, and the rule applied (for example "personality: character over scenario", FR-SCN-7).
- **FR-SCN-6 (M).** **Creating a story from a scenario.** The story-creation endpoint shall accept: `scenario_id` (and optionally a version — default the latest published), **slot assignments** for every NPC role (a catalog `character@version`, or an ad-hoc character definition for `open` roles; `locked` roles, and `default` roles kept as pre-filled, need none), **player slot assignments** (the principal and a persona — a saved persona or an ad-hoc one, FR-CAT-6; the scenario fixes which role the player fills), permitted **overrides** (FR-SCN-2), an optional **content rating** (FR-RATE-3,6,7), an optional `max_characters_at_start` override, an optional `strict` flag (FR-SCN-7), and an idempotency key. Creation is rejected without side effects if a required slot is empty, a locked slot is reassigned, a choice fails eligibility, a non-overridable field is overridden, the slot count exceeds the limit, a persona, character definition, or seed fails an input policy (FR-GUARD-10), or a requested rating that adds guardrails to the scenario's fails its check (FR-RATE-7); rating mismatches are returned as warnings (FR-RATE-5); the owner and listing status of the chosen entries are not checked (FR-AUTH-8). The story's owner is the requesting principal unless the request names another, and each player slot's principal is recorded on the story as a `player` relation (FR-AUTH-5,6). A story may also still be created **blank**, with no scenario.
- **FR-SCN-7 (M).** **Merge rule: facts from the scenario, personality from the character.**
  - **World and story facts: scenario > character.** Everything true in the story's world — backstory events, relationships, secrets, schedules, possessions, history — comes from the scenario (world seeds over role seeds). Any world fact found in a character's fields is seeded at the lowest precedence and loses to any conflicting scenario fact.
  - **Personality: character > scenario.** Appearance, personality and temperament, likes and dislikes, behavioral dispositions, values, and interaction style always come from the character who fills the role. Personality-like statements in a scenario role are guidance that yields to the character; for `open` and `default` roles, scenario validation warns when role text asserts personality, quoting the text that will yield and the rule (FR-SCN-5). At story creation the same warning also names the character whose personality applies instead.
  - **Within facts, conflicts are resolved by seed type** (scenario world > scenario role > character), and only where two seeds of the same type genuinely conflict: **objective facts** — a contradiction under FR-PROP-10 (the role says "has a sister"; a character's background flavor says "only child") resolves to the higher source, and a losing fact is dropped entirely; **beliefs** — a seeded false belief never conflicts with canon; two seeds conflict only when they give the same holder contradictory beliefs about the same proposition over overlapping time; **secrets** — the same fact held secretly by different holders unites the holders; a visibility conflict resolves to the higher source; **nested beliefs** — conflict only with another nested belief of the same holder, attributed holder, and proposition; **scheduled events** — conflict only on the same event identity with incompatible times or owners; **relationships** — follow the objective-fact rule under functional predicates.
  **Fact-conflict detection needs the structured pipeline.** Deciding that two seeds contradict each other uses the contradiction rules of FR-PROP-10, so under `lite` genesis detects and drops no fact conflicts. The Lite prompt renders the scenario's facts — world, then role — ahead of any world facts in a character's fields, with an instruction that the scenario's facts prevail; nothing is dropped; and the creation report lists the fact-merge check as `check_unavailable`. The merge, with its conflicts reported, runs when the story's structured form is materialized (FR-SCN-11, FR-PROF-18). Personality precedence needs no conflict detection and applies under every profile: personality comes from the character's fields, and role text that asserts personality is rendered only as guidance that yields to the character.
  Every resolved conflict and every personality warning is returned in the creation response with its type, sources, and winner (with the `full` projection; the `card` projection returns only their counts, FR-SCN-10); with `strict` set, any resolved fact conflict or personality warning instead refuses the creation without side effects, with code `creation_conflicts` and the full report.
- **FR-SCN-8 (M).** **Epistemic seeding.** Every seeded item shall declare its holder, its **audience** — who in the story starts out knowing it: `self`, specific roles, `acquaintances` (the roles the scenario's relationships say know the holder), `perceivable` (anyone who meets them), or `public` (common knowledge) — and its **disclosure** — how the holder treats it: `open` (shares it when relevant), `guarded` (shares it only with trust), or `secret` (conceals it, and may lie to protect it). Audience levels are an extensible list, so named groups ("family", "the crew") can be added later without a schema change. Items use the normal epistemic model: objective canon (public knowledge, known to listed roles, or secret), a character's belief (false beliefs allowed), a nested belief (FR-BELIEF-15), or a scheduled event. Seeds are recorded with provenance `seed` (an author act), which is a legitimate antecedent for the beliefs they create (FR-EPI-13), and with valid-time before the story began unless stated otherwise. Relationships between roles create canon facts plus beliefs only for the roles that know them.
- **FR-SCN-9 (M).** **Genesis.** Story creation shall run as one atomic **genesis operation** at narrative position 0, before turn 1: it creates the story, its configuration and policies, and its characters; snapshots each chosen catalog character and the scenario version into the story in full (with `catalog_id@version` provenance); and materializes the scenario's other content by field class, as far as the story's effective capabilities use it (FR-SCN-11) — entities, aliases, seeded canon and memories, predicates, partitions, beliefs, States, the clock, and scheduled events each only where the story's capabilities include them. Whatever genesis materializes, it writes in one transaction. The opening narration is recorded as turn 1 (an authored narration turn with exposures for the roles present). Checkpoint `0` is the genesis state, so a story can be rewound to its very beginning. Later changes to the catalog never affect the story; the story's author changes it through the normal rewrite side-channel (FR-REWRITE).
- **FR-SCN-10 (M).** **Card and full projections.** Every catalog read and every story-creation response shall take a **projection**: `card` (the default) or `full`. `card` returns only the public cards — a scenario's name, public description, media, labels, and content rating; each role's public label and setup description; each character's name, public description, images, labels, and content rating — and, for story creation, the new story's ID, its cast as cards, the number of merge conflicts and warnings, the number of deferred and inactive items grouped by field class and by the capability each needs, and the names of the checks that could not run (`check_unavailable`) — enough for a player-facing client to show what the story will and won't use, without revealing any private field. `full` returns everything, including world descriptions, role seeds, secrets, director guidance, planned reveals, character definitions, merge-conflict details, and, for story creation, every report entry in the shape of FR-SCN-5, with its location and the exact text affected. Epistrel does not decide who receives which projection (FR-AUTH-1); a consumer showing entries to players uses `card`, so choosing a scenario or a character never spoils it. Inside a story, the story's own visibility rules apply.
- **FR-SCN-11 (M).** **Scenario field classes and staged genesis.** Every scenario field belongs to exactly one class, which fixes where it is stored and where it may go:
  - **Public card** — name, public description, media, labels, content rating, and each role's public label and setup description: catalog metadata returned in the card (FR-SCN-10); never seeded and never placed in a generation prompt.
  - **Knowledge seeds** — the world description, locations and entities with aliases, name overrides, seeded world memories, role seeded memories, relationships between roles, starting locations, the hidden truths of planned reveals, and pre-scheduled events: the only fields that become story truth — objective canon, memories, beliefs, or scheduled events, with provenance `seed` and audiences (FR-SCN-8).
  - **Story rules** — author-declared predicates, closed sets, and rules: written to the story's predicate registry (FR-PROP-4). They define how facts are read; they are not facts.
  - **Starting state** — State trackers with initial values (including role-scoped ones), the starting clock, and the opening (opening narration and which roles are present): objective starting values and the authored first turn.
  - **Director guidance** — plot hooks, objectives, director guidance, the conditions of planned reveals (who may learn them, and when), milestones, and endings: instructions to the storytelling. They enter only the director's context — or, under `lite`, the single prompt as author notes, labeled apart from the scenario's facts — and are never written as canon, placed in a character's context, retrieved as memory, or used to support or contradict a claim.
  - **Story configuration** — story settings defaults, story-scoped guardrail policies, required external providers, `max_characters_at_start`, roles' fill modes, eligibility filters, and default participation roles, and the creation rules: applied to the story's configuration and policies, or used only during creation; never facts.
  - **Engine recommendation** — the recommended engine profile and capabilities: compared with the story's profile at creation to produce warnings (FR-PROF-7); never facts.
  - **Style** — the visual style: used only in image prompts (FR-IMG-2), never in a text-generation prompt.
  **Staged genesis.** Genesis always creates the story, its configuration and policies, and its characters with their true ages; snapshots every field of the scenario and of each chosen character; and records the opening narration as turn 1. It materializes the other classes only as far as the story's effective capabilities use them (FR-PROF-13). Under `lite`, knowledge seeds and starting locations are rendered as scenario text and director guidance as author notes in the Lite prompt (FR-LITE-1,5), and the clock and States appear only in their prompt-only Lite forms, when enabled. Under `structured`, knowledge seeds are written as canon and memories, and story rules go to the predicate registry. With per-character partitions, seeds route by audience into partitions as beliefs, including false and nested beliefs, and the opening creates exposures. With States and the clock, State trackers, the clock, and scheduled events are created. Anything the story's capabilities cannot use is **deferred**: it stays in the snapshot, is never silently dropped or written as an empty or placeholder record, and is listed in the creation report with outcome `deferred` and the capability it needs — entry by entry under the `full` projection, and as counts by field class and capability under `card` (FR-SCN-10). A Lite story renders knowledge seeds as text and defers their structured form. Only knowledge seeds, story rules, and starting state can be deferred: public-card fields and style have no genesis form, director guidance and engine recommendations are always consumed, and story configuration is always applied — or, for a setting whose capability the story lacks, stored and listed `inactive`. When the story later gains that capability, its deferred content is materialized at position 0 as part of the change (FR-PROF-18). Every class is fixed in the scenario schema, so a field cannot change channel by accident.

### 18.3 Engine profiles (FR-PROF) — Orchestrator + Engine Core

How hard the engine works is tunable per story. An **engine profile** is a saved, named, versioned set of capability modules and dials; each story runs under one profile. Profiles span from **Lite** — the equivalent of today's roleplay engines — to **Max**, where every capability runs at its most conservative setting with little regard for cost. Which profiles a given player or plan may use is the consumer's business; Epistrel does not enforce tiers.

- **FR-PROF-1 (M).** Epistrel shall support **engine profiles**: named, versioned configurations stored in the deployment (`engine_profiles` and a version table), created and edited through the API (FR-API-6), each with an owner (FR-AUTH-5). Every story runs under exactly one profile. **Deleting** a profile removes it from listings and from new assignment, with a warning naming the stories that still use it; those stories keep running on its last version, and the profile is purged once no story uses it. A story created without one uses the deployment's default profile, which is configurable; a scenario may name a **recommended profile** (FR-SCN-2).
- **FR-PROF-2 (M).** A profile shall be organized as **capability modules**, each with an enable flag or level and its own dials:
  - **Pipeline:** `lite` (FR-LITE) or `structured` (the full Engine Core path).
  - **Memory:** rolling auto-summary (window and compression thresholds); episodic retrieval (k, hybrid search, reranking); consolidation and reflections (cadence); hot-set budgets (FR-MEM-8).
  - **Character knowledge:** shared context, or per-character partitions; with partitions, nested beliefs (off, or a depth of at least 2), lazy belief resolution (on or off), and testimony adjudication (`model` or `defaulted`).
  - **Perception:** `none` (nothing is routed; the only level without per-character partitions), `co_location` (every authoritatively co-located character perceives every beat in full — no envelope/content split, and whisper, aside, eavesdrop, and remote-channel qualifiers are not applied), or `full` routing (envelope/content split, qualifiers, validation; FR-TURN-2,13).
  - **Verification:** off, declared claims only, plus claim extraction (`gated` or `always`), plus entailment escalation (gate threshold).
  - **Commitment:** off or on; salience detection (rules only, or rules plus model).
  - **World clock:** off or on (its mode — `paced`, `manual`, or `external` — is a story setting, FR-CLOCK-5); time-claim verification on or off.
  - **States and external data:** off or on.
  - **Multi-character:** one combined render, or per-character renders (sequential or simultaneous is the story's `interaction_mode`, FR-MULTI-5).
  - **Repair and polish:** maximum repair attempts; polish pass on or off.
  - **Budgets:** per-turn model calls and deadline (NFR-PERF-6).
  - **Models:** per-purpose routing (FR-MODEL) and generation defaults — temperature, top_p, response length.
- **FR-PROF-3 (M).** **Presets.** Epistrel shall ship at least four presets: **Lite** (the `lite` pipeline); **Standard** (structured; per-character partitions; co-location perception; declared-claim verification with gated extraction; commitment on; world clock on; consolidation on; one repair attempt; moderate budgets); **Full** (every module on; extraction `always`; entailment escalation at its default gate; nested beliefs to depth 2; full perception routing); and **Max** (Full at its most conservative: escalate every uncertain verdict, recall-biased salience, the strongest configured model for each verification purpose, more repair attempts, frequent consolidation, generous budgets). Presets are ordinary profiles and can be copied and edited.
- **FR-PROF-4 (M).** **Dependency validation.** Modules depend on one another (every module except the rolling summary, the prompt-only clock and States of FR-LITE-5, budgets, and models requires the `structured` pipeline; per-character partitions require perception at `co_location` or `full`, and perception other than `none` requires partitions; nested beliefs, lazy belief resolution, and testimony adjudication require per-character partitions; time-claim verification requires the clock and verification; scheduled-event stops require the clock; in the `structured` pipeline the clock requires commitment, because its anchors are commitments (FR-CLOCK-3); contradiction checking requires at least declared-claim verification; consolidation requires episodic memory). Every profile, and every story's effective configuration after overrides, shall be validated against a declared dependency graph; an invalid combination is rejected with the missing dependencies named. Only valid configurations ever run.
- **FR-PROF-5 (M).** **Story overrides.** A story may override individual dials of its profile. The **effective configuration** is the deployment defaults, then the profile's current version, then the story's overrides, validated as a whole (FR-PROF-4). Story settings that describe the story rather than the engine (FR-SCN-2's story settings defaults) are story configuration seeded at genesis, not profile overrides. Settings that appear elsewhere in this specification as per-story options and are engine dials — `extraction_mode`, the escalation gates, per-turn budgets, model routing, generation defaults — are set by the profile and may be overridden per story. Overrides persist across profile version changes.
- **FR-PROF-6 (M).** **Follow the latest version.** A story follows its profile's **latest** version. Each setting is classified as **behavioral** (thresholds, gates, budgets, models, generation parameters, repair limits — they change how hard the engine works, not what is stored) or **data-producing** (enabling or raising a module that writes structured data: per-character partitions, nested beliefs, perception routing, extraction, commitment, the clock, States, consolidation, or the switch from `lite` to `structured`). Behavioral changes take effect at the story's next turn boundary under the configuration-revision rules (FR-CONC-14..16) and never need a backfill. Data-producing changes follow FR-PROF-18.
- **FR-PROF-7 (M).** **Warn, never block.** Any operation whose effects may degrade a story — assigning or changing a story's profile, editing a profile that stories follow, applying story overrides, or creating a story whose profile lacks capabilities its scenario recommends (FR-SCN-2) — shall run in two stages: without `ignore_warnings`, Epistrel makes no change and returns an **impact report** (affected stories; capabilities lost or gained; whether a backfill is needed, with its estimated model calls, tokens, and duration; scenario recommendations not met; guarantees that no longer apply, FR-VERIFY-15); with `ignore_warnings = true` (`ignoreWarnings` for camelCase clients), the change is applied regardless. Epistrel never blocks a change the consumer has confirmed, except for invalid configurations (FR-PROF-4), which the operation itself rejects; calls without a valid service credential (FR-AUTH-1); and a data-producing increase for a story with history when the deployment provides no upgrade mode (FR-PROF-8) — the impact report lists such a story as `upgrade_unavailable`, and a confirmed change applies to every other affected story while that one keeps its previous configuration.
- **FR-PROF-8 (M).** **Upgrades that add data.** When a confirmed change adds data-producing capability to a story with existing history, the request shall choose `upgrade_mode` ∈ {`backfill` (default), `forward_only`}. `backfill` runs the backfill of FR-PROF-9 before the new configuration takes effect, with the story paused until it completes. `forward_only` applies the new configuration at the next turn boundary without a backfill; the turns before the switch lack the data that would be derived from their transcript, and retrieval, verification, and the impact report mark that gap. The one exception is the story's deferred genesis content, which is authored, not derived, and is added at position 0 under either mode (FR-PROF-18). For a profile edit that affects many stories, each affected story is queued, and each pauses only while its own backfill runs.
- **FR-PROF-9 (M).** **Backfill re-derives; it never regenerates.** A backfill shall re-derive structured data from the stored transcript (FR-PROF-11) — it never regenerates or alters any message, input, or narration the player saw. It processes the history in scene-sized chunks (extraction in parallel), then a single ordered reconciliation pass assigns positions, valid-times, exposures, commitments, clock advances, and State changes in narrative order. Everything it writes carries provenance `backfill` at a lower trust tier than live-verified data. It cannot recover what was never generated (for example private thoughts from a Lite story), and it infers presence and perception from the text, so those results are marked inferred. It is resumable after a crash, reports progress, and can be cancelled, in which case its partial results are discarded and the story returns to its previous configuration.
- **FR-PROF-10 (M).** **Backfill conflicts.** When the historical text contradicts itself (after fluent interpretation, so values at different times are not conflicts, FR-PROP-9), the story's `backfill_conflict_policy` ∈ {`last_mention` (default), `first_mention`, `ask`} decides: `last_mention` — the most recent statement becomes canon for the overlapping valid-time; `first_mention` — the earliest establishing statement becomes canon; in both cases the losing statements remain in the transcript unaltered and are recorded as in-world claims (sincere errors or lies, by the normal classification), and characters who heard them may hold the corresponding beliefs. `ask` — conflicts are listed for the user or consumer to resolve; the backfill finishes its pass and the story stays paused until they are resolved, or until the consumer resumes it with `ignore_warnings`, which leaves the unresolved facts `uncertain`.
- **FR-PROF-11 (M).** **The full transcript is always stored.** Under every profile, every player input, ingested event, and final rendered message shall be stored as events with its narrative position, so any story can later be backfilled, rewound, forked, or switched to another profile.
- **FR-PROF-12 (M).** **Guarantees follow capabilities.** Each requirement in this specification applies when the capability it belongs to is enabled; the **capability map** (FR-PROF-13) lists which modules each requirement area depends on. Every respond response shall report the story's profile ID and version, its quality status (FR-PROF-16), and any degradation steps taken (NFR-PERF-7), and the guarantee table (FR-VERIFY-15) shall be published per preset.
- **FR-PROF-13 (M).** **Capability map.** These requirement areas apply only with the listed modules, at the levels shown:
  - **The `structured` pipeline:** FR-TURN (the turn contract), FR-BITEMP, FR-PROP, FR-RET, FR-EMBED, FR-MEM-1,2,4,5,7,8, FR-STORE-3's projections of beliefs, relationships, and placement, FR-RESP-8, FR-DIRECT, FR-REWRITE, the structured read set and rewrite parts of FR-CONC (FR-CONC-3,7,11..13 — the Lite read set of FR-CONC-4 is floor), and the memory parts of FR-GUARD (FR-GUARD-4,5).
  - **Per-character partitions:** FR-EPI, FR-BELIEF, NFR-PRIV-4 structural isolation, FR-MEM-11, the viewpoint checks of FR-RESP-11, and the parts of FR-COMMIT that write or check one character's knowledge — FR-COMMIT-4's observation, FR-COMMIT-11's could-have-known flag, FR-COMMIT-13's knocker-side commitment for a modeled character, and FR-COMMIT-14's knowledge obligations and epistemic checks (its position obligations are checked with shared knowledge too). Within them, nested beliefs (FR-EPI-2's nested clause, FR-BELIEF-15) apply only when that dial is on — otherwise no nested belief is recorded, and claims about another character's beliefs get no nested-belief check; lazy resolution (FR-BELIEF-5,6,9) only when it is on — otherwise every witness's transition is resolved when the exposure is recorded; and model adjudication of testimony (FR-BELIEF-3) only at `model` — at `defaulted`, every acceptance follows the deterministic default of trust, priors, and consistency.
  - **Perception:** FR-TURN-9,10 and the audience filter (FR-RESP-13) at `co_location` or `full`; FR-TURN-2's envelope/content split and qualifiers, and FR-TURN-13, at `full` only.
  - **Verification**, at its level: FR-VERIFY, FR-PROP-10, and FR-REPAIR — FR-VERIFY-13's model extraction backstop only at levels with claim extraction, and FR-VERIFY-3's entailment escalation only at the level that adds it.
  - **Commitment:** FR-COMMIT. **The world clock:** FR-CLOCK. **States and external data:** FR-STATE and FR-EXT. Under `lite`, the clock and States apply only in the prompt-only forms of FR-LITE-5, and no external-data provider is used.
  - **Per-character renders:** FR-MULTI. **Consolidation:** FR-MEM-3,6,9,10.
  Repair of a missing or invalid structured field — a character's age (FR-CAT-12), a State effect (FR-STATE-5,6), a time stop (FR-CLOCK-16) — applies wherever that field is required, whether or not verification is on. The **floor** — every requirement area not listed above, including FR-STORE event storage and the transcript (FR-PROF-11), the rest of FR-CONC, FR-AUTH, FR-ADMIN including erasure, budgets (NFR-PERF-6,7), the catalog, and content ratings with their prompt guidance and the rest of FR-GUARD (FR-RATE, FR-GUARD) — applies under every profile.
- **FR-PROF-14 (M).** **Guardrails.** Guardrail policies are not a profile module. If guardrail policies are defined, no engine profile setting, override, or preset bypasses or weakens them, in either pipeline; a deployment or story with no policies defined simply has none to enforce.
- **FR-PROF-15 (M).** **Capability enabled ≠ quality tested.** A quality floor (NFR-QUAL) is claimed only for a **certified configuration**: an eval run (§8 of the testing plan) against a specific **configuration fingerprint** (FR-PROF-16) produces a certification record listing which floors passed, with sample sizes and bounds (NFR-QUAL-8).
- **FR-PROF-16 (M).** A **configuration fingerprint** identifies an effective configuration for quality purposes: the profile version, the model identifier and reported version for every model purpose, and every setting tagged **quality-relevant** (gates and thresholds, `extraction_mode`, repair and polish limits, prompt-template versions, budgets); every setting in the profile schema is tagged quality-relevant or not. Every respond response, effective-configuration read, and impact report shall state the fingerprint, the **capabilities enabled**, and the **quality status** ∈ {`certified` (with the certification ID and the floors it passed), `uncertified` (no certification has ever matched the fingerprint — a new configuration, including any change to a quality-relevant setting, a model, or a model's reported version), `stale` (the fingerprint matched a certification that has since been invalidated — by a scheduled canary eval falling below a floor, or by detected drift in a model whose identifier and reported version are unchanged)}. A profile may be labeled as meeting a floor only while a matching certification exists. Presets ship certified only for the reference model tier they were evaluated on; the same preset on other models is `uncertified` until evaluated.
- **FR-PROF-17 (M).** **Changes and certification.** A change to any quality-relevant setting — a model swap, a threshold or gate change, a story override of such a dial — produces a new fingerprint; the impact report says whether the result remains certified, and following FR-PROF-7 it is a warning, never a block. A certification run can be requested per profile (or per story's effective configuration), with an estimate of its cost; it records results without changing the configuration. Because hosted models can change behind an unchanged name, a deployment may schedule **re-certification** and a sampled **canary eval** at a configurable cadence (S); a canary that falls below a floor marks the certification `stale`.
- **FR-PROF-18 (M).** **Data-producing profile changes.** A data-producing **increase** is handled by FR-PROF-8; under `forward_only`, earlier turns lack the data derived from their transcript. It also materializes the story's **deferred genesis content** for that capability (FR-SCN-11) at position 0, under either `upgrade_mode`, because that content is authored, not derived from the transcript. It is written with the upgrade's transaction-time and with valid-time before the story began, so it is part of the corrected history at every checkpoint — those before the upgrade included — and reads and verification use it from then on. The as-originally-recorded view of a checkpoint recorded before the upgrade does not show it (FR-STORE-23), and turns committed before the upgrade are not re-verified against it. Under `backfill`, conflicts between the materialized content and the re-derived history are detected and resolved by the backfill conflict policy (FR-PROF-10), with the seeds counted as the earliest statements, at position 0, and reported. Under `forward_only`, the earlier turns' structured data is never derived, so conflicts with them are not detected; the impact report says so. A data-producing **decrease** stops producing that data; existing structured data is kept dormant, not deleted, and is reused if the module is enabled again.

### 18.4 The Lite pipeline (FR-LITE) — Orchestrator

The bottom of the range: how roleplay engines work today, using the same catalog, scenarios, transcript, and API.

- **FR-LITE-1 (M).** The `lite` pipeline shall assemble, for each turn, one prompt from: the story rating's **prompt guidance** (FR-RATE-4); the story's **custom instructions** block; the scenario's knowledge seeds and the characters' definitions rendered as text, the persona guidance, and the director guidance as labeled author notes (from the story's snapshots, FR-SCN-9,11) — never a public card or the visual style; **pinned memories**; the **rolling auto-memory** summary; the most recent N messages verbatim; and the player input. It records the input and reply in the transcript. It does not run the Engine Core's structured machinery: no claim detection or extraction, no verification, no partitions, no commitment, no perception routing, no State validation.
- **FR-LITE-7 (M).** **What a Lite turn calls and checks — the same wording everywhere:** each turn makes exactly **one generation call**. The only other model calls a Lite turn can make are (a) one `guardrail check` call for each **model-assisted** policy that applies to the story, for each text it checks — the input and the output each count, so a policy that applies to both costs two (FR-GUARD-9, NFR-PERF-6); deterministic policies cost no model call — and (b) guardrail-triggered regenerations, bounded by the bounded-retry contract (FR-GUARD-6) and the turn budget, ending in the safe fallback. With no model-assisted policies and no violation, a Lite turn is exactly one model call. Rolling-summary compression runs in the background, off the turn, and is not counted against the turn. The turn budget (NFR-PERF-6) applies; the **reserved claim-detection calls do not**, because Lite performs no claim detection; Lite's guarantee table lists claim detection, verification, commitment, structural knowledge separation, and audience filtering as **not provided**.
- **FR-LITE-2 (M).** **Rolling auto-memory.** The Orchestrator shall maintain a running memory log: when the verbatim window exceeds its budget, the oldest messages are compressed into summary segments by the consolidation model purpose, and old segments are re-compressed into coarser ones as the summary grows. Segments carry the narrative positions they cover and follow timeline membership, so rewinding, regenerating, or forking rebuilds the affected segments.
- **FR-LITE-3 (M).** **Pinned memories and custom instructions** shall be editable story-level text items available under every profile: in `lite` they are always included in the prompt; in `structured` they are author-pinned memories (FR-MEM-8) and standing guidance included in every render's prompt, respectively. Custom instructions are never facts.
- **FR-LITE-4 (M).** **Generation settings** (temperature, top_p, response length, and similar) come from the profile, may be overridden per story, and are honored per request (FR-RESP-3).
- **FR-LITE-5 (M).** **Characters in Lite.** Multiple characters are rendered in one combined generation. Character knowledge is separated only by instructions in a shared prompt — not structurally — so characters' secrets seeded from the catalog or scenario are present in the shared context; this limit is stated in the guarantee table (FR-PROF-12). The **world clock** may be enabled in `lite` in a prompt-only form (pacing advances, current time and schedules shown in the prompt, no verification); **States** may be shown in the prompt and changed only through the State API (FR-STATE-9).
- **FR-LITE-6 (M).** **Upgrade and downgrade.** Moving a story from `lite` to `structured` is a data-producing increase (FR-PROF-8,9). Moving from `structured` to `lite` builds the rolling auto-memory from the transcript (a summarization backfill) and keeps the structured data dormant; a later upgrade backfills only the turns played since the downgrade.

### 18.5 Media (FR-MEDIA) — Engine Core store + API

- **FR-MEDIA-1 (M).** Images and videos for catalog characters and scenarios, and story images (FR-IMG-5), shall be stored as **immutable media assets** in a pluggable blob store — the local filesystem by default, or any S3-compatible endpoint — with metadata in Postgres: owner, kind, MIME type, size, dimensions or duration, checksum, content rating (from the deployment's ratings, FR-RATE-1), alt text or caption, and generation metadata for images (FR-CAT-4). Allowed types and size limits are configurable. An image upload declares its depicted subjects (FR-IMG-9) — an explicitly empty list is accepted, an omitted one is rejected — so erasure reaches every image from the first upload.
- **FR-MEDIA-2 (M).** Catalog versions and story snapshots reference assets by ID. An asset is purged only when no catalog version, no catalog draft, no story, and no live candidate record references it (found by a periodic sweep, not reference counting), or by erasure (FR-ADMIN-2). The general sweep skips assets in state `candidate`; only the candidate-expiry sweep removes them, after `candidate_ttl` (FR-IMG-7). Because blobs are content-addressed, bytes are deleted only when no asset row of any state still has their checksum. **Deleting** an asset removes it from listings and from new references; its content stays available to the catalog versions, catalog drafts, stories, and live candidate records that already reference it until the sweep finds none. Epistrel does not moderate media content itself; it records the declared content rating and exposes an upload hook the consumer can use for moderation.
- **FR-MEDIA-3 (M).** **Large media delivery.** Content reads shall support HTTP **byte ranges**, so video can seek; with an S3-compatible store, Epistrel shall issue short-lived **signed URLs** so large files are served by the store rather than streamed through the API. Uploads larger than a configurable size shall be **resumable** (multipart). Every video shall have a **poster image** — uploaded with it, or extracted from its first frame with ffmpeg. Epistrel does not transcode video, and does not generate it.

### 18.6 Content ratings (FR-RATE) — Engine Core store + Orchestrator

A content rating says what kind of content a story may contain. It is not access control — who may play a story at a given rating is the consumer's decision (FR-AUTH-1) — and it is more than a label: a story's rating decides the prompt guidance its generation receives and the guardrails its content must pass.

- **FR-RATE-1 (M).** **Ratings are defined per deployment.** Content ratings shall be records managed through the API (under `/admin`, FR-AUTH-1), each with: a name; a **content-policy description** — what the rating permits and excludes, in prose; a **display order**, used for listing only — nothing compares ratings by order, because ratings need not form a line; **prompt guidance** for text and, separately, **image guidance** (FR-RATE-4); the rating's own **guardrail policies** (FR-GUARD-8); and the ratings it **inherits** guardrails from (FR-RATE-2). Deployments may add, rename, reorder, edit, and retire ratings. Epistrel seeds four — **Everyone**, **Teen**, **Mature**, and **Explicit** — with starter descriptions, guidance, and guardrails, each inheriting from the next less restrictive one (Everyone from Teen, Teen from Mature, Mature from Explicit). Every edit creates a new rating version; stories follow the latest version in every operation that commits after the edit — an in-flight turn is re-checked under it at commit (FR-CONC-16) — and every operation records the rating version it ran under (FR-CONC-14). Editing a rating governs future content only: existing histories are not re-checked. Deleting a rating that a story, catalog entry, or media asset still uses retires it — hidden from listings and from new assignment, kept for what already uses it. Every story has exactly one rating: a blank story uses the rating its creation request names, or the deployment default (seeded: Everyone), and a fork copies its story's rating.
- **FR-RATE-2 (M).** **Guardrail inheritance.** A rating may inherit from any other ratings. Its **effective guardrails** are its own policies plus the effective guardrails of every rating it inherits from, transitively: Everyone inheriting from Teen gets everything Teen has, including what Teen inherits, and adds its own. A policy reached by several paths applies once; an inheritance cycle is rejected. Prompt guidance is not inherited. The API returns each rating's effective guardrails with the rating each policy comes from.
- **FR-RATE-3 (M).** **Every character and scenario has a rating; the story's rating governs.** Every catalog character, scenario, and media asset shall carry a content rating from the deployment's set, required to publish or upload; a companion scenario starts with its character's rating and may be changed. Every story has exactly one rating: its scenario's at creation unless the creation request names another (FR-RATE-6,7); a blank story's rating follows FR-RATE-1. **Scenario over character:** every character in a story plays under the story's rating, whatever its own; characters created during play have no rating of their own. Only an explicit consumer request changes a story's rating (FR-RATE-6,7); story content never does — the guardrails keep a Teen story from drifting into Explicit content.
- **FR-RATE-4 (M).** **Prompt guidance.** The story rating's prompt guidance shall be included in every generation prompt of the story — character renders, regenerations and repairs, the director and the opening narration, composition and polish, and the single Lite prompt — under every engine profile, at no extra model call. Its image guidance is included in every image prompt for the story (FR-IMG-2). The guidance steers; the guardrails enforce (FR-GUARD-8).
- **FR-RATE-5 (M).** **Mismatches warn, never block.** Ratings are compared by their guardrails, not their order: an item is **looser** than a scenario or story rating when its own rating's effective guardrails lack any policy that the scenario or story rating has. Scenario validation (FR-SCN-5) and story creation (FR-SCN-6) shall return a warning for every looser default, locked, or assigned character and every looser media asset — an Explicit character in an Everyone scenario brings a definition written for looser rules into a story whose guardrails will hold it back — and a companion scenario rated differently from its character warns the same way. Items that are not looser need no warning.
- **FR-RATE-6 (M).** **Relaxing a story's rating.** A change to a rating whose effective guardrails are a subset of the current rating's — Teen to Explicit, say — only removes guardrails. Epistrel shall apply it on explicit request, without checking content and without verifying that the consumer may make it (FR-AUTH-1), recorded as an interpretive configuration change (FR-CONC-15) with the acting principal and effective for every operation that commits after it (FR-CONC-16).
- **FR-RATE-7 (M).** **Tightening a story's rating requires a clean history.** A change to a rating whose effective guardrails include any policy the current rating's lack — Explicit to Teen, or a sideways move between ratings that each have policies the other lacks — shall be applied only if the story's **entire active history** passes the target rating's effective guardrails: the genesis seeds and opening narration, every active turn's player input and rendered beats, ingested events, pinned memories, custom instructions, and active story images (FR-IMG-5) — each image by its prompt and, through the `image check` model, by the image itself; an image that cannot be checked because no image-check model is configured counts against the change, so the tightening is refused until it is removed or a checker is configured. The story is paused while the check runs as a background job (progress readable; model-assisted policies run outside the turn budget). If everything passes, the rating changes; otherwise the change is refused, nothing changes, and the response lists each violation by position and policy. Rewriting a history to fit a stricter rating is out of scope. Creating a story at a rating that adds guardrails to its scenario's runs the same check over its genesis content. **Reactivation re-checks.** Every turn variant records the effective guardrail set — the rating version and the global and story policy versions — it last passed. An untruncate, a swap, or promoting a dormant continuation into a fork (FR-STORE-28) that would make turns active shall first check every such turn, with its story images, whose recorded set lacks any policy now in effect for the story — run as the same background check, with the story paused — and shall be refused, with each violation listed, if any fails. Turns already checked against the current set are not checked again. The rule is the same whatever left a turn unchecked: a tightening after it was discarded, a policy added since, or an import that brought it in inactive (FR-STORE-7). A fork copies its story's rating (FR-RATE-1).
- **FR-RATE-8 (M).** **Rating suggestion.** Epistrel shall provide a read-only operation that takes a scenario or character — a draft or a published version — and returns a **table with one row for every rating** in the deployment: whether the rating is **appropriate** for the entry (yes or no), and, for each *no*, the **concerns** — every specific conflict between the entry's content and that rating's content-policy description or effective guardrails, naming the policy or description clause and the part of the entry that conflicts (a field, a seed, a role, a planned reveal, a cast character's definition, a media caption). Its inputs are each rating's description, prompt guidance, and effective guardrails, and the entry's full content (for a scenario, including the definitions of its default and locked characters). The judgment is **limited to content policy**: it reports only conflicts with what the ratings and their guardrails state, never other reasons — not taste, audience fit, or quality ("too childish for Explicit" is never a concern); a rating is appropriate unless the content breaks its policies. Deterministic policies are evaluated directly; the rest uses the `rating suggestion` model purpose (FR-MODEL-2). The table is advisory: it never changes a rating or blocks a publish, and it records the rating versions it evaluated. Its judgments are model-dependent and measured, not guaranteed (FR-VERIFY-15). Because ratings need not form a line, the whole table is always returned, never a single answer. The response is labeled as a suggestion (`advisory: true`), and no guardrail, publish, story-creation, or rating-change path reads it: it is not a safety control, and output guardrails apply whatever it says. Its concerns quote private fields, so it is an author-facing read like the `full` projection (FR-SCN-10).

### 18.7 Images and image generation (FR-IMG) — Orchestrator + Engine Core

Images are optional. A deployment can have Epistrel generate them from its own prompts, have Epistrel generate them from prompts the consumer writes, have the consumer upload them, or use none at all, and Epistrel stores all of them. What else it does depends on the source. For images it generates from **its own prompts**, it builds the prompt from what the audience perceived and checks both the prompt and the result (FR-IMG-2,3,8). For **consumer-written prompts**, it checks the prompt — including the protected-term match — and the result, but what the prompt asks for is the consumer's choice (FR-IMG-8). For **uploads**, it checks the image only if an image-check model is configured; otherwise it stores the image as `unchecked`, with no rating or viewpoint assurance from Epistrel (FR-IMG-3,10).

- **FR-IMG-1 (M).** **Image-generation port.** Epistrel shall generate images through an `ImageGenerator` port with pluggable adapters, configured per deployment like the model purposes (FR-MODEL): the adapter, the model, default size, aspect ratio, and quality, and credentials held in Epistrel config (NFR-SEC-3). It shall ship one adapter, for **OpenRouter's image API**, (`POST /api/v1/images`, base64 results), which reaches many image models through one interface. Capabilities are discovered **per endpoint**, never assumed per model: the adapter reads each endpoint's supported parameters (seed, reference images, sizes and aspect ratios, `n`, streaming), routes a request only to endpoints that support the parameters it carries, and, when none does, generates without them and records which requested parameters were not applied, so generation metadata never claims a seed or reference image that was not used. Output dimensions and format are recorded from the returned image, not from the request. **Submission.** The port separates sending a request from collecting its results: `submit` sends it and `collect` waits for its outputs. Every adapter declares its **submission mode**: `async` — the provider acknowledges each request with its identifier before generating, so `submit` returns that identifier at once and `collect` then waits for the results; or `sync` — the provider returns its identifier only with the results, so `submit` returns when generation has finished and `collect` is not used. Epistrel commits an `async` acknowledgement before awaiting results (FR-IMG-11), so a crash after it leaves a known request rather than an ambiguous send; for a `sync` adapter, the whole call is the window in which a crash leaves the send ambiguous. **Completion confirmation** is an optional adapter capability, `confirms_completion`. An adapter may declare it only if it uses `async` submission and can look up a request's state by its identifier from any worker; registration rejects a `sync` adapter that declares it. The lookup must report one of: a **terminal** state — `succeeded` (with its outputs), `failed`, or `cancelled` — or a non-terminal `running` or `unknown`, together with the request's usage and cost when the provider supplies them; when it does not, the cost is recorded as `unknown`. An adapter declaring the capability must implement both `status` and `cancel`; `cancel` returns `accepted` or `not_supported`, and neither answer is definitive. A terminal state reported by the provider for that specific request is the only definitive completion. A cancellation counts as definitive only when a later status lookup reports `cancelled` (or another terminal state); a cancellation request that the provider merely accepts proves nothing, since the provider may still be processing and may still bill. `unknown` is never definitive. An adapter that cannot meet all of this declares `confirms_completion = false`; the bundled OpenRouter adapter is `sync` — its image endpoint returns the images in the response — so it does not declare it. An adapter may also declare **`idempotency_keys`** if the provider deduplicates requests that carry the same client-supplied key; such an adapter sends the attempt's key with every call (FR-IMG-11). The bundled OpenRouter adapter declares it only if that deduplication is verified. Generation is optional: with no adapter configured, generation operations report `not_configured`, and consumers generate images themselves and upload them (FR-MEDIA-1). Video generation is not provided.
- **FR-IMG-2 (M).** **Image prompts.** Epistrel shall build image prompts from structured sources: the depicted characters' appearance and the visual-identity elements their audience may see (FR-CAT-4, FR-IMG-8); each depicted character's **apparent age**, as the age band the audience perceives — never the true age, which goes only to the safety path (FR-IMG-12); the scenario's visual style (FR-SCN-2); the story rating's image guidance (FR-RATE-4); and, for a story image, the scene as its audience viewpoint perceived it (FR-IMG-8). Catalog images are public-card content, so their audience is anyone browsing: they use only `perceivable` elements and an apparent age band. The `image prompt` model purpose writes the prompt from those inputs. A **prompt-builder** operation returns the prompt and its parameters — negative prompt, seed, reference-image IDs, size — without generating, for consumers that generate images themselves.
- **FR-IMG-3 (M).** **Generated images fail closed; nothing Epistrel generates is stored unchecked.** Every image prompt — built by Epistrel or supplied by the consumer — shall be checked against the policies that apply to image prompts before any generation, including the seeded minors policy, using the true ages of the depicted characters (FR-GUARD-11); a violation returns the policy error, as for text input (FR-GUARD-10). This prompt-side check is the primary control. Known subjects, their true ages, and presence are resolved deterministically; only a figure that resolves to no character is classified by a model, as adult, minor, or indeterminate, and an indeterminate figure is treated as a minor (FR-IMG-12). Generated bytes shall go to **private staging** — never addressable as a media asset, never given a URL, never returned — and be checked there against the policies that apply to image outputs, using the `image check` model purpose (a vision-capable model). Only an image that passes every applicable check is **promoted**: its media-asset row, the only thing that makes bytes addressable, is created in the same transaction that attaches it to its target — a story position, after revalidation (FR-IMG-4), or the catalog entry's candidate list (FR-IMG-7). Candidates leave staging when promoted and have their own retention, so the staging sweep never touches them. A violating image is deleted from staging, and generation retries within the bounded retry budget (FR-GUARD-6), each retry's outputs counting against the image limits (FR-IMG-11), then reports failure. If a policy that applies to image outputs cannot be evaluated because no image-check model is configured, the image is deleted from staging and the job reports the policy. Staged bytes are also deleted when a job fails, is cancelled, or ends `stale` or `target_gone`; a sweep removes any staging object older than a configured age (default 1 hour) left by a crash, and any promoted blob that never received an asset row. The audit record of a rejected image holds the job, the policy IDs, and the outcome — never the image. The output check is a **backstop with measured error rates** (NFR-QUAL-12), not an assurance that every image is safe; documentation shall describe it that way, and every generated image records its image-check model and, for each applicable policy, whether that model is certified for it (NFR-QUAL-12). Uploaded images go through the same staging and checks when an image-check model is configured; otherwise they are promoted as `unchecked`, and the consumer's moderation hook is the control (FR-MEDIA-2).
- **FR-IMG-4 (M).** **Generation jobs are bound to where they came from.** Image generation shall run as background jobs, never inside a turn's budget or deadline. A request returns a job ID and is idempotent (FR-CONC-6). Each job records its **origin**: for a story image, the story, the originating operation (the turn, for automatic illustration, or the image request), the target position with its turn variant, the audience viewpoint, and the timeline revision at enqueue; for a catalog image, the entry, the draft revision it was requested from, and a fingerprint of that draft's **image inputs** (visual identity, appearance, true age, content rating, visual style). Before promoting a story image (FR-IMG-3), the job **revalidates** in the attaching transaction. A story image is attached only if: the story still exists; the target turn variant is still active — not truncated, regenerated, or swapped away; the story is not paused (promotion waits while a backfill or rating check pauses it, then revalidates); the image passes the policies in force at that moment, so a rating tightened during generation applies; the erasure ledger names none of its depicted or named subjects (FR-ADMIN-9); and no amendment since enqueue changed the target turn's beats or a depicted character's appearance. Catalog results are never attached automatically; they become **candidates** (FR-IMG-7). A result that fails revalidation is deleted from staging, and the job ends `stale` (the source changed) or `target_gone` (the story or catalog entry no longer exists), with the reason; nothing is attached or returned. A promoted image is a media asset with full generation metadata: adapter, model, serving endpoint, prompt, negative prompt, requested and applied parameters (seed and reference images included), reference-image IDs, check status with the image-check model and its per-policy certification (FR-IMG-10), depicted subjects (FR-IMG-9), and the cost and usage the adapter reports. Limits and cost accounting follow FR-IMG-11.
- **FR-IMG-5 (M).** **Story images are anchored in the story.** An image in a story shall be a story record at a **narrative position** — after a given beat of a turn, or at an inter-turn slot — with an **audience viewpoint**: the output viewpoint (FR-RESP-12) that may receive it and, for an image Epistrel generates, whose perception its inputs are built from (FR-IMG-8). History reads return each image in place, next to the content it illustrates, and only to reads for its audience viewpoint; an image whose audience is `omniscient` is returned only to omniscient reads. Separately, a story image may name a **camera POV** — how the picture is framed: `third_person` (the default), `establishing`, or `over_the_shoulder` or `first_person` of a character present at that position. The camera POV is composition only: it never widens what the inputs may contain and grants no access. Story images follow timeline membership: truncation and regeneration discard them with their turn, untruncate and swap reactivate them, forks copy them by reference, and erasure deletes images that depict or name an erased subject (FR-IMG-9). A story image is created on request — the consumer names the position, the audience viewpoint, and optionally a camera POV, and asks Epistrel to generate it or uploads one (FR-IMG-8,10) — or automatically (FR-IMG-6), and may be deleted on request. Story images are generated one per request.
- **FR-IMG-6 (M).** **Automatic illustration.** A story setting `illustration_mode` ∈ {`on_request` (default), `auto`} shall control automatic images. Under `auto`, a render may mark an **illustration point** — a new location, a character's first appearance, a moment the scene turns on — and after the turn commits the Orchestrator queues a generation job with the turn's output viewpoint as its audience viewpoint and the default camera POV, at most `max_auto_images_per_turn` (default 1). The respond response lists pending images by job ID; each appears in history at its position when done. A regenerated turn gets new automatic images for its new content.
- **FR-IMG-7 (M).** **Catalog images are candidates, attached deliberately.** A character or scenario may request generated images — a primary image, gallery images, or a cover, `n` candidates at a time — built from its draft's perceivable visual identity or visual style under the entry's own rating guidance and image policies (FR-IMG-2,3). Each image that passes the checks becomes a **candidate**: its bytes leave staging for durable storage, and it gets a media-asset row in state `candidate`, owned by the entry's owner, plus a candidate record — candidate ID, entry, job, the draft revision and image-input fingerprint it was generated from (FR-IMG-4), and an expiry. A candidate is private: it is readable only through the entry's candidate endpoints — listed by job and previewed by content read or short-lived signed URL (FR-MEDIA-3) — and never appears in a card or full projection, in a story, or through general media reads. When every output of a catalog job has been checked, the job ends `candidates_ready` with the candidate IDs, or `failed` if none passed. The caller attaches a candidate deliberately, as an ordinary draft save that names the current draft revision (FR-CAT-3); the asset's state becomes `attached`, and from then on it is an ordinary media asset of the draft. A stale draft revision is rejected as a conflict, and a candidate whose image-input fingerprint no longer matches the draft — its appearance, visual identity, true age, rating, or style has changed — is rejected as `stale`; edits to other fields do not matter. A candidate generated before a publish can still be attached to a later draft whose image inputs match. Unattached candidates — asset row and bytes — are deleted after `candidate_ttl` (default 7 days). If the entry is deleted while a job runs, the job ends `target_gone`, and deleting an entry deletes its candidates.
- **FR-IMG-8 (M).** **A story image's audience viewpoint is enforced on its inputs.** Everything the image model receives for a story image — the prompt and any reference images — shall be built only from what the image's audience viewpoint perceived (FR-RESP-12,13): its filtered beats, the viewpoint character's own location described only as that character has perceived it, and the characters present as that viewpoint perceives them — never hidden world state, such as an unperceived occupant, a concealed feature of the place, or a character's undisclosed identity. With perception `none`, the filtered beats are every beat less `think` and `latent`. A character whose identity the viewpoint does not know (FR-PROP-7) is described from perceived appearance only, without that character's visual identity, seed, or reference images. A character whose identity the viewpoint does know contributes only visual-identity elements whose audience is `perceivable`; `restricted` elements are used only for `omniscient` story images (FR-CAT-4). Each depicted character's age reaches the image model only as the age band the viewpoint perceives (FR-IMG-12). Before generation, the prompt passes the deterministic protected-content match used for text (NFR-PRIV-4): it may contain no name, alias, or protected term that the viewpoint does not hold. Under `lite`, the prompt is built from the message the player was shown. **What is claimed:** a generated story image is made only from information its audience viewpoint perceived; the image model is never given anything else. **What is not:** images are not inspected pixel by pixel for unperceived content, so an image model can still produce such content by coincidence. A consumer-supplied prompt for a story image passes the same protected-content match but carries no further guarantee, and story images the consumer uploads carry none: Epistrel files them at the position and viewpoint the consumer names, and checking them is the consumer's responsibility. Documentation and product claims shall state the guarantee in this form.
- **FR-IMG-9 (M).** **Images declare who they depict, and erasure reaches them through it.** Every image shall carry a list of its **depicted subjects** — the story characters and catalog characters, personas included, that it shows. Epistrel fills it for images it generates, from the characters the prompt builder depicted, and a catalog character's own images always include that character. Age-conditioned checks never rely on this list alone (FR-IMG-12). Every upload and every consumer-prompted generation shall declare it: an explicitly empty list is accepted, an omitted one is rejected. Unnamed figures who are not characters (a crowd, a passer-by) are not subjects. Erasure (FR-ADMIN-2) reaches an image through its depicted subjects and through subjects named in its prompt, caption, or alt text (FR-ADMIN-6). Epistrel does not recognize people in pixels: a subject who appears in an image only visually, with no declared or named reference, is outside the erasure boundary, and the documentation says so (FR-ADMIN-8).
- **FR-IMG-10 (M).** **Image metadata states what is promised.** Every image read shall return the image's **source** — `generated` (from an Epistrel-built prompt), `generated_from_consumer_prompt`, or `uploaded` — and its **check status**: `passed`, with the image-check model and, **for each applicable policy**, the result and whether the model is certified for that policy (NFR-QUAL-12) — certification is never reported as a single status for the checker; or `unchecked`, meaning Epistrel did not check it (rejected images are never stored). A story image also returns its **viewpoint basis**: `filtered_inputs` for Epistrel-built prompts, `protected_term_match` for consumer prompts, and `none` for uploads (FR-IMG-8). `unchecked` means exactly that and shall never be presented or interpreted as passing. Epistrel makes no claim that an `unchecked` image fits the story's rating, or that an uploaded image respects its audience viewpoint, and the API documentation says so; a `passed` image carries only the measured assurance of its checker (NFR-QUAL-12).
- **FR-IMG-11 (M).** **Image limits count outputs, reservations are atomic, and cost counts every attempt.** The unit of the image limits is the **output image**: every image the provider returns counts once — kept, discarded by a check, discarded as stale, or left as an unattached candidate. Limits apply per story turn (the turn whose position the image is anchored to; an image at an inter-turn slot counts toward the turn before it), per story per day, per catalog entry per day, and per deployment per day, automatic and requested images together. **Defaults:** 4 per turn, 40 per story per day, 16 per catalog entry per day, and 200 per deployment per day, counted in output images; a catalog request asks for `n` candidates (default 4). Each limit is a whole number. 0 disables generation at that scope — requests are rejected at enqueue with `images_disabled` — and there is no unlimited value, so once an image adapter is configured, every deployment caps the outputs it admits per day. The limits govern admission, not spend: there is no currency ceiling, usage can exceed a limit through reported overage (below), some costs are recorded as `unknown`, and an ambiguous send may be billed twice by the provider. Before an adapter is configured, generation returns `not_configured` and costs nothing. The deployment and entry limits are deployment settings; the per-turn and per-story limits are story settings whose defaults come from the deployment, and configuration validation rejects a negative or missing limit. **Reservations are atomic:** before every provider call — the first attempt or a retry — the job reserves the outputs it is about to request against every applicable limit in one database transaction that locks the counters in a fixed order (deployment, story, turn, entry) and increments all of them or none. A request whose reservation fails is rejected at enqueue; a retry whose reservation fails ends the job `cap_reached`, with its staged results deleted. When the provider returns, the reservation converts to usage for the outputs actually returned and the rest is released; a provider that returns **more** outputs than requested has the extras discarded unchecked and unpromoted, while all of them count as usage and cost, the excess as overage flagged `extra_outputs`; a job that ends for any reason releases whatever it still holds, and a stalled or crashed attempt's reservation is released only at its horizon (below). **Fencing late returns:** every provider attempt carries an attempt token and has its own **reservation record**: job, attempt token, `requested` (the outputs reserved for that attempt — fixed when the record is created and never changed), `used`, `overage`, `extra_outputs`, and state ∈ {`held`, `settled`, `released`}. When an attempt settles with *m* outputs, its record gets `used = m`; `overage = m − covered`, where `covered = min(m, requested)` if the record was `held` and 0 if it was already `released`; and `extra_outputs = max(0, m − requested)`. For each limit scope and period, the **counters** are defined from the records: `reserved` = the sum of `requested` over records in state `held`; `used`, `overage`, and `extra_outputs` = the sums of those fields over records in state `settled`. `used` therefore includes overage, and `extra_outputs` is part of `overage`. A reservation is admitted only if `used + reserved + k ≤ limit`. The counters are stored and updated in the same transaction as every record change, the records are the source of truth, and a reconciler verifies that the stored counters equal the sums above and reports any drift. Every promotion and attachment checks that its token is still the job's current token, so a worker whose lease has expired can never promote or attach anything. A fenced token may do exactly one thing: **settle its own attempt** through the settlement path — one idempotent transaction, keyed by the attempt, that records the outputs returned and their cost against that attempt's reservation record and touches no other attempt's record. When a lease expires, the reaper advances the token and holds the attempt's reservation until the attempt's **horizon** — its start plus the adapter's request timeout and a grace period — and no new attempt for that job starts before then, so **before the horizon** a job never has two provider calls running at once. **After the horizon**, Epistrel cannot know whether the old call is still running unless the adapter can tell it. For an adapter that declares `confirms_completion` (FR-IMG-1), the job, now under its new token, calls `cancel`, then polls the old call's status until a terminal state is reported. **While the job waits for that definitive completion, no overlap is possible**; the wait is bounded by `confirm_wait_max` (below). **What a terminal state leads to:** on `succeeded`, the job **adopts** the outputs the status returned — no retry. It settles the old attempt's reservation record through the settlement path, with cost from the status or `unknown`. Because confirmation runs after the horizon, that record has already been `released`, so every adopted output is counted as usage **and as overage**. Overage is an accounting category only: the outputs within the requested `n` still go through the normal checks, revalidation, and possible promotion under the job's current token. Any outputs beyond `n` follow the extra-output rule — discarded unchecked and unpromoted, and flagged `extra_outputs`. On `failed` or `cancelled`, it settles the record (no outputs; cost from the status or `unknown`) and retries. Settlement is idempotent per attempt, so when the fenced worker's original call later returns the same outputs, its settlement finds the record already settled and changes nothing; its bytes are deleted, and the attempt is reported `late_duplicate`. The only exceptions are a cost still recorded as `unknown`, which that return may fill in once, and a **presumed** settlement, which accepts exactly one correction (below). Outputs are counted per attempt, never per copy. If no terminal state arrives within `confirm_wait_max` (default 30 minutes), the job stops polling and falls back to the non-confirming rule below, and the fallback is reported. From then on **overlap is possible**: the retry may run while the old call is still running, and the old call's output, if it ever returns, is a late result — settled as overage, reported `late_after_horizon`, never adopted or promoted. For an adapter that cannot (the default assumption), the job may retry at the horizon, and a late result from the old call can arrive while the retry runs: it is settled as overage (below) and never disturbs the retry's reservation or promotion. A result returned to a **fenced worker** is never promoted (a result the job's current owner retrieves through `status` is adopted instead, as described above): before the horizon, the settlement path converts its reservation record from `held` to `settled` with the outputs returned counted as usage (they were produced and may be billed) and the unused remainder released; its cost is recorded, its bytes are deleted, and the attempt is reported `late_discarded`. If no result arrives by the horizon, the reaper marks the record `released` and the attempt's cost is reported as `unknown`, unless the adapter can retrieve it from the provider. A result that arrives **after** its horizon is still settled — its outputs are added to usage as **overage** against an already-released record, its cost is recorded, its bytes are deleted, and the attempt is reported `late_after_horizon`. Overage — usage beyond what a reservation covered — can push a counter past its limit, but only by outputs a provider actually returned beyond their reservation: late results from attempts abandoned at their horizon (normally at most that attempt's `n`) and extra outputs from a provider that returned more than requested. New reservations then see the higher usage and are refused until the period resets, so the limit corrects itself, and overage is reported per job, story, and deployment. Concurrent requests therefore never jointly **reserve** beyond a limit; **usage** can exceed a limit only through overage (below). **Days** are calendar days in the deployment's configured time zone (default UTC); a reservation counts toward the day in which it is made, and per-turn limits never reset. **Each reservation record stores an immutable snapshot of the counters it charges:** the list of (scope, scope key, period) captured when the record is created — the deployment, the story, and the catalog entry, each with the calendar day then in effect, and the story with the turn index then targeted. Settlement, release, and reconciliation always use that snapshot, never the current time or the target's current state. A result settled after midnight therefore counts toward the day it was reserved in, and a deleted target or a regenerated turn changes nothing about which counters are charged. Counter rows and reservation records are deployment-level accounting with no story content: they outlive the story or entry they refer to until their period has closed, every record referring to them is settled or released, and the deployment's **accounting retention** (default 90 days) has passed, so a late result or a correction always finds them. A result that arrives even later still has its cost recorded and is reported `late_unaccounted`, without changing counters that no longer exist. **Provider delivery is at least once; promotion is at most once.** Before every provider call, the attempt is recorded as `sending`, with a provider idempotency key derived from the job and the attempt, and `submit` is called only after that record commits. For an `async` adapter (FR-IMG-1), `submit` returns the provider's request identifier on acknowledgement and it is committed (`accepted`) before the results are awaited through `collect`, so a crash after acknowledgement leaves a known request — recovered through `status` by a confirming adapter, and otherwise held to its horizon like any stalled attempt — never an ambiguous send. For a `sync` adapter, the identifier arrives only with the results, so the whole call is the ambiguity window. If a worker crashes after `sending` was recorded but before the request identifier or result was, the send is **ambiguous** — Epistrel cannot tell whether the provider accepted it — and recovery depends on the adapter (FR-IMG-1). With `idempotency_keys`, recovery re-sends the same attempt with the same key, so the provider returns the original request's result instead of starting a second one. `confirms_completion` cannot help, because a status lookup needs the request identifier that was never recorded. Otherwise the attempt is marked `ambiguous`, its reservation is held to its horizon and then settled as **presumed** — its requested outputs counted as usage, with cost `unknown` — so the limits err toward generating less, and the job may then retry, which can bill the provider twice for one job. **A presumed settlement is provisional.** The presumption settled the record while it was still `held`, so its outputs count as covered. If the attempt's actual result later reaches the settlement path, the record is **corrected once** to what a `held` settlement with *m* outputs would have recorded: `used = m`, `overage = extra_outputs = max(0, m − requested)`, and the result's cost. The counters named in its snapshot move by the difference — `used` falls when fewer outputs came back than were presumed, and `used`, `overage`, and `extra_outputs` rise when more did. The record's settlement basis becomes `corrected` (it was `presumed`; every other settlement is `actual`). The outputs are never adopted or promoted, since the job moved on at the horizon: their bytes are deleted, a retry already running is undisturbed, a job that already ended — including one ended `cap_reached` by the presumed usage — stays ended, and the attempt is reported `late_after_presumed`. Any later delivery of the same result is `late_duplicate`. An actual result that arrives **before** the horizon settles the record normally (`held` → `settled`, reported `late_discarded`), and the attempt is never presumed. Ambiguous sends are counted and reported per job, story, and deployment, so operators can reconcile them against provider billing. A result that never reaches Epistrel is never promoted, and no output is promoted twice. **Cost** reporting covers every provider attempt — billed outputs whatever became of them, and attempts the provider did not bill, recorded at zero — and is reported per job, per story, per catalog entry, and per deployment.
- **FR-IMG-12 (M).** **Two data paths: the safety check knows true ages; the image model does not.** The image **safety path** — prompt-policy evaluation and the image-output check (FR-IMG-3) — shall receive the canonical true age (FR-CAT-12) of every subject it resolves. The **generation path** — everything the image model receives — shall carry only what the image's audience may perceive (FR-IMG-2,8), and nothing from the safety path is fed into it. **Subject resolution** for age-conditioned policies covers the union of: (a) the subjects the prompt builder depicted or the request declared (FR-IMG-9); (b) every character named in the prompt, caption, or alt text, resolved through names and aliases (FR-PROP-6), so a consumer prompt that names a character is checked against that character's true age even when its declared list is empty; and (c) for a story image, the characters authoritatively present at its position (FR-TURN-10), which is what "in the presence of" means for an image. A depicted person who resolves to no character — "a young girl", "a couple", or a name the story does not know — is classified from the prompt's description as adult, minor, or indeterminate (model-assisted), and an indeterminate figure is treated as a minor for age-conditioned policies, so an unresolvable figure fails closed. The image-output check receives the same resolved subjects and true ages as context for its judgment.
- **FR-IMG-13 (M).** **The safety path's data flow is stated, and hosted checkers are outside the erasure boundary.** The safety path's model calls — model-assisted prompt-policy evaluation and figure classification (the `guardrail check` purpose) and the image-output check (the `image check` purpose) — shall send only: the image prompt, caption, and alt text; the text of the applicable policies; each resolved subject as an opaque label with its true age and the visual descriptors the prompt already uses; and, for the output check, the image itself — generated, or uploaded when a checker is configured (FR-IMG-3). They shall not send story text, beliefs, other canon, or any character name the prompt does not itself contain. The model guide's **data-flow table** (FR-MODEL-13) shall list, for every model purpose and for the image adapter, what each receives, and shall state that when the safety purposes are routed to a hosted provider, the images and true ages they receive leave the deployment and are kept under that provider's terms, outside Epistrel's erasure boundary (FR-ADMIN-8); a deployment that needs them kept in-house routes both purposes to self-hosted models. The model-configuration read names the endpoint for each purpose (FR-MODEL-1), which is how an operator sees where this data goes.

### 18.8 Message feedback (FR-FB) — Engine Core store + API

Players can rate any message Epistrel generated. Feedback is a signal for whoever runs the deployment: it never changes the story or, for now, the engine's behavior.

- **FR-FB-1 (M).** **Rating a message.** The consumer shall be able to rate a generated message — identified by its message ID, which names the turn and the variant — with a **rating from 1 to 5**, optional **reason tags**, and optional **free text** (length-capped). The seeded tags are `out_of_character`, `repetitive`, `forgot_something`, `factual_error`, `ignored_my_action`, `too_long`, `too_short`, `should_have_been_blocked`, and `other`; a deployment may add its own, and an unknown tag is rejected. Each rating records the requesting principal (FR-AUTH-4) and the context the message was produced under: its operation, configuration fingerprint, profile version, model per purpose, content-rating version, and quality status (FR-PROF-16). A principal has at most one rating per message: rating again replaces it (the earlier value stays in the audit history), and a rating can be retracted.
- **FR-FB-2 (M).** **Feedback never touches the story.** Feedback shall be an audit-category record (FR-STORE-25): it never enters memory, canon, beliefs, retrieval, or any generation context, and it changes no engine behavior. It belongs to the message variant it rated: a regenerated message keeps its own feedback, and the new variant starts unrated. It has its own retention setting — by default, kept for the life of the story. Its free text is indexed for subject references, so erasure redacts it (FR-ADMIN-6); deleting the story deletes its feedback; feedback on a compacted message is kept, marked `compacted` (FR-STORE-32); and operational metrics carry counts only, never feedback text (NFR-SEC-4).
- **FR-FB-3 (M).** **Reporting and review.** Epistrel shall report feedback aggregates by profile version, configuration fingerprint, model per purpose, content rating, scenario, tag, and time window, together with the implicit signals already in the log: regeneration rate, regenerations shortly after a low rating, swaps back to an earlier variant, and rewinds. Ratings tagged `should_have_been_blocked` appear on a **guardrail review list** (candidate guardrail misses), and ratings tagged `forgot_something` or `factual_error` on a **memory review list** (candidate memory or verification misses). Feedback is flag-only: nothing in the engine reads it to change a turn, a profile, or a guardrail.
- **FR-FB-4 (M).** **Opt-in export for evaluation.** A deployment setting `feedback_export` (default **off**) shall enable an operator endpoint (under `/admin`, FR-AUTH-1) that exports rated messages as labeled cases for the eval harness: the message text, the player input it answered, its story position, configuration fingerprint, rating, tags, and free text. Every export is recorded (what, when, by which principal). Delivered exports are outside the erasure boundary (FR-ADMIN-8), and the documentation says so.

## 19. Observability (FR-OBS)

- **FR-OBS-1 (M).** Structured logs, metrics, and traces for all operations.
- **FR-OBS-2 (M).** Eval hooks: raw render, verification verdicts, repair rung used, per-purpose model-call counts, and per-operation latency. For every escalation to the entailment model, the following shall be recorded: the **gate reason** (unresolved predicate / world-knowledge conflict / partial match), the **deterministic tentative verdict** that would have been returned, the **model's final verdict**, an **agreement flag** (did the model flip the tentative verdict), the **normalized predicate/claim shape and confidence** (for clustering), and the **downstream correction outcome** (did a `contradicted` lead to a repair that was kept).
- **FR-OBS-3 (S).** Per-turn model cost and call counts tracked for budget enforcement.
- **FR-OBS-4 (M).** The engine shall support **shadow evaluation** of a proposed gate tightening: continue escalating as configured while recording what the tightened gate *would* have decided, so a tightening can be validated against real traffic before promotion (see NFR-PERF-5).

## 20. Non-functional requirements

### Performance & efficiency (NFR-PERF) — dev/hobby scale targets
- **NFR-PERF-1 (M).** Viewpoint-scoped retrieval (resolution + hybrid search + ranking), excluding model calls, shall complete within **p95 ≤ 150 ms** for a story with up to ~50k memories.
- **NFR-PERF-2 (M).** Deterministic `verify` (no model fallback) shall complete within **p95 ≤ 50 ms**.
- **NFR-PERF-3 (M).** An atomic turn commit shall complete within **p95 ≤ 250 ms**, excluding model/embedding latency.
- **NFR-PERF-4 (M).** **Concurrency on a reference host.** Epistrel shall sustain **10 stories in active play at once** on the **reference host** — 4 vCPU, 16 GB RAM, NVMe SSD, with Postgres and the background workers on the same host. The **reference workload** is open-loop: each story submits turns on a fixed schedule with `turn_concurrency = queue`, so a slow engine builds a backlog instead of slowing its arrivals, for 30 minutes, against a stub model that answers every call after a fixed 2 seconds. It has three variants, each run once the capabilities it needs are delivered: **Lite** — stories of 20,000 events (a 10,000-message transcript with its rolling-summary segments) and 50 pinned memories each, one turn every 15 seconds per story; **structured** — stories of 10,000 memories and 20,000 events each, single-character turns, one every 60 seconds per story; and **multi-character** — the structured stories playing two-character turns with per-character renders, one every 60 seconds per story. Model time is excluded, as in the engine-only budgets. A variant passes when the budgets that apply to what its stories run hold at p95 across all stories — turn commit (NFR-PERF-3) in every variant, and viewpoint-scoped retrieval and deterministic verify (NFR-PERF-1,2) in the structured ones — no request fails, no turn is lost or duplicated, and **each story separately**, not only in aggregate: completes every turn submitted at least 2 minutes before the run ends; after the first 5 minutes, never has more than one turn waiting behind the one in progress; never keeps a turn waiting longer than one schedule interval (15 or 60 seconds) to reach the front of its queue; and starts each turn's first model call within 1 second of the turn reaching the front, at p95. Results on other hosts are reported, not gated.
- **NFR-PERF-5 (M).** Entailment escalation shall be launched conservatively (high continuity) and driven down by evidence, not capped by a fixed launch target. The engine shall measure and report **escalation yield** — per gate-reason and per predicate-shape cluster, the fraction of escalations where the model *flips* the deterministic tentative verdict — and the **consequence** of those flips (did a flip prevent a kept repair). A predicate-shape may be tightened to deterministic-resolved only when its yield is low **and** its residual flips are low-consequence, and only after **shadow validation** (FR-OBS-4) shows the tightened gate would have agreed with the model over a real-traffic window. (~20% overall escalation is a useful reference baseline, not a launch gate; an operator may set an explicit escalation ceiling if their deployment has a hard cost limit.)
- **NFR-PERF-6 (M).** **Per-turn model budget and deadline.** Every turn shall run under a **model-call budget** and a **wall-clock deadline**, configurable per story and per request. `max_model_calls_per_turn` defaults to **4 + 5 per primary character + G + O** (G and O below): per primary character, its render, its claim extraction, one entailment check, and one repair (a re-render plus that re-render's extraction); per turn, salience, time estimation, the polish render, and claim detection on the composed message; plus the guardrail calls G and, when the turn can become staged, its outcome step O. `turn_deadline` defaults to 45 s, excluding any synchronous external-confirmation wait, which has its own budget (FR-EXT-15). Retries and repairs count against the budget. **Safety reservation (structured pipeline):** when a turn is planned, Epistrel reserves **S = B + C + G + O** calls that optional work can never spend: **B**, one extraction per planned beat — one beat per primary render, with reactive narration part of its narrator's beat — reserved under both `always` and `gated` extraction and released if unused; **C**, one for claim detection on the composed message, released if composition falls back to deterministic assembly, which adds no new text (FR-RESP-8); **G**, the model-assisted guardrail calls (FR-GUARD-9,10): one per model-assisted policy that applies to input, for the turn's input, plus one per model-assisted policy that applies to output, for the turn's first **output checkpoint**. A model-assisted policy costs one call per text it checks, so a policy that applies to both input and output costs two. An ordinary turn has one output checkpoint, its released message; a staged turn has two — its intent-stage beats, checked before the intent commits because they are readable from then on (FR-EXT-16,19), and its completed message. **O**, the staged-turn reservation: whether a turn becomes staged is known only once a render requests an effect, so O is reserved at planning for every turn in a story with a write-capable provider declaring `confirmation = synchronous` (FR-EXT-15). A staged turn has exactly one outcome step, so O is fixed: the outcome step's render, its extraction, and one call per model-assisted output policy for the second output checkpoint — 2 + the number of model-assisted output policies. O is part of the safety minimum, so it can cause a turn to be planned smaller or rejected like the rest of S, and it is released for optional work as soon as every render has finished without requesting such an effect. In stories with no such provider, O = 0. A repair may start only if its re-render and that re-render's extraction can both be reserved; otherwise the deterministic repair rungs or the safe fallback apply (NFR-PERF-7). A repair triggered by an output policy must also reserve the re-check of its output by every model-assisted output policy; otherwise the stored safe fallback is used (FR-GUARD-6). **Fitting the budget:** a turn is planned so that its renders plus S fit within `max_model_calls_per_turn`. If they do not, primary characters beyond the first become reactive narration or are deferred (NFR-PERF-7 step 5) until they do. If even one primary render plus its safety reservation exceeds the budget, the turn is **rejected before any model call** with `budget_below_safety_minimum` and the minimum required, and nothing is recorded. Configuration validation warns when a story's effective budget is below that single-primary minimum (FR-PROF-7). Because every beat needs its reserved extraction, the budget also bounds the number of beats in a turn. In `lite` there is no claim detection: the budget covers the one generation call, model-assisted guardrail checks on input and output (reserved first; a policy applying to both is two calls), and guardrail-triggered regenerations (FR-LITE-7), and a Lite budget smaller than one generation call plus those checks is rejected the same way.
- **NFR-PERF-7 (M).** **Degradation when the budget or deadline is exhausted** shall follow a fixed order and shall never release unchecked content: (1) skip the polish pass and use the deterministic assembly of verified beats (FR-RESP-8); (2) stop repair attempts after the first and use the deterministic rungs of the repair ladder (trim, drop the offending span) or the stored in-character safe fallback (FR-GUARD-6); (3) default any remaining model-adjudicated testimony acceptance (FR-BELIEF-3); (4) resolve any remaining entailment questions to the safe disposition (FR-VERIFY-8); (5) without a time estimate, remove the undeclared narrated skip by deterministic span removal rather than guess a duration; (6) render further characters requested as primary as reactive narration where the story allows and the character's `primary` role is not fixed (FR-MULTI-7), otherwise defer them to the next turn, listed in the response's `deferred_characters` — applied first, at planning, whenever the safety reservation would not otherwise fit (NFR-PERF-6), and a turn whose single-primary minimum exceeds the budget is rejected before any model call; (7) if a beat cannot receive its reserved claim detection before the deadline, that beat is not released — the safe fallback replaces it. The response shall report `model_calls`, `elapsed_ms`, and the list of degradation steps taken.
- **NFR-PERF-8 (M).** **End-to-end latency is reported, not assumed.** Because full-turn latency is dominated by model time and varies by model and hardware, the model matrix (NFR-PORT-3) shall report end-to-end p50/p95 turn latency and model calls per turn, by purpose, for single-character, multi-character, and repair-heavy turns on each tested model tier; the engine-only budgets of NFR-PERF-1..3 are not end-to-end promises.

### Determinism (NFR-DETERM)
- **NFR-DETERM-1 (M).** With the stub model adapter and a fixed embedding, identical inputs shall produce byte-identical Engine Core outputs and state. After an erasure, the guarantee applies to replay of the post-erasure log; replays from before the erasure are not reproducible by design (FR-STORE-1, FR-ADMIN-2). Vectors re-embedded by a live embedding model on reactivation are outside this guarantee unless `retain_dormant_vectors` is on (FR-STORE-30).
- **NFR-DETERM-2 (M).** Regeneration shall satisfy the commit/regen boundary (FR-COMMIT-8) deterministically.

### Scale (NFR-SCALE)
- **NFR-SCALE-1 (M).** Performance budgets shall hold for stories up to ~50k memories / ~100k events, with a documented path beyond. Capacity is claimed only for the measured range (P-06); any larger figure is labeled an unvalidated estimate until a benchmark measures it, and the dev/hobby target (NFR-PERF-4) is stated separately from any future capacity.
- **NFR-SCALE-2 (M).** **Storage growth, stated honestly:** append-only history grows linearly with story length, and so does the number of **active records** on a long active timeline. The bounded guarantees are: (a) **retrieval-eligible** (hot) memories and hot vectors stay within the aggregate bounds of FR-MEM-8 (unpinned budgets plus the per-character and per-story pin caps) except during an overflow episode, and every overflow episode ends no later than `retirement_max_lag` committed turns after it began; enforced by mandatory retirement and admission-limited pinning (FR-MEM-8); (b) the **retrieved context** per turn stays within its token budget (FR-MEM-6); and (c) total storage stays linear with a bounded constant under the retention and compaction policy (FR-STORE-30). Neither the active record count nor total storage is claimed to be bounded.

### Quality floors (NFR-QUAL)
Initial floors, measured on the recommended model tier and recalibrated as labeled sets grow:
- **NFR-QUAL-1 (M).** Knowledge-asymmetry violations: **0**; private-thought leaks: **0**. These are **zero-tolerance metrics** with their own gate (NFR-QUAL-8): they pass only if no violation is observed across all seeds on a labeled set of at least the configured minimum size. Passing is evidence of a low rate (reported with its upper bound), not proof of a zero rate; the structural control of NFR-PRIV-4 is what bounds leakage by construction. Product and documentation claims shall follow the same rule: a clean eval run may be described as "no leaks observed in n cases (95% upper bound ≈ 3/n)", never as "leak-free" or "cannot leak".
- **NFR-QUAL-2 (M).** Entailment: false-contradiction rate **≤ 2%**; false-support rate **≤ 1%**.
- **NFR-QUAL-3 (M).** Consolidation faithfulness: **≥ 98%** of reflections entailed by their source records.
- **NFR-QUAL-4 (M).** Salience detection: recall **≥ 95%**, precision **≥ 70%**.
- **NFR-QUAL-5 (M).** Structured output: **≥ 99%** valid after retry.
- **NFR-QUAL-6 (M).** Resolution retrieval: recall@10 **≥ 0.9**.
- **NFR-QUAL-7 (M).** Generation conformance (prompt params honored, valid turn structure): **≥ 98%**.
- **NFR-QUAL-8 (M).** **Gate rules and reporting.** Rate metrics (NFR-QUAL-2..7, 9, 10, 14, and the deployment-set image-check floors of NFR-QUAL-12) pass when the mean across seeds clears the floor by more than one standard deviation. Zero-tolerance metrics (NFR-QUAL-1, and the minors-policy false-negative rate of NFR-QUAL-12) use an **observed-zero rule** instead: zero violations across every seed, on a labeled set of at least **300** cases per metric, reported with the one-sided 95% upper confidence bound on the true rate (≈ 3 / n). Every eval result shall report its sample size, seed count, and model/version.
- **NFR-QUAL-9 (M).** Time estimation (FR-CLOCK-7): **≥ 85%** of estimated narrated durations fall within the human-labeled acceptable range on the time-skip eval set.
- **NFR-QUAL-10 (M).** Claim-detection recall (FR-VERIFY-13): **≥ 95%** of labeled factual claims embedded in structurally valid output — possession changes, quantities, time expressions, identity and relationship facts, and protected content — are detected, measured on an adversarial labeled set separately from verification accuracy on already-extracted propositions, and reported per layer and per `extraction_mode`.
- **NFR-QUAL-11 (M).** Quality floors apply to the presets (FR-PROF-3) that enable the capability each one measures, and are claimed only for certified configurations (FR-PROF-15,16); every eval report states the configuration fingerprint it ran under; floors are reported per preset so tiers can be compared on quality as well as cost (NFR-PERF-8).
- **NFR-QUAL-12 (M).** **Image-check quality.** For each image-check model and each policy that applies to image outputs, false-negative and false-positive rates shall be measured on a labeled image eval set that includes **age-sensitive cases** — adults with youthful features, minors in ordinary non-sexual scenes, ambiguous apparent ages, characters whose true age differs from how they look — and **adversarial images** — stylization, partial occlusion, overlaid text, crops — and reported per policy and per model with confidence bounds. The seeded minors policy's false-negative rate is a zero-tolerance metric under the observed-zero rule (NFR-QUAL-8): reported with its upper bound, never as zero. Other policies' rates are reported against floors the deployment sets. An image-check model counts as certified for a policy only after such a run (FR-PROF-15); until then it is an uncertified backstop, and generated images say so (FR-IMG-3).
- **NFR-QUAL-13 (M).** **Creative quality is outside the guarantee.** Epistrel guarantees, structurally, that each character's definition (personality, dispositions, interaction style, sample dialogue) reaches that character's generation context, that the scenario's story drivers (hooks, objectives, director guidance, planned reveals) reach the director's context, and that planned reveals reach characters only through their visibility rules (FR-EPI). It does **not** guarantee, hold to a floor, or gate on whether a character stays in voice or whether a story follows its hooks, objectives, and planned reveals: that depends on the model and its prompts and is an application-level concern. Epistrel does report these as measured signals (NFR-QUAL-15), and it holds its own interventions in the prose to a relative, aggregate floor (NFR-QUAL-14). Documentation and product claims shall say so.
- **NFR-QUAL-14 (M).** **Engine interventions must not degrade prose, in aggregate.** This is an aggregate evaluation objective, not a per-message promise: an individual repaired, composed, or polished message can still read worse than its draft. Wherever the engine changed the model's first draft — a repair, a regeneration under constraints, multi-character composition, or polish — the final message shall be no worse than the first draft (for a multi-character turn, the raw renders in order) on **voice consistency and readability**, judged with differences in factual content excluded. On the text-quality eval set, a pairwise judge with positions swapped shall prefer the first draft in at most **55%** of non-tied comparisons — parity within a five-point margin — reported per intervention type (each repair rung, composition, polish). **Evidence per type:** a type needs at least **300 non-tied pairs** before it can pass. It passes when the mean first-draft preference across seeds plus one standard deviation is at most 55% (NFR-QUAL-8), and every report gives the rate with its 95% confidence interval. A type below the minimum is reported as `insufficient_evidence` — neither passed nor failed — and a certification states which intervention types the floor was established for. The eval set includes scenarios built to trigger each repair rung, so rarely used rungs can reach the minimum. The judge uses the `quality judge` model purpose and must first be **calibrated**: at least **75%** agreement with human preferences on at least 200 labeled pairs, reported with its confidence interval. An uncalibrated judge's results are reported but cannot certify the floor (FR-PROF-15).
- **NFR-QUAL-15 (M).** **Text-quality signals are reported, not gated.** For each configuration fingerprint, Epistrel shall report, without floors: **repetition** — the share of messages whose n-gram overlap with the previous few messages exceeds a threshold, and repeated openings — and **length accuracy** — the share of messages within the requested length's tolerance — both computed without a model; and, on the scenario suites, judge-scored **voice consistency** (does each character's speech fit their definition) and **story-driver adherence** (are hooks and objectives offered, and does the story move toward planned reveals). Each judge score states its calibration status and, where message feedback exists, its correlation with users' ratings (FR-FB-3). These are measurements, not guarantees (NFR-QUAL-13).

### Reliability (NFR-REL)
- **NFR-REL-1 (M).** A crash mid-turn shall leave no partial ordinary turn applied, and shall leave a staged turn exactly at a **stage boundary** — never partway through a stage — from which it resumes (FR-EXT-17).
- **NFR-REL-2 (M).** State shall be fully recoverable from the event log.
- **NFR-REL-3 (M).** Model/provider timeouts or failures shall degrade gracefully, never block the hot path indefinitely, and never corrupt state.
- **NFR-REL-4 (M).** A client retry after a timeout, dropped connection, or engine restart — using the same idempotency key — shall never produce a duplicate turn or a second, different message for the same request (FR-CONC-6). The full original result is returned within the result window; after it, the retry resolves to a reference to the original operation rather than a re-execution.
- **NFR-REL-5 (M).** **Background work survives missed wake-ups and restarts, and every timed lifecycle job has an owner.** Every background job and every timed lifecycle action shall be a durable database row with a due time; notifications only shorten latency, and no work depends on one being delivered. Workers shall claim due rows when notified **and** on a fixed polling interval (default 5 s), so a missed notification delays work by at most one interval. Every claim holds a renewable lease, and on start-up each worker shall run a **recovery pass**: reclaim jobs whose lease has expired (with fencing, FR-IMG-11), recover image attempts left in `sending` (FR-IMG-11), and run every overdue timer. **Epistrel's own workers own every timed lifecycle job**, with no external scheduler, cron, or broker required: lease expiries and image-attempt horizons, `confirm_wait_max` fallbacks, ambiguous-send settlement, staging cleanup and candidate expiry (FR-IMG-3,7), the media sweep (FR-MEDIA-2), idempotency-result expiry (FR-CONC-6), outbox recovery and expired-hold release (FR-EXT-17,22), State reservation expiry (FR-STATE-14), retention and automatic compaction runs (FR-STORE-30,32), counter reconciliation (FR-IMG-11), and scheduled certification canaries (FR-PROF-17). Each recurring task runs once per due time across all workers, and every timed action is idempotent, so repeating one after a crash changes nothing. Work that came due while no worker was running runs at the next start-up — late, never skipped — and a recurring task that missed several runs runs once. The default deployment runs the workers alongside the API (NFR-OPS-1). A health endpoint shall report worker heartbeats and the age of the oldest overdue job and timer, and shall report `degraded` when no worker has sent a heartbeat within a configurable timeout (default 60 s) or a timer is overdue beyond a configurable lag (default 5 min), so a deployment running without workers is visibly degraded rather than silently broken.

### Security (NFR-SEC)
- **NFR-SEC-1 (M).** The policy store shall be immutable to in-world and external content.
- **NFR-SEC-2 (M).** Memory, tool, and external content shall be treated as an injection surface; provenance/trust tiers shall gate trust.
- **NFR-SEC-3 (M).** Model API keys shall live in Epistrel config, never in story data.
- **NFR-SEC-4 (M).** Operational logs, metrics, and traces shall not contain story content (prose, thoughts, memories) by default; any content-bearing debug logging shall be opt-in, access-restricted to operators, and subject to bounded retention and erasure.
- **NFR-SEC-5 (M).** Service authentication (FR-AUTH-1) shall be enforced on every REST endpoint. Epistrel shall expose no MCP server and no end-user-facing interface (FR-API-2, FR-AUTH-2), and the output-viewpoint rules (FR-RESP-12) shall apply identically over REST and the in-process library.

### Privacy (NFR-PRIV)
- **NFR-PRIV-1 (M).** Private `think` memories (of any character, minor characters included) shall never leak across character viewpoints **and shall never be disclosed in player-facing output** — verbatim, paraphrased, or as narrated inner state recorded only in `think` (FR-TURN-3) — while legitimate inference from a character's own perceived `say`/`do` remains allowed (enforced structurally at retrieval and context assembly, NFR-PRIV-4, and additionally — as a measured, secondary check — at composition and by the output-viewpoint filter, FR-RESP-12; property-tested).
- **NFR-PRIV-2 (M).** Right-to-be-forgotten erasure shall be complete and verifiable within the supported erasure boundary (FR-ADMIN-6..8), including subject references in derived prose.
- **NFR-PRIV-3 (M).** No private knowledge shall be granted on the basis of non-authoritative input. Perception, co-location, and audience shall be determined from authoritative state; the consumer-supplied scene roster may inform candidates but shall never grant perception (FR-TURN-10). Property-tested with manipulated/mistaken rosters.
- **NFR-PRIV-4 (M).** **Privacy is structural first.** The primary privacy control is context assembly: a character's generation context shall be built only from that character's authorized partition, viewpoint-filtered working memory (FR-MEM-11), objective canon visible to them, and their own time belief and schedules (FR-CLOCK-11); content the character is not authorized to know is never placed in their context. Output scanning — protected-content matching, claim detection, and the PRIV checks — is a **secondary, measured** control: exact and alias matching catches some disclosures, but paraphrase and indirect disclosure are only caught to the extent model-based detection catches them. Documentation shall not describe output scanning as proof of zero leakage, and NFR-QUAL-1 results shall be reported as evidence with an upper bound (NFR-QUAL-8), not as a true zero rate. For generated story images, the same structural rule applies to the image model's inputs (FR-IMG-8); the images themselves are not inspected for unperceived content.

### Portability (NFR-PORT)
- **NFR-PORT-1 (M).** **Protocol compatibility:** Epistrel shall connect to any model endpoint that speaks the OpenAI-compatible wire format, public or local, for every model purpose and for embeddings.
- **NFR-PORT-3 (M).** **Capability is stated separately from protocol.** Each model purpose shall publish its capability requirements (structured-output support or reliable parse-validate-retry, minimum context length, and passing that purpose's conformance suite at its eval floor, NFR-QUAL). A model "works" for a purpose only if it meets those requirements; protocol compatibility alone is not a quality claim.
- **NFR-PORT-2 (M).** Model, embedding, lexical-search, and external-provider adapters shall be swappable without Engine Core changes.

### Operability (NFR-OPS)
- **NFR-OPS-1 (M).** A single `docker compose up` plus one model endpoint shall stand up a working deployment, including the workers that own every timed lifecycle job (NFR-REL-5).
- **NFR-OPS-2 (M).** No external broker, cache, or scheduler shall be required at hobby scale.

### Maintainability & licensing (NFR-MAINT)
- **NFR-MAINT-1 (M).** Apache-2.0 with a license-compatible dependency graph.
- **NFR-MAINT-2 (M).** Public contracts shall be typed and schema-documented.
- **NFR-MAINT-3 (M).** Test and eval gates per *04* shall be enforced in CI.

### Cost (NFR-COST)
- **NFR-COST-1 (M).** The deterministic-first design shall minimize per-turn model calls; call counts shall be observable and budgeted per turn (NFR-PERF-6,7).

## 21. Traceability

Each requirement is exercised by one or more tests in *04 — Testing Plan*. The binding per-requirement mapping is the generated appendix in *04 §15*: every **M** requirement maps to at least one identified test, and the table is regenerated and checked in CI. Acceptance of the full release = all **M** requirements have passing tests meeting their thresholds, including the NFR-QUAL eval floors; each milestone is accepted on its own gate (§22, *04 §13*).

## 22. Delivery milestones

The specification describes the whole engine. It is built in **milestones** M0–M8. **M0 (infrastructure)** and **M1 (project setup and CI)** come first; they are not yet planned and carry no requirements. The engine itself is delivered in seven milestones, M2–M8, so that a game can integrate early and the riskiest subsystems are proven before the rest is layered on them. Each milestone is independently testable. Its **gate** is every **M** requirement assigned to it or to an earlier milestone, tested over every capability delivered so far, including the eval floors of the capabilities it delivers (*04 §13*). A requirement is assigned to the milestone that first delivers what it is about. Cross-cutting requirements — atomicity, idempotency, determinism, budgets, guardrails, security, observability — are gated from the milestone that introduces them and extend to each capability as it lands: their tests grow with the engine, and a later milestone fails its gate if it breaks one. Tests are scoped the same way: every test, or every **milestone part** of a test, gates from exactly one milestone and may exercise only capabilities delivered by then (*04 §13*), so a milestone's gate never depends on a later capability. CI checks each part's requirements against this table and its text against a capability lexicon of the terms each milestone introduces. Operations, endpoints, and settings appear with the milestone that delivers their capability; no earlier milestone ships them as inert placeholders. The sequence may be changed by an ADR, provided the dependency order below holds; the assignment table is the source of truth for the milestone column in *04 §15*.
