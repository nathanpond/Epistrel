# Epistrel Engine

[![CI](https://github.com/nathanpond/Epistrel/actions/workflows/ci.yml/badge.svg)](https://github.com/nathanpond/Epistrel/actions/workflows/ci.yml)

A viewpoint-aware memory engine for character/actor GenAI: it tracks what each character knows and believes, and how characters stand in relation to one another and the truth. This repository is the service (Engine Core + Orchestrator) and has no UI. The human-facing test harness lives in [Epistrel-Console](https://github.com/nathanpond/Epistrel-Console).

**Status:** early scaffold. The design is in [`docs/`](docs/): whitepaper, architecture, requirements, testing plan, ADR log.

## Run

With Docker only (builds locally; or pull the **unstable** `edge` image, `docker pull ghcr.io/nathanpond/epistrel:edge`, which tracks `main` — releases and rollbacks are described in [RELEASING.md](RELEASING.md)):

```bash
docker compose up            # Engine + PostgreSQL 16/pgvector; migrates, then serves http://localhost:8000
curl localhost:8000/health   # {"status":"ok","checks":{"database":"ok","workers":{"alive":2,...},...}}
docker compose down -v       # stop and drop the database volume
```

**One model endpoint is all it needs** (NFR-OPS-1): every model call goes to an OpenAI-compatible server you point it at; nothing else is required (no broker, cache or scheduler). With [LM Studio](https://lmstudio.ai) on the host, load a model, start its server (port 1234), then tell the engine where it is and play a turn:

```bash
CRED='Authorization: Bearer dev-only-credential-change-me-00000000'   # the compose file's dev-only credential
WHO='X-Epistrel-Principal: me'
curl -X PUT localhost:8000/admin/model-config/default -H "$CRED" -H "$WHO" -H 'Content-Type: application/json' \
     -d '{"base_url": "http://host.docker.internal:1234/v1", "model": "<the model LM Studio has loaded>"}'
curl -X PUT localhost:8000/admin/model-config/default/api-key -H "$CRED" -H "$WHO" -H 'Content-Type: application/json' \
     -d '{"api_key": "lm-studio"}'
curl -X POST localhost:8000/stories -H "$CRED" -H "$WHO" -H 'Content-Type: application/json' -d '{"name": "The Lantern Road",
     "characters": [{"name": "Wren", "definition": "A traveller.", "true_age": 24, "is_player": true},
                    {"name": "Ada", "definition": "An innkeeper who trusts no one.", "true_age": 41}]}'
# → {"story_id": "<story>", "characters": [{"id": "<wren>", ...}, ...], ...}
curl -X POST localhost:8000/stories/<story>/respond -H "$CRED" -H "$WHO" -H 'Content-Type: application/json' \
     -d '{"actor_character_id": "<wren>", "player_input": {"say": "Is there a room for the night?"}}'
docker compose ps --services   # engine, db — the whole deployment
```

Every purpose (`generation`, `guardrail_check`, `lite_summary`) falls back to `default`, so one entry configures them all; any other OpenAI-compatible server (Ollama, vLLM, a hosted provider) works the same way with its own `base_url`, model and key. See [Models](#models).

The engine runs in `all` mode: the API and the background workers (`EPISTREL_WORKER_CONCURRENCY` loops, default 2) in one process. The workers own every timer and sweep (idempotency-result purge hourly, audit-record retention daily, the turn-queue safety net every 30 s, the media sweep every `media_sweep_interval`, default hourly), so no scheduler, cron, broker or cache is needed. Larger deployments run `epistrel serve --mode api` and `epistrel serve --mode worker` (alias `epistrel worker`, which serves only `/health` and `/metrics`) as separate processes. `/health` answers `degraded` (still HTTP 200) when no worker has sent a heartbeat for `worker_heartbeat_timeout` (60 s) or timed work is overdue by more than `timer_lag_alert` (5 min). It answers `unavailable` (503) while the database is down.

Logs are JSON lines on stdout carrying identifiers, counts and durations, never story text; `GET /metrics` serves Prometheus metrics (worker processes serve it too); setting `EPISTREL_OTLP_ENDPOINT` exports OpenTelemetry traces over OTLP/HTTP. `EPISTREL_CONTENT_DEBUG_LOGGING=1` (refused unless `EPISTREL_DEBUG` is on) lets story content into the logs for at most 24 hours and shows as `content_logging: true` on `/health`; keep such logs at most 7 days (docs/02 §11).

Backups are three things taken separately: `epistrel backup dump` (`pg_dump -Fc` of the database), the `media` volume or bucket, and the `erasure-ledger` volume (`EPISTREL_ERASURE_LEDGER_DIR`), which holds the erasure ledger outside every database backup. After a restore, no restored story, and nothing of the catalog a pending catalog erasure reaches, is served until Epistrel has reapplied every erasure the ledger holds and the backup predates (503 `erasure_pending` meanwhile), so a restore reproduces the post-erasure state. `epistrel backup verify <dump>` lists erasure markers as expected gaps and checks the dump's ledger rows against the file. [docs/OPERATIONS.md](docs/OPERATIONS.md) has the procedure and the erasure boundary, which `GET /admin/erasure/boundary` also serves.

The compose file's database password, service credential (`EPISTREL_SERVICE_CREDENTIALS`) and config key (`EPISTREL_CONFIG_KEY`) are dev-only defaults; set `EPISTREL_DATABASE_URL`, `EPISTREL_SERVICE_CREDENTIALS` and `EPISTREL_CONFIG_KEY` yourself for anything but local use. Every call except `GET /health`, `/metrics`, `/openapi.json`, `/docs` and `/redoc` needs the credential (`curl -H 'Authorization: Bearer dev-only-credential-change-me-00000000' …`), and every `POST`/`PUT`/`PATCH`/`DELETE` also sends `X-Epistrel-Principal`. The one other exception is `GET /media/{id}/content` fetched with a short-lived signed URL from `GET /media/{id}/url` (see Media). A model server on the host (e.g. LM Studio) is reachable from the container as `host.docker.internal`.

Without Docker: requires [uv](https://docs.astral.sh/uv/) and Python 3.14 (the single supported version, ADR-148).

```bash
uv sync                                  # create .venv and install dependencies
cp .env.example .env                     # then set EPISTREL_DATABASE_URL and EPISTREL_SERVICE_CREDENTIALS
uv run --env-file .env alembic upgrade head   # bring the database to the current schema
uv run --env-file .env epistrel serve    # http://127.0.0.1:8000
```

## Models

Every model call goes through the Model Access Layer (`epistrel.orchestrator.models`, docs/02 §5) to an external OpenAI-compatible endpoint; Epistrel runs no model itself. Each purpose (`generation`, `guardrail_check`, `lite_summary` today; `GET /admin/model-config` lists them) has its own `{base_url, model, api_key, params}` in the `model_config` table and falls back field by field to the `default` row. Operators change it at runtime with `PUT /admin/model-config/{purpose}` and set a key with `PUT /admin/model-config/{purpose}/api-key`; the next model call uses the change, without a restart. API keys are stored encrypted with `EPISTREL_CONFIG_KEY` and never returned (`GET` shows `***` and the first 8 hex of the key's SHA-256). `EPISTREL_MODEL_ADAPTER=stub` swaps in a deterministic stub that needs no endpoint. To check a model server directly:

```bash
uv run python -m epistrel.tools.model_probe generation "Say hello" \
    --base-url http://localhost:1234/v1 --model <loaded model> --api-key lm-studio
EPISTREL_MODEL_ADAPTER=stub uv run python -m epistrel.tools.model_probe generation "Say hello"
```

## Configuration

`GET /admin/settings` returns every deployment setting with the deployment's `config_revision`. These are the default rating, the default engine profile (`default_engine_profile_id`) and the engine profiles' defaults (`profile_defaults`, see Engine profiles), `minor_age_threshold`, the Lite summary chunking, the caps on pinned memories and instructions, the idempotency result window, the default `turn_queue_max`, `structured_retry_budget`/`uncertain_below`, `default_safe_fallback` (the line a character says when every regenerated reply broke an output policy and it has no `safe_fallback_text` of its own; `{name}` becomes the character's name), the catalog's `listing_status_values`, `validation_model_calls`, the model calls one catalog validation may spend on model-assisted input policies, `require_primary_image`, whether a catalog character needs a primary image to publish (default `false`; see Catalog), and message feedback's `feedback_tags`, `feedback_text_max_chars` and `feedback_retention` (see Message feedback). `PUT /admin/settings` merges a partial update into them. A story's own settings are changed with `PATCH /stories/{id}/settings`. Each setting is tagged *interpretive* or *prospective* (FR-CONC-15). A change that alters anything takes a new configuration revision, which is separate from the story's timeline revision. It also records one `config_changes` row per changed setting. `GET /admin/config-changes` and `GET /stories/{id}/config-changes` list those rows newest first, and you can filter them by `setting`, `class` and `since`. Each operation records in `config_revisions` the configuration it ran under (`GET /operations/{id}`). A prospective change, such as a budget, cap, queue mode or model routing, affects only work that starts after it. An interpretive change, such as a policy, the story rating's guardrails, `minor_age_threshold` or the default output viewpoint, also reaches a Lite turn that is still generating. That turn's reply is re-checked under the new rules before it commits, and it is regenerated if it no longer passes.

## Catalog

Catalog characters (`/catalog/characters`) and scenarios (`/catalog/scenarios`) are drafts with immutable published versions, read as their public `card` or in `full`.

A catalog character's document has four groups. `public_card` holds its `name`, `public_description` and `images` (an optional `primary` and a `gallery`, as media ids). `definition` is private: `true_age`, `appearance`, `personality`, `likes_dislikes`, five `dispositions` (`threat_response`, `dominance`, `honesty`, `warmth` and `caution`, each a closed five-step `setting` plus free-text `nuance`), `values_motivations`, `interaction_style`, and optionally `background_flavor`, `deflection_style` (how the character refuses or changes the subject, in its own voice) and `safe_fallback_text`. `metadata` holds `aliases`, `labels` and `content_rating_id`. The optional `visual_identity` holds the preferred image model, a base appearance prompt, a negative prompt, a seed, reference images and opaque adapter parameters; every reference image declares its `audience`, `perceivable` or `restricted`, with no default. A draft may hold just a name, and a character carries no world facts: those belong to a scenario, normally its companion. Publishing needs the rest: a true age (`true_age_missing`), a content rating (`content_rating_missing`), every disposition, the definition's other text, an audience on each reference image (`reference_image_missing_audience`), live images, and a primary image when `require_primary_image` is on (`primary_image_required`); the report names every missing field at once. Images are optional otherwise. The `card` shows each image as its id and alt text, and `full` shows each image's alt text, caption, type, size and generation metadata as uploaded. `GET /catalog/characters` and `GET /catalog/scenarios` list cards, newest first: the published entries of every owner and listing status, or the drafts or archived ones with `status`. `q` searches each entry's latest published public card (name, labels, aliases or a scenario's role labels, and public description; never a private field, and drafts are not searchable) with `websearch_to_tsquery` syntax, words as written, best match first. `label` (repeat it; every one must hold), `content_rating`, `listing_status`, `owner` and `relation` narrow a list only when the request names them. Pages hold `limit` cards (1 to 200, default 50); pass `next_cursor` back as `cursor`, with the same filters, for the next page. A scenario list leaves out companion scenarios unless you pass `include_companions=true`.

Publishing validates the draft first, and `POST /catalog/scenarios/{id}/validate` runs the same validation as a dry run that writes nothing: of the draft (`{"draft_revision": n}` makes sure it is the draft you hold) or of a published version (`?version=n`), answered `{valid, report}`. Every surface answers one report shape: `errors`, `warnings` and `unavailable`. Each entry has a stable `code`, a `location` (`entry`, `version` or `"draft"`, `role`, `field`, `seed_id`), the exact `text` affected, an `outcome` (`rejected` for an error; `kept`, `ignored`, `dropped`, `deferred` or `inactive` for a warning), the `source` it names and the `rule` applied. Any error refuses the publish with 422 `publish_invalid` and `details.report`; warnings never block and come back on the 201, and the version keeps its report. A scenario needs a name, a content rating, a role, a world description, an opening narration, and every seed's holder, audience and disclosure. Its roles must fit the starting-cast limit, and each `locked` or `default` role's character must exist, be published and not archived, and pass the role's eligibility (labels, ratings, age range). Its media must be live and of an allowed type, size and kind, and every provider its content names must be declared. A character or asset whose rating lacks a guardrail the scenario's rating has warns `rating_looser`, and so does role text that asserts personality (`personality_in_role`: the character's personality applies). Text that fails an input policy warns `input_policy`; model-assisted policies run within `validation_model_calls` (default 0), and those it does not reach are listed `unavailable`, as are the checks this deployment cannot run (`seed_normalization`, `fact_consistency`, `state_schema` in M3).

Every catalog character comes with its companion scenario, created with it: the "just talk to this character" starting point, where the character's default world lives (its backstory, relationships and secrets). `GET /catalog/characters/{id}/companion` reads it (its draft until it is first published), and `PATCH /catalog/scenarios/{companion_id}` edits it like any scenario, except its two roles: `npc`, locked to the character, and `player`. Changing either role's `id`, `kind`, `fill` or `character`, or adding or removing a role, is 422 `companion_slots_fixed`. The companion takes the character's content rating until you set its own. Its owner, listing status, archiving and deletion follow the character's. A character and its companion keep separate version sequences: each companion version is pinned to a character version (`pinned_character_version`). Publishing the character also publishes a companion version pinned to the new character version, a copy of the companion's latest published content (its defaults on the first publish), and leaves an unpublished companion draft as it is, its pin moved. To publish the companion's draft with the character, pass `?with_companion=true` and the draft's `companion_draft_revision`; to publish it alone, publish the scenario, which pins the character's latest published version. Either way it is one transaction: if either side cannot be published, nothing is, and `details.entity` says which side refused. A rating that differs between the two is a `rating_looser` warning, never a refusal.

Every entry carries a listing status: a value of your own publishing workflow that Epistrel never interprets. It restricts no read, no story creation and no transition between values. The values come from `listing_status_values` (`PUT /admin/settings`; default `private`, `in_review`, `public`), and a new entry starts at the first. `PUT /catalog/{characters|scenarios}/{id}/listing-status` with `{"value": …}` changes it; a value outside the list is 422 `invalid_listing_status`. Each change is recorded in `ownership_events` with the acting principal. A character's companion scenario follows its character's value. Removing a value from the list while any entry holds it is 409 `listing_status_in_use`, so move those entries first.

## Personas and story characters

A player plays a persona: a `name`, an optional `gender`, an `age` (its true age) and a short `description`. `POST /personas` saves one for reuse, owned by the requesting principal or the `owner` you name. A name is unique per owner, ignoring case (409 `persona_name_taken`). `GET /personas` lists every owner's personas, newest first, unless you filter by `owner` or `relation`. `PATCH /personas/{id}` is a JSON merge patch, and `DELETE /personas/{id}` deletes one. A persona is not a catalog entry, and a story keeps a snapshot of the one it was created with, so editing or deleting a persona never changes a story.

`POST /stories/{id}/characters` adds a character to a running story: a name, a free-text definition, a required `true_age`, and optionally `safe_fallback_text`, `deflection_style` and `images` (media ids). It belongs to the story and never appears in the catalog. Its definition and deflection style pass the input gate, and the addition moves the story's revision. A character of a new story's cast may carry a `deflection_style` too: the Lite prompt shows it with the character's notes, so a reply regenerated after a guardrail violation refuses in character. `POST /stories/{id}/characters/{cid}/promote` turns one of a story's characters (never the player's) into a new draft catalog character. It copies the character's true age, its definition (as `definition.background_flavor`), its fallback line and deflection style, its images and the story's rating, and nothing else from the story. The story character records the new entry's id in `promoted_to`, shown by an omniscient `GET /stories/{id}`.

## Principals and offboarding

`GET /principals/{id}` lists everything linked to a principal, by type (stories, catalog characters, scenarios, personas, media, engine profiles): what it owns, and what names it in a relation, each type a page with its count. A character's item names its companion, which is not listed as a scenario. Principals are opaque, so one that nothing names answers empty pages. When you delete a user account, `POST /admin/offboarding` cleans up after them: `{principal, actions, transfer_to}`, with `delete`, `transfer` or `keep` for each owned type and `remove` or `keep` for the relations naming them on others' entities. A type you leave out is kept. Send `dry_run: true` first: it answers the counts and warns of a shared story to be deleted, of profiles or media to be retired that other owners use, and of the default profile, which is never deleted. A request whose plan warns changes nothing until you send it again with `ignore_warnings: true`. It then answers 202 with a `job_id`: a worker applies each action through the type's own delete or transfer, one entity at a time. A character takes its companion, and media a transferred entry shows move with it. Read the progress and the final report at `GET /admin/offboarding/{job_id}`. The report lists every entity deleted, transferred, kept or skipped, and anything still linked; it is kept for `offboarding_report_retention_days` (90). Offboarding is not erasure: the principal stays recorded on the turns it played in stories it did not own.

## Media

`POST /media` stores an image or video as an immutable, content-addressed asset: a `multipart/form-data` body with a JSON `metadata` part (`kind`, `content_rating_id`, the `depicted_subjects` every upload must declare, `[]` for none, and optional `alt_text`, `caption`, `generation_metadata` and `owner`) followed by the `file` part. The type is sniffed from the bytes and checked against `media_allowed_types`; the size against `media_max_bytes`. Bytes live in the local blob store under `EPISTREL_MEDIA_ROOT` (the image's `/var/lib/epistrel/media`, the compose `media` volume) as `<sha256[:2]>/<sha256>`, so identical bytes are stored once. `DELETE /media/{id}` retires an asset: it leaves listings and refuses new references, but whatever already shows it keeps reading it until the media sweep finds nothing referencing it and purges it. Epistrel does not moderate media itself. Set `media_moderation_webhook_url` (`PUT /admin/settings`) and every upload is POSTed there first, with a 5-minute signed `content_url` for the bytes (fetched with the service credential), and stored only on `{"decision": "accept"}`; a rejection is 422 `moderation_rejected`, and a hook that is unreachable, slow or answers anything else is 503 `moderation_unavailable`. Verify the requests' `X-Epistrel-Signature` (`sha256=` + HMAC-SHA256 of `<X-Epistrel-Timestamp>.<body>`) with the secret `epistrel moderation-secret` prints, which is derived from `EPISTREL_CONFIG_KEY` without revealing it.

Large media (FR-MEDIA-3). `GET /media/{id}/content` answers one `Range` with 206 (`Accept-Ranges: bytes`), so video seeks; `If-None-Match` and `If-Range` follow its `ETag`, and `HEAD` answers the headers. `GET /media/{id}/url` returns a URL that serves the bytes without the credential for `media_signed_url_ttl` seconds (default 300): hand it to the player or browser that shows the asset, and to no one else. With the local store it is Epistrel's own signed `/media/{id}/content?exp=&sig=` under `public_base_url` (which must be set). An upload larger than `media_multipart_threshold` (default 8 MiB) is 413 `use_multipart` on `POST /media`; open a resumable session instead (`POST /media/uploads` with the metadata and the upload's `size`, `mime_type` and `sha256`), send each `part_size` piece with `PUT /media/uploads/{id}/parts/{n}`, check `GET /media/uploads/{id}` to see which parts arrived (to resume after a failure), and `POST /media/uploads/{id}/complete`. Every video gets a poster: name one (`poster`, an image asset id), send one (a `poster_file` part after `file`), or let Epistrel take the first frame with ffmpeg, which the image installs and runs as a separate program (`EPISTREL_FFMPEG_PATH`; ADR-151). Bytes can live in any S3-compatible bucket instead of the media root: set `EPISTREL_MEDIA_STORE=s3`, `EPISTREL_MEDIA_S3_BUCKET` (it must exist) and, unless it is AWS with its own credential chain, `EPISTREL_MEDIA_S3_ENDPOINT`, `EPISTREL_MEDIA_S3_ACCESS_KEY` and `EPISTREL_MEDIA_S3_SECRET_KEY` (see `.env.example`). Signed URLs are then the store's own presigned URLs, and the store serves the bytes. The store is chosen at the first start; switching it while media exist refuses the start (exit 78). For a local MinIO, run `docker compose -f docker-compose.yml -f docker/compose.minio.yml up`.

## Engine profiles

An engine profile is a named, versioned set of capability modules and dials that sets how hard the engine works for a story (FR-PROF). `GET /engine-profiles/schema` shows what this deployment has delivered, with each setting's tags. Today that is the `lite` pipeline, the rolling summary, pinned memories, the polish pass, budgets, and models (per-purpose routing and the generation defaults).

- `POST /engine-profiles` creates a profile at version 1 with any of those settings. What it leaves out takes the default.
- A setting outside the delivered schema, or a module whose dependencies are off, is 422 `invalid_profile`, and the answer names each one.
- `PUT /engine-profiles/{id}` makes a new version when the settings change. It runs in two stages (FR-PROF-7): its `impact` report lists every story that follows the profile, with the capabilities each would gain or lose, its fingerprint before and after, and the capabilities and quality status it would then run with (`capabilities_after`, `quality_status_after`). When no story follows the profile, the report's top states the profile's own instead: its fingerprint before and after the edit, and its capabilities and quality status after it. When the report has `warnings`, nothing is written and the answer is `applied: false`, until you send the edit again with `ignore_warnings: true` (or `ignoreWarnings`). Settings that cannot run are refused all the same.
- `POST …/copy` copies a profile, and `POST …/validate` checks settings without saving them.
- `POST /stories/{id}/impact-preview` reports what assigning a profile, or applying overrides, would do to one story, and changes nothing. `GET /stories/{id}/effective-config` shows the deployment's defaults, the profile and version a story runs on, the story's overrides and its effective settings.
- `PUT /stories/{id}/engine-profile {profile_id}` moves a story to another profile, at its latest version, and keeps the story's overrides. `PATCH /stories/{id}/profile-overrides {settings}` changes the story's own dials with a JSON merge patch: `null` removes an override, so the dial follows the profile again, and `expected_revision` guards a concurrent change. Both run in the same two stages, are refused when the result cannot run, and are recorded as the story's configuration changes (`engine_profile_id`, `profile_overrides.<path>`).

The Lite preset ships owned by `system`. It is an ordinary profile: edit it, copy it, or delete it once another profile is the default.

Every story runs under one profile. A new story gets the deployment's default (`default_engine_profile_id` in `/admin/settings`, Lite until you choose another), and a fork keeps its source's, with its overrides. `DELETE /engine-profiles/{id}` hides a profile and answers with warnings that name the stories still using it and the scenarios recommending it. Those stories keep running on it, and the daily retention sweep purges the profile once no story uses it. The default profile cannot be deleted.

A story's effective configuration is three layers, validated as a whole (FR-PROF-5): the deployment's `profile_defaults` (in `/admin/settings`, seeded from Lite), then its profile's latest version, then its own overrides. A story follows its profile's latest version (FR-PROF-6): a new version is a configuration change (`engine_profile:<id>` and one `engine_profile:<id>.<path>` row per changed setting in `/admin/config-changes`), and every story on the profile runs under it from its next turn, keeping its overrides. A turn captures its configuration when it starts and runs under it to the end: the generation settings (the profile's, then the overrides', then the request's `prompt_params`, FR-LITE-4), the call cap and deadline (`budgets`), the verbatim window, and whether the rolling summary and pinned memories are on. The respond response names the `profile` and version it ran under. The engine's dials are the profile's, not the story's: M2's story and deployment dials (`generation_settings`, `lite_window_messages`, `lite_summary_max_tokens`, `max_model_calls_per_turn`, `turn_deadline`, `guardrail_retry_budget`, `lite_generation_defaults`) moved into overrides and `profile_defaults` (migration 0030 carried stored values over), and writing one is 422 naming its replacement.

Every respond response, effective-configuration read and impact report states the configuration's `fingerprint` (`sha256:` over the profile version, each purpose's model and every quality-relevant setting, prompt templates included), the `capabilities` it enables and its `quality_status`, which is `uncertified` until certification arrives (FR-PROF-16). Each turn records them in `config_revisions`. No delivered module produces structured data yet. Once one does, an edit that adds it cannot reach a story with history (a committed turn still on its timeline) until backfill exists (M7): the report marks that story `upgrade_unavailable`, and a confirmed edit leaves it on the version it ran on.

## Guarantees

**The model proposes; the engine validates structured claims, effects, and permissions** (FR-VERIFY-15). [`docs/guarantees.md`](docs/guarantees.md) lists every step. Each one is either deterministic or depends on a model, and each model-dependent step names the eval metric that measures it, or says `unmeasured`. The document also has one table per seeded profile showing what that profile provides. Under Lite there is no structural knowledge separation, no audience filtering (its perception is `none`), no verification and no commitment. Only the claims detected in an output are checked, and the rest of its prose is not. `GET /engine-profiles/{id}/guarantees` returns the same table as JSON for any profile, and `GET /stories/{id}/guarantees` returns it for a story's effective configuration. The impact report's `guarantees_lost` names, by id, the deterministic rows of this table that a change would lose. CI regenerates the document with `uv run python -m epistrel.tools.guarantees --check` and fails when it is stale, or when a delivered model purpose has no row.

## Scale

**What stays bounded, and what does not** (NFR-SCALE-2). A long story's append-only history grows linearly with its length, and so does the number of active records on its timeline: neither the active record count nor total storage is claimed to be bounded. Total storage grows linearly with a bounded constant under the retention policy (FR-STORE-30). Two things are bounded:

- **The hot set** (FR-MEM-8): the memories retrieval searches. Each character's unpinned hot memories are held to the profile dial `memory.hot_set.memories_per_character` (`hot_memory_budget_per_character`, default 2,000) and the story's unpinned hot vectors to `memory.hot_set.vectors_per_story` (`hot_vector_budget_per_story`, default 50,000). Pinned memories (`POST /stories/{id}/memories/{mid}/pin`) are never retired and sit outside the budgets, but a character may hold at most `max_pinned_per_character` (default 200) and a story at most `max_pinned_per_story` (default 2,000, its text pins included) — deployment settings in `/admin/settings`; a pin past either is 422 `pin_limit_exceeded`. So, for every story: hot memories per character ≤ `hot_memory_budget_per_character` + `max_pinned_per_character`, and hot vectors per story ≤ `hot_vector_budget_per_story` + `max_pinned_per_story`, except during an overflow episode. An episode starts at the commit that takes a set over its budget and ends no later than `memory.hot_set.retirement_max_lag` (default 50) committed turns after it began: retirement prefers records consolidation already covers or whose decayed importance is below `memory.hot_set.importance_floor` (0.2), and at the deadline retires the lowest-ranked uncovered records anyway (`retired_uncovered`). A retired record stays in history, is still found by keyed lookups and is rehydrated on demand by time-window and lexical lookup, without returning to the hot set; it drops its vector unless `memory.hot_set.retain_retired_vectors`. Overflow is reported by `epistrel_hot_overflow{scope}`, and `GET /admin/stories/{id}/hot-set` shows a story's counters, pins, open episodes and latest retirements.
- **The retrieved context** of every turn stays within `memory.episodic.retrieval_token_budget` (FR-MEM-6), however long the story.

Vectors are kept only for active hot records: a truncation, swap or regeneration drops the vectors of what it makes inactive unless `memory.hot_set.retain_dormant_vectors`, and a reactivation re-embeds them with the story's pinned embedding model (not byte-identical to the originals). Capacity is claimed only for the range the vector-scale curve measures (NFR-SCALE-1). The weekly soak (`.github/workflows/soak.yml`, X-01) plays 20,000 turns and checks these bounds.

## Message feedback

A player can rate any message the engine produced: `PUT /stories/{id}/messages/{message_id}/feedback` with `{"rating": 1-5, "tags": [...], "text": "..."}`, where `message_id` is the `message.message_id` a respond or regenerate answered (FR-FB-1). Tags come from `feedback_tags` (`PUT /admin/settings`; FR-FB-1's nine to start: `out_of_character`, `repetitive`, `forgot_something`, `factual_error`, `ignored_my_action`, `too_long`, `too_short`, `should_have_been_blocked`, `other`), and an unknown one is 422 `unknown_feedback_tag`. The text is optional, trimmed, and at most `feedback_text_max_chars` characters (2000). The rating is the requesting principal's (`X-Epistrel-Principal`): each principal has one per message, and `GET` reads your own, with the history of its earlier values. Rating again replaces it (the earlier value stays in the history), and `DELETE` retracts it. Each rating records the configuration the message was produced under: its operation, fingerprint, profile version, models, content-rating version and quality status. A regenerated message is a new message and starts unrated. These calls take no `Idempotency-Key`: sending the same rating again changes nothing.

Feedback never changes the story (FR-FB-2): no prompt, view, retrieval or summary reads it, and it is not an event. Ratings are deleted with their story, and a fork copies none. `feedback_retention` keeps them for the story's life (`story_lifetime`, the default) or a number of days, after which the daily retention sweep deletes them. Removing a tag from `feedback_tags` while a rating or its history still carries it is 409 `feedback_tag_in_use`.

## Changing a story's rating

`PUT /stories/{id}/content-rating` with `{"content_rating_id": ...}` changes a story's rating (FR-RATE-6,7). The two ratings are compared by their effective guardrails, never by their order. A move that only removes guardrails (Teen to Explicit, say, or between ratings with the same guardrails) applies at once: 200 `{applied: true, rating_version}`, recorded as the interpretive setting `content_rating_id` with who asked (`GET /stories/{id}/config-changes`). A turn that is still generating is re-checked under the new rating before it commits. A move that adds any guardrail (Explicit to Teen, or sideways) answers 202 with a `job_id` and pauses the story while a worker checks its whole active history against the target rating. That covers every active turn's player input and replies, ingested ones included, plus the pinned memories and custom instructions. Model-assisted policies use up to `rating_check_model_calls_per_record` (default 2) calls per record, outside any turn budget. While the story is paused, every call that would change it answers 409 `story_paused` with the check's progress; reads still work. Read the check at `GET /stories/{id}/content-rating/checks/{job_id}`. If everything passes, the rating changes. Otherwise nothing changes and the check lists each violation by position (turn, variant, beat) and policy, never the text. Either way the story plays again. Checks are kept for `rating_check_retention_days` (30).

## The minors policy

Epistrel ships a seeded global policy, `minors_no_sexual_content`: **no sexual content involving a minor, or in the presence of a minor**, at every content rating, Explicit included. It applies to text the consumer sends in and to text the model writes. A minor is a character younger than the deployment's `minor_age_threshold` (default 18; `PUT /admin/settings`), judged from each character's true age, which every character must declare at creation. The age check is deterministic and costs nothing: a story whose cast has no minor never calls a model for this policy. When a minor is in the cast, the `guardrail_check` model judges the text, seeing the cast only as anonymous labels with ages. A refused request says that a minor is involved or present, never who or how old. A reply that breaks it, like a reply that breaks any output policy, is generated again with the policy's message as a constraint, up to the story's polish budget (its profile's `repair.polish.max_regenerations`, default 2), and then replaced by the character's safe fallback line (`guardrail.fallback_used` in the response); rejected drafts are kept only as audit records.

**The policy ships enabled.** It is ordinary policy data: an administrator can edit or retire it with `/admin/policies`, and the change is recorded with the acting principal. Removing or weakening it is the deployment's decision and responsibility.

## Trust boundary

Epistrel runs behind the consumer and must never be exposed to end users. It authenticates only the calling service, which sends one of the deployment's service credentials as `Authorization: Bearer <credential>`, and it holds no user roles, grants, or permissions: which end user may call which operation, act as which character, or request which output viewpoint is the consumer's decision, made before it calls. Its privacy guarantee is relative to the request: output is produced for the output viewpoint the request names, and Epistrel does not verify that the consumer was entitled to request that viewpoint, so Epistrel by itself does not stop a player from reaching another character's secrets. Every mutating call carries an opaque requesting principal in `X-Epistrel-Principal`, which Epistrel records for attribution and never interprets; use opaque IDs rather than names or email addresses, so recorded attribution identifies no one without your own records. Ownership and relations are labels the consumer defines; the engine never grants or withholds an action because of them. Ownership exists for listing, attribution and offboarding only.

## Test and check

```bash
uv run pytest                            # everything; integration tests start a pgvector container (Docker)
uv run pytest -m "not integration"       # unit tests only, no Docker
uv run ruff check && uv run ruff format --check && uv run mypy
uv run pytest --cov=epistrel.core --cov-report=term-missing --cov-fail-under=90   # what CI gates on, in one run
uv run python -m tools.gates check-assignment   # docs/03 §22: every requirement assigned exactly once
```

Every pull request runs the same checks in CI (lint, types, tests, core coverage ≥ 90 %, Docker build); the `gate` check is required by the `main` ruleset, so a red gate blocks the merge for everyone. CI runs the tests as a matrix of directory shards (`.github/workflows/ci.yml`), each writing its own coverage data, and the `coverage` job combines them and applies the 90 % gate once; `tests/test_workflows.py` checks that the shards run every test module exactly once.

The chaos suite (`tests/chaos/`, marker `chaos`) kills the engine at named crash points (X-03), cuts its database (X-06, which needs Docker even when `EPISTREL_TEST_DATABASE_URL` is set) and storms it with retries. Pull requests run its `chaos_quick` tests at their quick defaults; the weekly `chaos.yml` workflow runs all of it with `EPISTREL_CHAOS_ITERATIONS=500`. Each seeded test prints its `EPISTREL_CHAOS_SEED`; running it again with that seed repeats the test's random draws, which is not always the same run. In X-04 the seed fixes which requests drop and after how long, the backoffs, which client always drops its first request, and how long after the engine is back each later restart comes. X-04's engine is a separate process that races the clients on the wall clock, though, and that interleaving is not replayed: when the first kill comes and which turns a kill catches, for example, can differ (the module docstring of `tests/chaos/test_x_04.py` lists what a seed fixes and what it does not). `tests/determinism/` replays a committed script twice on fresh databases and compares the Engine Core state (NFR-DETERM-1).

The soak (`tests/soak/`, marker `soak`, X-01) plays one structured story for 20,000 stub turns and checks the bounds of [Scale](#scale) at every checkpoint. It is opt-in: the weekly `soak.yml` workflow runs it, and `EPISTREL_SOAK_TURNS=1000 uv run pytest -m soak tests/soak` runs a short one locally.

The deployment smoke (C-10, `tests/smoke/`, marker `smoke`) runs against a live compose stack, with `tests/smoke/fake_openai.py` as the one model endpoint; it is opt-in, and without `EPISTREL_SMOKE_BASE_URL` it fails rather than skips. `publish-edge.yml` and `release.yml` run it on the built image before publishing anything:

```bash
docker compose -f docker-compose.yml -f tests/smoke/compose.override.yml up -d --build --wait
EPISTREL_SMOKE_BASE_URL=http://127.0.0.1:8000 uv run pytest -m smoke tests/smoke   # EPISTREL_SMOKE_FAKE_PORT if 1234 is taken
docker compose -f docker-compose.yml -f tests/smoke/compose.override.yml down -v
```

It stops `db` (expecting 503 `database_unavailable`, then recovery) and restarts `engine` (expecting the start-up recovery pass to fail an orphaned operation), so run it on a stack you can disturb. `tests/test_c_11.py` (C-11) proves each `tools.gates` check fails on a fixture violation and passes on the repository, and that `ci.yml` wires every one into the required `gate` check.

P-04's reference workload (`python -m perf.lite_smoke`, #76) is run by hand, and `tests/perf/test_p_04.py` fails the gate once the newest committed report in `perf/results/` is more than 30 days old: rerun `uv sync --group perf && uv run python -m perf.lite_smoke --minutes 30 --host-class mac` and commit the report before then (the first one is dated 2026-10-11). `p04-expiry.yml` checks every day (`python -m perf.lite_smoke.freshness`) and, from 14 days before the newest full-length report expires, opens one "P-04 report expires" issue with that command (#283).

Integration tests live under `tests/integration/`. Set `EPISTREL_TEST_DATABASE_URL` to reuse a running PostgreSQL 16 + pgvector server instead of a container (its role needs `CREATEDB`); with neither Docker nor that variable they fail with a message, never skip. Schema changes go through Alembic: edit `epistrel.core.schema`, run `uv run alembic revision --autogenerate -m "..."`, and a test fails until metadata and migrations agree.
